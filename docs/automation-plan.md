# План: автоматика pipeline поверх существующего движка

Статус: реализация в 2.81.529+ · принцип: простая, предсказуемая рабочая лошадка.
Всё строится на уже существующем: `DebateOrchestrator` (жизненный цикл RUNNING / PAUSED, `requestContinue`),
`DebateStageExecutor`, `DebateResponseAcceptance`, метка доставки `[[AO-xxxxxx]]`, шаблон «Architecture».

## 1. Что показала проверка движка (до работ)

| # | Факт | Следствие |
|---|---|---|
| F1 | `runLoop` проходит все плановые этапы подряд. Режим «Auto / manual» влияет только на режим финализации (`finalization.mode`). Прогон 3 этапов с выключенным Auto: 3 этапа за один запуск. | Полуавтомат «этап за этапом» **не существовал**. Запись в документации «после этапа движок ждёт подтверждения» была неверной. |
| F2 | Этап, где не ответил никто, планировщик ставит заново снова и снова: до лимита шагов (60 вызовов моделей на 3 этапа и 2 модели). | Сжигает вкладки и квоты; автоматика без этого не может быть «исправной». |
| F3 | Этап, где ответила часть моделей, закрывается как выполненный (`partial`), недостающая модель один раз перезапрашивается. | Нормально, оставляем. |
| F4 | Есть всё для паузы: `requestPause` / `requestContinue`, состояние `PAUSED`, кнопка «Продолжить» (`deriveRunControls`: `paused → resume`). | Паузы между этапами реализуем **этим же состоянием**, а не новым механизмом. |

## 2. Режимы запуска

| Режим | Пауза | Для чего |
|---|---|---|
| `manual` (полуавтомат, Auto выключен) | после **каждого** этапа | модератор смотрит, жмёт Get it / «Дальше» / «Продолжить» |
| `auto` | только на **воротах** шаблона, на **вопросе владельцу** (`ASK`) и на **сбое этапа** | модель работает сама, человек вызывается только когда нужен |

Пауза всегда одна и та же: состояние `PAUSED` с причиной
`stage_done` | `gate` | `ask` | `stage_failed`. Кнопка «Продолжить» одна.

## 3. Разметка ответов: необходимое и достаточное

Система должна уметь ответить на три вопроса о ответе модели. На каждый есть ровно один маркер:

| Вопрос | Маркер | Откуда | Кто использует |
|---|---|---|---|
| Ответ полный и это ответ на **этот** запрос? | `[[AO-xxxxxx]]` последней строкой | уже есть (метка доставки) | транспорт, завершение этапа |
| Нужен ли человеку (владельцу) ответ, который модели дать не могут? | `[[ASK: вопрос || вариант 1 || вариант 2]]` (одна строка, до 3; 2–5 вариантов, владелец выбирает, слово «несколько» последним — множественный выбор) | **новый** | движок: пауза `ask`, диалог «Вопрос владельцу» |
| Для проверяющих этапов: есть ли блокирующие замечания? | `[[VERDICT: pass]]` или `[[VERDICT: issues_found]]` | **новый** (словарь совпадает с `DebateResponseAcceptance.parseAuditVerdict`) | карточка этапа, отчёт, подсказка на воротах |

Чего **нет** и почему: маркеров прогресса, уверенности и «я закончил» — «закончил» доказывает метка доставки,
а прогресс измеряется подтверждёнными результатами, не активностью (правило проекта). Лишние маркеры
модели путают, и каждый надо разбирать и проверять.

Правила разбора (модуль `disput/stage-markers.js`, чистые функции):
- маркер — строка целиком `[[ИМЯ: значение]]`, регистр имени не важен, значение обрезается;
- учитываются маркеры **в тексте ответа**; текст внутри кода (```) и цитат (`>`) игнорируется;
- `VERDICT` — последний валидный, значение вне словаря = нет вердикта (не ошибка);
- `ASK` — до 3 вопросов на ответ, дубликаты схлопываются; пустой вопрос игнорируется;
- маркеры остаются в тексте ответа (человекочитаемы), в промпт следующего этапа попадают как есть.

Инструкция про маркеры добавляется в промпт **только шаблонных этапов** (у которых есть задание этапа):
`ASK` — всем, `VERDICT` — этапам с назначением `critique` / `verification` / `evidence_review`.

## 4. Изменения в движке

1. **Политика паузы** `policies.stagePause = { mode: 'never' | 'every_stage' | 'gates' }` (по умолчанию `never`,
   чтобы не менять поведение существующих тестов и пресетов). Ворота шаблона — метка `meta.gateAfter`
   у плановых этапов (этап 12 → G1, 16 → G2, 21 → G3, 29 → G4).
2. **Пауза после этапа**: после выполнения созданных этапов `runLoop` сам переводит запуск в `PAUSED`
   (`RUN_PAUSED` с причиной), отпускает lease и возвращает управление. «Продолжить» = существующий `requestContinue`.
3. **Сбой этапа**: этап, где никто не дал принятого ответа, **не** ставится заново бесконечно: пауза
   `stage_failed` (технический режим), один сигнал модератору. Повтор — осознанно, кнопкой «Продолжить»
   (этап ставится заново один раз).
4. **ASK**: исполнитель разбирает маркеры принятых ответов; этап хранит `asks` и `verdict`;
   оркестратор после этапа ставит паузу `ask`. Ответ владельца сохраняется страницей и подставляется
   в `task.currentInstruction` следующих этапов (поле уже есть в шаблоне промпта: «Текущее указание человека»).
5. **Страница**: политика паузы выводится из режима (`manual → every_stage`, `auto → gates`);
   на `RUN_PAUSED` агрегат получает `PAUSE_REQUESTED` (кнопка «Продолжить» уже работает), диалог «Вопрос
   владельцу» для `ask`, причина паузы в уведомлении и в карточке этапа.
6. **Исправить документацию**: что «Дальше» делает на самом деле, и что пауза между этапами появилась с этой версией.

## 5. Телеметрия (минимум для понимания автоматики)

События журнала: `run_paused` (причина, этап, `asks`, `verdict`), `owner_answer`, `run_resumed`.
В диагностике — проблема `stage_failed` и список пауз с причинами; в строке пакета видно «пауза: gate G1».

## 6. Порядок работ и приёмка

| Шаг | Что | Приёмка |
|---|---|---|
| A | политика паузы + `RUN_PAUSED` + «Продолжить» | тест на настоящем движке: `every_stage` — 3 этапа = 3 паузы; `gates` — только на воротах; `never` — как раньше |
| B | сбой этапа не крутится | всё молчат → 1 попытка этапа (+ внутренняя), пауза `stage_failed`, число вызовов ограничено |
| C | модуль маркеров + инструкция в промпте | юнит-тесты разбора (код, цитаты, дубликаты, регистр), промпт содержит нужные инструкции |
| D | ASK: пауза, диалог, ответ владельца в промпт | тест движка: ответ с `[[ASK:]]` → пауза `ask`; ответ владельца виден в промпте следующего этапа |
| E | телеметрия | диагностика показывает паузы и причину |
| F | документация и версия | CHANGELOG, `project-overview`, исправление F1 |

Вне этого плана (сознательно): авто-повторы шаблонных этапов по `VERDICT` (в схеме за проверкой уже стоят
этапы закрытия решений), автоматическое прохождение ворот (по схеме владелец не подменяется моделью),
оптимизации по стоимости.
