Архитектура MVP «Remote Viewfinder»
1. Цели и границы
Телефон A (камера) передаёт видео по WebRTC в локальной сети Wi-Fi на телефон B (видоискатель) и принимает команды: старт и стоп записи, зум, переключение камеры. Запись идёт на A. Интернет не нужен, включая сеть мобильной точки доступа. Одно приложение с двумя ролями, iOS 17+ и Android 10+, любая пара платформ. Цель: P95 ≤ 200 мс «стекло–стекло» на 5 и 2,4 ГГц. Задержка показывается только в диагностике.
Статус: архитектура является проверяемой гипотезой. «Готовой» она считается после прохождения плана проверки (раздел 9): прототип должен подтвердить оба SLO по задержке, четыре направления ОС, отказоустойчивую запись и корректность состояний при разрывах.
2. Ограничения (решения владельца)
1:1; запись на A, файл только в хранилище приложения A; QR без сетевых параметров; точку доступа включает пользователь вручную; только видео, микрофон не запрашивается; переключение камеры при записи отклоняется; потеря записи при аварии ≤ ~1 с; на A подтверждение «Разрешить» с моделью B; iOS 17+, Android 10+; ориентация записи фиксируется на старте; задержка только в диагностике.

4. Компоненты

Pairing: QR, ключи, psk, TTL, одноразовость, перевыпуск QR.
Discovery: mDNS, резервный поиск, повторное обнаружение при смене сети.
Signaling: WSS-сервер на A (лимит соединений, размера SDP, таймаут до одобрения), клиент на B.
Session: автомат связи и авторизации.
RtcCore: PeerConnection, битрейт, DataChannel, статистика, abs-capture-time.
Capture: камера, зум, выбор камеры, матрица ориентации.
Recorder: энкодер, fMP4, журнал, восстановление, квоты.
Control: исполнитель команд, идемпотентность, версии state.
Platform: разрешения, привязка к сети, wake lock, служба, подсказки OEM.
Diagnostics: RTT, потери, dropped frames, задержка «стекло–стекло».
Export: выдача записи владельцу из песочницы A (вариант определяется вопросом 3).
UI: экраны A и B.

5. Потоки
Сопряжение.

A создаёт sid и psk (по 128 бит) и эфемерный TLS-сертификат. QR содержит {версия, sid, SHA-256 сертификата, psk, срок ≤ 120 с}. Адресов и параметров сети в QR нет.
A поднимает WSS и публикует mDNS.
B сканирует QR, находит A по хешу sid и подключается с пиннингом сертификата.
A отправляет случайный challenge; B отвечает HMAC(psk, challenge ‖ транскрипт TLS) и сообщает модель.
До одобрения A принимает одно соединение, размер сообщений ограничен.
A показывает «Разрешить: модель B» (модель заявлена самим B).
После согласия A шлёт offer, B отвечает answer. sid аннулируется; B получает одноразовый resume-токен, привязанный к ключу B и сессии.

Три неверных ответа аннулируют sid; A показывает новый QR без перезапуска. Отказ владельца освобождает слот.
Видео. Захват 1080p, стрим 720p30, ≤ 2,5 Мбит/с (на 2,4 ГГц старт 2 Мбит/с). Ключевые кадры стрима по PLI, NACK включён, FEC выключен, maintain-framerate; при потерях снижение до 540p. На B минимальный jitter buffer, вывод по vsync, поздние кадры отбрасываются. Каждый кадр несёт abs-capture-time, B вычисляет задержку до вывода. Номинальный бюджет (мс): захват 35, кодирование 15, сеть 20, буфер 20, декодирование 15, вывод 35, итого ~140. Это ориентир, а не доказательство P95: процентили звеньев не складываются, истинный P95 даёт только измерение (раздел 9).
Управление.

Команды: start_rec, stop_rec, zoom, switch_camera, ping, каждая с монотонным id. A выполняет их сериализованно; повтор по id возвращает прежний результат.
State публикуется с версией: запись, камера, зум и версия диапазона, качество записи (1080p/720p), причина деградации.
Зум с устаревшей версией диапазона или sequence отбрасывается, частота ограничена.
start_rec подтверждается после первого записанного кадра, stop_rec после закрытия файла.
При записи switch_camera даёт ERR_REC_ACTIVE; кнопки на B и A заблокированы.
Повторные start/stop при совпадающем состоянии дают OK_ALREADY.
После разрыва B считает state неизвестным; команды не принимаются, пока канал не авторизован заново и state не синхронизирован.

Запись.

Старт. Фиксируется матрица ориентации по датчику устройства; зеркалирование фронтальной камеры, crop и метаданные контейнера считаются из одной матрицы. Источник времени — host clock. До полезной записи пишется и проверяется init segment (параметры H.264).
Кодирование и сброс. Энкодер записи: GOP ≤ 1 с, IDR на границе каждого фрагмента. Фрагмент ≤ 1 с с подфрагментным flush каждые 0,5 с и fsync завершённых данных; журнал состояния обновляется атомарно.
Критерий потери. На kill -9 потеря ≤ 1 с от последнего декодируемого кадра в 95% прогонов, максимум ≤ 2 с. Если измерения покажут худшее, критерий пересматривает владелец (вопрос 2).
Стоп. Файл финализируется и переименовывается из *.part.
Восстановление при запуске. Валидатор fMP4 обходит боксы, отрезает неполный фрагмент, при необходимости делает remux, проверяет воспроизведение системным декодером и помечает файл «восстановлено». Дыры в таймстемпах при троттлинге записываются как есть, без подмены.
События. Обрыв связи запись не останавливает. Нехватка места или перегрев: остановка с сохранением файла.
Уход A в фон, блокировка, звонок. По умолчанию (до решения вопроса 4): немедленный graceful stop с закрытием фрагмента; статус для B при возвращении.
Жизненный цикл файлов. Квота и предупреждение STORAGE_LOW задолго до заполнения (≈ 100 МБ/мин при 1080p30), список записей, удаление владельцем, автоочистки нет.
Экспорт. Файл остаётся в песочнице A; выдача владельцу идёт по варианту из вопроса 3 (умолчание: системное «Поделиться» из списка записей A, вручную). Запись на B не переносится.

Автоматы (независимые).

Связь: Idle → Pairing → Discovering → Authenticating → AwaitingApproval → Negotiating → Connected → Reconnecting → Failed/Closed.
Захват и запись: Idle → Starting → Active → Stopping → Finalized | Recovered | Aborted(причина).
Reconnecting: детект смены интерфейса → освобождение привязки к сети → переобнаружение → новый WSS → предъявление resume-токена → ICE negotiation. Если топология изменилась и токен не принят (вопрос 6), нужно новое QR-сопряжение. Таймауты настраиваемые (старт 15 с), уточняются прототипом.

Ошибки: QR_EXPIRED, PEER_NOT_FOUND, AUTH_FAILED, USER_DENIED, LOCAL_NET_DENIED, CAMERA_DENIED, ERR_REC_ACTIVE, STORAGE_LOW, THERMAL_LIMIT, ICE_FAILED, ENCODER_FAILURE, RECORDER_DEGRADED, CONFLICT_VERSION.
6. Android и iOS
iOS 17+

Один AVCaptureSession; кадры VideoDataOutput идут в RTCVideoSource и AVAssetWriter (movieFragmentInterval 1 с). Очередь рекордера без дропа, ретайминг по host clock.
Ориентация: AVCaptureDevice.RotationCoordinator.
NSCameraUsageDescription, NSLocalNetworkUsageDescription, NSBonjourServices. Универсального API проверки доступа к локальной сети нет: проверка по факту сбоя mDNS или сокета и экран-подсказка.
Камера в фоне недоступна; isIdleTimerDisabled защищает только от автоблокировки. Кнопка питания и звонок приводят к штатной остановке записи.
iOS-хотспот (bridge 172.20.10.x, Bonjour) тестируется отдельно как ключевой сценарий пары без роутера.
B в фоне: сокеты замораживаются, A показывает «зритель недоступен», запись продолжается. Это зафиксированное требование, а не побочный эффект.
Если по вопросу 3 выбран доступ через Files, общий доступ к Documents включается явно только для экспорта и не нарушает правило владельца.

Android 10+

Camera2 → один EGL-источник → WebRTC, превью, MediaCodec Surface. Muxer: Media3 FragmentedMp4Muxer с зафиксированной версией (API экспериментальный); запасной вариант — собственный fMP4-writer.
CAMERA, FOREGROUND_SERVICE_CAMERA (с Android 14); тип camera с Android 11, на Android 10 служба без типа. Запуск из видимого Activity.
Wake lock, WifiLock (WIFI_MODE_FULL_LOW_LATENCY, API 29+; эффективен при включённом экране и foreground), MulticastLock.
Зум: Android 10 — crop region, с 11 — zoom ratio.
Сеть без интернета: requestNetwork(TRANSPORT_WIFI) и bindProcessToNetwork; привязка снимается при смене сети.
OEM (Xiaomi, Oppo, Vivo): экран-инструкция с переходом в настройки батареи и запросом исключения из оптимизации.

Capability gate. Перед стартом сессии проверяется возможность одновременной работы двух аппаратных энкодеров и допустимость комбинации потоков камеры (Camera2 stream combinations, iOS activeFormat). При неуспехе запись понижается до 720p, затем до общего энкодера; решение отражается в state.
7. Сетевые режимы без интернета
Режимы: общий роутер, точка доступа на A, точка доступа на B (iOS и Android). Код один: устройства в одной подсети, A слушает WSS и публикует mDNS.

Основной механизм — mDNS/NSD. Резерв при тишине 6 с: адреса собственных интерфейсов с корректной маской, ограниченный набор портов, throttle на стороне A.
Клиентская изоляция даёт PEER_NOT_FOUND с подсказкой.
Фактический диапазон определяется на runtime; при 2,4 ГГц показывается предупреждение («Максимальная совместимость» на iOS, «Диапазон» на Android).
STUN и TURN не используются.

8. Безопасность

QR одноразовый, ≤ 120 с; слот зрителя один, освобождается при отказе или сбросе.
Пиннинг сертификата защищает от подмены A. psk с challenge от A защищает от повтора. Подтверждение на A обязательно для каждого нового B, поэтому фото QR его не обходит.
Модель B не аутентифицирована и помечена «заявлено устройством».
До одобрения: один сокет, лимит размера SDP, rate-limit, таймаут.
DTLS-SRTP обязателен, отпечатки сверяются.
Resume-токен одноразовый, обновляется после использования, на диск не пишется. В логах нет sid, psk, токена.
Записи в песочнице, из резервных копий исключены.

9. План проверки MVP
Измерение задержки. A снимает таймер или LED-панель; рядом с экраном B стоит внешняя камера 240 fps; задержка равна разнице показаний на покадровом разборе. Не менее 3000 кадров на сценарий, строится распределение, берётся P95. Параллельно внутренний abs-capture-time сверяется с внешним измерением для калибровки диагностики.
Матрица. 4 пары ОС (Android→Android, iOS→iOS, Android→iOS, iOS→Android) × сеть (роутер, хотспот на A, хотспот на B) × 5 и 2,4 ГГц × 30 мин. Для 2,4 ГГц: чистый эфир, зашумлённый (заданный уровень помех, Bluetooth), старая точка с DTIM=3. Минимум по два устройства на ОС, включая слабый Android 10. P95 > 200 мс в заявленных условиях — непрохождение приёмки.
Сценарии на двух телефонах.

Сопряжение: успех, истёкший QR, три неверных ответа, отказ «Разрешить», второй B.
Старт и стоп записи, повтор команды, гонка start/stop.
Зум: непрерывный, при смене камеры.
Переключение камеры без записи (успех) и во время записи (ERR_REC_ACTIVE).
Ориентация: четыре положения, фронтальная камера, поворот во время записи.
Разрыв связи 5, 15, 60 с: запись продолжается, B возвращается в синхронное состояние без дублей команд.
Смена сети: роутер ↔ хотспот, выключение хотспота.
Фон: блокировка, звонок, уход B в фон.
Нагрев, сессия 60 мин, нехватка места.
Права: отказ камеры и локальной сети.
Экспорт записи владельцем по выбранному варианту.

Аварийное завершение. Не менее 100 прогонов kill -9 (и принудительное завершение через систему) на каждой ОС в разных фазах записи. После каждого: валидатор, воспроизведение системным декодером, измерение потерянного хвоста. Критерий: ≤ 1 с в 95%, максимум ≤ 2 с, 0 нечитаемых файлов. Harness готовится в первую неделю, до UI.
Недели 1–2: спайки. Одновременные энкодеры; хотспот на iOS и Android; jitter buffer; fMP4. Результат определяет итоговые решения.

12. Журнал отклонённых замечаний

| Замечание | Причина |
| --- | --- |
| Streaming ⇄ Recording связывает запись со связью | Принято по существу, автоматы разделены; формулировка «ошибочно» неточна, поскольку уже v1 оставляла запись при разрыве. |
| Сканирование IPv6-only и нестандартных масок | Вне MVP; маска берётся с интерфейса. |

| Отдельный раздел аудита безопасности локальной сети | Меры включены в §5 и §8 компактно. |

13. Вне MVP
Несколько зрителей, звук, постоянные доверенные устройства, передача файла на B, запись на B, фоновая запись на iOS, ручной фокус и экспозиция, автоматическое включение точки доступа, TURN и интернет-доступ, показ задержки в основном UI, IPv6-only сети, автоочистка записей.
