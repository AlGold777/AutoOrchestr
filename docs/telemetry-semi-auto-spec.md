# ТЗ: телеметрия доставки для полуавтоматического pipeline

Статус: частично реализовано в 2.81.523–2.81.525 (T7, T1 для пути global_state_hydrate, T3, T4, T5); не сделано: T2, T6, `displayed` для остальных путей · основа: 2.81.521 · исходный материал: отчёт
`message-delivery-report (5).json` (2.81.522, Le Chat + Perplexity, ручная отправка
модератора).

## 1. Зачем

Отчёт о доставке должен отвечать на один вопрос: **совпадает ли то, что видит
пользователь, с тем, что принял движок, и если нет — почему.** В полуавтоматике
к этому добавляется второй вопрос: **что сделал модератор и что из этого
получилось** (Get it, «Дальше», подтверждение этапа).

Сейчас отчёту нельзя доверять: он строится только из журнала `MessageDelivery`, а
ответ может попасть на экран в обход журнала.

## 2. Что не так в отчёте (5)

| # | Наблюдение | Причина в коде | Последствие |
|---|---|---|---|
| D1 | Perplexity: последняя запись «Ответ ещё не получен», хотя ответ давно в ленте | `hydrateAnswerFromGlobalState` (`results.js`) выводит `entry.answer` из глобального состояния фона в карточку ленты **без проверки финальности и без записи в журнал**. В ожидание этапа (`pipelineWaiter`) и в журнал ответ попадает только при `finalStatusRecorded && transportRequestId` | Экран и журнал расходятся; отчёт показывает «waiting» для ответа, который пользователь видит |

## 3. Требования

### T1. Единый журнал всего, что показано пользователю (закрывает D1)

Каждый вывод текста в карточку модели (главная страница, лента pipeline) пишет
событие `displayed`:

```
{ kind: 'displayed', model, requestId, dispatchId, chars, source,
  final: bool, acceptedByWait: bool | null, rejectReason?, surface: 'main'|'feed' }
```

- `source` ∈ `live`, `get_it`, `global_state_hydrate`, `global_state_recovery`,
  `post_terminal_revision`, `session_restore`.
- `acceptedByWait` — принял ли ответ открытый `pipelineWaiter` (результат
  `handleFinal`); `null`, если ожидания нет.
- `rejectReason` — `missReason` ожидания (`no_request_id`, `unknown_request`,
  `model_mismatch`, `batch_settled`) или `not_final`.

Диагностика строит для каждой отправки строку «показано / принято» и выдаёт новую
проблему **`display_desync`** (warning), если текст показан, а ожидание его не
приняло. В подсказке — источник и причина.

### T2. Снимок экрана в момент отчёта (закрывает D1, D4)

При генерации отчёта для каждой модели текущего прогона записывается
`snapshot`: длина текста в карточке, источник последнего вывода, время, статус
индикатора, открыто ли ожидание и с какими моделями. Диагностика сверяет снимок с
журналом; расхождение = `display_desync`.

### T3. Контекст запуска (закрывает D2, D6)

В `batch_start` и в шапку отчёта:

- `runMode`: `auto` | `semi_auto` (Auto выключен, активный шаблон) |
  `manual_dispatch` (Auto выключен, шаблона нет);
- `template`: имя сохранённого pipeline, `presetId`, список этапов холста
  (`plannedStageId`, назначение, участники);
- `stageId` / `stageAttemptId` для этапных запусков; для ручной отправки вместо
  `unscoped:a1` — `manual:<sessionId>:<n>`;
- включённые автоматические механизмы: визиты, автоматический Get it, отсрочка
  неопределённого финала, восстановление из глобального состояния.

### T4. События модератора (полуавтоматика)

| Событие | Поля |
|---|---|
| `moderator_get_it` | `models`, `failedOnly`, `stageId`, затем по каждой модели `get_it_result`: `status`, `chars`, `acceptedByWait` |
| `moderator_stage_close` | `stageId`, `answered`, `skipped`, `stillWaiting` (из `closeAnsweredBatches`) |
| `moderator_approve` | `stageId`, следующий этап |
| `moderator_close_refused` | причина (`no_answers`, отказ в подтверждении) |

`batch_end` с исходом `moderator_closed` уже пишется (2.81.521); в отчёте он
показывается как отдельный исход, не как таймаут. `PARTICIPANT_SKIPPED`
попадает в отчёт как «пропущена модератором на этапе X», а не как отказ.

### T5. Карточки проблем с возрастом и последним фактом (закрывает D4, D5)

Каждая проблема несёт `ageMs` (от события до отчёта) и `lastFact` — последнее
наблюдение по модели (`first_text 312 симв. на 17 с`, `status RECEIVING`).
«Ожидается ответ» допустимо, только если с момента последнего факта прошло
меньше порогового времени; иначе — `stalled` с подсказкой «нажмите Get it».

### T6. Полуавтоматика без эффекта наблюдателя (закрывает D3)

В режиме `semi_auto` и `manual_dispatch` автоматические визиты и повторная
активация вкладки после отправки **выключены**: фокус меняется только по
действию модератора (Get it, двойной клик). Каждое переключение фокуса всё равно
журналируется с источником; `focus_churn` в этих режимах — ошибка конфигурации,
а не дефект распознавания.

### T7. Ложные пересмотры после завершения

`Ответ обновлён после завершения · GLOBAL_STATE_ANSWER_RECOVERY · Δ -9` —
это не новый ответ. Восстановление из глобального состояния повторно выводит
уже показанный ответ, а `appendPostTerminalAnswerRevision` не сравнивает
новый текст с показанным: любое отличие нормализации (метка `[[AO-…]]`, хвост
вроде `8:55pm`, пробелы) становится «пересмотром». Требование:

- перед созданием пересмотра сравнивать **очищенный** текст (`MessageDelivery.clean`,
  схлопнутые пробелы) с показанным; совпадение — не пересмотр;
- `hydrateAnswerFromGlobalState` не выводит текст в ленту, если карточка этого
  запроса уже закрыта, и очищает текст так же, как живой путь;
- настоящий пересмотр журналируется событием `displayed` с
  `source: 'post_terminal_revision'` и `delta`.

## 4. Порядок работ

1. T7 + T1 для пути `global_state_hydrate` — устраняет ложные пересмотры и
   самое опасное расхождение экрана и журнала.
2. T3 + T4 — контекст запуска и действия модератора (нужны для проверки
   полуавтоматики на шаблонах).
3. T2 + T5 — снимок и возраст проблем в отчёте.
4. T6 — отключение автоматических визитов в полуавтоматике.

## 5. Приёмка

- Повтор сценария отчёта (5): Perplexity с ответом в ленте даёт в отчёте либо
  `delivered`, либо `display_desync` с источником и причиной — но не голое
  «Ответ ещё не получен».
- Прогон шаблона из 2+ этапов в полуавтоматике: в отчёте видны `runMode`,
  шаблон, этапы, каждый Get it, каждое «Дальше» с пропущенными моделями и каждое
  подтверждение; нет `automation_visit_activate`.
- Ни одного «Ответ обновлён после завершения» при повторном выводе того же
  ответа; настоящий пересмотр по-прежнему показывается.
- Тесты: на `displayed`/`display_desync` (диагностика), на сравнение очищенного
  текста в `appendPostTerminalAnswerRevision`, на поля `runMode` и события
  модератора.
