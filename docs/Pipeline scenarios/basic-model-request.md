# Запрос для моделей: составить схему Basic

Текст между линиями копируется целиком и отправляется модели. Модель отвечает одним JSON-объектом и тремя короткими пунктами. JSON вставляется в приложение окном «Вставить схему» (кнопка в шапке панели pipelines): текст до и после JSON окно сохранит вместе со схемой как комментарий модели (поле `comment`, видно в окне ▶ под описанием). Полный справочник по полям — [basic-schema-guide.md](basic-schema-guide.md); он нужен, если запрос понадобится уточнить.

Запрос написан по фактическому поведению движка: отдельный чат каждого участника, приложение не принимает содержательных решений, документы и опросники, редкое участие User. Основной пример в конце проверяется тестом (`tests/basic-model-request.test.js`): он проходит проверку схемы и исполняется движком.

Для обычных схем используйте `schemaVersion: 1`. Если один провайдер нужен как несколько участников или нужны подписи и явно пустые настройки, используйте формат 2: задайте каждому участнику постоянный уникальный `id`, а отображаемую подпись — полем `label`. Входы и ссылки продолжайте адресовать по ID.

Задание: спроектировать процесс под реальную задачу и записать его как схему Basic в строгом формате JSON.

О приложении.
Это расширение для браузера. Пользователь ставит задачу, а приложение отправляет её сразу нескольким нейросетевым чатам (ChatGPT, Gemini, Claude и другим), собирает ответы и передаёт их дальше по схеме. Схема — список шагов сверху вниз. Шаги выполняются строго по порядку, ветвлений, возвратов назад и условий нет.

КАК ПРОЕКТИРОВАТЬ ПРОЦЕСС
Схема — это дизайн процесса: как из цели получить результат, которому можно доверять. Сначала продумайте процесс, потом записывайте JSON.

1. Смысловая логика этапов и связей.
Начните с цели и признака готовности результата; назовите их в `description`. Разделите работу на необходимые этапы. Для каждого определите:
— назначение: что он даёт процессу;
— входы и выход: какие материалы ему нужны и что он производит;
— критерии качества: по чему оценивать результат;
— зависимости: результаты каких более ранних этапов ему нужны.
Назначение, ожидаемый результат и критерии сформулируйте в `task`, передачу материалов задайте через `input` и при необходимости `output`. Каждый промежуточный результат должен использоваться дальше, а итоговый — решать задачу User. Если этап можно убрать без потери качества, уберите его. Не объявляйте каждый ответ именованным артефактом: это нужно для повторного использования, версий или документа для User.

2. Логика взаимодействия участников.
Определите, кто кому передаёт работу и в каком виде, кто какой контекст видит, где нужны независимые предложения, проверка, сведение результатов и решение User.
Независимость определяется историей участника, а не названием модели или ролью. Другой участник того же провайдера с отдельным чатом может дать независимое предложение. Смена роли автора на «проверяющий» не делает его проверку независимой. Для отдельной проверки используйте участника, который не писал проверяемый документ; для независимых предложений участники не должны заранее видеть ответы друг друга. `chat: "new"` позволяет начать без прежней истории, но нужные исходные материалы и проверяемый документ придётся передать заново. Отдельный чат уменьшает влияние прежнего контекста, но не гарантирует правильность ответа или отсутствие общих ошибок у моделей.
Независимость, взаимную проверку и участие User вводите только там, где они полезны для задачи. Коротко объясните выбранное взаимодействие в `description` и втором пункте после JSON; поля `why` в Basic нет.

3. Решения и доработка.
Приложение передаёт материалы и ждёт ответы, а содержательные суждения делают модель (`round`) или User (`owner`). Проверка — обычный раунд с конкретными критериями в `task`. Если замечания можно применить без решения человека, следующий раунд дорабатывает результат сам. Шаг User нужен для выбора или утверждения, которое нельзя поручить модели. Вердикт «прошло» не включает условный переход: все записанные этапы выполняются по порядку. При необходимости заранее поставьте ниже этап доработки и повторной проверки; не обещайте цикл «до успеха» или автоматический пропуск этапов.

Как работает приложение (на этом строится схема).
1. Постоянный чат участника. Модель (`name`, например Claude), участник (`id`, например claude-author) и его переписка — разные вещи. По умолчанию один участник продолжает свой чат между шагами в пределах прогона; помнит только материалы и ответы своего чата. Два участника Claude работают в отдельных чатах, историю друг друга не видят. Одинаковый `id` в следующем шаге означает того же участника; новая роль или подпись не создаёт новый чат. Адреса переписок и ID вкладок приложение хранит само: в схему их не пишите. Ссылка на шаг в `input` вставляет в запрос ПОЛНЫЙ текст ответов этого шага, каждый раз заново; передавайте участнику только нужные материалы, которых ещё нет в его текущем чате. При `chat: "new"` прежняя история участника в новый чат не переносится: нужные материалы передайте через `input` заново.
2. Приложение само ничего не понимает и не решает. Оно рассылает запросы, собирает ответы, подставляет нужные ответы в следующие запросы, показывает документ User и ждёт его ответа. Условий по тексту ответа оно не вычисляет и не читает слов «прошло» или «не прошло». Если нужна проверка, её делает модель, а её ответ читает User или следующая модель.
3. Приложение само дописывает в запрос служебное: предел длины ответа, правило меток документа, формат опросника, просьбу исправить ответ. Не пишите это в `task`.
4. Исходные файлы в схему не пишите: поле `files` участника заполняет User в окне участника (📎). Файлы User прикладывает к запросу сам, они уходят вместе с первым сообщением каждого чата. Если задаче нужны материалы, напишите в `description`, что User должен приложить, а в `task` первого шага ссылайтесь на «приложенные файлы».

Участие User. Оно редкое и осмысленное.
- User не помощник, на которого перекладывают работу. Не просите его писать, исправлять или проверять большой текст, искать данные, оценивать то, что может оценить модель.
- Допустимы только два случая: (а) в начале, когда задача неоднозначна: один опросник с выбором, чтобы уточнить ключевое (какой функционал, для кого, какой бюджет); (б) решение или утверждение там, где его нельзя поручить модели: выбрать вариант, утвердить документ.
- Не больше двух шагов User на схему. Не ставьте шаг User, если без него схема работает.

Виды шагов (`kind`).
1. `round` — запрос уходит всем моделям шага, они отвечают независимо. Поля: `ref`, `kind`, `task` (общее задание), `models` (список моделей), `input`, `output`, `chat`.
2. `owner` — шаг User: он читает документ или пишет ответ и нажимает «Отправить». Поля: `ref`, `kind`, `models` (всегда `[]`), `task` (что User должен сделать), `document` (ссылка на более ранний раунд из ОДНОЙ модели, документ которого User увидит в окне), `goal` (необязательно: для чего шаг), `input`.
Видов два. Синтез, судья, жюри, проверяющий — роли и обычные раунды, а не отдельные виды. Синтез: раунд из одной модели с ролью `interaction_meta_synthesis`. Проверка: раунд с критериями в `task`; замечания применяет следующий раунд. Если требуется решение User, добавьте шаг `owner` и передайте ему документ и вердикт.
Чтобы одна модель увидела ответ другой, поставьте шаг этой модели ниже и дайте ему ответ источника (см. «Входы»).

Поля схемы.
Корень: `schemaVersion` (1 для обычных схем; 2 для отдельных ID/подписей участников), `origin` ("user"), `description` (презентация для человека, 3–6 фраз: цель, признак готовности, как устроен процесс и что должен приложить User), `run`, `steps`.
`run`: `policy` — "auto": шаги идут без остановки, но если на шаге ответил не каждый участник, приложение спрашивает User (повторить, пропустить участника или шаг, остановить); шаг User всё равно ждёт ответа. Без `run` и при "manual" приложение ставит паузу после каждого шага. `maxWords` — общий предел длины ответа: только 300, 500, 700 или 1000. Без поля предел 300 слов. Предел — просьба уложиться в него: по умолчанию (`strictLength: false`) документ не сокращается, длинный ответ принимается; при `strictLength: true` ответ длиннее предела отклоняется, и модель просят сократить. Для документов ставьте 700 или 1000. У модели можно задать свой `maxWords` (любое положительное целое).
Модель в шаге: `name` (обязательно), `role` (необязательно), `task` (личное задание: ЗАМЕНЯЕТ общее `task` шага целиком, а не дополняет; общие требования повторите в личном или не задавайте личных заданий), `maxWords`. В формате 2 у КАЖДОГО участника обязателен `id`; `label` — понятная подпись, например «Claude · Автор» и «Claude · Проверяющий». Один `id` повторяйте во всех шагах работы этого участника с неизменными `name` и `label`; в одном раунде ID не повторяются. У разных участников одной модели подписи должны различаться. Несколько участников могут иметь одинаковое `name`, но разные ID. Не создавайте отдельного участника только ради смены задания или роли; отдельный участник нужен для независимого контекста. Ссылки адресуются по `id`, а не по `label` или общему имени провайдера.
`settingsMode: "explicit"` нужен только для намеренно пустого персонального профиля: отключает наследование задания, дисциплины, входа и выхода шага; отсутствующий личный `input` означает "none". Для обычной исполняемой схемы это поле не добавляйте. `enabled: false` выключает отправку участнику в данном раунде; без поля участник включён. `onCanvas: true` оставляет выключенного участника на холсте. При ручном нажатии «+» приложение создаёт выключенную карточку; в готовой схеме нужных исполнителей оставляйте включёнными.
Имена моделей — только Claude, GPT, Gemini, Grok, Le Chat, Qwen, DeepSeek, Perplexity, Z.ai, Kimi (не «ChatGPT»).
Роли (`role`): interaction_meta_synthesis (свести в одно решение), interaction_critical_audit (критически проверить), interaction_select_ideas (выбрать идеи), interaction_pattern_clustering (сгруппировать по сути). Роль необязательна.
`chat` раунда: "continue" (по умолчанию) — каждый участник продолжает собственный чат; "new" — новый чат для каждого участника на первом запросе захода этого шага. Исправления и повторы внутри того же захода идут в этот же чат. Используйте "new" только для намеренного сброса контекста, а не для разделения двух участников одной модели. При потере сохранённого чата приложение пробует восстановить ту же переписку; если это невозможно, отправка останавливается. Не рассчитывайте на молчаливую замену новым чатом.
`ref`: раунды — r1, r2, r3… строго по порядку без пропусков; шаг User — owner:<латиница, цифры, _ или ->, например owner:ok.

Входы (`input` шага).
Не указан: самый первый шаг получает только задачу User; любой следующий — ответы предыдущего шага (после шага User — ответ User). Так передавайте по умолчанию, поле не пишите. Явно: "none", "previous", "all" или список ссылок на более ранние шаги, например ["r2", "owner:q"]. Ссылаться можно только на шаги ВЫШЕ по списку.
Для одного ответа используйте `{ "step": "r1", "participant": "claude-author", "required": true }` внутри списка: например, `"input": [{ "step": "r1", "participant": "claude-author", "required": true }]`. В формате 2 здесь нужен `id`; в формате 1 — имя модели. Личный `input` участника заменяет вход шага: так можно дать каждому только недостающие ему материалы. Участники одного раунда отвечают независимо; чтобы проверяющий прочитал ответ автора, поместите проверку в следующий раунд и явно передайте ответ автора.

Документы и опросники.
Документ — результат шага, который User читает и правит или который читает другая модель. Объявите его в `output` раунда ОДНОЙ модели: `{ "document": "read", "artifacts": [ { "id": "map", "name": "Карта функций", "pointer": "" } ] }`. Приложение само попросит модель написать документ между метками, вырежет его из ответа и покажет User в окне (пояснения модели вокруг в документ не попадают). Затем шаг `owner` с `"document": "<ref раунда>"` покажет его User; User может исправить текст и нажать «Отправить», дальше уходит его утверждённый вариант.
Опросник: раунд одной модели с `"output": { "format": "json", "document": "form" }`; модель сама составит пункты (выбор одного, выбор нескольких, текст, да/нет, ключевые обязательные), User заполнит форму в окне и нажмёт «Отправить», ответы «вопрос — ответ» уйдут следующему шагу. В `task` раунда опишите только тему опросника (число пунктов до 7, в основном с выбором), формат JSON приложение допишет само.
Документ от нескольких моделей: сначала раунд нескольких моделей без документа, затем раунд из одной модели с ролью interaction_meta_synthesis, он и объявляет документ.
Именованный артефакт: если результат шага читают несколько шагов ниже, объявите его в `output` шага: `{ "artifacts": [ { "id": "shortlist", "name": "Короткий список", "pointer": "" } ] }` (в текстовом ответе один артефакт, `pointer` пустой). Ссылайтесь на него во `input` адресом `{ "artifact": { "step": "r2", "participant": "Claude", "id": "shortlist" }, "version": "latest", "required": true }`: придёт только этот артефакт, а не весь ответ шага (`participant` — ID участника, в формате 1 это имя модели; у шага User — "owner"). Доработка: шаг, который возвращает исправленный документ, объявляет свой артефакт с `"revisionOf"` — тем же адресом, что стоит у него во `input`; дальше по `"version": "latest"` приходит новая версия. Правка User в окне документа тоже новая версия, поэтому изменённый документ подавайте модели снова, хотя прежнюю версию она видела.
Этап после шага User ОБЯЗАН применить ответ User: напишите в его `task`, что делать, и просите вернуть документ целиком, а не отдельный раздел с правками. Каждый ответ User должен читать какой-то более поздний шаг.

ЖЁСТКИЕ ПРАВИЛА (нарушение — схема не установится).
1. Только поля из этого запроса; неизвестное поле — ошибка. Двойные кавычки, без комментариев, без запятой после последнего элемента, числа числами.
2. Шагов `file`, `gate`, `route`, `synthesis`, `foreach`, полей `block`, `why`, `inputs` с точками и «исходных артефактов» нет. Нужное записывайте обычными раундами.
3. `models` у `owner` — `[]`; у `round` хотя бы одна модель. `document` у `owner` ссылается на раунд с одной моделью, у которого объявлен `output.document`.
4. Не придумывайте шагов ради объёма: столько шагов, сколько нужно задаче.

Сначала ОДИН JSON-объект (первый символ {, последний }), без markdown-ограждений. После него — три коротких пункта (см. ниже). Если не помещается: сокращайте тексты заданий до одной фразы, но НЕ убирайте шаги и НЕ обрывайте JSON.

ПРОВЕРЬТЕ ПЕРЕД ОТВЕТОМ (про себя):
 □ в `description` названы цель и признак готовности результата;
 □ каждый этап нужен, промежуточные результаты используются дальше, итог решает задачу User;
 □ проверки имеют конкретные критерии, независимость проверена по истории участников, выбранное взаимодействие объяснено;
 □ содержательные решения делает модель или User; схема не обещает ветвлений, автоматического пропуска этапов или цикла «до успеха»;
 □ ни один `input` не ссылается на шаг ниже или на себя;
 □ в формате 2 у каждого участника есть `id`, в следующих шагах он сохранён с теми же `name` и `label`; подписи участников одной модели различаются, ссылки используют ID;
 □ участники одной модели имеют разные ID и независимые чаты; нужные исполнители не выключены через `enabled: false`;
 □ документ, который участник уже получил в текущем чате и который с тех пор не менялся, не подан во `input` второй раз (кроме входа, на который ссылается `revisionOf`), а в `task` есть ссылка по названию; после `chat: "new"` нужные материалы переданы заново;
 □ шагов User не больше двух, каждый нужен (опросник в начале и/или утверждение документа), ответ каждого читает более поздний шаг;
 □ после шага User стоит шаг, который применяет ответ и возвращает документ целиком;
 □ `document` у `owner` указывает на раунд из одной модели с объявленным `output.document`;
 □ в раунде либо общее `task`, либо личные `task` у всех моделей (личное заменяет общее);
 □ `run.maxWords` достаточен для самого длинного документа;
 □ у каждого шага укажи `title` и `goal`, у каждого документа — `description` в `output.artifacts[]` (например: «Список функций с пользой для каждой»): из них строятся подсказки при наведении на холсте. Личный `task` у модели ставь только когда задания участников шага различаются: он ЗАМЕНЯЕТ общее задание шага целиком, поэтому в личный `task` нужно вписать полный текст;
