## Подтверждённые дефекты

Приоритет P1: неправильный чат/рабочий источник либо небезопасное принятие чужого ответа. P2: блокировка допустимого сценария, неполная готовность восстановления или недоступная функция. Номера V относятся к этому обзору и не заменяют R/N из ТЗ.

### V01 · P1 · F03 + F05 · Continue теряет чат до первого ответа

Статус (14.10.2026, 2.81.761): исправлено. Страница пишет привязку чата в запись раз в секунду, пока батч в полёте (`syncParticipantChats`, `CustomRunRecord.setChatBindings`); продолжение участника, который уже отправлял в этом прогоне и не имеет привязки, помечается `strict`, и фон отказывает с `participant_chat_lost` (`binding_missing`), не ища чужую вкладку и не открывая новый чат. Текст ниже — описание дефекта на момент проверки.

Код: `results.js:7541–7543`, `background/job-orchestrator.js:5288`, `background/tab-manager.js:344–349,1125–1127`.

Страница получает фактический binding только **после завершения batch**. Доответный checkpoint его не содержит. Другой run вызывает pruneParticipantRuns и удаляет старую background-привязку; отмена также её очищает. Resume без binding выглядит для openParticipantChat как первый запрос и допускает глобальный поиск вкладки.

Повторено на production tab-manager в VM: run1 был связан с tab 2001; старт run2 удалил связь; resume run1 из доответного состояния отправил `resume` в посторонний tab 2003 (`attach_existing`), результат ok:true.

[Воспроизведение](basic-fixes-review-oct12/lost-pending-chat.js). Это реальный алгоритм выбора/dispatch со стабом Chrome, не отправка аккаунту.

Исправление: перед отправкой обеспечить долговечный run checkpoint с фактическим binding/идентификатором попытки либо сохранение/доступность run-binding до его передачи в record. Различать «ещё не отправлялся» и «отправлялся, binding утрачен»; во втором случае не делать global attach. Не удалять единственную доступную привязку возобновляемого run. Приёмка: abort/reload до ответа → промежуточный другой run → resume; ни чужого чата, ни пустого new как continue.

### V02 · P1 · F04/F02 · Feedback не участвует в invalidation

Код: `disput/custom-engine.js:800–812,971–991,1253–1256`.

Feedback попадает в запрос доработки, но dependencies визита строятся только из обычного input. Последующая инвалидация источника замечаний не инвалидирует производный результат.

Повторено: r1 визит 2 построен на feedback B-v1 из r2; затем возврат в r2 инвалидирует r2 визиты 1/2. r1 визит 2 остаётся valid:true, потребитель получает `A-based-on-B-v1`, прогон завершает steps_done.

[Воспроизведение](basic-fixes-review-oct12/feedback-invalidation.js).

Исправление: включить точные источники активного feedback (step/participant/visit и artifact version, если есть) в фактические зависимости визита; сохранить их через checkpoint/resume. Приёмка: инвалидация B-v1 делает зависимый A stale; required потребитель не отправлен до явного пересчёта. Несвязанный результат остаётся valid.

### V03 · P1, пока скрыт V04 · F03 · Check может признать старый ответ новым

Код: `background/tab-manager.js:1182–1202`, `background/job-orchestrator.js:323+`.

Совпадение requestId в binding не связывает извлечённый текст с этим запросом. Extractor читает последнее сообщение assistant. При пустом excludeText старый ответ может стать found.

Повторено с production extractor в jsdom и production endpoint в VM: live.requestId и transportRequestId = new-request; DOM содержит только ответ предыдущего запроса. Возвращается ok:true/status:found с `OLD ANSWER…`.

[Воспроизведение](basic-fixes-review-oct12/check-old-answer.js). В нём extractor сделан доступным для изоляции этой ошибки; без этого сейчас срабатывает V04. Движок пока не вызывает endpoint, поэтому это риск готовящейся интеграции, а не доказанное принятие старого ответа в текущем прогоне страницы.

Исправление: found только при доказанной связи с сохранённой попыткой/запросом и его ответом. Если доказательства нет — ambiguous/no_answer, без повторной отправки. Одна проверка tab ID или отсутствие текста в excludeText не является доказательством. Тест: old assistant + новый незавершённый запрос не даёт found.

### V04 · P2 · F03 · Endpoint check недоступен в реальном service worker

Код: `background/tab-manager.js:1193`, `background/job-orchestrator.js:323`, порядок загрузки `background/index.js:272–277`.

extractLatestAssistantSnapshotInPage объявлена внутри IIFE job-orchestrator и не экспортирована. Bare reference из tab-manager вызывает ReferenceError, который превращается в chat_unavailable/read_failed. VM-тесты вручную устанавливают extractor в глобальный context и маскируют дефект.

Полный Jest обнаружил **новое падение background-global-scope**. Загрузка production index.js с реальным порядком importScripts подтвердила: extractorVisibleToTabManager=undefined, endpoint=read_failed.

[Воспроизведение](basic-fixes-review-oct12/check-background-scope.js).

Исправление: явно доступная общая функция/экспорт с тем же контрактом, затем интеграционный тест фактического порядка загрузки. Не удалять защитный тест и не ограничиваться добавлением функции в sandbox. V03 проверять после устранения scope.

### V05 · P2 · F02 · Повтор owner-ревизии теряет законный исходник

Код: `disput/custom-engine.js:718–724,1031–1042,1253–1256`.

Для модели, дорабатывающей свою линию, latest допускает действительный исходник через base. Это условие требует Boolean(model); owner разрешает input без model. После инвалидации owner-ревизии владелец не получает базовый документ и не может выполнить доработку.

Повторено: r1 создаёт map v1; owner:revise создаёт ревизию; gate возвращает в owner:revise. Прогон завершается missing_input, окно владельца вызвано только один раз. Та же схема с моделью-доработчиком покрыта успешными тестами.

[Воспроизведение](basic-fixes-review-oct12/owner-revision-and-input.js).

Исправление: единый effective-author контракт для owner и модели в разрешении входа revisionOf и записи зависимостей. Законный base доступен доработчику; обычный latest потребителя остаётся заблокированным. Тест: второй owner input получает действительный base, новая owner-ревизия снимает блокировку линии.

### V06 · P2 · F01 · Owner input none/all отвергается схемой

Код: `disput/basic-schema.js:382–386`.

N07 требует тот же формат входа, что у модели, но owner объединён с route и разрешает только previous/массив. Явные none и all отклоняются. Assemble и Engine их исполняют: all передаёт все ответы, none даёт пустой вход.

Повторено schema.validate и прямым runtime запуском в [owner-revision-and-input.js](basic-fixes-review-oct12/owner-revision-and-input.js): ошибка steps[1].input при runtime steps_done.

Исправление: owner допускает none/previous/all/массив; отсутствие поля остаётся none. Не расширять контракт route автоматически. Проверить validate → assemble → настройки/Save → run для обоих значений.

### V07 · P2 · F05 · Неполный snapshot объявляется возобновляемым

Код: `disput/custom-run-record.js:160–169`, `disput/custom-engine.js:1193–1195`.

isComplete проверяет schema/current и текстовые ссылки, но не обязательную форму состояния. Запись без pc/visits/results/counters/stack/dependencies получает canResume:true и export.resumable:true. Restore трактует отсутствующий pc как конец плана.

Повторено actual Engine: schema содержит неисполненный r1, snapshot не содержит pc → steps_done, 0 отправок, 0 завершённых шагов.

[Воспроизведение](basic-fixes-review-oct12/incomplete-snapshot.js).

Исправление: проверить обязательную форму полного checkpoint и согласованность позиции/текущего шага. Отличать явно сохранённый pc:null завершённого прогона от отсутствующего pc. Повреждённую/частичную запись оставить для истории, resume не обещать; Engine тоже отклоняет некорректное состояние, не завершает молча. Экспорт ссылок R04 сам по себе исправлен, проверка resumable — нет.

### V08 · P2 · F03/F05 · Resume вложений читает незаписанное поле

Код: `results.js:7481–7483`, `disput/custom-run-record.js:29–40`; путь runCustomFromPage не присваивает attachments в record.

Resume читает resumeRecord.attachments или [] вместо composer, но исходные вложения в record не сохраняются. После reload новый чат получает [] даже если исходный run имел файлы. Отказ использовать новый composer правильный; замена исходных данных пустым списком не закрывает R05.

Доказательство: чтение production createRun/serialize и пути runCustomFromPage; фактическая отправка бинарного файла провайдеру не выполнялась. Текущие tests/basic-participant-transport проверяют наличие строк с чтением attachments, а не save → reload → доставку.

Исправление: долговечное сохранение исходных файлов/ссылок/метаданных до первой отправки, разрешение при resume и явный отказ при утрате required файла. Объединить с хранением owner-file F05, не копировать весь файл в нескольких местах. Приёмка: run с файлом → save/reload → new chat получает те же байты; изменённый composer не влияет.
