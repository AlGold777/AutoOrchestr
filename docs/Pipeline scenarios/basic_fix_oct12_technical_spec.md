## 3. Уточнения общего контракта

Эти уточнения имеют приоритет над неполными формулировками исходного ТЗ. Старые допустимые схемы сохраняются; `schemaVersion: 1` не менять только из-за необязательных полей.

### 3.1 Обязательный источник целого шага (D3)

Разрешить объект без participant:

```json
{ "step": "r1", "required": true }
```

Это весь принятый актуальный результат указанного шага в порядке его участников. Достаточность определяется `require` источника: `any` — минимум один принятый ответ; `all` — все включённые; число — соответствующий порог. Обязательный источник должен быть завершён, действителен, не пропущен и иметь доступный результат; требуемое подтверждение владельца/gate также должно быть пройдено. Потребитель не получает частичный незавершённый источник. У owner достаточен принятый человеческий результат. Шаг без результативного выхода не становится источником текста лишь потому, что маршрут выполнен.

`{step,participant,required}` по-прежнему требует ответ именно указанного участника независимо от порога остальных. Строковая ссылка сохраняет прежнюю необязательность. При невыполнении required — `missing_input` с адресом до отправки. Дубликат строковой ссылки и объекта на весь тот же шаг запрещён, как и прежние дубликаты адресов.

### 3.2 Выход участника (D4)

Для round/synthesis/gate разрешить `models[].output` с тем же контрактом, что `step.output`. Явное индивидуальное объявление **целиком заменяет** общее; отсутствие наследует общее. Не сливать массивы artifacts/requiredFields. Проверять объявление, приёмку и регистрацию по эффективному output конкретного участника.

```json
{
  "id": "author-A", "name": "claude", "input": [
    { "artifact": { "step": "r1", "participant": "author-A", "id": "proposal" }, "version": "latest", "required": true }
  ],
  "output": { "artifacts": [
    { "id": "proposal", "name": "Доработанное предложение A", "pointer": "",
      "revisionOf": { "artifact": { "step": "r1", "participant": "author-A", "id": "proposal" }, "version": "latest", "required": true } }
  ] }
}
```

Это фрагмент участника, не самостоятельная схема. Второй автор с ID author-B ссылается на свою линию. Один provider не объединяет авторство. Ссылки на объявленный artifact валидировать по эффективному output источника; ошибочный pointer/revisionOf отклонять с полным путём. Для нескольких документов сохраняется требование JSON из исходного ТЗ. Каждый revisionOf должен присутствовать в эффективном input именно этого автора с тем же адресом artifact/version. Output участника route не расширять: у выбора маршрута свой контракт; owner не имеет models.

### 3.3 Источник владельца

У `kind: owner` единственный синтетический participant ID — `owner`, без фиктивной модели. Одинаковое правило применить к step/participant, artifact, версии, revisionOf, feedback и runtime-проверке. ID owner в обычном шаге не превращает модель в человека. Owner text/file — результат владельца; не записывать его как ответ LLM.

### 3.4 Актуальность линии

История версии и доступность рабочего latest — разные свойства. После инвалидации актуальной ревизии линия ожидает пересчёта; старый valid предок не становится latest. Pending/failed/skipped пересчёт блокирует required latest. Успешная принятая новая ревизия снимает блокировку. Это состояние входит в checkpoint/export/resume.

Историческая точная версия сохраняется. Явно закреплённый действительный исходник может быть входом автора доработки; запрещено подменять им latest потребителя. Точная инвалидированная версия не выдаётся как рабочий вход. Нельзя инвалидировать исходник так, что сама законная доработка теряет свой объявленный вход. Конкретное внутреннее представление блокировки выбирает F02 совместно с F04; внешний JSON не расширять ради реализации.

## 4. Задания и обязательные проверки

### R01 · F03 · Строгий continue

Восстановить привязку из snapshot данного run ID + participant ID, включая фактический tab/request ID. При существующей, но потерянной привязке не выбирать другую вкладку и не создавать пустой чат как успешный continue. Минимальное решение — остановка с понятной причиной до отправки и явное решение владельца; восстановление контекста допустимо только явно и из сохранённых данных. Первый запрос участника без предыдущей привязки может создать чат. `new` создаёт чат один раз на visit; исправляющий retry использует его же.

Проверки: закрытый bound tab + чужой открытый tab → ноль отправок в чужой; без кандидатов → нет молчаливого continue; два прогона с одинаковым participant ID не меняют привязки друг друга; resume после промежуточного другого прогона использует свой snapshot; повтор внутри visit не создаёт новый чат. Записать фактический binding до следующей отправки.

### R02 · F02/F04 · Latest после провала

Устранить выбор старого предка вместо актуального пересчёта согласно 3.4. Проверить цепочку исходник → ревизия → возврат → failed, отдельно skipped, несколько ревизий и reload в момент инвалидации. Required потребитель не отправлен и получает missing_input; optional не получает старый текст. Явный действительный исходник доработки доступен. После успешного пересчёта потребитель получает новую версию правильного автора. Несвязанные линии не инвалидируются.

### R03 · F05 · Достоверное сохранение

В callbacks get/set/remove настоящего chromeStorage читать `chrome.runtime.lastError` и отклонять Promise. Проверить синхронный throw тоже. Ошибка checkpoint останавливает дальнейшую отправку/переход: checkpoint_failed; завершение/cleanup не превращает её в успех. Тесты через adapter: отказ get, quota на set, отказ remove, успешная запись/чтение. В engine→page→adapter тесте число внешних отправок после неудачного предшествующего checkpoint равно нулю. Отказ сохранения уже полученного ответа также не допускает следующий запрос или переход.

### R04 · F05 · Самодостаточный экспорт

Экспорт должен сохранять snapshot и все данные по используемым textRef/answerRef/file refs, точные зависимости, состояние линий, chats и адрес попытки: ref, participant, visit, attempt, phase. Применить существующие serialize/очистку ссылок; не дублировать все тела документов в snapshot. JSON.stringify → JSON.parse не оставляет неразрешимых ссылок. Старые записи version 1 продолжают читаться/экспортироваться без обещания resume. Экспорт version 2 объявлять resumable только при полном состоянии; отсутствие UI импорта не выдавать за готовый импорт прогона.

Проверка: экспорт с owner, feedback, registry, незавершённой попыткой и вложением; пройти все сохранённые ссылки, восстановить их содержимое и идентичность. Не достаточно проверить наличие одного поля snapshot.

### R05 · F03 · Адресные вложения

Учитывать подтверждённую доставку по конкретному чату/visit, а не только participant ID. Новый чат получает необходимые вложения; retry в том же чате не повторяет уже доставленные. Волны с разными наборами вложений разбивать или делать адресными: чужие файлы и повторная доставка из-за соседа запрещены. При resume брать сохранённые исходные вложения, а не изменённый composer текущей страницы. Ошибка доставки не помечает файл успешно приложенным.

Проверки: new на повторном visit; continue; mixed wave старого и нового участника; два ID одной модели; reload; неудачная доставка с retry.

### R06 · F03 · API без молчаливого обхода

Минимальная реализация этого исправления: для participant chat не использовать stateless tryApiDirect, пока отдельная история участника не поддержана. Если выбран API-режим, явно отклонить неподдерживаемую комбинацию до отправки; не менять выбранный пользователем режим молча. Для выбранного вкладочного режима использовать точную привязку R01. Не менять API старых pipelines. Не добавлять новый API-движок истории в рамках исправления.

Проверки: включённый API + participant continue не вызывает stateless API и получает явную ошибку; отдельно выбранный вкладочный путь соблюдает R01; неподдерживаемая конфигурация не отправляет запрос; прежний API-путь других pipelines сохраняется. Обновить исследование A03 фактическим состоянием кода и ограничениями.

ChoiceDialog принимает AbortSignal/контекст прогона и закрывается при отмене с очисткой обработчиков. Передать отмену в owner, route, unknown ожидания. Поздний клик не меняет record/решение/шаг и не вызывает второй resolve. Чужое окно просмотра истории не закрывать как активное решение прогона.

Проверка в настоящем DOM: Stop на каждом из трёх окон → cancelled, ноль оставшихся блокирующих окон, ноль поздних действий; Escape; повторный новый прогон после Stop.

### N04 · F03/F05/F06 · Unknown: проверить ответ

В окне три действия: проверить / отправить заново / пропустить. Проверка read-only использует сохранённые request/tab/participant/visit, не отправляет запрос повторно и не выбирает посторонний чат. Найденный доказанный ответ проходит обычные output/require проверки и checkpoint. При отсутствии или неоднозначной привязке ответа статус остаётся unknown с понятным сообщением; при недоступном чате нельзя объявить успех. Resend — новая попытка с retryOf после явного выбора; skip не обходит require. Stop прерывает проверку и закрывает окно.

Проверки: найденный принятый ответ; найденный невалидный ответ; нет ответа; потерянная вкладка; неоднозначный ответ; reload повторно; отсутствие дублирующей отправки при check; counters/attempt identity сохранены.

### N05 · F04/F07 · Полный CHG, а не остановка вместо приёмки

Подготовить явный тестовый путь S19 → пересмотр baseline → gate → пересчёт всех инвалидированных зависимостей → S19. Список обязательных пересчитываемых refs и точку return задать в fixture, бизнес-условия Q10 не угадывать. Контрольный сценарий завершается успешно с новыми версиями, исходным continuationStack и правильным авторством; missing_input здесь не является успехом T12.

Отдельные отрицательные сценарии: пересчёт failed/skipped, stale input, превышение maxLoops, reload в CHG. Они должны безопасно останавливаться. Не добавлять автоматический планировщик пересчёта: схема явно задаёт маршрут, движок исполняет его и проверяет зависимости. Переход и его инвалидация после reload применяются ровно один раз. Проверить вложенный CHG и точные source/visit замечаний; инвалидировать target, явно заданные refs и транзитивные фактические зависимости, а не весь диапазон между target и resumeAt. В таблице S01–S30 различать доказанную механику и ещё не заданные бизнес-решения.

### N06 · F03/F07 · Документы транспорта

### N07 · F01/F02/F05/F06 · Вход шага владельца

Закрыть вторую часть D5 из приложенного отчёта: owner должен видеть результаты, на основании которых его просят дать ответ. Разрешить поле `input` у шага `kind: owner` в том же формате источников, что у шага модели (owner.input ниже — сокращённое название, не вложенный JSON-объект); поле отсутствует — пустой вход, сохранить прежнее поведение owner. Применять required/версии/актуальность до открытия окна. В callback `provideOwnerResult` передавать разрешённые входные элементы с адресом, participant/visit, текстом либо долговечной ссылкой файла; не собирать из них запрос к LLM. В окне показать контекст и дать открыть файл. Исполнение/повторные решения/resume используют snapshot и те же зависимости, чтобы изменение источника инвалидировало построенный на нём ответ владельца.

Проверки: owner получает выбранный artifact и ответ участника, отсутствующий required блокирует окно, optional пропускается, устаревший latest не подставляется, бинарный файл доступен владельцу без преобразования в текст. Import → редактирование input → Save → reload → ответ сохраняет адреса и зависимости. F01 объявляет/проектирует формат; F02 разрешает источники; F05 сохраняет pending контекст; F06 редактирует и показывает его.

## 6. Приёмка и завершение

F07 составляет матрицу R01–R12/N01–N07 → тест → команда → результат → commit. Пробелы отчёта покрыты: D3/D4=N01, UI=N02, file=N03, unknown=N04, CHG=N05, A03=N06; отдельная часть D5 из приложенного сообщения — owner.input=N07. Воспроизведения `basic-review-oct12/` служат исходным доказательством; превратить критические сценарии в регрессионные тесты. Простое изменение ожидаемого stopReason без проверки текста/адреса/числа отправок не исправляет дефект.

1. Проверить новые положительные и отрицательные сценарии на production-модулях.
2. Прогнать T00–T21 исходного ТЗ. T07/T14/T17 обязательно через реальную сборку страницы; T12 — успешный полный пересчёт плюс безопасные отказные ветки.
3. Прогнать профильные тесты и полный `npm test -- --runInBand`. Baseline обзора: 333/6 suites, 3194/20 tests; все 20 прежних имён в `basic-review-oct12/test-summary.json`. Дополнительное падение не списывать на baseline без сверки имён и причины.
4. В настоящем браузере проверить Stop окон и Import/редактирование/Save. Живые провайдеры: отдельный ручной сценарий с двумя ID, new/continue, потерянной вкладкой и вложением. Mock не считать подтверждением доставки. Если реальные отправки не выполнялись, прямо отметить это в результате.
5. Обновить basic-schema-guide/basic-windows/basic-developer/basic-start-here по фактическому поведению, карту документации и CHANGELOG. Сведения о будущем оставить в ТЗ, не выдавать их за поддержку.
6. Кодовые изменения сопровождаются согласованным подъёмом связанных версий. Каждое самостоятельное исправление закоммичено отдельно с необходимыми тестами/документами. Чужие изменения не стадировать. Commit по AGENTS поручается Haiku; если модель недоступна, сообщить и использовать уже согласованный в сессии локальный fallback.

Итог F07: закрытые пункты с доказательствами; незакрытые требования; отдельно реальные провайдеры и вопросы бизнеса. Объявить полное соответствие можно только при закрытии всех обязательных контрактов; явное ограничение binary input и неподтверждённые платные вызовы должны быть названы прямо.
