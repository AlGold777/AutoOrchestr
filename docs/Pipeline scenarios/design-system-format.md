# Design System создания pipeline: формат

Статус: формат согласован с автором в обсуждении 11.10.2026 и записан этим документом 14.10.2026. Пример заполненного документа — [design-system-architecture.md](design-system-architecture.md) (30 этапов). Что умеет исполнять Basic — [basic-start-here.md](basic-start-here.md).

## Зачем нужен документ

Design System — документ, который пишут для **одной конкретной задачи**. У него две функции:

1. **Спецификация для людей** (автор, коллега, руководитель): вся бизнес-логика и логика процесса, всё, что нужно для понимания происходящего.
2. **Единственный источник для модели, которая пишет схему pipeline.** Он настолько однозначен, что даже небольшая модель может по нему составить схему.

Цепочка: автор пишет Design System для задачи → модель составляет схему Basic (JSON, формат в [basic-schema-guide.md](basic-schema-guide.md)) → схема «натягивается» на движок (`validate` → запись → холст). Движок под задачу не меняется: то, что Basic не умеет, фиксируется как несоответствие (см. «Правило переноса»).

## Состав: три слоя

**1. Pipeline в целом.** Назначение; решаемая задача; исходные данные; итоговый результат; применение результата; критерии готовности результата; общие правила и ограничения; границы; участие владельца; поведение при сбое; объём.

**2. Схема процесса.** Фазы; этапы и их порядок; связи между этапами (откуда, куда, что передаётся, когда); параллельность, ветвления и повторы — только там, где они нужны.

**3. Этап** (карточка каждого этапа). Идентификатор и название; цель; задание; участники (число и роли); порядок работы и независимость; вход; выход; предел длины; правила и ограничения; критерии качества и способ проверки; участие владельца.

## Правила заполнения

- Идентификаторы этапов уникальны; каждая ссылка (вход, связь) ведёт к существующему этапу или результату.
- Правило этапа сильнее общего правила; значение по умолчанию записывается один раз, а не в каждом этапе.
- Пустое поле означает умолчание Basic; «не применимо» пишется явно.
- Каждое поле помечено: ✔ взято из исходных материалов автора дословно; ◐ выведено из них, нужно подтвердить; ❓ в исходных материалах нет, вопрос автору.
- Неопределённость — это вопрос автору, а не догадка. Все структурные вопросы решаются до написания схемы. Бизнес-условия (признаки возврата, критерии, названия) задаёт автор; модель их не выдумывает.

## Правило переноса

Требование Design System, которое Basic не может исполнить, **записывается как несоответствие и ждёт решения**; оно не теряется и не подменяется похожим. Решение — доработка Basic, изменение требования автором или явная оговорка в документе.

## Как проверять документ

- Поле каждой связи имеет парное поле у принимающего этапа (вход этапа совпадает со связями схемы процесса).
- Схема, выведенная из документа, проходит `validate`, открывается на холсте и после Save → загрузки даёт те же шаги.
