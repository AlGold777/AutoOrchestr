# Запрос для моделей: составить схему в формате стенда

Текст между линиями копируется целиком и отправляется моделям вместе со скриншотами холста (общий вид, окно раунда, окно модели). Ответ модели вставляется в стенд (кнопка «i» → «Применить»), см. [README.md](README.md). Формат проверяет `stand.js`; технический контракт — [CONTRACT.md](CONTRACT.md).

Запрос написан простым языком и ужесточён по результатам прогонов: модели путали форму ответа (присылали внутренний файл прототипа или Mermaid), забывали закрывать петли повторной проверкой, ссылались на пропускаемые этапы как на обязательные, задавали веса в разных единицах и просили приложение самому загрузить материал. Каждое правило ниже закрывает конкретный наблюдавшийся сбой. При изменении формата стенда обновляйте запрос и поднимайте версию стенда.

---

````
Задание: собрать одну реальную схему из готовых блоков и записать её в строгом формате JSON.

О приложении.
Это расширение для браузера. Пользователь формулирует задачу, а приложение отправляет её сразу нескольким нейросетевым чатам (ChatGPT, Gemini, Claude и другим), собирает ответы и показывает вместе. Ответы можно пускать по кругу: модели видят ответы друг друга, критикуют, уточняют, одна из них сводит итог. Весь ход работы описан схемой: пользователь собирает её на экране, как конструктор, из блоков. На скриншотах показан наш холст: слева направо идут этапы, у каждого раунда под значком стоят блоки моделей, под ними серые артефакты, справа финальный синтез.

Как устроена схема.
Схема — список этапов сверху вниз. Порядок в списке и есть порядок выполнения. Каждый этап берёт на вход результаты более ранних этапов и выдаёт свой результат. Стрелок назад нет и быть не может.

БЛОКИ (значение `block`)
— `round`: несколько моделей отвечают одновременно или по очереди. Поля: `models` (список; у каждой модели `name`, можно `role`, `task`, `maxWords`, `request`), `order` (`parallel` — одновременно, `sequential` — по очереди, каждая видит ответы тех, кто ответил до неё), `task` (общее задание раунда), `inputs`.
— `synthesis`: одна модель сводит ответы. Поля: `model`, `role`, `task`, `inputs`. Допустимые `role`: свести, судья, жюри, отобрать идеи, сгруппировать, критический разбор.
— `gate`: проверка по критериям. Поля: `criteria`, `inputs`.
— `route`: выбор пути вперёд. Поле `choices`: [{"when": "условие", "goes": ["id этапа НИЖЕ"]}].
— `owner`: этап человека, прогон ждёт ответа. Поле `ask`.
— `form`: HTML-опросник, который создаёт модель, а пользователь заполняет. Поля: `purpose`, `inputs`.
— `source`: внешний материал. Поля: `kind` (`text` / `document` / `link`), `title`, `content` или `attachment` (см. ниже).
— `file`: запись или чтение файла в папке пользователя. Поля: `file`, `mode` (`overwrite` / `append` / `read`), `inputs`.
— `list`: делит материал на пронумерованные части. Поля: `from`, `rule`.
— `foreach`: один и тот же вложенный кусок схемы для каждого пункта списка. Поля: `over` (id этапа `list`), `body` (список этапов в том же формате).
— `block`: готовая часть схемы. Поля: `name`, `inputs`.
— `assemble`: склейка документа без нейросети. Поля: `inputs`, `template`.
— `score`: приложение считает баллы. Поля: `inputs`, `criteria`, `weights`.

ОБЩИЕ ПОЛЯ ЛЮБОГО ЭТАПА
`id` (уникальный, s1, s2, …; внутри `body` — свои, например s5a), `block`, `title` (по-русски), `why` (ОБЯЗАТЕЛЬНО, одна строка), `inputs`, `optional_inputs`, `repeats`, `because`.
`artifacts` — список артефактов этапа; у каждого артефакта ОБЯЗАТЕЛЬНО описание, поэтому пишите его объектом {"name": "Карта функций", "description": "что в нём лежит и кому он нужен, 1–2 фразы"}; ссылки в `inputs` по-прежнему «s3.Карта функций» (по имени).
На верхнем уровне также `description` — презентация проекта для человека, который будет запускать эту схему. Не короткая строка: опишите проект целиком. На работу схемы не влияет.
Необязательные поля настроек: на верхнем уровне `defaults` {roundTask, synthesisTask, discipline: {lines: [строки]}, modelNotes: {"Claude": "текст"}} — общие правила для всех моделей; у модели и синтеза `maxWords` (целое число слов), `request` (полный свой запрос вместо автоматического).

МАТЕРИАЛЫ (блок `source`)
Приложение ничего само не загружает, не открывает ссылки и не ищет в интернете. Всю информацию и все материалы, которые нужны этапам, вы даёте сами одним из двух способов:
— полный текст материала в поле `content` (бриф, критерии, шаблон, образец данных);
— отдельный файл, приложенный к вашему ответу в чате, и в поле `attachment` его точное имя с расширением (например, `бриф.md`).
Если реальный материал вставит пользователь, опишите в `content`, каким он должен быть: формат, объём, пример. Не рисуйте этапов вида «найти в интернете» или «прочитать ссылку».

ЖЁСТКИЕ ПРАВИЛА (нарушение = схема считается неверной)
1. `inputs` ссылаются только на этапы ВЫШЕ по списку. Конкретный артефакт: "s3.Название артефакта", артефакт должен быть в `artifacts` у s3. Внутри `body` у `foreach` текущий пункт — `item`, и только там.
2. `route.goes` ссылается только на этапы НИЖЕ. Если этап читает результат этапа, который развилка могла пропустить, этот вход пишется в `optional_inputs`, а не в `inputs`.
3. ЛЮБАЯ петля пишется так, и никак иначе. Четыре этапа, не обязательно подряд, но все четыре:
   а) этап работы; б) `gate` (проверка);
   в) повтор этапа работы: `repeats` = id этапа работы, `because` = «<id gate> не пройден»;
   г) повторная проверка: этап `gate` с `repeats` = id первой проверки.
   Петля без повторной проверки (пункт г) запрещена. Кругов не больше трёх.
4. У повтора можно не писать `models`, `model`, `order`, `role`: они копируются с повторяемого этапа.
5. Имена моделей — только Claude, GPT, Gemini, Grok, Le Chat, Qwen, DeepSeek, Perplexity, Z.ai, Kimi. Не «ChatGPT».
6. `weights` — объект с долями, которые в сумме дают 1: {"безопасность": 0.4, "стоимость": 0.6}.
7. `{item}` в тексте `task` допустим только внутри `body` у `foreach`, и тогда в `inputs` этого этапа есть "item".
8. У каждого этапа есть `id`, `block`, `title`, `why`. Все `id` в схеме уникальны.
9. Артефакт, который этап обновляет, называется так же (новая версия).
10. Артефакт — всегда документ (текст с названием и версией), а не запрос к модели и не обрывок ответа. Артефакт — не любой результат этапа. Обычный результат этапа следующий этап получает сам через `inputs: ["s2"]` (без точки и без артефакта). Объявляйте артефакт, только если он нужен не только соседнему этапу: его читают этапы дальше по схеме, он обновляется новыми версиями, или это документ для человека или для файла. Не объявляйте артефактом каждый результат.

ФОРМА ОТВЕТА (строго)
— Ответ: ОДИН блок JSON и больше ничего до него. После него — только три коротких пункта (см. ниже).
— Только настоящий JSON: двойные кавычки, без комментариев, без запятой после последнего элемента, без «...», «…», «и т.д.», без многоточий вместо этапов.
— Не пишите Mermaid, JavaScript и не присылайте внутренние файлы приложения (никаких `window.ProtoState = …`).
— Если ответ не помещается: сокращайте тексты заданий до одной фразы, но НЕ убирайте этапы и НЕ обрывайте JSON.

ПРОВЕРЬТЕ ПЕРЕД ОТВЕТОМ (про себя, по списку)
 □ этапов верхнего уровня не меньше 8, разных блоков не меньше 5;
 □ есть хотя бы одна петля, и она закрыта повторной проверкой (правило 3);
 □ ни один `inputs` не ссылается на этап НИЖЕ по списку (и на сам этап), «стрелок назад» нет;
 □ у каждого этапа есть `why`; на верхнем уровне есть `description`;
 □ каждый «s3.Имя» ссылается на объявленный артефакт;
 □ у каждого артефакта есть description;
 □ артефактами объявлены только документы, нужные не одному соседнему этапу (правило 10)
 □ после `route` все пропускаемые входы вынесены в `optional_inputs`;
 □ у каждого `source` есть `content` или `attachment`;
 □ имена моделей из списка, `weights` — доли с суммой 1;
 □ JSON закрыт до конца и разбирается без ошибок.

Что нужно от вас.
Выберите реальную задачу, которую человек действительно ставит перед нейросетями (подготовка большого документа, анализ множества материалов, выбор решения, исследование). Не копируйте задачи из примера. Соберите схему и запишите её JSON. Затем тремя короткими пунктами:
— каких блоков не хватило или какой был непонятен («ничего», если всё ясно);
— какие блоки не использовали и почему;
— самое слабое место вашей схемы.
````

## Что стенд делает с нарушениями

| Нарушение в ответе | Реакция стенда |
| --- | --- |
| Лишний текст до и после JSON, служебные строки расширения копирования | Убирает, текст вне JSON сохраняет как «Комментарий модели» |
| Кавычки, запятые, комментарии, ключи без кавычек | Исправляет с предупреждением |
| Алиасы (`stages`, `type`, `name`, `input`), строка вместо списка, обёртки | Исправляет с предупреждением |
| Формат `state.js`, Mermaid, текст без JSON, оборванный JSON | Отклоняет с пояснением, что просить у модели |
| Ссылка вниз, `route` назад, нет `why`, `repeats` без `because`, `item` вне `foreach` | Ошибка с названием этапа |
| Артефакт без `description` (старая строка-имя тоже принимается) | Замечание: «У артефакта «X» нет описания» |
| Петля без повторной проверки, пропускаемый вход вне `optional_inputs`, `weights` не объектом, неизвестное имя модели, «...» вместо текста, `source` без `content` и `attachment` | Предупреждение |
