# Запрос для моделей: составить схему в формате стенда

Текст между линиями копируется целиком и отправляется моделям вместе со скриншотами холста (общий вид, окно раунда, окно модели). Ответ модели вставляется в стенд (кнопка «i» → «Применить»), см. [README.md](README.md). Формат проверяет `stand.js`; технический контракт — [CONTRACT.md](CONTRACT.md).

Запрос написан простым языком и ужесточён по результатам прогонов: модели путали форму ответа (присылали внутренний файл прототипа или Mermaid), уходили в возвраты назад и просили приложение самому загрузить исходные данные. Каждое правило ниже закрывает конкретный наблюдавшийся сбой. При изменении формата стенда обновляйте запрос и поднимайте версию стенда.

---

````
Задание: собрать одну реальную схему из этапов и артефактов и записать её в строгом формате JSON.

О приложении.
Это расширение для браузера. Пользователь формулирует задачу, а приложение отправляет её сразу нескольким нейросетевым чатам (ChatGPT, Gemini, Claude и другим), собирает ответы и показывает вместе. Ответы можно передавать дальше по схеме: следующий этап видит ответы предыдущих, модели критикуют, уточняют, одна из них сводит итог. Весь ход работы описан схемой: пользователь собирает её на экране, как конструктор, из этапов. На скриншотах показан наш холст: этапы идут слева направо, у каждого этапа под значком раунда (R1, R2…) одной строкой лежат артефакты этого этапа, а под ними стоят модели.
Каждая модель ведёт один и тот же чат на протяжении всей схемы: она помнит всё, что ей уже отправляли и что она отвечала. Поэтому документ, который модель уже получила, повторно подавать не нужно. `inputs` определяет только то, что добавляется в очередной запрос этой модели.

Словарь (только два слова).
Этап — действие, у которого есть исполнитель: модель, User или приложение.
Артефакт — любой документ или данные. Его производит этап, либо он дан с самого начала (бриф, образец, вложенный файл).
Правило проверки: если у этапа есть исполнитель (модель, User, приложение), это этап; если нет — это артефакт.

Как устроена схема.
Схема — список этапов сверху вниз. Порядок в списке и есть порядок выполнения: все этапы выполняются по очереди, ветвлений нет. Каждый этап берёт на вход артефакты более ранних этапов и исходные артефакты и выдаёт свои. Стрелок назад нет и быть не может: схема не содержит возвратов.

ВИДЫ ЭТАПОВ (значение `block`)
| Вид этапа | Исполнитель | Что делает | Поля |
| --- | --- | --- | --- |
| `round` | модели | одна или несколько моделей отвечают на один запрос | `models` (список; у каждой `name`, можно `role`, `task`, `maxWords`), `task` (общее задание раунда), `inputs` |
| `owner` | User | ответ User на вопрос `ask`; следующий этап читает этот ответ | `ask` (вопрос User), `inputs` |
| `file` | приложение | запись файла в папку пользователя | `file`, `mode` (`overwrite` / `append`), `inputs` |

Раунд — один запрос всем его моделям, они отвечают независимо. Чтобы одна модель видела ответ другой, поставьте этапы по одной модели подряд.

Видов три. Синтез, судья, жюри, проверяющий — это роли, а не отдельные виды этапов. Синтез = `round` из одной модели с role «свести»: `"models": [ { "name": "Claude", "role": "свести" } ]`. Склейка нескольких артефактов в один документ — тоже `round` из одной модели с role «свести» и заданием «объедини без изменений»; результат — новый артефакт.
Проверка — `round` с критериями в `task`: в задании просьба ответить словом «прошло» или «не прошло», затем замечания списком. Если по её результату нужно решение User, следующим этапом ставится `owner` с вопросом в `ask`.

ОБЩИЕ ПОЛЯ ЛЮБОГО ЭТАПА
`id` (уникальный: s1, s2, …), `block` (вид этапа), `title` (по-русски), `why` (ОБЯЗАТЕЛЬНО, одна строка), `inputs`, `artifacts` (артефакты, которые этап производит).
У каждого артефакта в `artifacts` ОБЯЗАТЕЛЬНО описание, поэтому пишите его объектом: {"name": "Карта функций", "description": "что в нём лежит и кому он нужен, 1–2 фразы"}. Ссылки в `inputs` — по имени: "s2.Карта функций".
На верхнем уровне также `description` — презентация проекта для человека, который будет запускать эту схему. Не короткая строка: опишите проект целиком. На работу схемы не влияет.
Необязательные настройки: на верхнем уровне `defaults` {roundTask, discipline: {lines: [строки]}, modelNotes: {"Claude": "текст"}} — общие правила для всех моделей; у модели `maxWords` (целое число слов).

ИСХОДНЫЕ АРТЕФАКТЫ.
Исходный артефакт — не этап. Он записывается на верхнем уровне схемы списком `artifacts`: объекты с полями `name` (обязательно), `description` (желательно) и одним из полей `content` (полный текст) или `attachment` (точное имя файла с расширением, приложенного к ответу в чате).
Ссылка из этапа: в `inputs` строка "in.Имя" (например, "in.Бриф"). Этап для неё не нужен, ссылка допустима на любом месте списка.
Подавайте исходный артефакт в первый этап, которому он нужен; следующим этапам тех же моделей его повторять не нужно.
Приложение само ничего не загружает и не ищет в интернете. Исходные данные даёте вы сами: полным текстом в `content` или файлом в `attachment`. Если реальный текст вставит пользователь, опишите в `content`, каким он должен быть: формат, объём, пример. Не рисуйте этапов вида «найти в интернете» или «прочитать ссылку».
Не путайте два поля `artifacts`: верхнеуровневое — исходные (объекты), у этапа — производимые (с описанием, см. выше).

ЖЁСТКИЕ ПРАВИЛА (нарушение = схема считается неверной)
1. `inputs` ссылаются только на этапы ВЫШЕ по списку (и не на сам этап). Конкретный артефакт: "s2.Название артефакта", артефакт должен быть в `artifacts` у s2. Исходный артефакт: "in.Название".
2. Возвратов назад нет. Если после проверки нужна доработка, ставится следующий этап «ответ User» (`owner`): он решает, доработать или утвердить; затем этап доработки, который читает вердикт проверки и ответ User; дальше всё по порядку. Если нужна ещё одна проверка, это ещё один обычный этап ниже по списку. Число повторов определяется числом записанных этапов.
3. Имена моделей — только Claude, GPT, Gemini, Grok, Le Chat, Qwen, DeepSeek, Perplexity, Z.ai, Kimi. Не «ChatGPT».
4. У каждого этапа есть `id`, `block`, `title`, `why`. Все `id` в схеме уникальны.
5. Артефакт, который этап обновляет, называется так же (новая версия).
6. Артефакт — всегда документ (текст с названием и версией), а не запрос к модели и не обрывок ответа. Артефакт — не любой результат этапа. Обычный результат этапа следующий этап получает сам через `inputs: ["s1"]` (без точки и без артефакта). Объявляйте артефакт, только если он нужен не только соседнему этапу: его читают этапы дальше по схеме, он обновляется новыми версиями, или это документ для человека или для файла. Не объявляйте артефактом каждый результат.
7. Входы минимальны: в `inputs` этапа — только то, без чего он не может работать и чего его модели ещё не получали. Не повторяйте документ, который эти модели уже видели в прошлых этапах, и не добавляйте ссылку «на всякий случай».

ФОРМА ОТВЕТА (строго)
— Ответ: ОДИН JSON-объект и больше ничего до него. После него — только три коротких пункта (см. ниже).
— Только настоящий JSON: двойные кавычки, без комментариев, без запятой после последнего элемента, без «...», «…», «и т.д.», без многоточий вместо этапов.
— Не пишите Mermaid, JavaScript и не присылайте внутренние файлы приложения (никаких `window.ProtoState = …`).
— Если ответ не помещается: сокращайте тексты заданий до одной фразы, но НЕ убирайте этапы и НЕ обрывайте JSON.

ПРОВЕРЬТЕ ПЕРЕД ОТВЕТОМ (про себя, по списку)
 □ этапов верхнего уровня не меньше 8, разных видов этапов (`block`) не меньше 3 (round, owner, file);
 □ ни один `inputs` не ссылается на этап НИЖЕ по списку (и на сам этап), «стрелок назад» нет;
 □ у каждого этапа есть `why`; на верхнем уровне есть `description`;
 □ каждый «s2.Имя» ссылается на артефакт, объявленный в `artifacts` у s2; каждый "in.Имя" — на исходный артефакт верхнего уровня;
 □ у каждого артефакта этапа есть `description`; артефактами объявлены только документы, нужные не одному соседнему этапу (правило 6);
 □ если после проверки нужна доработка, между ними стоит `owner`;
 □ у каждого исходного артефакта есть `content` или `attachment`;
 □ у каждого входа этапа есть причина: без него этап не справится;
 □ имена моделей из списка;
 □ JSON закрыт до конца и разбирается без ошибок.

Что нужно от вас.
Выберите реальную задачу, которую человек действительно ставит перед нейросетями (подготовка большого документа, анализ множества документов, выбор решения, исследование). Не копируйте задачи из примера. Соберите схему и запишите её JSON. Затем тремя короткими пунктами:
— каких видов этапов не хватило или какой был непонятен («ничего», если всё ясно);
— какие виды этапов не использовали и почему;
— самое слабое место вашей схемы.
````

## Что стенд делает с нарушениями

| Нарушение в ответе | Реакция стенда |
| --- | --- |
| Лишний текст до и после JSON, служебные строки расширения копирования | Убирает, текст вне JSON сохраняет как «Комментарий модели» |
| Кавычки, запятые, комментарии, ключи без кавычек | Исправляет с предупреждением |
| Алиасы (`stages`, `type`, `name`, `input`), строка вместо списка, обёртки | Исправляет с предупреждением |
| Формат `state.js`, Mermaid, текст без JSON, оборванный JSON | Отклоняет с пояснением, что просить у модели |
| Ссылка вниз, нет `why` | Ошибка с названием этапа |
| Вид этапа `route` (развилка) | Ошибка этапа: «Вид этапа «route» не поддерживается. Ветвления в схеме нет: все этапы выполняются по порядку. Если нужно решение User — поставьте этап owner с вопросом ask, а следующий этап читает его ответ.» |
| Вид этапа `assemble` (сборка) | Ошибка этапа: «Вид этапа «assemble» не поддерживается. Склейка — просто новый артефакт: запишите этап round, который объединяет входы и выдаёт новый артефакт.» |
| Вид этапа `synthesis` (синтез) | Ошибка этапа: «Вид этапа «synthesis» не поддерживается. Синтез — это роль: запишите этап round из одной модели с role «свести» (models: [{ "name": "Claude", "role": "свести" }]).» |
| Вид этапа `gate` (проверка) | Ошибка этапа: «Вид этапа «gate» не поддерживается. Проверка — обычный этап моделей: критерии запишите в task, затем поставьте этап owner: User читает вердикт и решает, нужна ли доработка». |
| Удалённый вид этапа (перебор по пунктам, список, форма, источник, готовая часть, оценка баллами) | Ошибка этапа с пояснением, как выразить иначе |
| Вложенный `body` | Ошибка |
| Удалённые поля (повторы, основания, веса, запрос, `choices`, `template`) | Предупреждение; значение игнорируется |
| Поле `optional_inputs` | Предупреждение: «Поле «optional_inputs» не поддерживается и не применяется: пропускаемых этапов нет, все входы обязательны.» Значение игнорируется |
| Артефакт этапа без `description` | Замечание: «У артефакта «X» нет описания» |
| Неизвестное имя модели, «...» вместо текста, исходный артефакт без `content` и `attachment` | Предупреждение |
