# Как написать схему Basic: полная инструкция

Версия формата схемы: **1**. Этот документ самодостаточен: чтобы написать рабочую схему, другие файлы читать не нужно.
Его читает человек или модель (в том числе небольшая) и выдаёт один JSON-файл, который расширение принимает с первого раза.
Все примеры и списки ниже проверяются тестом `tests/basic-schema-guide.test.js` против кода: если код изменится, а документ нет,
тест упадёт.

## 0. Как этим пользоваться

**Человеку.**
1. Скопируйте этот документ целиком в модель и допишите в конце, что должен делать pipeline (своими словами).
2. Модель вернёт JSON. Сохраните его в файл с расширением `.json` (внутри только JSON, без ``` и пояснений).
3. На странице pipeline нажмите **Import schema**, выберите файл. Имя нового pipeline предлагается из имени файла (без `.json`), его можно изменить. Схема встанет на холст и будет в списке.
4. Введите задачу в поле модератора и запустите pipeline, как обычно.

**Запрос для модели** (вставьте перед описанием вашей задачи):

```text
Ты автор схемы pipeline для движка Basic. Прочитай инструкцию ниже целиком и выполни её буквально.
Верни ровно один JSON-объект: без пояснений, без комментариев, без markdown-ограждений.
Перед ответом пройди чек-лист из раздела 11 и исправь всё, что не проходит.
Что должен делать pipeline: <здесь описание задачи>
```

## 1. Что такое схема (коротко)

- **Basic** — движок, который выполняет pipeline: несколько шагов подряд, в каждом шаге один или несколько моделей отвечают на задачу.
- **Схема** — JSON-описание такого pipeline: из каких шагов он состоит, какие модели в каждом шаге и чем отличается от настроек по умолчанию.
- Схема описывает **как** обрабатывать задачу, а не саму задачу. Задачу пользователь вводит при запуске.
- Пишите в схеме **только то, чем она отличается от умолчаний** (раздел 4). Всё, что не указано, Basic возьмёт сам. Так схема короче, и ошибиться негде.

## 2. Формат ответа (жёсткие правила)

- Один JSON-объект. Первый символ `{`, последний `}`.
- Двойные кавычки у всех ключей и строк. Без комментариев (`//`, `/* */`). Без запятой после последнего элемента.
- Числа — числами (`300`, не `"300"`). Булевы — `true` / `false`.
- Не придумывайте поля: неизвестное поле — ошибка, схема не установится.
- Не пишите пустые строки `""` как значения: пустая строка — это «пусто», а не «по умолчанию». Чтобы получить значение по умолчанию, **не пишите поле вообще**.

## 3. Алгоритм: как собрать схему за 7 шагов

1. **Сформулируйте цель одной фразой** и разложите на этапы словами («сначала несколько моделей отвечают независимо, потом одна сводит ответы, потом две критикуют…»). Каждый такой этап с моделями — раунд.
2. **Определите раунды.** Раунд — это шаг, где одна или несколько моделей отвечают. Самый первый шаг схемы получает только задачу пользователя; раунд после любого шага (в том числе шага User) по умолчанию получает ответы предыдущего шага. Раундов не больше 50; обычно 1–3.
3. **Решите, кто в каждом раунде.** Выберите имена моделей строго из списка в разделе 7.1. Одна модель не должна повторяться в одном раунде.
4. **Нужен ли синтез** (свести ответы в один): это не отдельный вид шага, а роль. Синтез — раунд из одной модели с ролью `interaction_meta_synthesis` (7.2) и, при желании, своим `task`. Между раундами он сводит ответы, и следующий раунд работает уже со сводом. Итоговый синтез — последний раунд из одной модели с ролью: итог прогона — принятые ответы последнего шага. Если свод не нужен — пропустите.
5. **Нужны ли шаги User** (`owner`, 5.9): User даёт данные или принимает решение между раундами.
6. **Для каждого раунда после первого решите две вещи** (если умолчания не подходят): вход (`input`) и задание (`task`) — раздел 5.4. Роли моделей (`role`) — раздел 7.2.
7. **Соберите JSON** по шаблону из раздела 9, подставьте свои значения и пройдите чек-лист (раздел 11).

**Как выбрать вход раунда (`input`)** — самый частый вопрос:

| Что нужно | Что писать |
| --- | --- |
| Модели раунда работают с ответами предыдущего шага (улучшают, критикуют, проверяют) | ничего (умолчание: `previous`) |
| Модели должны видеть ответы **всех** предыдущих шагов, а не только последнего | `"input": "all"` |
| Модели раунда отвечают на задачу заново, не видя прежних ответов | `"input": "none"` |

**Как модели раунда работают вместе.** Раунд — один запрос всем его моделям: они отвечают независимо и одновременно, раунд ждёт ответов всех своих включённых моделей. Поля порядка и числа нужных ответов нет. Чтобы одна модель видела ответ другой («эстафета»), поставьте раунды по одной модели подряд: следующий раунд получает ответ предыдущего через вход (шаблон C). Холст показывает модели каждого раунда в порядке `models`.

## 4. Что Basic берёт сам (это писать в схему не нужно)

| Что | Значение по умолчанию |
| --- | --- |
| Политика запуска `run.policy` | `manual` — после каждого шага User подтверждает продолжение. Для автоматической цепочки пишите `"auto"` |
| Общий предел длины `run.maxWords` | `300` |
| Строгая длина `run.strictLength` | `false` — длину ответа проверяет только просьба в запросе |
| Вход первого раунда | `none` (только задача) |
| Вход остальных раундов | `previous` (ответы предыдущего шага) |
| Задание раундов после первого | `Учти ответы предыдущего шага и дай свой улучшенный ответ на задачу.` |
| Инструкция длины | `[RESPONSE_LIMIT] Объём ответа: {от}-{слов} слов, не больше.` |
| Требования к содержанию | `Сосредоточься на ясной концепции и ключевых идеях; убери повторы, длинные пересказы и второстепенные детали.` |
| Инструкция доставки | `Последней строкой ответа напиши только метку {метка}` |
| Запрос исправления | `Твой предыдущий ответ {причина}. Дай ответ на задание полностью.` |
| Попытки приёма ответа | 2: исходный запрос и одно исправление той же моделью в том же чате; пустой ответ повторяется тем же запросом, без исправления |

Задание первого раунда из ▶ и из Basic не отправляется: первый раунд получает задачу пользователя и задание, которое вы сами записали в `task` шага или модели.

## 5. Справочник полей

Условные обозначения: **обязательно** — без поля схема не пройдёт проверку; остальные поля можно не писать.

### 5.1. Корень схемы

| Поле | Тип | Значение | Если не указано |
| --- | --- | --- | --- |
| `schemaVersion` | число | всегда `1` | **обязательно** |
| `origin` | строка | всегда `"user"` | **обязательно** |
| `basedOn` | строка | на какой схеме основана эта (только пометка) | нет |
| `description` | текст | презентация pipeline для человека (длинный текст); в окне ▶ блок Description, при наведении на ▶ — подсказка; на прогон не влияет | нет |
| `run` | объект | политика запуска и общий предел (5.2) | значения Basic |
| `defaults` | объект | общие значения для всех шагов (5.3) | значения Basic |
| `spec` | объект | спецификация pipeline, только для документа (5.10) | нет |
| `steps` | список | шаги по порядку выполнения (5.4) | **обязательно** |

### 5.2. `run`

| Поле | Значение | Если не указано |
| --- | --- | --- |
| `policy` | `"auto"` — шаги идут без остановки; `"manual"` — после каждого шага User подтверждает | `manual` |
| `maxWords` | общий предел длины ответа в словах: **только 300, 500, 700 или 1000** | `300` |
| `strictLength` | `true` — ответ длиннее предела отклоняется на всех шагах, где у `output` нет своего `strictLength`; `false` — проверки нет | `false` |

`strictLength` — необязательное поле схемы (`schemaVersion` остаётся 1). Предел тот же, что у `output.strictLength` шага: максимум слов модели или общий `maxWords`. Явный `output.strictLength` шага (в том числе `false`) сильнее `run.strictLength`. Отказ — `too_long` с числом слов, запрос повторяется с исправлением.

### 5.3. `defaults` (общие значения; необязательно)

| Поле | Значение |
| --- | --- |
| `roundTask` | задание для всех раундов после первого, у которых нет своего |
| `discipline` | общая дисциплина ответа (5.6) для всех моделей |
| `modelNotes` | `{ "<имя модели>": "<текст>" }` — особенность модели; добавляется к каждому запросу этой модели (раздел 6) |
| `roundPrompts` | `{ "<ref раунда>": "<текст>" }` — текст для роли `custom` в этом раунде (7.2) |

### 5.4. Шаг (`steps[]`)

| Поле | Значение | Если не указано |
| --- | --- | --- |
| `ref` | уникальное имя шага (правила ниже) | **обязательно** |
| `kind` | `"round"`; `"owner"` — шаг User (5.9). Видов `synthesis`, `gate` и `route` нет (5.9): синтез — раунд из одной модели с ролью | **обязательно** |
| `input` | для `round`: `"none"`, `"previous"`, `"all"` или список источников (5.7) | самый первый шаг схемы — `none`, раунд после любого шага (шаг User тоже шаг) — `previous` |
| `task` | задание шага для всех его моделей | задание из `defaults`, затем из Basic (4); при `input: none` отправляется только записанное в схеме задание шага или модели |
| `models` | список моделей шага (5.5) | **обязательно**; пустой список выключает шаг |
| `output` | форма ответа (`form`, `sections`, `strictLength`, `format: json`, `requiredFields`) и объявленные артефакты (`artifacts`, `revisionOf`) (5.8) | ответ как есть |
| `owner` | `"approve"` — после шага User подтверждает продолжение, даже в `auto` и на последнем шаге. Движок исполняет подтверждение. Страница сохраняет значение со схемой и передаёт его в прогон; задаётся в окне раунда (`basic-windows.md`, «Поля шага») | без подтверждения |
| `chat` | `"continue"` — участник продолжает свой чат; `"new"` — новый чат на первом запросе каждого захода шага, исправления и повторы внутри захода идут в тот же чат. `"new"` исполняется транспортом по участникам (страница его передаёт). По умолчанию (`continue`) каждая модель ведёт один чат на всю схему. | `continue` |
| `document` | для шага User (5.9): ref более раннего раунда с одной моделью, документ которого User читает в окне | не задан: поле текста |
| `title` | название этапа для человека (только для документа, 5.10) | нет |
| `goal` | цель этапа: для документа (5.10); у User показывается в окне (5.9) | нет |
| `rules` | правила и ограничения этапа (только для документа, 5.10) | нет |
| `quality` | критерии качества этапа и способ проверки (только для документа, 5.10) | нет |

**Имена шагов (`ref`):**
- Раунды: `"r1"`, `"r2"`, `"r3"`… строго по порядку, без пропусков. Синтез — тоже раунд и получает следующий номер.
- User: `"owner:<id>"`, где `<id>` — только латинские буквы, цифры, `_` и `-` (например, `"owner:check"`).

### 5.5. Модель шага (`models[]`)

| Поле | Значение | Если не указано |
| --- | --- | --- |
| `name` | имя модели из списка 7.1; в одном шаге не повторяется, если у участников нет разных `id` | **обязательно** |
| `id` | ID участника в шаге: непустой текст. Один участник — один ID; у одного ID имя во всех шагах одно. Движок различает участников по ID. Страница сохраняет `id` со схемой; страница не показывает два участника одной модели в одном шаге и отклоняет такую схему при установке, с указанием шага | имя модели (`name`) |
| `input` | вход этого участника вместо входа шага: `"none"`, `"previous"`, `"all"` или список источников (5.7). Движок исполняет его. Страница сохраняет его со схемой и передаёт в прогон; окна настройки пока нет (значение задаётся в JSON) | вход шага |
| `enabled` | `false` — модель выключена: её настройки хранятся, но она не вызывается. Объявление выключенного участника (`name`, `id`, `enabled: false`) сохраняется в настройках даже без других полей; на него можно ссылаться (необязательная ссылка допустима, обязательная решается при исполнении), раунд не ждёт его ответа | включена |
| `onCanvas` | `true` — модель стоит на холсте, даже если она снята (флажок «Участие в раунде») во всех раундах; без этого поля такая модель после Save и перезагрузки с холста пропадает. Страница пишет поле сама только для таких моделей; у модели, включённой хотя бы в одном раунде, его нет | не стоит на холсте |
| `role` | id роли из списка 7.2 | без роли |
| `request` | **полный** свой запрос этой модели вместо автоматического (раздел 6, внимание!) | автоматический |
| `maxWords` | личный предел длины ответа этой модели: целое положительное число | общий предел `run.maxWords` |
| `task` | личное задание этой модели: ЗАМЕНЯЕТ общее `task` шага целиком, а не дополняет его | задание шага |
| `discipline` | личная дисциплина ответа (5.6) | значения из `defaults`, затем Basic |
| `output` | собственный выход этого участника (5.8). Целиком заменяет общий `output` шага, не сливается с ним. Движок проверяет ответ, регистрирует артефакты и выдаёт промпт по этому выходу | общий `output` шага |

Два участника одной модели в одном шаге (разные `id`) холст не показывает: схема с ними не устанавливается, с указанием шага. Движок и транспорт передают каждого участника отдельным запросом в свою вкладку. Это проверено моками; ручная проверка в реальных вкладках провайдеров не выполнена (см. `basic-developer.md`, «Что не проверено вживую»).

### 5.6. `discipline` (в `defaults` и в модели)

| Поле | Значение |
| --- | --- |
| `limit` | инструкция длины; подстановки `{от}` (предел минус 50) и `{слов}` (предел) |
| `content` | требования к содержанию |
| `delivery` | инструкция доставки; подстановка `{метка}` |
| `correction` | запрос исправления; подстановка `{причина}` |
| `lines` | список своих строк-инструкций (`["Отвечай по-русски.", "Приведи источники."]`); каждая добавляется в запрос отдельным абзацем после требований к содержанию. Строки из `defaults` идут первыми, затем строки модели |

Значение модели главнее значения из `defaults`, оно главнее значения Basic. Для `lines` это не замена, а добавление.

### 5.7. Входы по ссылкам (исполняется)

Список источников в `input` исполняется: ссылка-строка берёт все принятые ответы шага, объект `{ step, participant, required }` — ответ одного участника; `required` по умолчанию `false`. Обязательный источник без ответа останавливает прогон (`missing_input`) до первого запроса. Ссылка на артефакт `{ artifact: { step, participant, id }, version }` берёт содержимое объявленного документа (5.8): `version: "latest"` — последняя актуальная версия линии, объект `{ step, participant, visit }` — точная версия.

| Источник в списке | Пример | Что передаётся |
| --- | --- | --- |
| Шаг | `"r1"` | все принятые ответы шага, в порядке участников |
| Шаг целиком, обязательный | `{ "step": "r1", "required": true }` | весь принятый результат шага в порядке участников (шаг сохраняется только с ответами всех своих участников). Источник должен быть завершён и пройти гейт или подтверждение User, иначе `missing_input` до отправки |
| Участник шага | `{ "step": "r2", "participant": "A", "required": true }` | ответ одного участника шага |

- Список непустой. Порядок сохраняется. Один и тот же адрес дважды — ошибка, даже если `required` различается. Строка `"r1"` и объект `{ "step": "r1" }` — один и тот же адрес, поэтому их вместе указывать нельзя.
- Источник — только более ранний шаг. Выключенный шаг или участник — допустимая ссылка.
- `required` — `true` или `false`; по умолчанию `false`.
- Вход вставляется текстом полностью при каждой ссылке, повторная передача того, что модель уже получала в этом чате, не отфильтровывается. Если все модели шага уже получали документ в том же чате (у шага нет `chat: "new"`), не передавайте его в `input` снова: сошлитесь на документ по названию в `task`, например: «Используй документ «Карта функций», он у тебя уже есть.»

### 5.8. Выход шага и артефакты (исполняется)

Артефакт — всегда документ (текст с названием и версией), а не запрос к модели и не обрывок ответа.

Исполняются `form`, `sections`, `strictLength`, `format: "json"` с `requiredFields` и объявленные `artifacts`: каждый принятый ответ регистрирует свои артефакты в реестре прогона (`result.artifacts`), текст ответа хранится один раз (`putText`/`getText` страницы или словарь прогона). Реестр хранится в записи прогона (`record.artifacts`), тексты ответов — в `record.texts`. `revisionOf` (ревизия) присоединяет версию к линии артефакта, который автор получил во входе: версия остаётся со своим автором и заходом. Ссылка обязана быть во входе каждого участника шага; если автор её не получил, шаг не отправляется (`missing_input`).

| Поле `output` | Значение |
| --- | --- |
| `name` | название результата шага |
| `form` | инструкция о форме ответа |
| `sections` | заголовки, которые должны быть в тексте ответа (список непустых строк; только для текстового формата) |
| `strictLength` | `true` — ответ длиннее предела отклоняется; `false` — не проверяется, даже если в `run` стоит `strictLength: true`; без поля действует `run.strictLength` |
| `format` | только `"json"`: весь ответ — один JSON-объект |
| `requiredFields` | только для `json`: список JSON Pointer к обязательным полям ответа, например `"/correctedMap"` |
| `artifacts` | объявленные документы: `{ "id", "name", "pointer" }`, необязательные `description` (строка) и, для доработки, `revisionOf` |
| `document` | вид документа для раунда, чей ответ читает User (5.9): `read` — документ для чтения (ровно один артефакт в `artifacts`), `form` — опросник; `form` требует `format: "json"` | не объявлен: раунд нельзя указать в `document` шага User |

- `artifacts` с `pointer: ""` — весь текстовый ответ; такой артефакт один. Несколько артефактов — только в `json`, у каждого свой указатель на поле.
- `output.document: "read"` требует ровно один артефакт; его `pointer` — `""`. Текст документа модель пишет между метками `[[DOC: <id>]]` и `[[/DOC]]`, где `<id>` — id этого артефакта. Всё вне меток (вводные фразы, пояснения) в документ не попадает. Нет меток или текст между ними пуст — ответ отклоняется причиной `missing_artifact`, та же модель исправляет ответ; целый ответ вместо документа не берётся. Для `format: "json"` документ — поле по указателю артефакта, как у других артефактов. Правило меток приложение добавляет в запрос само, в `task` его писать не нужно.
- Раунд из нескольких моделей тоже может объявлять артефакты (у каждого участника своя линия). Но источником документа для User (5.9) может быть только раунд с одной включённой моделью. Если документ нужен от нескольких моделей, сделайте раунд без артефакта, а затем раунд «свести» из одной модели с артефактом и `output.document`.
- `description` артефакта — необязательная строка для человека: сохраняется в реестре прогона и показывается первой строкой в окне артефакта. Движок её не читает.
- `revisionOf` — ссылка на артефакт (объект с полем `artifact`), которая должна быть во входе того участника, чей выход её объявляет. Общий `output` шага относится к участникам без собственного `output`; собственный `output` участника целиком заменяет общий.
- Пример (ТЗ 3.2): фрагмент участника `author-A` шага `r2`, не самостоятельная схема; шаг `r1` общий, участник `author-A` объявлен в нём:

```text
{ "id": "author-A", "name": "claude", "input": [
  { "artifact": { "step": "r1", "participant": "author-A", "id": "proposal" }, "version": "latest", "required": true }
], "output": { "artifacts": [
  { "id": "proposal", "name": "Доработанное предложение A", "pointer": "",
    "revisionOf": { "artifact": { "step": "r1", "participant": "author-A", "id": "proposal" }, "version": "latest", "required": true } }
] } }
```
- Указатель не может содержать сегменты `__proto__`, `prototype`, `constructor`.
- Вход по артефакту (`{ "artifact": { "step", "participant", "id" }, "version": "latest" }`) принимается только для артефакта, объявленного в `output` более раннего шага. Вход по артефакту берёт только его содержимое: `latest` — последняя зарегистрированная версия линии, если она действительна; если она инвалидирована (возврат, пропуск или провал пересчёта), линия ждёт новой версии, и старый действительный предок не становится `latest`. Объект версии — точная версия (действительная; инвалидированная не даётся как вход). Обязательный источник без актуальной версии останавливает прогон (`missing_input`), необязательный не даёт текста. Автор ревизии получает последнюю действительную версию своей линии — объявленный вход доработки.

### 5.9. User (`owner`); синтеза, проверок и развилок нет

Шаги выполняются строго по порядку списка: ветвлений, переходов и возвратов в Basic нет. Видов шага два: `round` и `owner`. Видов `synthesis` (синтез), `gate` (проверка) и `route` (развилка) больше нет: схема с `gate` или `route` не проходит проверку с ошибкой «тип шага: допустимо round, owner; проверка — обычный раунд: критерии в task; решение принимает User шагом owner», схема с `synthesis` — с ошибкой «тип шага: допустимо round, owner; синтез — роль: раунд из одной модели с role». Конвертера нет, такую схему переписывают вручную:

- **Синтез** — раунд из одной модели с ролью `interaction_meta_synthesis` (7.2); своё задание пишется в `task` раунда. Итоговый синтез — последний такой раунд: итог прогона — принятые ответы последнего шага. Ref синтеза — номер раунда (`r2`, `r3`…), как у любого раунда.
- **Проверка** — обычный раунд (обычно из одной модели): критерии записываются в `task` («Проверь по критериям: … По каждому: выполнен или нет и почему»). Ответ проверяющего — обычный ответ шага; движок вердикт не читает и прогон по нему не останавливает.
- **Решение** («продолжать или нет», «какой вариант») принимает User шагом `owner`: в `input` — ответ проверки, в `task` — вопрос. Если решение «не продолжать», User останавливает прогон (Stop) и запускает новый.
- Поля прежних шагов (`criteria`, `pass`, `onFail`, `onPass`, `select`, `goto` и т. п.) в других шагах — неизвестные поля, ошибка с путём.

Страница передаёт движку окно ответа User (только текст; выбор файла пока не реализован). Холст показывает User карточкой после раунда или другого шага User (поле «Шаг после этого этапа» в окне раунда или карточки; подряд можно ставить несколько). Окно User редактирует `goal`, `task` и `output`; `input` User сохраняется как есть (см. `basic-windows.md`).

**User (`kind: "owner"`).** User вводит результат сам: текст или файл. Моделей нет.

| Поле | Значение |
| --- | --- |
| `task` | что нужно предоставить (непустой текст) — **обязательно** |
| `goal` | назначение этапа: в окне вопроса User идёт первым абзацем «Назначение: …», в карточке — поле «Назначение этапа» (пустое поле удаляет `goal`). Движок его не читает |
| `models` | `[]` — **обязательно** |
| `input` | `none` (умолчание), `previous`, `all` или список источников в том же формате, что у шага модели (5.7); не указано — пустой вход. Схема проверяет ссылки (раньше шага, не на себя). Движок разрешает источники до окна User: обязательный источник без ответа останавливает прогон (`missing_input`), окно не открывается; значения передаются в окно с адресом (`step`, `participant`, `visit`) и текстом или файлом; модель по ним не спрашивается |
| `output` | необязательно; ответ User проверяется по нему, как ответ шага, а объявленные `artifacts` регистрируются |
| `document` | необязательно: ref более раннего раунда с одной моделью, документ которого показывает окно (см. «Документ для User» ниже) | не задан: поле текста |
| Участник в источниках | единственный `"owner"`: `{ "step": "owner:o", "participant": "owner" }`; артефакт `{ "artifact": { "step": "owner:o", "participant": "owner", "id" } }`, версия `{ "step", "participant": "owner", "visit" }`, `revisionOf` — так же. Модели у User нет, поэтому другой участник шага User — ошибка |

Ответ User — текст или файл (окно страницы принимает пока только текст; файл движок принимает, если его передал вызывающий код). Текст проходит проверку `output`; при неудаче User спрашивают снова с причиной. Пустой текст не принимается. Отмена окна останавливает прогон (`stopped`), Stop — `cancelled`. Модели для этого шага не вызываются. Ответ идёт следующим шагам как данные (по ссылке на `ref` шага), но не выглядит как ответ модели. Изменение источника входа делает ответ User устаревшим: окно откроется снова с новым входом.

Файл: текстовый файл (с текстом) проходит как текст; двоичный файл текстом модели не передаётся — прогон останавливается `unsupported_input` до запроса. Файл без имени, MIME, размера или ссылки хранилища, а также `blob:` ссылка — ошибка `invalid_owner_result`. Двоичный файл нельзя проверить выходом шага: для него `output` с разделами, полями или артефактами не задаётся.

- Вход `previous` берёт ответы последнего шага, у которого они есть; пропущенный шаг ничего не передаёт дальше, и вход идёт от более раннего. Ответ User — тоже ответ шага: шаг после User с `previous` получает текст User.
- Ответ User по умолчанию идёт следующему раунду (его вход `previous`). Этап после шага User должен применить правки: напишите в его `task`, что делать с ответом User, и просите вернуть документ целиком, а не отдельный раздел с правками.
- Если у шага User нет `output`, принимается любой непустой текст. Схема не проверяет, что ответ User кто-то прочитает: сделайте так, чтобы шаг User стоял в `input` какого-то более позднего этапа.
- Опросник (`output.document: "form"`): модель отвечает JSON `{ "items": [{ "id", "type": "one|many|text|yesno", "question", "options", "required" }] }`; `options` нужны для `one` и `many`. Нарушение формата — причина `invalid_form`, ту же модель просят исправить ответ.

**Документ для User (`document`).** Шаг User показывает документ, который выдал раунд выше. Проверка схемы: `document` — ref более раннего раунда; у него ровно одна включённая модель; вид документа объявлен в выходе раунда (`output.document`: `read` или `form`). `form` требует `format: "json"`. Если ссылка неверна, у раунда не одна модель, нет принятого ответа, ответ не опросник или (для `read`) у раунда нет актуальной версии документа, прогон останавливается ошибкой движка `invalid_document` до открытия окна. Если текста версии нет в записи прогона, это тоже `invalid_document` (текст «текст документа не найден в записи прогона»).

- `read` — документ для чтения. Окно правки: заголовок «<имя>» (имя документа), поле с текстом документа; «Отправить» активна, пока текст не пуст. User может править текст. Ответ User — утверждённый текст документа: если текст изменён, создаётся новая версия линии (автор — User, `participant: owner`), и она утверждается; если не изменён, утверждается текущая версия. Утверждённый текст идёт дальше: следующий раунд по умолчанию (`input: previous`) получает именно его; явный вход `{ "artifact": { "step", "participant", "id" }, "version": "latest" }` тоже даёт последнюю, правленую версию. Запись шага User хранит `approved: { id }`.
- `form` — опросник. Ответ модели-источника — JSON-объект с полем `items`:

```text
{ "items": [
  { "id": "budget", "type": "one", "question": "Бюджет", "options": ["до 10k", "больше"], "required": true },
  { "id": "notes", "type": "text", "question": "Что ещё учесть" }
] }
```

  Типы пунктов: `one` (один вариант), `many` (несколько), `text` (поле), `yesno` (Да/Нет). `id` и `question` — непустые строки, `id` не повторяется. Для `one` и `many` — `options`: непустой список непустых строк без повторов; у `text` и `yesno` вариантов нет. `required` — `true` или `false` (по умолчанию `false`). Нарушение формата — отказ ответа с причиной `invalid_form` (`basic-start-here.md`): модель получает исправление. В окне User обязательные пункты помечены «*», «Отправить» активна, когда заполнены все они.

Ответ User — текст «вопрос — ответ» по отвеченным пунктам (для пунктов с вариантами — с «(комментарий: …)», если он есть). Если выход шага User объявлен как `format: "json"`, ответ — JSON `{ id: значение }`: `one` — строка, `many` — массив, `yesno` — `true`/`false`, `text` — строка; неотвеченные необязательные пункты пропускаются.


### 5.10. Спецификация (только для документа; необязательно)

Поля `spec` и текстовые поля шага (`title`, `goal`, `rules`, `quality`) описывают pipeline для человека: из них собирается
читаемая спецификация. **Они только для документа: на запросы моделям не влияют.** Движок и сборка запросов их не читают,
поэтому схема с этими полями и без них даёт одинаковые запросы и одинаковый холст. Все значения — текст; пустая строка
допустима и сохраняется как значение. Поля не обязательны, схема без них остаётся действительной (`schemaVersion` — 1).

| Поле корня `spec` | Значение |
| --- | --- |
| `purpose` | назначение pipeline |
| `inputs` | исходные данные: что требуется, в какой форме, что обязательно |
| `result` | итоговый результат: что получится |
| `application` | как применяется результат |
| `readiness` | критерии готовности результата |
| `rules` | общие правила и ограничения |
| `boundaries` | границы: что охватывает pipeline и чего не гарантирует |
| `failure` | поведение при сбое |

Поля шага (5.4): `title` — название этапа для человека; `goal` — цель этапа; `rules` — правила и ограничения этапа;
`quality` — критерии качества этапа и способ проверки. Поля подходят любому виду шага (раунд, User).
Неизвестное поле `spec` (например, `spec.foo`) или не текст в любом из этих полей — ошибка проверки с путём.

Пример (схема с текстом спецификации):

```json
{
  "schemaVersion": 1,
  "origin": "user",
  "spec": { "purpose": "Выбрать название для кофейни", "result": "Один вариант названия", "failure": "Если модели не дали вариантов, раунд повторяется" },
  "steps": [
    { "ref": "r1", "kind": "round", "title": "Варианты", "goal": "Получить независимые варианты", "models": [{ "name": "GPT" }, { "name": "Claude" }] },
    { "ref": "r2", "kind": "round", "title": "Итог", "quality": "Один вариант, без списка", "models": [{ "name": "Claude", "role": "interaction_meta_synthesis" }] }
  ]
}
```

Текст спецификации страница сохраняет: при Save, при запуске и в Export он берётся из схемы, которую загрузили (по `ref` шага).
Окна настроек его не редактируют; он попадает в схему через установку (Import) или сохранённую схему. Схема без этих полей
не получает их при Save.

### Пример документа для чтения

Пример: раунд `r1` пишет документ для чтения, шаг User утверждает его:

```json
{ "schemaVersion": 1, "origin": "user", "steps": [
  { "ref": "r1", "kind": "round", "models": [{ "name": "Claude" }], "task": "Напиши техническое задание на функцию.",
    "output": { "document": "read", "artifacts": [{ "id": "spec", "name": "ТЗ", "pointer": "" }] } },
  { "ref": "owner:o", "kind": "owner", "models": [], "task": "Проверьте ТЗ и утвердите его.", "document": "r1" }
] }
```

Ответ модели в этом примере: `[[DOC: spec]]` и текст ТЗ `[[/DOC]]`; пояснение до или после меток в документ не попадает.

## 6. Что получает модель (зачем нужны поля)

Запрос модели собирается из частей в таком порядке; части, для которых нет данных, пропускаются:

1. **Задача:** текст, который пользователь вводит при запуске.
2. **Ответы предыдущего шага** (вход `previous`) или **Принятые ответы всех предыдущих шагов** (вход `all`).
3. **Задание** — `task` (в первом раунде отправляется только записанное в схеме, не из ▶ и Basic).
4. **Дополнительно для тебя** — текст роли модели.
5. Особенность модели (`defaults.modelNotes`), инструкция длины, требования к содержанию, свои строки (`lines`).
6. Инструкция доставки добавляется при отправке (метка, по которой расширение находит конец ответа).

**Блок «Формат ответа».** Если у выхода шага есть требования к ответу, приложение само добавляет в запрос блок «Формат ответа» между «Заданием» и «Дополнительно»: описание формата опросника, правило меток документа («Документ — между метками [[DOC: id]] и [[/DOC]]; всё вне меток (пояснения) в документ не попадает»), для `json` — список полей и разделов. Список источников подписывается «Ответы выбранных источников:». Всё это писать в `task` не нужно.

Пример: второй раунд, модель GPT с ролью Critique, общая строка `"Отвечай по-русски."` в `defaults.discipline.lines`, задача «Придумай название для кофейни.» (предел 300 слов, две ответа первого раунда):

```text
Задача:
Придумай название для кофейни.

Ответы предыдущего шага:

Ответ 1:
Ответ первой модели.

Ответ 2:
Ответ второй модели.

Задание:
Учти ответы предыдущего шага и дай свой улучшенный ответ на задачу.

Дополнительно для тебя:
<ТЕКСТ РОЛИ Critique>

[RESPONSE_LIMIT] Объём ответа: 250-300 слов, не больше.

Сосредоточься на ясной концепции и ключевых идеях; убери повторы, длинные пересказы и второстепенные детали.

Отвечай по-русски.
```

**Внимание: `request`.** Если у модели есть `request`, он заменяет весь автоматический запрос, кроме последних частей (шаг 5–6), а роль не добавляется. В тексте `request` обязательно пишите подстановки `{задача}` (задача пользователя), для шагов с входом — `{вход}` (ответы). Без них модель не увидит задачу и ответы. **Если нет веской причины, `request` не используйте**: хватает `task`, `role` и `discipline.lines`.

**Синтез** — обычный раунд из одной модели: он получает ответы предыдущего шага и задание раунда, а роль `interaction_meta_synthesis` добавляет текст «Дополнительно для тебя». Своё задание синтеза пишется в `task` этого раунда.

### 7.2. Роли (`role`)

Роль — готовый мини-запрос, который добавляется модели как «Дополнительно для тебя». Допустимые id:

| id | Название | Что делает |
| --- | --- | --- |
| `interaction_meta_synthesis` | Synthes | строит собственное решение, используя версии как сырьё |
| `interaction_critical_audit` | Critique | аудит ответов: слепые зоны, ошибки, методология |
| `interaction_select_ideas` | Select ideas | извлекает все уникальные идеи списком |
| `interaction_pattern_clustering` | Clustering | группирует идеи по сути подхода |
| `custom` | Custom | берёт текст из `defaults.roundPrompts["<ref раунда>"]` |

Роль `custom` без записи в `defaults.roundPrompts` для этого раунда ничего не добавит. Нет подходящей роли — не пишите `role` и опишите нужное в `task`.

## 8. Правила холста (почему схема может не установиться)

Формат допускает больше, чем показывает холст страницы. При установке проверяется:

- **Раунды `r1`, `r2`, …** идут по порядку без пропусков: холст нумерует раунды сам, поэтому `r2` без `r1` — ошибка.
- **Синтез** — раунд из одной модели с ролью: на холсте это обычная колонка раунда, у которой «Участие в раунде» включено у одной модели. Отдельной колонки синтеза и кнопок вставки синтеза на холсте нет.
- **Исполнимый шаг**: хотя бы один раунд с включённой моделью или шаг User. Схема без раунда (например, только User) допустима и раунд не добавляет; пустая схема и схема без исполнимого шага — ошибка `steps`. Раундов не больше 50; шаги User в этот лимит не входят.
- **Имена моделей и ролей** — из списков раздела 7.
- **`run.maxWords`** — 300, 500, 700 или 1000.
- Модель, выключенная во всех раундах, стоит на холсте только с `onCanvas: true` (пример в разделе 9). Без этого признака она после установки на холст не попадает.

Порядок моделей внутри раунда на результат не влияет: все получают один запрос и отвечают независимо; после установки холст расставит модели в своём порядке.

## 10. Ошибки при установке и как их исправить

Расширение ничего не исправляет за вас: оно называет место ошибки (путь вида `steps[1].models[0].name`) и не устанавливает схему.

| Сообщение (в тексте ошибки) | Причина | Что исправить |
| --- | --- | --- |
| `версия формата не указана` | нет `schemaVersion` или это не целое число | добавьте `"schemaVersion": 1` |
| `схема создана более новой версией Basic` | `schemaVersion` больше, чем знает расширение | поставьте `1` |
| `происхождение: допустимо` | `origin` не `builtin`/`user` или отсутствует | `"origin": "user"` |
| `неизвестное поле` | поле, которого нет в справочнике (опечатка, выдумка) | удалите поле или исправьте имя по разделу 5 |
| `ожидается список шагов` | `steps` не список | `"steps": [ … ]` |
| `тип шага: допустимо` | `kind` не `round`/`owner`; для `gate` и `route` к тексту добавлено «проверка — обычный раунд: критерии в task; решение принимает User шагом owner», для `synthesis` — «синтез — роль: раунд из одной модели с role» | исправьте `kind`; синтез, проверку и развилку перепишите по 5.9 |
| `поле order не поддерживается` | в шаге есть `order`: все модели раунда отвечают независимо | удалите поле; эстафету запишите раундами по одной модели подряд (шаблон C) |
| `вход: допустимо` | `input` не `none`/`previous`/`all` | исправьте или удалите |
| `ref шага не указан` | нет `ref` | добавьте `ref` по правилам 5.4 |
| `повторяется` | два шага с одним `ref` или две одинаковые модели в одном шаге | сделайте имена уникальными |
| `имя модели не указано` | нет `name` или пустое | добавьте имя из 7.1 |
| `ожидается положительное целое число слов` | `maxWords` не целое положительное число (0, `"300"`, 1.5) | число без кавычек, больше 0 |
| `ожидается true или false` | `enabled` или `onCanvas` не булево | `true` или `false` |
| `ожидается текст` | текстовое поле не строка | строка в кавычках |
| `ожидается список текстов` | `lines` не список строк | `["…", "…"]` |
| `недоступна` | имя модели не из списка 7.1 | точное имя из 7.1 |
| `неизвестна` | `role` не из списка 7.2 | id из 7.2 или удалите `role` |
| `ref раунда должен быть` | раунды не `r1`, `r2`… по порядку | переименуйте |
| `нет исполнимого шага: нужен раунд с включённой моделью или шаг User` | пустая схема или все шаги выключены | включите модель или добавьте раунд или шаг User |
| `предел длины pipeline: допустимо` | `run.maxWords` не 300/500/700/1000 | одно из четырёх значений |
| `политика запуска: допустимо` | `run.policy` не `auto`/`manual` | `auto` или `manual` |
| `ID участника: непустой текст` | `id` пустой или не текст | непустой текст или удалите `id` |
| `уже записан с именем` | один `id` в разных шагах с разными именами | одно имя для одного `id` |
| `в формате json заголовки не проверяются` | `sections` вместе с `format: "json"` | для json — `requiredFields` |
| `ожидается непустой список заголовков` | `sections` пустой или не список | список строк |
| `список полей нужен только в формате json` | `requiredFields` без `format: "json"` | добавьте `"format": "json"` или уберите поле |
| `ожидается непустой список указателей` | `requiredFields` пустой | перечислите указатели |
| `указатель JSON Pointer начинается с` | указатель без «/» | например `"/correctedMap"` |
| `в указателе «~» допустим только как` | `~` не `~0` и не `~1` | экранируйте по RFC 6901 |
| `запрещён` | сегмент `__proto__`, `prototype` или `constructor` | другое имя поля |
| `укажите поле ответа: JSON Pointer к полю` | в json указатель пустой | укажите поле |
| `в текстовом формате указатель пустой` | текстовый артефакт с указателем | `pointer: ""` или формат `json` |
| `несколько артефактов выделяются только в формате json` | несколько артефактов без json | `"format": "json"` |
| `ожидается непустой список артефактов` | `artifacts` пустой | уберите поле или добавьте артефакт |
| `ID артефакта: непустой текст` | пустой `id` | непустой текст |
| `название артефакта: непустой текст` | пустое `name` | непустой текст |
| `ожидается указатель: строка` | `pointer` не текст | строка |
| `ожидается ссылка на артефакт: объект с полем artifact` | `revisionOf` не ссылка на артефакт | `{ "artifact": { … }, "version": … }` |
| `ссылка на версию должна быть во входе участника` | `revisionOf` нет во входе автора | добавьте её во вход шага или участника |
| `ожидается latest или объект версии` | `version` не `latest` и не объект | `"latest"` или `{ "step", "participant", "visit" }` |
| `версия не указана` | артефакт без `version` | добавьте `"version"` |
| `ожидается целое число больше 0` | `visit` не положительное целое | `1` |
| `участник не указан` | источник-артефакт без `participant` | укажите участника |
| `у User один участник «owner»` | участник шага User не `owner` | укажите `"participant": "owner"` |
| `ожидается объект: step, participant, id` | `artifact` не объект | `{ "step", "participant", "id" }` |
| `ref User: «owner:<id>»` | ref User без `owner:` | `owner:<id>` |
| `задание User: непустой текст` | у User нет `task` | задание |
| `у User нет моделей` | у User есть `models` | `"models": []` |
| `поле require не поддерживается` | в шаге есть `require`: раунд ждёт ответов всех своих моделей | удалите поле |
| `User в шаге: допустимо` | `owner` не `approve` | `"approve"` или уберите поле |
| `чат шага: допустимо` | `chat` не `continue`/`new` | `"continue"` или `"new"` |
| `ожидается непустой список источников` | `input` — пустой список | перечислите источники или уберите `input` |
| `документ: только более ранний раунд` | `document` ссылается на текущий или более поздний шаг | поставьте раунд выше шага User |
| `документ для User даёт одна модель` | в раунде-источнике больше одной включённой модели | оставьте одну модель или уберите `document` |
| `не объявлен вид документа` | в выходе раунда-источника нет `output.document` | `"document": "read"` или `"form"` |
| `опросник — формат json` | `output.document: "form"` без `format: "json"` | добавьте `"format": "json"` |
| `документ для чтения: объявите ровно один артефакт в output.artifacts (id, name, pointer)` | `output.document: "read"` без одного артефакта | `"artifacts": [{ "id", "name", "pointer": "" }]` |
| `неизвестный шаг` | ссылка на шаг, которого нет в схеме | укажите ref существующего шага |
| `вход ссылается только на более ранний шаг` | источник — текущий или поздний шаг | поставьте источник раньше шага-потребителя |
| `не объявлен в шаге` | участник не записан в указанном шаге | укажите имя модели из этого шага |
| `источник повторяется` | одинаковый адрес дважды в списке | оставьте одну запись |
| `ожидается ссылка на шаг, участника или артефакт` | элемент списка — не ссылка | строка-ref шага или объект `{ "step", "participant" }` |

## 11. Чек-лист самопроверки (пройдите перед ответом)

1. Ответ — один JSON-объект, без текста вокруг, без комментариев и запятых после последних элементов.
2. Есть `"schemaVersion": 1`, `"origin": "user"` и непустой список `steps`.
3. Раунды называются `r1`, `r2`, … по порядку; синтез — раунд из одной модели с ролью `interaction_meta_synthesis` и номером по порядку; вида `synthesis` нет.
4. В каждом шаге есть `ref`, `kind`, `models`.
5. Все имена моделей — из таблицы 7.1 точно как там; в шаге они не повторяются.
6. Все `role` — из таблицы 7.2; если `role` равно `custom`, для этого раунда есть запись в `defaults.roundPrompts`.
7. `run.maxWords` (если есть) — 300, 500, 700 или 1000; `run.policy` — `auto` или `manual`; `run.strictLength` (если есть) — `true` или `false`; `maxWords` у модели — целое число больше 0.
8. Нет выдуманных полей и нет полей со значением `""`.
9. В `request` (если он есть) присутствуют `{задача}` и, где нужно, `{вход}`.
10. Схема содержит только отличия от умолчаний раздела 4.

## 12. Установка и запуск

- **Import schema** (страница pipeline): выберите файл `.json` с одной схемой; имя нового pipeline предлагается из имени файла, его можно изменить. Имя, которое уже занято шаблоном в списке pipelines, занять нельзя; существующее имя спросит подтверждение замены. Остальные pipelines не затрагиваются.
- Чтобы получить схему из настроенного холста, нажмите **Export schema**: она выгрузится файлом `<имя pipeline>.json`; его можно отправить другому, отредактировать и импортировать обратно.
- **Export all schemas** (страница pipeline, рядом с Export schema) сохраняет все схемы списка одним файлом `Каталог Basic.json` в формате `{"basicCatalog":1,"schemas":[{"name":"<имя pipeline>","schema":{…}}]}`. В файл входят только сохранённые схемы; шаблоны и записи без схемы не входят, записи, не прошедшие проверку, перечисляются в уведомлении. **Import schema** распознаёт каталог по полю `basicCatalog`: валидные схемы добавляются под своими именами, занятое имя спрашивает новое имя (предлагается «<имя> (2)»), совпадение с существующим именем спрашивает подтверждение замены. Невалидные записи пропускаются, в уведомлении — «Добавлено схем: N, не добавлено: M» и путь ошибки для каждой.
- **Вставка**: ответ модели можно вставить кнопкой «Вставить схему» (поле текста в окне): ограда ```json, хвостовые запятые, комментарии и ключи без кавычек читаются; текст вокруг JSON сохраняется как комментарий модели. Оборванный ответ не применяется, в окне сообщается, до какого шага JSON цел.
- После установки pipeline выбран в списке, холст показывает раунды (синтез — раунд из одной модели) и модели; у раунда (клик по значку R1, R2…) видны порядок, вход и задание; у модели (двойной клик по блоку) — её запрос, длина и дисциплина.
- Введите задачу в поле модератора и запустите. При `run.policy: manual` User подтверждает каждый шаг; при `auto` шаги идут сами и останавливаются только если у шага нет принятых ответов.
- Схему можно менять на холсте и сохранять кнопкой Save: настройки сохраняются в той же схеме.

## 13. Чего не делать

- Не копируйте тексты умолчаний из раздела 4 в схему «для надёжности»: они тогда перестанут следовать за Basic.
- Не пишите `input` у первого раунда (ему подавать нечего).
- Не нумеруйте раунды с нуля и не пропускайте номера.
- Не пишите вид `synthesis` и ref `final`/`synth:…`: синтез — раунд `rN` из одной модели с ролью.
- Не используйте `request`, если хватает `task`, `role` и `lines`.
- Не вставляйте задачу пользователя в схему: её вводят при запуске.
- Не выдумывайте названия моделей и ролей: только из списков раздела 7.
