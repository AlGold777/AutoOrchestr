# Basic: несколько участников одной модели

Дата: 27.10.2026. Статус: реализовано в версии 2.81.900; тесты и изолированная проверка Chrome выполнены. Реальные отправки моделям не проверялись.

## 1. Цель и согласованное поведение

В одном раунде можно использовать нескольких участников одной модели: например, Claude и Claude 2. Каждый участник имеет постоянный ID, своё имя для показа User, настройки в каждом раунде и собственный чат в пределах прогона.

- На карточке модели справа сверху всегда виден небольшой «+»; доступен мышью, клавиатурой и на тач-экране.
- «+» создаёт нового участника той же модели: Claude 2, затем Claude 3. ID генерируется отдельно от подписи и не используется повторно после удаления.
- Новый участник получает выключенный Send и пустые редактируемые настройки. Можно вручную заполнить настройки и включить Send сразу в том же раунде.
- Подпись меняется по клику. Переименование не меняет модель, ID, входные ссылки, историю или чат. Пустое имя и совпадение подписи с другим участником той же схемы не сохраняются.
- Для использования того же участника в других раундах холст показывает выключенную карточку участника только в тех раундах, где он объявлен с `onCanvas: true` (участник одного раунда не появляется в колонках других). Их включение переиспользует ID; «+» всегда создаёт следующего участника во всех раундах с `onCanvas: true`.
- У дубля есть «×»: убирает его карточку только из текущего раунда. Первую карточку модели удалить нельзя. Участник в других раундах и история прогонов сохраняются. Глобальная синхронизация холста не должна возвращать удалённую карточку; повторное добавление существующего участника доступно через компактный выбор его имени рядом с добавлением в раунд, без создания нового ID.
- Если от удаляемого участия зависят входы/артефакты/документ последующих этапов, удаление блокируется с указанием зависимых этапов. Сначала User исправляет связи. Самостоятельно переназначать или удалять ссылки нельзя.
- В окне настроек участника сверху слева от Save располагается Default. Она заполняет черновые поля эффективными значениями текущего раунда; персональные настройки исходной карточки не копируются. Default не сохраняет, не включает Send и не отправляет запрос. Save сохраняет настройки обычным способом.
- Во время прогона добавление, удаление, переименование и изменение настроек блокируются существующим механизмом блокировки редактирования.

## 2. Идентичность: модель, участник, подпись, чат

Не смешивать эти четыре понятия:

| Данные | Назначение |
|---|---|
| `name: "Claude"` | Провайдер для транспорта; существующее значение поля не меняется |
| `id` | Постоянный ключ участника в схеме; настройки, ответы и ссылки адресуются по нему |
| `label: "Claude 2"` | Новая необязательная подпись; при отсутствии показывается `name` |
| Привязка `(runId, participantId)` | Конкретная переписка участника во время прогона |

Один ID во всех раундах обязан обозначать одну модель. Существующую проверку этого условия сохраняем. Переименование обновляет label участника во всех его вхождениях в редактируемой схеме. Старые записи прогонов сохраняют подпись на момент запуска.

Источником истины остаётся схема: участники выводятся из её вхождений по ID. Отдельный постоянный реестр, дублирующий схему, не вводится. Рабочий индекс для холста можно вычислять из схемы. Выключенные видимые карточки сохраняются с `enabled: false` и `onCanvas: true` по ID, включая несколько карточек одной модели.

Если удалено последнее вхождение дубля, участник исчезает из редактируемой схемы и списка переиспользования. Его история в записях прогонов остаётся. Следующее «+» создаёт нового участника с новым UUID, даже если показанная подпись снова свободна. ID не получают из подписи или порядкового номера; это исключает намеренное повторное присвоение старой идентичности и не требует отдельного списка удалённых участников. Выбор существующего участника доступен, пока в схеме есть хотя бы одно его вхождение.

## 3. Пустые настройки и Default

Сейчас отсутствие многих полей означает наследование. Для нового дубля это не выполняет пожелание User: поля должны оставаться пустыми до ручного заполнения или Default.

Ввести для новых дублей явный режим настроек участника, рабочее имя поля `settingsMode: "explicit"`. Это внутреннее поле схемы, дополнительный переключатель в интерфейсе не нужен. Его отсутствие сохраняет прежние правила для старых схем. Режим действует на настройки данного участника в данном раунде.

| Поле нового дубля | Начальное поведение |
|---|---|
| Роль | Не выбрана; роль исходного участника не копируется |
| Задание, персональный запрос | Пусты; задание раунда автоматически не добавляется |
| Лимит слов | Поле пустое; персональная инструкция длины не добавляется, числовое значение не подставляется скрыто |
| Дисциплина и дополнительные строки | Пусты; строки ▶ и особенности модели автоматически не дописываются |
| Вход | Входы раунда автоматически не наследуются; эффективное отсутствие входа отображается понятным состоянием редактора, в исполнении соответствует `none` |
| Выход | Нет персональных требований к форме ответа и наследования требований раунда |

Структурные данные (модель, ID, подпись), основная задача запуска, техническая проверка доставки и защитный бюджет контекста не являются пустыми полями настроек. Их сохраняем. Ограничения ответа, включая `run.strictLength`, должны учитываться согласованно с пустым профилем: нельзя скрыто применять унаследованный персональный предел; это проверяется отдельно.

Не записывать `maxWords: ""` или `0`: текущий формат их отвергает. Режим explicit должен задавать отсутствие локального ограничения без подмены значением запуска. Все слои — редактор, assemble, preview, проверка ответа и composeCustomPrompts — должны одинаково разрешать этот режим. После ручного заполнения выбранные значения применяются независимо от нажатия Default.

Default получает значения через единое разрешение настроек раунда: раунд → ▶ → Basic. Заполняет только настройки текущей карточки, сохраняет имя/ID/Send, не копирует настройки соседнего участника и ничего не меняет в других раундах. Пустой персональный шаблон запроса означает автоматическую сборку; Default показывает её корректное превью, не записывает в шаблон ответы уже прошедших этапов. Текущее действие Reset не должно уничтожить отличие «пусто» от «наследовать».

## 4. Совместимость схем

`label` и явный режим меняют контракт схемы: текущий валидатор v1 отвергает неизвестные поля. Для схем с новыми полями использовать `schemaVersion: 2`, сохранив поддержку v1 и её прежние умолчания. Схемы без новых возможностей можно продолжать выгружать в v1. Старое расширение должно явно отказаться от более нового формата, а не терять дубли или настройки.

- Участники v1 без ID продолжают адресоваться по `name`.
- Не выполнять массовое преобразование сохранённых схем. Конверсия при редактировании сохраняет все старые ссылки и данные.
- Изменения проходят через validate, assemble, toSettings, toCanvas, сборку со страницы, Save, загрузку, одиночный экспорт/импорт и каталог.
- Два одинаковых provider name допустимы при разных ID. Уникальность ID внутри раунда обязательна.
- Ограничение `recordFromSchema` на одинаковые модели снимать после сохранения ID во всех преобразованиях холста. Проверку запуска «нужен хотя бы один раунд моделей» ради дублей не менять.

## 5. Чаты и доставка

Транспорт по participantId и последовательные волны для одной модели уже существуют. Сохраняем их; одновременная отправка двух запросов одному провайдеру не нужна для первого выпуска.

1. Первая отправка каждого нового дубля открывает отдельный чат независимо от общего New pages. Не выбирать произвольную уже открытую переписку провайдера. До фактической отправки запрос связан с ID участника.
2. Повторы и последующие раунды с continue продолжают именно этот чат. Явное `chat: new` сохраняет своё существующее значение: новый чат по требованию схемы, затем новая привязка.
3. Сохранять в фоне и снимке прогона не только tabId, но и адрес конкретной переписки. Название чата сохраняется как вспомогательное, если доступно; оно не является идентификатором.
4. Новый чат может получить постоянный URL только после первой отправки. Обновлять привязку при появлении/изменении адреса; стартовая страница модели или адрес входа не доказывают идентичность чата. Запись должна переживать остановку и перезапуск service worker.
5. При continue проверять и живую вкладку: её могли перевести в другой чат того же провайдера. Если исходная вкладка закрыта или ушла на другой адрес, открыть сохранённую переписку в новой вкладке, проверить модель/идентичность/доступность, сохранить новый tabId и только затем разрешать запрос.
6. Если нет доказанного адреса, требуется авторизация или переписка недоступна — понятная остановка до отправки. Не создавать пустой чат вместо потерянного. Старые снимки без URL могут продолжать подтверждённую живую вкладку; закрытую восстановить автоматически нельзя.
7. Восстановление вкладки не равно повторной отправке. Неизвестная попытка после прерывания остаётся неизвестной и проходит существующий выбор проверки/повтора; найденный ответ должен сохранять артефакты обычным путём приёмки.
8. Вложения отправляются при первом входе участника в новый чат; открытие прежней переписки не означает новый чат и не должно повторять вложения автоматически.

Адреса чатов хранятся в записи прогона, а не в переносимой схеме. В телеметрию не добавлять полный URL сверх существующих правил экспорта и очистки данных.

## 6. Команда и границы владения

Главный агент отвечает за окончательные решения, сверку черновиков с кодом, интеграцию, документацию и итоговую приёмку. Черновики не принимаются автоматически. По прямому указанию User для этой задачи все помощники, включая исполнителя commits, — GPT-6 Luna (`gpt-6-luna`), reasoning high; это заменяет прежнее требование Haiku для commits в рамках данной задачи.

| Агент | Ответственность при реализации | Основные файлы |
|---|---|---|
| Luna A — схема и чаты | Черновик идентичности, формат, пустой профиль, адресация и восстановление переписок | `disput/basic-schema.js`, `disput/custom-engine.js`, `disput/custom-run-record.js`, `background/tab-manager.js`, нужные обработчики background |
| Luna B — интерфейс | Карточки, +/×, имя, Default, переиспользование в раундах, отображение участника в ответах | `results.js`, `results/stage-card.js`, стили pipeline, при необходимости разметка страниц |
| Luna C — проверки и commits | Независимая матрица, тесты и анализ результатов; выборочное сохранение только проверенных файлов по списку главного агента | `tests/*`; git-команды после приёмки |

Общий `results.js` редактирует только Luna B; Luna A передаёт ей согласованный контракт. Документацию интегрирует главный агент. Общие файлы версий обновляются последовательно при подготовке каждого самостоятельного изменения. Агенты не коммитят чужие изменения и не используют `git add -A`.

Черновики сведены в реализацию схемы v2, движка, привязки чатов, и интерфейса. Unit/jsdom-проверки и изолированная проверка Chrome выполнены без отправки prompt модели. Проверка реальных страниц провайдеров и восстановление авторизованной переписки остаются отдельным сценарием и требуют разрешения User на конкретный тестовый prompt.

Каждый законченный этап или меньшая самостоятельная часть — отдельный commit с соответствующей документацией. Поднимать версию кода в manifest.json, package.json, package-lock.json и связанных изменённых константах. Перед рискованной серией зафиксировать рабочую точку тегом; следовать git-правилам проекта. Не назначать номера версий заранее: текущий checkout содержит параллельные пользовательские изменения.

## 8. Проверки и критерии приёмки

Luna C запускает и анализирует проверки, главный агент разбирает находки и принимает исправления.

- Unit: уникальные ID, подписи, запрет смены провайдера одного ID, исходные пустые значения, ручное заполнение без Default, Default только текущей карточки, отсутствие скрытых инструкций и ограничений.
- Schema round-trip: Save → reload → Export → Import → Export сохраняет всех участников, выключенные карточки, label, ID, входы/артефакты и пустые настройки; v1 без изменений поведения.
- jsdom обеих страниц: две карточки Claude различимы; +/rename/Default/Save/×/Send адресуют participantId; Default не сохраняет и не отправляет; дубли включаются сразу в текущем раунде. Удаление локально и блокируется при зависимостях. Повторная синхронизация не возвращает удалённую карточку.
- Транспорт: два участника → разные tabId; ответы не перезаписывают друг друга; повтор, следующий раунд, stop/resume, перезапуск worker и reload используют нужный чат. Живая вкладка, ушедшая в другой чат, не принимается за прежнюю.
- Восстановление: закрытая вкладка → прежний URL → тот же чат; отсутствующий URL, страница входа, редирект в новый чат и ошибка сохранения binding → отказ до отправки. Неизвестная попытка не отправляется повторно автоматически.
- Изолированный Chrome: настоящий рендер/клавиатура/сохранение/перезагрузка на pipeline_panel.html и result_new.html без model prompts. Проверки маршрутизации на локальной fixture не считать проверкой провайдера.
- Реальные модели: отдельный профиль с авторизацией; два чата одного провайдера, два раунда, остановка и продолжение, закрытие и восстановление вкладки. Только после явного разрешения User на конкретный тестовый prompt; разрешение на план таким разрешением не является.

Опорные тесты: `basic-schema.test.js`, `basic-participant-transport.test.js`, `custom-engine-chat.test.js`, `custom-run-chat-bindings.test.js`, `custom-run-resume-wiring.test.js`, `tab-manager-session-scope.test.js`, `transport-participant-api.test.js`, `b03-participant-cards.test.js`, `results-debate-favorites.test.js`. Добавить целевые проверки к этим контрактам; не ограничиваться проверкой наличия строк в исходниках.

Перед доставкой — тесты затронутых модулей, `basic-schema-guide.test.js`, `basic-docs-refs.test.js` и по возможности общий набор. Результаты моков и настоящего Chrome указывать отдельно.
