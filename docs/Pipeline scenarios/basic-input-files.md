# Basic: входные файлы участников

С версии 2.81.900 пользователь может прикрепить свои файлы к любому участнику конкретного этапа: модели или User. Кнопка 📎 находится в Header карточки настроек модели справа от длины ответа; у User — в шапке окна настройки. Список позволяет добавить, заменить и удалить файл. Во время прогона настройка заблокирована. Default не удаляет вложения.

Это входные материалы участника. Файлы, создаваемые моделями, и загрузка файла как ответа User этой возможностью не добавляются.

## Схема и хранение

Необязательный массив `files` допустим у шага (`round` или `owner`) и модели в `models[]`. Файлы шага общие для его участников; файлы модели добавляются только её входу. Пустой массив допустим. Один ID обозначает один файл; одинаковый ID с несовместимыми описаниями отклоняется перед отправкой.

```json
{
  "ref": "r2", "kind": "round", "input": "none",
  "models": [{
    "name": "GPT", "task": "Проверь приложенный бриф.",
    "files": [{ "id": "brief-1", "name": "Бриф.pdf", "type": "application/pdf", "size": 1200 }]
  }]
}
```

`id` и `name` обязательны. `type` — необязательный MIME-тип, `size` — необязательный размер в байтах. `content` — необязательный исходный текст (UTF-8), например перенесённый со стенда; он превращается в текстовое вложение. Привязка отсутствующего импортированного файла по тому же имени сохраняет общий ID; замена уже выбранного файла создаёт новый ID только для этой карточки и не меняет вложения других участников. Метаданные входят в Save/Export/Import. Двоичные байты в JSON схемы не записываются: локальные файлы хранятся в IndexedDB расширения. После импорта на другом компьютере файлы нужно выбрать заново. Отсутствующий именованный файл также может быть найден среди общих вложений запроса по точному имени, если совпадение единственное и метаданные совместимы.

Ограничения совпадают с существующими вложениями: 5 МиБ на файл и 25 МиБ на пакет отправки. Приложение не извлекает текст из PDF/Word и не обещает поддержку содержимого конкретным провайдером: оно передаёт реальный файл существующему механизму загрузки сайта модели.

## Выполнение и продолжение

До первой отправки проверяется доступность всех объявленных файлов активных участников. Отсутствие файла или ошибка хранилища останавливает запуск с причиной; отправки без файлов нет.

Файлы передаются при выполнении назначенного этапа, в том числе в существующий чат. Разные наборы вложений отправляются отдельными группами: соседний участник не получает чужих файлов. Подтверждённые файлы запоминаются по ID внутри чата участника; исправление в том же чате не повторяет их. Новый чат получает нужные файлы заново. Общие вложения исходного запроса сохраняют прежнее правило первого сообщения каждого чата.

При старте байты входных файлов фиксируются отдельным снимком IndexedDB по ID прогона. Продолжение читает этот снимок и привязки чатов из записи, а не текущую карточку или изменённый файл. Если снимок недоступен, продолжение останавливается. Окно ответа User показывает ссылки для скачивания его входных файлов; это не меняет тип его ответа.

## Перенос стенда

Экспорт стенда v66 переносит `in.Имя` как `files` шага: `content` становится текстовым файлом, `attachment` — объявлением для выбора файла. Для обычных именованных результатов он задаёт JSON-поля и `output.artifacts` с JSON Pointer; потребитель получает точную ссылку на артефакт, а не весь ответ. У нескольких моделей могут быть собственные линии одного объявления, но ссылка стенда без участника неоднозначна и блокирует экспорт. Неподдерживаемый этап `file` также блокирует экспорт: новый вид этапа Basic не введён. Обратный перенос Basic → стенд остаётся ограниченным и сообщает о потерях предупреждениями.
