# Basic: документы для User (план)

Статус:
- концепция согласована с User 24.10.2026;
- 24.10 переписана по замечаниям независимой проверки (GPT): граница «документ / данные этапа» вместо «файл / память», нет тихих откатов к старой версии, сначала полный путь внутри приложения, документы хранятся отдельно от истории прогонов;
- **этап 1 реализован в 2.81.855; этапы 2–4 не реализованы.**

Имена полей этапов 2–4 — предложение. В формат схемы (`basic-schema-guide.md`) они войдут вместе с кодом.

## 1. Что решено

1. **Модель пишет ответ, документ из него извлекает приложение** по правилам схемы. Документ — тело ответа. Файлы, которые модель создаёт у себя в чате (скачиваемые файлы ChatGPT, артефакты Claude), не используются: у каждого провайдера они устроены по-своему, и надёжно их не забрать.

   Цепочка: **ответ модели → извлечение документа → проверка и сохранение → рамка на холсте → работа User → OK/Send → дальше уходит утверждённая версия.**
2. **Документ для User даёт одна модель.** Раунд-источник, указанный в шаге User, имеет ровно одну включённую модель.
3. **Документ открывается в отдельном модальном окне** с кнопкой **OK/Send**. После Send ответ User идёт дальше по схеме; следующий раунд по умолчанию получает его как вход `previous` (B-2, 2.81.854).
4. **Граница — по роли результата, а не по месту хранения и не по сроку жизни:**
   - **документ** — самостоятельный именованный результат, с которым работают как с целым: ТЗ, план, опросник, отчёт. Его читают, правят, утверждают; у него есть версии;
   - **данные этапа** — выбор, подтверждение, комментарий, уточнение.

   Что считать документом, решает автор схемы. Приложение само не решает. Размер и срок использования вторичны: промежуточное ТЗ, нужное только внутри прогона, — тоже документ, если его нужно читать и утверждать.
5. **Где хранить — отдельное решение.** Документ всегда хранится в приложении. Файл на диске — способ сохранить его и работать с ним вне приложения (этап 3).
6. **Дальше уходит ровно утверждённая версия.** После OK/Send фиксируется конкретная версия документа, и именно она становится входом следующего шага. Если нужную версию прочитать не удалось, User видит вопрос. Тихой подмены другой версией нет.
7. **Утверждённые документы не вытесняются вместе с историей прогонов.** Срок хранения документов отдельный: удаляет их User.

## 2. Договорённость «схема ↔ ответ модели»

От неё зависит надёжность всей цепочки. Схема объявляет у выхода раунда документ (имя, вид), а запрос модели содержит правило, где документ в ответе.

| Вид ответа | Где документ | Как извлекается |
|---|---|---|
| JSON (`format: "json"`) | поле по указателю | `output.artifacts[].pointer`, как сейчас |
| текст | между метками границ | например `[[DOC: spec]] … [[/DOC]]` (предложение); разбор — модулем меток (`DebateStageMarkers`, как вопросы `[[ASK]]`) |

**Не удалось извлечь** (нет меток, нет поля, нарушен формат) — отказ ответа, и та же модель исправляет ответ существующим путём (причины `missing_artifact`, `invalid_form`). Ответ целиком вместо документа не подставляется.

**Этап 1 сейчас:** опросник извлекается из JSON-ответа. Документ для чтения пока берётся целым ответом, вместе с вводными фразами модели. Этап 2 переводит его на правило из таблицы.

## 3. Окно User (этап 1, сделано в 2.81.855)

**Схема.**
- Шаг User: `document` (ref раунда-источника).
- Раунд: `output.document` = `read` (для чтения) или `form` (опросник); `form` требует `format: "json"`.
- Проверка: источник выше по схеме, у него одна включённая модель, вид объявлен.

| Вид | Что видит User | Когда активна OK/Send |
|---|---|---|
| `read` | документ для чтения | сразу |
| `form` | заполняемая форма | когда заполнены все обязательные пункты |

**Формат опросника:** `{ "items": [{ "id", "type": "one|many|text|yesno", "question", "options"?, "required" }] }`. Нарушение формата — причина `invalid_form`. Ошибка ссылки в движке — `invalid_document` до открытия окна.

**Ответ User** — текст «вопрос — ответ»; при `format: json` у выхода шага User — JSON `{ id: значение }`. Документ для чтения при пустом комментарии отвечает «Документ прочитан, замечаний нет.»

Шаг User без `document`: задание и поле текста (`provideOwnerResult` в `results.js`), Send неактивна при пустом поле.

**Карточка User:** выбор «Документ для User» из раундов выше с одной моделью.

## 4. Документ внутри приложения (этап 2)

1. **Извлечение** по договорённости раздела 2, включая документ для чтения.
2. **Документ — артефакт с версиями.** Автор версии — модель или User. Правка User в окне создаёт новую версию.
3. **Рамка на холсте.** Видна с загрузки схемы и сначала неактивна (пунктир). Когда документ извлечён и сохранён, рамка становится обычной; клик открывает документ в окне. Подпись показывает версию и состояние: «ТЗ v2 · утверждено». На стенде зона артефактов уже есть.
4. **Правка и утверждение в окне.** User открывает документ, правит, нажимает OK/Send. Утверждённая версия фиксируется и уходит во вход следующего шага (п. 1.6).
5. **Хранение документов отдельно от записей прогонов.**
   - Записи прогонов (`CustomRunRecord`, предел 4 МБ, старые вытесняются) — история и диагностика.
   - Документы — свой ключ `chrome.storage.local`, без автоматического вытеснения; удаляет User.
   - Запись прогона ссылается на документ и версию.
   - Нужно ли разрешение `unlimitedStorage`, решается при реализации по размерам.
6. **Продолжение после перезапуска.** Прогон, продолжающийся после перезагрузки, видит те же документы и ту же утверждённую версию.
7. **Дефекты карточки User из этапа 1:**
   - при удалении раунда номера `r1…rN` пересчитываются, а ссылка `document` не обновляется (запуск падает с ошибкой пути `steps[N].document`). Ссылка должна следовать за раундом; если раунд удалён — сбрасываться с видимым замечанием;
   - смена документа в списке карточки не меняет значение (осталось `r1`). Выбор должен сохраняться в схему.

## 5. Файл на диске (этап 3)

Подключается после того, как этап 2 работает.

- **Где.** Папка, которую User выбрал через File System Access, — так же стенд работает с `stand-templates.json`. Путь: `<папка>/<pipeline>/<дата-время прогона>/<имя> vN.<md|json>`. Доступ запоминается; после перезапуска Chrome подтверждается при старте ►. Папка, а не «Загрузки» (`chrome.downloads`): из «Загрузок» расширение не может прочитать файл обратно.
- **Экспорт.** Сохранённая версия документа записывается в файл.
- **Импорт правки вне приложения.** Перед шагом, у которого документ во входе, расширение сравнивает файл с последней версией в приложении. Файл изменён — User видит вопрос: взять правку как новую версию или оставить версию из приложения. Файл недоступен — тоже вопрос. Тихого выбора нет (п. 1.6).

## 6. Стенд (этап 4)

Те же поля, рамки и договорённость об извлечении; Export/Import; правило для моделей в `canvas-prototype/model-prompt.md`. Этап `file` стенда при переносе в Basic становится документом с сохранением в файл, а не отдельным видом шага.

## 7. Связь с тем, что есть

- **Файл User на странице** (N03, `basic-developer.md`, раздел 5) решается тем же путём: ответ User со своим файлом — документ с автором User.
- **Экспорт ответов в HTML** остаётся как есть.

## 8. Порядок реализации

1. Окно User: документ от одной модели, опросник, OK/Send (сделано в 2.81.855).
2. Документ внутри приложения: извлечение, версии, рамка, правка и утверждение, отдельное хранение, продолжение после перезапуска, дефекты карточки User.
3. Файл на диске: экспорт и импорт с явным вопросом при расхождении.
4. Стенд.

Каждый этап — отдельная поставка с тестами и правкой документов Basic, по [инструкции исправления](../agent-team-fix.md) в части «тест до правки, приёмка, интеграция».
