# Basic: документы для User (план)

Статус:
- концепция согласована с User 24.10.2026;
- 24.10 переписана по замечаниям независимой проверки (GPT): граница «документ / данные этапа» вместо «файл / память», нет тихих откатов к старой версии, сначала полный путь внутри приложения;
- **этапы 1–2 реализованы (2.81.855, 2.81.856, упрощён в 2.81.857); этап 3 частично: запись копии сделана (2.81.872), перечитывание файла (2.3b) отложено; этап 4 не реализован.** 2.81.857 убрал отдельное хранилище документов: тексты лежат в записи прогона, как и остальные результаты.

Имена полей этапов 2–4 — предложение. В формат схемы (`basic-schema-guide.md`) они войдут вместе с кодом.

## 1. Что решено

1. **Модель пишет ответ, документ из него извлекает приложение** по правилам схемы. Документ — тело ответа. Файлы, которые модель создаёт у себя в чате (скачиваемые файлы ChatGPT, артефакты Claude), не используются: у каждого провайдера они устроены по-своему, и надёжно их не забрать.

   Цепочка: **ответ модели → извлечение документа → проверка и сохранение → рамка на холсте → работа User → OK/Send → дальше уходит утверждённая версия.**
2. **Документ для User даёт одна модель.** Раунд-источник, указанный в шаге User, имеет ровно одну включённую модель.
3. **Документ открывается в отдельном модальном окне** с кнопкой **OK/Send**. После Send ответ User идёт дальше по схеме; следующий раунд по умолчанию получает его как вход `previous` (B-2, 2.81.854).
4. **Граница — по роли результата, а не по месту хранения и не по сроку жизни:**
   - **документ** — самостоятельный именованный результат, с которым работают как с целым: ТЗ, план, опросник, отчёт. Его читают, правят, утверждают; у него есть версии;
   - **данные этапа** — выбор, подтверждение, комментарий, уточнение.

   Что считать документом, решает автор схемы. Приложение само не решает. Размер и срок использования вторичны: промежуточное ТЗ, нужное только внутри прогона, — тоже документ, если его нужно читать и утверждать.
5. **Где хранить.** Документ хранится в записи прогона (раздел 4). Файл на диске — способ сохранить документ и работать с ним вне приложения (этап 3).
6. **Дальше уходит ровно утверждённая версия.** После OK/Send фиксируется конкретная версия документа, и именно она становится входом следующего шага. Если нужную версию прочитать не удалось, приложение останавливает прогон ошибкой с понятным текстом. Тихой подмены другой версией нет.

## 2. Договорённость «схема ↔ ответ модели»

От неё зависит надёжность всей цепочки. Схема объявляет у выхода раунда документ (имя, вид), а запрос модели содержит правило, где документ в ответе.

| Вид ответа | Где документ | Как извлекается |
|---|---|---|
| JSON (`format: "json"`) | поле по указателю | `output.artifacts[].pointer`, как сейчас |
| текст | между метками границ | например `[[DOC: spec]] … [[/DOC]]` (предложение); разбор — модулем меток (`DebateStageMarkers`, как вопросы `[[ASK]]`) |

**Не удалось извлечь** (нет меток, нет поля, нарушен формат) — отказ ответа, и та же модель исправляет ответ существующим путём (причины `missing_artifact`, `invalid_form`). Ответ целиком вместо документа не подставляется.

**Реализовано в 2.81.856:** документ для чтения извлекается по меткам `[[DOC: id]] … [[/DOC]]` (`BasicOutput.extractDocument`); раунд объявляет ровно один артефакт. Опросник по-прежнему извлекается из JSON-ответа.

## 3. Окно User (этап 1, сделано в 2.81.855)

**Схема.**
- Шаг User: `document` (ref раунда-источника).
- Раунд: `output.document` = `read` (для чтения) или `form` (опросник); `form` требует `format: "json"`.
- Проверка: источник выше по схеме, у него одна включённая модель, вид объявлен.

| Вид | Что видит User | Когда активна OK/Send |
|---|---|---|
| `read` | документ для чтения | сразу |
| `form` | заполняемая форма | когда заполнены все обязательные пункты |

**Формат опросника:** `{ "items": [{ "id", "type": "one|many|text|yesno", "question", "options"?, "required" }] }`. Нарушение формата — причина `invalid_form`. Ошибка ссылки в движке — `invalid_document` до открытия окна.

**Ответ User** — текст «вопрос — ответ»; при `format: json` у выхода шага User — JSON `{ id: значение }`. Документ для чтения при пустом комментарии отвечает «Документ прочитан, замечаний нет.» (действовало в 2.81.855; в 2.81.856 окно правки, см. раздел 4)

Шаг User без `document`: задание и поле текста (`provideOwnerResult` в `results.js`), Send неактивна при пустом поле.

**Карточка User:** выбор «Документ для User» из раундов выше с одной моделью.

## 4. Документ внутри приложения (этап 2)

1. **Извлечение** по договорённости раздела 2, включая документ для чтения (сделано в 2.81.856).
2. **Документ — артефакт.** Версии документа — записи реестра артефактов. Автор версии — модель или User: правка User в окне регистрируется записью реестра с автором User (`source.participant: owner`) в той же линии. (сделано в 2.81.856)
3. **Рамка на холсте.** Видна с загрузки схемы и сначала неактивна (пунктир, подпись — имя). Когда документ появился, рамка становится обычной и показывает «<имя>»; после утверждения — «<имя> · утверждено». Клик открывает документ в окне только для чтения (кнопка «Закрыть»). Рамки строятся из записи прогона (реестр и `snapshot.results[].owner.approved.id`), обновляются при каждом сохранении состояния и в конце прогона. (сделано в 2.81.856, подпись без номера версии — 2.81.857)
4. **Правка и утверждение в окне.** User открывает документ, правит, нажимает OK/Send. Утверждённая версия фиксируется: шаг User хранит `approved: { id }`, и именно этот текст уходит во вход следующего шага (п. 1.6). Следующий раунд по умолчанию получает `previous`; явный вход `latest` — правленая версия. (сделано в 2.81.856)
5. **Хранение — в записи прогона.** Тексты версий лежат там же, где и другие результаты: реестр артефактов (`record.artifacts`), тексты по отпечатку (`putText`/`getText`), снимок (`snapshot.results[].owner.approved`). Записи прогонов вытесняются по пределу 4 МБ (общее правило записи прогонов); отдельного срока хранения документов нет. (2.81.857)
6. **Продолжение после перезагрузки страницы.** Рамки и утверждённый документ восстанавливаются из последней записи прогона этого pipeline (`customRunStore.latest(имя)`). Если текста нет в записи, User видит уведомление «Текст документа «…» не найден в записи прогона». (сделано в 2.81.856, источник — запись прогона с 2.81.857)
7. **Дефекты карточки User из этапа 1** (сделано в 2.81.856: (а) сброс при удалении раунда; (б) смена документа в списке — не воспроизведено, тест защиты добавлен):
   - при удалении раунда номера `r1…rN` пересчитываются, а ссылка `document` не обновляется (запуск падает с ошибкой пути `steps[N].document`). Ссылка должна следовать за раундом; если раунд удалён — сбрасываться с видимым замечанием;
   - смена документа в списке карточки не меняет значение (осталось `r1`). Выбор должен сохраняться в схему.

## 5. Файл на диске (этап 3)

**Сделано (2.81.872):**
- **Папка.** User выбирает папку в окне ответа User с документом (строка «Папка документов», File System Access, `showDirectoryPicker`). Одна папка на все pipelines. Дескриптор хранится в IndexedDB расширения.
- **Путь.** `<папка>/<pipeline>/<дата-время начала прогона YYYY-MM-DD_HH-mm-ss>/<имя документа>.md`; для опросника — `.json` с ответом. Имя очищается от запрещённых символов, длина до 80.
- **Запись.** При OK/Send утверждённый текст записывается в файл; повторное OK/Send перезаписывает его. Файл — копия для человека, главное хранилище — запись прогона.
- **Доступ и ошибки.** Папка не выбрана — ничего не происходит. После перезапуска Chrome доступ запрашивается на ▶ и на «Продолжить прогон». Нет доступа или ошибка записи — прогон не останавливается, одно уведомление за прогон.
- Схема и движок не менялись; рамка документа на холсте не менялась; вида `file` в Basic нет.

**Отложено (2.3b): импорт правки вне приложения.** Перед каждым шагом, у которого документ во входе, страница читает файл и сравнивает его с утверждённой версией. Расхождение — вопрос «взять правку / оставить версию приложения»; «взять» — запись реестра с автором User. Файл недоступен — вопрос «записать заново / продолжить без файла». Папка не выбрана — проверка пропускается. Тихого выбора нет (п. 1.6). Нужен ли пакет, решит менеджер по реальным прогонам; пока это только описание.

## 8. Порядок реализации

1. Окно User: документ от одной модели, опросник, OK/Send (сделано в 2.81.855).
2. Документ внутри приложения: извлечение, документ как артефакт, рамка, правка и утверждение, продолжение после перезагрузки, дефекты карточки User (сделано в 2.81.856; упрощено в 2.81.857: хранение в записи прогона).
3. Файл на диске: запись копии сделана в 2.81.872 (папка, путь, запись при OK/Send, доступ); перечитывание файла и вопрос при расхождении — 2.3b, отложено.

Каждый этап — отдельная поставка с тестами и правкой документов Basic, по [системе работы команды](../Agents/agent-team.md), раздел «Реализация сложных изменений».
