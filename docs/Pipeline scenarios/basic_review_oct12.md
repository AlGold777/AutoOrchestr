## Подтверждённые дефекты

Приоритет P1 — исправить до приёмки архитектурного процесса; P2 — исправить до объявления полного соответствия ТЗ. Приоритет не означает, что код уже исправлен.

### R01 · P1 · Continue допускает другой чат

**Триггер:** у участника была привязанная вкладка, затем её закрыли; нужно продолжить чат.

`background/job-orchestrator.js:5647–5675` вызывает поиск с `allowGlobalReuse: true` и предпочтительным tab ID. `background/tab-manager.js:536–546` лишь сортирует подходящие вкладки, не ограничивает выбор привязанным ID. При отсутствии исходной вкладки допускается другая незанятая вкладка того же провайдера; без неё создаётся пустая новая вкладка. Вопроса владельцу и восстановления сохранённого контекста нет.

**Повторённый результат:** bound tab 11 отсутствует, unrelated tab 22 доступна → запрос выбирает 22 и перепривязывает участника. Без кандидатов запускается создание нового пустого чата. Это воспроизведение выбора production-функций со стабами Chrome, а не реальная отправка провайдеру.

**Исправление:** при существующей, но потерянной привязке — явный отказ/решение владельца или восстановление контекста. Не использовать глобальную подстановку как continue. Отдельно проверить восстановление привязки конкретного сохранённого прогона, если между остановкой и resume запускался другой pipeline с тем же participant ID.

### R02 · P1 · Latest возвращает старую версию после неудачной доработки

**Триггер:** r1 создал v1, r2 создал revision v2, gate вернул в r2; повторная доработка провалилась/пропущена; следующий шаг требует latest исходной линии.

`disput/basic-artifacts.js:28–32` выбирает последнюю запись среди valid; r2.v1 инвалидирована, исходная r1.v1 остаётся valid. `disput/custom-engine.js:696–700` подставляет её потребителю.

**Повторённый результат:** `stopReason: steps_done`, потребитель получил `v1`, хотя актуальная доработка отсутствует. Это не бизнес-неопределённость: ТЗ запрещает старый fallback после failed/skipped пересчёта.

**Исправление:** линия, ожидающая пересчёта новой ревизии, не должна откатывать рабочий latest на исходную версию. Сохранить историю, но required потребитель должен получить missing_input, пока не сформирована допустимая актуальная версия. Проверить как latest, так и конкретную версию.

### R03 · P1 · Ошибка Chrome Storage выглядит как успешный checkpoint

`disput/custom-run-record.js:235–241` разрешает Promise в callbacks get/set/remove, не проверяя `chrome.runtime.lastError`. Страница ожидает writeRecord, но получает успех при отказе записи по квоте.

**Повторённый результат:** runtime.lastError = Quota exceeded; `save()` успешно завершился, `load(runId)` вернул null. Это обходит checkpoint_failed и допускает внешнее действие без подтверждённого сохранения состояния.

**Исправление:** читать lastError внутри callback и отклонять Promise. Тест должен проходить через настоящий chromeStorage-адаптер с ошибкой callback, а не только через fake checkpoint, который сам бросает исключение.

### R04 · P2 · Экспорт теряет ссылки и адреса попыток

`disput/custom-run-record.js:161–185` разрешает feedback, но оставляет taskRef/textRef в snapshot; таблица texts не экспортируется. При этом attempts экспортируются без ref, participant, visit и phase.

**Повторённый результат:** snapshot содержит `{ok:true,textRef:"..."}`, но словаря для ссылки нет; exported attempt не содержит четырёх полей идентичности. Export объявляется resumable, однако полного самодостаточного состояния не несёт.

**Исправление:** экспортировать разрешаемый словарь/все необходимые данные и сохранять адрес попытки. Проверить сериализуемый экспорт отдельно от локального resume. Не обещать импорт/восстановление по неразрешимым ссылкам.

### R05 · P2 · Новый чат повторного захода не получает вложения

`results.js:7494` определяет вложения через `wave.some(request => !attached.has(participantId))`; затем участник добавляется в attached на весь прогон. Новый chat при новом visit не сбрасывает эту отметку.

**Сценарии из фактической функции:** участник с уже приложенными файлами получает новый чат на следующем visit, но attachments пусты; в смешанной wave общий набор может повторно уйти уже приложившему участнику, если другой участник новый.

**Исправление:** учёт доставки файлов по конкретному чату, а не по ID на весь прогон; разделение волн/адресная доставка при разных наборах вложений. Проверить повтор исправления, новый visit и смешанную волну.

### R06 · P2 · API-путь обходит семантику participant chat

`background/job-orchestrator.js:5390–5395` вызывает tryApiDirect по имени модели раньше participant tab path. В вызове нет participant ID, chat и истории диалога. При успешном API-вызове вкладочная ветка вообще не выполняется.

**Последствие:** выбранный API режим не реализует контракт продолжения конкретного чата участника. Вкладочная проверка new/continue не подтверждает API-путь.

**Исправление:** явно ограничить неподдерживаемый API режим либо реализовать отдельную историю участника; ошибку/ограничение показывать до отправки. Выбор поддержки API может быть продуктовым решением, но молчаливое нарушение схемы — недопустимый обход.

### R07 · P2 · Stop оставляет модальное окно

`CustomEngine.ownerWait` (`disput/custom-engine.js:643–657`) прекращает ожидание через AbortSignal; `results/choice-dialog.js:15–35` не принимает signal и не предоставляет закрытие. `results.js:7666–7670` закрывает другие окна, но не ChoiceDialog.

**Повторено в настоящем Chromium:** abort во время owner-input → `stopReason: cancelled`, `openDialogs: 1`, `dialogStillVisible: true`. Компонент остаётся блокирующим и реагирует на поздний клик.

**Исправление:** связать жизненный цикл ChoiceDialog с сигналом/прогоном; на Stop закрыть и снять обработчики. Тестировать route, owner и unknown окна.

### R08 · P1 · Нельзя обратиться к артефакту владельца

`disput/basic-schema.js:216–220` ищет participant только в step.models. У owner-шага список пуст, хотя движок создаёт результат/артефакт от participant `owner`.

**Повторённый результат:** корректный owner:evidence с артефактом evidence → required вход следующей модели с participant owner отвергается: «участник owner не объявлен». Движок отдельно создаёт этот артефакт успешно. Блокируется человеческое evidence → обработка моделью, а не только оформление документа.

**Исправление:** единый контракт источника owner во всех ссылках: ответ, artifact, revisionOf и feedback; владелец не обязан становиться фиктивной моделью.

### R09 · P2 · Control-only pipeline отвергается оболочкой

Owner-only схема проходит validate, но `toCanvas` (`disput/basic-schema.js:658`) требует round. `runCustomFromPage` (`results.js:7389`) также требует round, вопреки ТЗ 8.1.

**Исправление:** согласовать наличие исполняемого шага для schema/canvas/run; проверить самостоятельный owner и допустимые gate/route процессы. Не добавлять пустой фиктивный раунд как обход.

### R10 · P1 · Два участника одной модели не устанавливаются

`results.js:9130–9139` recordFromSchema отклоняет повтор modelName, даже при разных ID. Валидатор такие разные ID принимает; движок и transport adapter имеют поддержку participant requests.

**Подтверждение:** существующий интеграционный тест `tests/results-debate-favorites.test.js:3434–3444` специально ожидает отказ. Зелёный тест здесь подтверждает сохранение ограничения, а не закрытие T07.

**Исправление:** сохранять участников холста по ID, не схлопывать по modelName; закрыть реальный Import → Run → Save для two Claude с разными ID. Повтор одинакового ID внутри шага валидатор правильно отвергает, это не дефект.

### R11 · P2 · Validate и холст расходятся рядом с synthesis/control

`r1 → synth → gate → r2` и `r1 → gate → synth → r2` проходят validate, но `toCanvas` (`disput/basic-schema.js:643–644`) отвергает их из-за непосредственного соседства synth с раундами. Страница также блокирует такую вставку (`results.js:4356`).

**Исправление:** один согласованный контракт порядка, сохраняющий смысл и позицию control-step. Нельзя валидировать схему как исполнимую, а затем предлагать её импорт с потерей control. Повторить Save/Export/Import этих сочетаний.

### R12 · P2 · Выключенный ID-источник может потеряться при Save

Схема объявляет участника только `{name,id,enabled:false}`; на него ссылается optional вход. `toSettings` (`disput/basic-schema.js:602–610`) не сохраняет участника без собственных настроек; toCanvas не показывает его, а обратная сборка (`results.js:7037–7044`) сохраняет выключенных только из cards с собственными полями.

**Доказательство:** Node-проверка проекции показала valid исходную схему и отсутствие выключенного ID в settings/canvas; код обратной сборки не восстанавливает его из исходной декларации. Полный browser Save данного частного сценария не выполнялся, поэтому это вывод из проекции и пути сборки, а не заявленный e2e прогон.

**Исправление:** сохранять объявленных выключенных участников, на которых есть ссылки, отдельно от их собственных настроек. Проверить реальный round-trip, чтобы не превращать valid optional источник в неизвестный ID.

## Недостающие возможности и ограничения ТЗ

1. **Обязательный вход целого шага (D3).** Строка ref выбирает весь шаг, но required задать нельзя; `{step,required:true}` без participant отвергается. Это пробел нашего уточнённого JSON-контракта, не только ошибка исполнителя. Добавить однозначную форму «все ответы данного шага — обязательный источник» и определить достаточность результата через require источника.
2. **Индивидуальные revisionOf (D4).** Output общий для шага; models[].output запрещён. Двум авторам одного параллельного этапа нельзя явно дать каждому свою исходную линию. Fixture разносит их на разные шаги. Нужно либо поддержать индивидуальные объявления выхода, либо документировать и проверить преобразование в отдельные технические шаги. Такой обход нельзя выдавать за поддержку общего per-participant output.
3. **Редактор новых полей не завершён.** UI сохраняет часть полей из импортированного JSON, но не позволяет задать ID, индивидуальный вход, artifact/version/required, chat, JSON output/requiredFields/artifacts/revisionOf. Сохранение скрытого поля не равно реализации окна настройки по ТЗ 9. Rule-route не редактирует все artifact-источники.
4. **Owner-file отсутствует на странице.** ProvideOwnerResult поддерживает текст; файл как содержательный результат не принимается. Безусловно закрыть 4.1 и T14 нельзя. В движке бинарный вход ограничен unsupported_input, но отсутствует полный UI/сохранение/доставка.
5. **Unknown нельзя проверить перед повтором.** Окно содержит resend/skip, но не «проверить наличие ответа» через сохранённый request/tab ID, как требует ТЗ 8.3. Это повышает риск повторной отправки после reload.
6. **CHG/T12 только частично.** Fixture показывает missing_input при возврате, потому что зависимые результаты устарели. Остановка корректна; полный путь пересчёта перед продолжением не доказан. Это не основание выносить CHG из схемы автоматически: нужен явный путь пересчёта и его тест. Условия бизнеса Q10 не выдумывать, но механические ошибки R01–R12 не зависят от этих ответов.
7. **Отчёт A03 устарел относительно кода.** В A03-research-report написано, что sendParticipants не сделан. В проверенном commit реальный Basic путь его передаёт, делит запросы по волнам и использует participant tab map. Отдельное new создаётся для вкладочного пути; утверждение, что транспорт вообще не реализован, неверно. Проблемы — строгий continue, API, вложения и отсутствие полной проверки провайдеров.

## Воспроизведения

Файлы ниже ничего не изменяют в production. Node-скрипты показывают наблюдаемое поведение проверенного commit; после исправления ожидается другой результат. Chromium-скрипты используют Playwright и изолированный браузер без аккаунтов и отправок провайдерам.

```bash
node 'docs/Pipeline scenarios/basic-review-oct12/artifact-fallback.js'
node 'docs/Pipeline scenarios/basic-review-oct12/tab-fallback.js'
node 'docs/Pipeline scenarios/basic-review-oct12/record-defects.js'
node 'docs/Pipeline scenarios/basic-review-oct12/dialog-browser.js'
node 'docs/Pipeline scenarios/basic-review-oct12/stop-dialog-browser.js'
```

Tab-fallback извлекает production-функции и подставляет API Chrome: доказан алгоритм выбора, а не завершённая доставка реальной вкладке. Stop-dialog-browser загружает модули в порядке фактической страницы. Сам факт прохождения существующих тестов не снимает воспроизведённые несоответствия.
