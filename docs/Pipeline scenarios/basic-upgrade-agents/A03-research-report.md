## 2. Ответы по пунктам задания

### (а) Два независимых чата одной модели: нет

Все уровни адресуют запрос по имени модели:

- Вкладка: `llmTabMap[llmName]` (`tab-manager.js:272`, `:321`) — одна вкладка на имя.
- Запись состояния: `jobState.llms[llmName]` (`job-orchestrator.js:5310-5313`) — одна запись на имя.
- Запуск по модели: `llmStartChains[llmName]` (`job-orchestrator.js:5359-5360`).
- ID запроса: `transportRequestIds` строится по имени (`results.js:6013`).
- Батч: `waitForModels` делает `Array.from(new Set(models))` (`results.js:3151`), поэтому два участника с одним именем в одном батче схлопнутся в один.

Следствие: два участника одной модели в одном батче не получат двух запросов; при последовательных батчах оба попадут в одну и ту же вкладку (см. (в)).

### (б) Новый чат по команде для `chat: "new"`: нет

- В контент-скриптах нет команды «новый чат» для открытой вкладки. Совпадения по `new chat` в `content-scripts/content-gemini.js:297,753`, `content-deepseek.js:687,1026` относятся к подписям кнопок и распознаванию ответа, а не к командам.
- Единственный механизм создания «нового чата» — новая вкладка на корневом URL провайдера: `createNewLlmTab` (`tab-manager.js:660`, `cleanUrl` в `:672`, `chrome.tabs.create` в `:678`). Он вызывается только при `forceNewTabs` (`job-orchestrator.js:5642-5647`).
- Для модели, уже открытой в прогоне, новая вкладка не создаётся (`results.js:6021-6026`). Значит, новый заход (`visit` 2) этой модели сейчас продолжает прежний чат, даже если шаг требует нового.
- Новая вкладка создаётся по модели, а не по участнику.

### (в) Продолжить именно указанный чат по participant ID: нет

- Продолжение сейчас выбирается по модели: при `forceNewTabs: false` вызывается `tryAttachExistingTab` с `allowGlobalReuse: true` и `mandatoryReuse: true` (`job-orchestrator.js:5661-5668`).
- Список кандидатов (`tab-manager.js:503-511`) включает любую вкладку провайдера, совпавшую с URL-шаблоном. Привязанная вкладка сортируется первой (`:510`), но при её отсутствии берётся самая свежая вкладка провайдера. Это тихая подстановка, которую ТЗ 8.3 запрещает («не привязываться к произвольной вкладке той же модели»).
- Повтор исправления внутри захода: `send` вызывает тот же `runModelBatch` (`results.js:7075`), `forceNewTabs` для уже открытой модели = `false` (`results.js:6021-6026`), поэтому повтор уходит в ту же привязку по имени модели. Для двух участников одной модели повтор не различим: оба идут в одну вкладку.
- Механизма «вкладка или чат по participant ID» нет. Отсутствующий элемент: привязка `participantId → tabId` и выбор вкладки по ней без подстановки чужой вкладки модели.

Что сейчас обеспечивает «later steps continue in that chat» (`results.js:7052`): не ID чата, а сочетание `newPagesModels` (`results.js:6021-6027`, `:6300-6303`) и привязки по имени модели (`tab-manager.js:503-511`, `job-orchestrator.js:5638-5668`). Комментарий в `results.js:7052` описывает намерение, а не отдельный механизм.

### (г) Вложения первым сообщением в новый чат: нет адресной передачи

- Вложения собираются один раз на прогон: `results.js:7051` (`buildAttachmentPayload`).
- Передаются батчу целиком, если хотя бы одна модель ещё не в `attached`: `results.js:7080` — `attachments: models.some((model) => !attached.has(model)) ? attachments : []`. Значит, уже приложенная модель получит вложения повторно, если в том же батче есть новая модель. Это отклонение от правила «вложения с первым сообщением каждой новой вкладки».
- Для новой вкладки вложения передаются в `createNewLlmTab(prompt, attachments)` (`job-orchestrator.js:5642-5647`). Адресной передачи по участнику нет: набор общий для батча.

### Ограничения параллельного выделения вкладок

1. Одна активная отправка: `startProcess` отклоняет второй старт, пока `startProcessReserved` (`job-orchestrator.js:5197-5212`); ответ `RUN_ALREADY_ACTIVE`, `results.js:6263-6276` ждёт не дольше `PIPELINE_START_BUSY_WAIT_MS`.
2. `RunGuard.canStartNewRun` (`shared/run-guard.js:33-54`): отказ при `roundsInProgress`; при `forceNewTabs: false` отказ, если любая модель ещё генерирует (`findGeneratingModel`).
3. `ensureNoOtherViewRun` (`results.js:2182`, проверка в `results.js:6103`): отказ, если другая страница держит запрос.
4. Существующие вкладки: выделяются параллельно (`job-orchestrator.js:5714`, `Promise.allSettled`), но цепочка запуска по каждой модели своя (`llmStartChains`, `:5359-5360`).
5. Новые вкладки: открываются последовательно с паузой `ROUND0_OPEN_STAGGER_MS` (`job-orchestrator.js:5745`).
6. Ожидание ответа: ответ сопоставляется только по `transportRequestId` (`results.js:3138-3139`, `:3193`, `:3293-3297`); батч ключуется по имени модели.
7. API-путь: `tryApiDirect(llmName)` (`job-orchestrator.js:5384`, `:5396`) вызывается раньше вкладок и тоже ключуется по имени. В строках 5380–5520 нет учёта истории диалога; сохраняет ли API контекст между шагами, не проверено.

Недостающие механизмы, без которых независимый чат нельзя надёжно выбрать:

1. Ключ `participantId` вместо имени модели в `transportRequestIds` (`results.js:6013`), `waitForModels` (`results.js:3151`), `jobState.llms` (`job-orchestrator.js:5310`), `llmTabMap` (`tab-manager.js:272`), `llmStartChains` (`job-orchestrator.js:5359`). Сейчас все таблицы состояния индексированы именем модели.
2. Привязка `participantId → tabId` (или `chatId`) с сохранением в записи прогона и возможностью восстановления после reload.
3. Режим выбора вкладки без подстановки: если привязанной вкладки участника нет, возвращать явную ошибку, а не `findReusableTabsForLlm` (`tab-manager.js:503-511`).
4. Команда «новый чат» в открытой вкладке. Её нет ни в одной контент-скрипте. Без неё `chat: "new"` возможен только через новую вкладку на каждый заход.
5. Вложения по участнику: первое сообщение нового чата получает вложения, а уже приложенный участник — нет (`results.js:7080` сейчас передаёт их батчу целиком).

Расширение: минимальным его назвать нельзя. Оно затрагивает `background/job-orchestrator.js`, `background/tab-manager.js`, `background/message-router.js`, `shared/run-guard.js`, `results.js` (waiter, батч, `send`), а также формат ответа контент-скриптов, который должен нести participant. Изменение касается общего состояния транспорта, которым пользуются другие pipelines (ТЗ 1: «не переписывать транспорт других pipelines»). Поэтому по карточке A03 (шаг 2, «Если безопасное расширение не помещается в такой объём… НЕ реализуй») реализация не начата.

## 4. Что проверить вручную в реальных вкладках

Mock-тесты не подтверждают реальный транспорт. Сценарий для владельца или тестировщика, с открытыми страницами провайдеров и залогиненными аккаунтами:

1. Открыть одну модель (например, Claude) в двух вкладках вручную. Запустить Basic с одним раундом из двух участников одной модели. Проверить, в какую вкладку уходит каждый запрос и уходят ли оба в одну.
2. Запустить Basic с `chat` по умолчанию в два шага. Проверить, что второй шаг уходит в ту же вкладку (журнал `batch_start`, поле `requestIds`, и вкладка по `tabId` в `jobState.llms`).
3. Закрыть вкладку модели между шагами. Проверить, что транспорт берёт другую вкладку этой модели (подстановка), и зафиксировать, открыт ли другой чат.
4. Прогнать исправление (`attempt` 2): проверить, что оно уходит в тот же чат, где был первый ответ.
5. Проверить вложения: при двух моделях в батче, где одна уже приложила файлы, проверить, получила ли она их повторно (ожидаемо по `results.js:7080`).
6. Проверить API-путь (`useApiFallback` включён и ключ есть): сохраняет ли API контекст между шагами.
7. Проверить параллельное выделение: при нескольких открытых вкладках одного провайдера убедиться, что `tryAttachExistingTab` выбирает вкладку, совпадающую с привязкой, а не самую свежую.

## 5. Решения, которые нужны от владельца продукта

1. Что считать «новым чатом» для `chat: "new"`: новая вкладка на корне провайдера или команда «новый чат» в открытой вкладке (это новый код во всех контент-скриптах провайдеров).
2. Поведение, если привязанный чат участника недоступен при `continue`: явная ошибка и вопрос владельцу (как в ТЗ 8.3) или восстановление контекста из сохранённых входов. Текущий fallback на свежую вкладку модели по ТЗ недопустим.
3. Допустимое число новых вкладок на шаг (независимость двух участников одной модели потребует двух вкладок, и у пользователя появятся дополнительные открытые страницы).
4. Политика API-пути для участников с `chat: "new"`: отключать API или сохранять API-историю отдельно.
5. Вложения при новом чате: передавать ли их каждому новому чату (по ТЗ 2.2 — да) и как поступать с уже приложившими модель участниками.
