2. [Общее ТЗ](../basic_upgrade_oct11_technical_spec.md): разделы 3–11 обязательны. Точные JSON-форматы и причины отказа брать оттуда, не изобретать похожие.
3. [План](../basic_upgrade_oct11.md), `basic-developer.md`, существующие тесты вашего участка.

Статус: задание выполнено 11–12.10.2026 (версии 2.81.731–755), карточка сохранена как история. Текущие задания на исправления — в `../basic-fix-agents/`. Раздел ниже — исходная постановка. Не запускать других исполнителей автоматически. Не менять бизнес-условия архитектуры и не обходить неизвестные требования догадками.

Каждый подпункт выполняется отдельно: прочитать код → добавить проверку конкретного поведения → изменить минимальный участок → запустить относящиеся тесты → документация/версия → commit. Не писать один огромный коммит на весь участок. Версии согласовать с интегратором; commit по правилам AGENTS.md.

## Назначение и зависимости

Пакет P03 после P01, параллельно A02 при отсутствии пересечения файлов. Владеете только адаптером Basic в `results.js` и минимально необходимым участком транспорта. Передайте файл A05 по завершении. В общую отправку других pipelines не вносить изменённые умолчания.

## Порядок работ

1. **Исследование до кода.** Проследить runCustomFromPage → runModelBatch → START_FULLPAGE_PROCESS → выбор вкладки/контекста. Зафиксировать фактические пути файлов и функции. Проверить: две вкладки одной модели, выбор существующего tab по ID, создание new chat, корреляция ответа по request ID, повтор в том же чате, API fallback. Результат сохранить рядом с карточкой как A03-transport-findings.md; это отчёт, не предположение.
2. **Граница поддержки.** Если транспорт пока адресует только modelName, показать точку ограничения и расширить адресацию tab/session/request без изменения legacy-вызовов. Если реального механизма создания/выбора чата нет, явно отметить блокирующую часть; запретить silent substitution одним чатом.
3. **Bindings.** Для прогона хранить participantId → modelName/chatId/tabId/доступный transport handle. Эти handles не использовать как бизнес-ID. Два участника одной модели не разделяют историю.
4. **Send adapter.** Реализовать callback sendParticipants из ТЗ. Prompts и результаты ключуются participant ID, отправка провайдеру — modelName. Не переименовывать провайдер в participant ID. Результат одного запроса не прикреплять к чужой попытке.
5. **Chat new/continue.** New создаёт чат на новом visit; attempt 2 остаётся в чате attempt 1. Continue возвращается к чату того же участника между этапами. Если чат отсутствует — явная ошибка/решение, не выбор первой вкладки модели.
6. **Вложения.** Первое сообщение каждого нового чата получает нужные вложения. Проверить файл из owner-step через A05 позже. Не отправлять общий набор вложений всем участникам, если схема задаёт разные входы.
7. **Независимость.** S18: candidate A/B в разных чатах. S19: reviewer ID отличается от автора, новый чат, только назначенные входы. S20: revision исходного author ID. Для ограниченного транспорта допускается последовательная доставка в независимые чаты, а не общий контекст.
8. **Stop и attribution.** Abort прекращает ожидающие запросы, поздний ответ не меняет чужую/завершённую попытку. Сохранить request ID и вкладку для resume. A05 получает сериализуемые bindings и способ проверить unknown.

## Проверки

Контрактные mocks transport + T07, retry и Stop. Тестировать два одинаковых modelName с разными prompts/ответами и их точную корреляцию. Отдельно выполнить ручной сценарий двух реальных чатов только в разрешённой среде; если не выполнен, отчёт честно содержит «unit подтверждён, реальный транспорт не проверен».

## Готовность

Отчёт исследования имеет ссылки на реальные функции. ID не теряется между схемой, запросом, транспортом и карточкой. Independent означает реальное отсутствие общего чата; continue — чат правильного участника. Другие pipelines работают по старому пути. Переданы bindings/unknown resolution A05 и контракты UI A06.

## Что передать

- Commit каждого самостоятельного изменения и перечень затронутых файлов.
- Какие части контракта реализованы, список тестов и фактические результаты.
- Один положительный и один отрицательный JSON-пример вашего участка.
- Нерешённые ограничения перечислить отдельно. Заглушку, silent fallback и тест только на mock не выдавать за реальную поддержку транспорта.
- Если нужен файл другого владельца, передать ему точный запрос с входом/ожидаемым выходом и тестом. Не редактировать параллельно его файл.
