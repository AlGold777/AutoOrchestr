# A07 · интеграция и приёмка

## Обязательное чтение и границы

1. `AGENTS.md`, git status и `docs/Pipeline scenarios/basic-start-here.md`.
2. [Общее ТЗ](../basic_upgrade_oct11_technical_spec.md): разделы 3–11 обязательны. Точные JSON-форматы и причины отказа брать оттуда, не изобретать похожие.
3. [План](../basic_upgrade_oct11.md), `basic-developer.md`, существующие тесты вашего участка.

Статус: задание выполнено 11–12.10.2026 (версии 2.81.731–755), карточка сохранена как история. Текущие задания на исправления — в `../basic-fix-agents/`. Раздел ниже — исходная постановка. Не запускать других исполнителей автоматически. Не менять бизнес-условия архитектуры и не обходить неизвестные требования догадками.

Каждый подпункт выполняется отдельно: прочитать код → добавить проверку конкретного поведения → изменить минимальный участок → запустить относящиеся тесты → документация/версия → commit. Не писать один огромный коммит на весь участок. Версии согласовать с интегратором; commit по правилам AGENTS.md.

## Назначение и зависимости

Интегратор ведёт передачу P00–P09. Не выполняет чужие функции вместо владельцев: возвращает точный дефект с примером и expected outcome. Владеет общей матрицей проверок, документацией и архитектурными fixtures. Если нужен общий файл, получает его после текущего владельца.

## Порядок работ

1. **Baseline.** Снять git status, текущую версию manifest/package, результаты Basic-тестов и известные несвязанные падения по basic-developer. Существующие проблемы не приписывать новым агентам; новые — фиксировать.
2. **Contract gate P01.** Сверить весь JSON contract ТЗ с validator/assemble. Проверить, что A02/A03/A06 используют тот же input/address/participant/route форматы. Частичный allow unknown fields не считается поддержкой.
3. **Пакеты и locks.** Не разрешать A02/A04/A05 одновременно писать custom-engine; A03/A05/A06 — results.js. Собрать commit по зависимостям, отдельно проверить version/docs. Не cherry-pick конфликтующий commit вслепую.
4. **Новые modules.** Проверить browser script loading и exports в реальном entrypoint. Unit-test require без подключения в extension не закрывает пакет. Не добавлять отдельный build, если существующий путь достаточно просто подключает модуль.
5. **Acceptance T00–T21.** Нужен сценарий с конкретными prompts/order/events, не только итоговой причиной. Критические отрицательные: null decision, invalid route, missing required artifact, stale version, lost textRef, checkpoint error, duplicate participant name, loop after resume.
6. **Architecture fixture.** Из DS собрать все 30 этапов в тестовую схему, отдельную таблицу S→ref. Расширить Reviewer+Producer и gates/control/owner в нужные технические шаги. Неразрешённые условия Q10 не придумать: записать blockers бизнеса. Fixture может использовать помеченные synthetic inputs/conditions для теста механики.
7. **Count.** Вычислить бизнес-этапы, round/synthesis/gate/route/owner и число участников/базовых запросов. Максимальные повторы/маршруты учитывать отдельно как границу, а не обещать точное число runtime запросов. Убедиться, что контрольные шаги не расходуют лимит 50 rounds.
8. **Budget.** S13/S30 реальные размеры либо явно помеченные stress fixtures. Context full до transport; feedback также в бюджете. Отчёт без реальных данных не объявляет доказанной вместимость конкретного бизнес-прогона.
9. **Real transport.** С A03 записать проверку новых/продолжаемых чатов, attribution и attachments. Непроверенный провайдер/режим указать отдельно. Mock независимость не доказывает наличие двух настоящих чатов.
10. **Documents.** Basic-start-here, schema-guide, windows, developer, documentation-map и CHANGELOG соответствуют реализованному состоянию. OI-3 закрывать только на реально поддержанной приёмке. Архитектурные gaps 5.2 закрывать по доказанным тестам, а не по наличию поля в validator.
11. **Final report.** Пакеты, commits, тесты, старые/новые падения, matrix status, round-trip, размеры/лимит, бизнес-blockers и реальные transport ограничения. Финальное «готово» только если отсутствуют обязательные незакрытые требования движка.

## Проверки

Команда из раздела 10 ТЗ плюс все добавленные suite. Полный набор проекта запускать на интеграционной точке, сверяя набор известных падений; бессмысленно повторять его после каждой docs-строки. Экспорт/импорт схемы и прогона проверять отдельно.

## Готовность

Есть trace S01–S30→ref→test, нет потерянных контрактов и обхода require/approve, реестр/route/feedback/resume состыкованы. Каждый заявленный результат имеет подтверждение; открытая бизнес-информация не подменена. Все самостоятельные изменения закоммичены.

## Что передать

- Commit каждого самостоятельного изменения и перечень затронутых файлов.
- Какие части контракта реализованы, список тестов и фактические результаты.
- Один положительный и один отрицательный JSON-пример вашего участка.
- Нерешённые ограничения перечислить отдельно. Заглушку, silent fallback и тест только на mock не выдавать за реальную поддержку транспорта.
- Если нужен файл другого владельца, передать ему точный запрос с входом/ожидаемым выходом и тестом. Не редактировать параллельно его файл.
