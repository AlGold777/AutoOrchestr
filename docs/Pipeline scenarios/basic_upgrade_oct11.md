# Доработка Basic · 11 октября 2026

План развития движка Basic, составленный по практическому прогону: архитектура из 30 этапов переписана в формат Design System создания pipeline ([design-system-architecture.md](design-system-architecture.md), раздел 5.2 «Несоответствия с Basic»). Документ самодостаточен: по нему можно ставить задания исполнителям без чтения переписки. Устройство Basic — в [basic-start-here.md](basic-start-here.md), формат схемы — в [basic-schema-guide.md](basic-schema-guide.md), код и правила — в [basic-developer.md](basic-developer.md).

## 1. Принципы доработки

1. **Только добавляем.** Каждая возможность — необязательное поле схемы. Схема без поля работает как раньше (умолчание — контракт). Версия формата `schemaVersion` не меняется, пока поля только добавляются; исключение — п. 0.1 волны 0, там меняется документированное поведение (запись в CHANGELOG).
2. **Включается явно в схеме.** Движок ничего не включает сам и не угадывает.
3. **Ошибка схемы называет место.** Каждое новое поле проверяется в `BasicSchema.validate` с путём вида `steps[2].output.sections`.
4. **Один путь схема → холст → схема.** Новое поле обязано пройти `toCanvas`, карточку на странице и `basicSchemaFromPage` без потерь. Тест на круговой проход обязателен.
5. **Один коммит = код + тесты + документы Basic + версия.** Документы сверяются с кодом тестами `basic-schema-guide.test.js` и `basic-docs-refs.test.js`.
6. **Результат этапа и есть артефакт.** Отдельный реестр версионируемых артефактов не вводим (см. раздел 6).
7. **Бизнес задаёт процесс, движок исполняет.** Автор задаёт условия переходов, состав выходов и область пересмотра. Движок передаёт данные, выбирает заданный маршрут и контролирует актуальность результатов. Недостающие бизнес-данные и переводы названий не являются дефектами движка.
8. **Маршрутизация — самостоятельный элемент схемы.** Gate проверяет критерии; маршрут определяет следующий шаг. Возврат — частный случай маршрута. Выбор маршрута не должен зависеть от свободной трактовки текста движком.

## 2. Проверенные дефекты (волна 0)

Оба воспроизведены на текущем коде короткими проверками.

**Д1. Явное задание пропадает при `input: "none"`.** `BasicSchema.assemble` (`disput/basic-schema.js`, функция `assemble`) при `input: none` обнуляет и задание шага, и задание модели, включая написанные автором. Правило записано в инструкции (`basic-schema-guide.md`, строка про `task`), но нарушает принцип «набранное автором значение остаётся явным». Бессмысленно отправлять только унаследованное умолчание («доработай предыдущие ответы»).
Исправление: при `input: none` отправлять задание, если его источник — модель или шаг (`resolveFields(...).task.source` равен `model` или `round`); умолчания слоёв `pipeline` и `basic` не отправлять. Обновить строку в инструкции и тест.

**Д2. Порядок участников теряется на холсте.** Схема с последовательным раундом `B → A` после `BasicSchema.toCanvas` даёт стек `A, B` (порядок общего списка моделей). После сохранения порядок в схеме тоже будет чужим.
Движок уже выполняет участников в порядке схемы; дефект находится в преобразовании на холст. Исправление: стек каждого раунда строится отдельно — сначала включённые модели в порядке схемы, затем остальные модели холста. При обратной сборке схемы (`basicSchemaFromPage`) порядок включённых участников сохраняется. Тест: схема с `[B, A]` проходит Save → загрузка → Save с тем же порядком; последовательная отправка остаётся `B → A`.

Подтверждено чтением кода (исправлять в волнах ниже): в Auto этап считается завершённым при одном принятом ответе (`custom-engine.js`, условие `accepted.length && !semiAuto`); имя модели в шаге уникально (`validate`, «модель повторяется в шаге»); последующие шаги продолжают прежний чат модели (`results.js`, комментарий «later steps continue in that chat»).

### Волна 1 · вход, выход, обязательность, владелец

**1.1 Вход по ссылкам на этапы и участников.** *Закрывает: «выбор конкретных результатов прошлых этапов» и адресный вход участника.*
- Схема: `input` принимает массив ссылок на более ранние шаги: `["r1", "synth:a"]`. Допустим у раундов и синтезов. У синтеза без поля — `previous`, как сейчас; строковые `none` и `all` для синтеза по-прежнему запрещены. `validate` должен разрешить массив у синтеза, сохранив ограничения строковых значений. Ссылка на `final` и на текущий или поздний шаг — ошибка. Массив непуст, элементы уникальны.
- Дополнительно нужна ссылка на ответ конкретного участника этапа и необязательный `input` у участника текущего шага. Без индивидуального `input` используется вход шага; с ним — только явно выбранные источники. Формат адреса включает ссылку этапа и `id` участника (2.1); не склеивать их неоднозначной строкой, поскольку ссылки синтезов уже содержат двоеточие. До начала волны 1 зафиксировать формат и проверку адреса.
- Выбор ответа участника не равен выбору документа внутри его ответа. Если S08 выдаёт несколько документов одним ответом, можно передавать ответ целиком и указать нужный документ в задании S09/S10. Отдельный выбор частей ответа в этот пункт не входит.
- Обычные входы ссылаются только на более ранние шаги. Результат позднего шага при возврате передаётся отдельным механизмом обратной связи (3.3), без отмены этого ограничения.
- Проверка ссылок выполняется по полному `schema.steps`, до фильтрации выключенных шагов в `assemble`. Выключенный шаг остаётся допустимой ссылкой, но не даёт ответов.
- Сборка: `assemble` передаёт массив в движок и для синтезов; `toSettings` сохраняет вход синтеза. Сейчас обе функции обрабатывают вход только у раундов — это препятствие необходимо устранить.
- Движок: `normalizeSteps` сохраняет массив, `inputFor` берёт принятые ответы только указанных шагов в указанном порядке; шаг, выключенный, пропущенный или без принятых ответов, ничего не даёт и не заменяется другим шагом. Подпись ответа во входе содержит этап, участника-автора и название результата; после волны 3 — также заход. Ответы одного участника разных этапов не смешиваются.
- Страница: в окнах раунда и синтезов вариант «выбранные этапы» со списком более ранних шагов и ответов участников; индивидуальный вход доступен в настройках участника. Предпросмотр запроса показывает метку «ответы выбранных этапов появятся при запуске». Вход сохраняется через `basicSchemaFromPage`.
- Тесты: проверка схемы (неверная и дальняя ссылка, дубликат, пустой массив, ссылка на выключенный шаг), разрешение массива и запрет строк `none`/`all` у синтеза, `inputFor`, адрес участника и ошибка неизвестного участника, индивидуальный вход без примеси общего входа, круговой проход через холст для раунда, промежуточного и финального синтезов. После волны 2 проверить S19–S20 с адресными входами.

**1.2 Выход этапа заданной формы.** *Закрывает: «выход заданной формы».*
- Схема: у шага необязательный `output: { name, form, sections, strictLength }`.
  - `name` — название результата этапа; подписывает вход следующих этапов вместо «Раунд N»;
  - `form` — текст, который добавляется в запрос блоком «Формат ответа»;
  - `sections` — список заголовков, которые должны быть в ответе (регистр не важен, как подстрока строки ответа);
  - `strictLength` — если `true`, ответ с числом слов больше эффективного предела отклоняется (закрывает OI-3): берётся `maxWords` модели, а при его отсутствии — общий `run.maxWords`, включая умолчание Basic. Собранный `maxWords` модели может быть `null`; проверять длину против него нельзя. По умолчанию `false`: поведение прежнее.
- Движок: после проверки приёмки страницы дополнительная проверка по `sections` и `strictLength`. Причины отказа: `missing_section` (в тексте причины название раздела), `too_long`. Отказ даёт обычный повтор с исправлением в том же чате (`REASON_TEXT` расширяется).
- Проверка обязательных полей объектов — отдельный явный режим выхода. `form` и заголовки `sections` не гарантируют состав объектов из раздела 4.3 архитектуры. Для машинной проверки согласовать формат структурированного ответа и контракт обязательных полей до реализации; не пытаться проверять поля поиском слов в свободном тексте. Неверный формат или отсутствующее обязательное поле отклоняют ответ и дают повтор с конкретной причиной. Без включённого режима текстовый выход сохраняется. Смысл и достоверность содержимого оцениваются проверяющими моделями, gate или владельцем.
- Страница и холст: поля `output` в окнах раунда и синтезов; значения проходят `toCanvas` и обратно.
- Тесты: каждая причина отказа, повтор с исправлением, строгая длина с индивидуальным и общим пределами (ровно предел допустим), круговой проход для раунда и синтезов; значения по умолчанию не меняют поведение. Для структурированного режима: неверный формат, пропущенное обязательное поле, корректный объект и повтор с исправлением.

**1.3 Обязательное число ответов этапа.** *Закрывает: этап завершается с неполным составом ответов.*
- Схема: у шага `require`: `"any"` (умолчание, как сейчас), `"all"` или целое число N от 1 до числа включённых моделей выполняемого шага. Выключенные модели не входят в `all`. Выключенный целиком шаг не выполняется; его настройки сохраняются, а N проверяется относительно включённых моделей при включении шага.
- Движок: условие завершения шага — `accepted.length >= нужное число`. Меньше — шаг считается проблемным: решение владельца с вариантами «повторить / пропустить / остановить»; вариант «продолжить» предлагается только при выполненном условии. Обе автоматические ветки завершения в `run` проверяют порог, а не просто наличие принятого ответа.
- Отсутствующее или недопустимое решение при недостигнутом пороге завершает прогон через `StopRun('no_decision')`. Существующий fallback «есть хотя бы один принятый ответ → продолжить» не должен обходить `require`.
- Сохранить существующее поведение повтора: вызываются только не прошедшие приёмку модели; принятые ответы не отправляются заново и учитываются при последующей проверке порога.
- Страница: выбор в окнах раунда и синтезов («Сколько ответов нужно»); пауза показывает принятое и требуемое число ответов.
- Тесты: `all` при одном провале, N при N−1 принятых, выключенная модель не входит в `all`, отсутствующее и недопустимое решение ниже порога дают `no_decision`, повтор вызывает только неудавшихся; `any` без изменений, круговой проход для раунда и синтезов.

**1.4 Решение владельца на заданном этапе.** *Закрывает: «владелец на заданных этапах».*
- Схема: у шага `owner: "approve"`. Значение отсутствует — поведение прежнее.
- Движок: после шага с `owner: "approve"` решение владельца запрашивается даже в Auto и даже на последнем шаге. При выполненном `require` доступны продолжение, повтор неудавшихся при их наличии и остановка; ниже порога — повтор, пропуск или остановка, без продолжения.
- Отсутствующее или недопустимое решение даёт `StopRun('no_decision')`, даже если ответы приняты: обязательное подтверждение нельзя обойти существующим fallback. Последний шаг не завершает прогон успешно до подтверждения.
- В ручном режиме использовать одну паузу этапа, без второго такого же окна. Сохранить отдельную обработку содержательных вопросов `[[ASK]]` и передачу ответов владельца следующим шагам. Stop прерывает ожидание подтверждения.
- Страница: отметка на карточке и выбор в окнах раунда и синтезов («Спросить владельца после этапа»).
- Тесты: Auto с одним шагом `approve`, последний синтез с `approve`, `approve` вместе с недостигнутым `require`, отсутствующее и недопустимое подтверждение дают `no_decision`, одна пауза в manual, совместимость с `[[ASK]]`, Stop во время ожидания, круговой проход; без поля — как раньше.

### Волна 2 · участники и контекст

Перед реализацией — исследование: умеет ли транспорт открывать два независимых чата одной модели и начинать новый чат по команде. Результат исследования определяет форму 2.1 и 2.2; без него задания не ставятся.

**2.1 Участник отдельно от модели; авторство между этапами.** *Закрывает: «участник отождествляется с моделью» и потерю авторства.*
- Схема: у записи модели необязательный `id` (умолчание — `name`). Одинаковое `name` в шаге допустимо, если `id` разные. Внутри шага `id` уникален; одинаковый явно заданный `id` в разных шагах означает одного участника pipeline. Для такого участника модель согласована между шагами. Смена роли сама по себе не создаёт нового участника. Старые схемы сохраняют прежнее поведение.
- Авторство записывает движок, а не только модель в тексте ответа: источник включает этап, участника и заход. В S19 назначается рецензент, отличный от автора кандидата; в S20 результат передаётся исходному автору для доработки. Это должно выражаться схемой и адресными входами (1.1).
- Движок: ответы внутри шага ключуются по `id`, между шагами — по адресу «этап + участник + заход»; стабильный `id` связывает автора между этапами. Вход «до тебя» сохраняет авторство.
- Страница: отображение двух участников одной модели в стеке раунда.
- Тесты: два участника одной модели, сохранение автора S18→S20, отдельный рецензент S19, ошибочная повторная запись участника в шаге, несогласованная модель одного явно заданного `id`, адресные входы и круговой проход.

**2.2 Контекст чата.** *Закрывает: «изоляция ограничена новым запросом».*
- Схема: у шага `chat: "continue"` (умолчание) или `"new"`.
- Страница: при `new` перед отправкой открывается отдельный новый чат каждого участника. При `continue` продолжается чат этого участника, а не произвольный чат модели. Привязки чатов сохраняются для возобновления (4.2). Вложения уходят с первым сообщением в новый чат.
- Тесты: независимая рецензия не видит прежнего чата рецензируемого варианта.

### Волна 3 · проверка, маршрутизация и возвраты

**3.1 Gate.** *Закрывает: «проверка gate».*
- Схема: шаг `kind: "gate"` с `criteria` (список строк, не пуст), `models` (проверяющие), `pass`: `"all"` (умолчание) или `"any"`, `onFail`: `"stop"` (умолчание) или `"ask"`.
- Движок: строит запрос из критериев и входа шага. Последняя строка ответа — `ВЕРДИКТ: ПРОШЁЛ` или `ВЕРДИКТ: НЕ ПРОШЁЛ`; при провале перед ней обязательна строка `НЕ ВЫПОЛНЕНО: <критерий>`. Ответ без вердикта отклоняется (причина `no_verdict`) и повторяется с исправлением. Итог шага: событие `custom_gate`, причина остановки `gate_failed` при `onFail: "stop"`.
- Gate проверяет критерии и выдаёт вердикт. Выбор следующего шага описывается отдельно в 3.2; прежние `onFail: stop/ask` сохраняются. До реализации определить совместимость общего маршрута с `onFail/onPass`; конфликтующие инструкции схемы отклоняются.
- Страница и холст: gate отображается как вставка рядом с синтезом, с меткой; решение о форме карточки принимается в задании на реализацию, до кода показывается макет.
- Тесты: вердикт разных проверяющих, `pass: any/all`, отсутствие вердикта, остановка.

**3.2 Выбор маршрута.** *Закрывает: ветвления и условные переходы.*
- Маршрут — самостоятельный элемент схемы, доступный после обычного этапа, gate и этапа владельца. До реализации согласовать JSON-контракт: источники данных для выбора, условия, направления переходов, способ выбора и обработка неоднозначности.
- Кто выбирает: детерминированное правило, модель или владелец. Правило проверяет явно описанные данные; модель возвращает идентификатор одного из разрешённых маршрутов; владелец выбирает из заданных вариантов. Свободный текст модели не исполняется как условие или команда.
- Бизнес задаёт, какой исход ведёт к какому этапу. Движок проверяет существование целей и допустимость выбора. Если подходят несколько маршрутов или ни один, применяется явно заданный вариант: приоритет, маршрут по умолчанию, вопрос владельцу или остановка. Без такого разрешения неоднозначности — остановка с конкретной причиной, а не произвольный переход.
- S29 должен выбирать S26, S28 или S30; S27 — S24 либо S28. Несколько направлений можно реализовать цепочкой бинарных gates, если преобразование сохраняет условия и данные и явно записано в схеме.
- Движок выполняет шаги по указателю. Запись прогона сохраняет выбранный маршрут, источник решения и причину. Без маршрутизации схема выполняется по прежнему линейному порядку.
- Страница: видимые направления и условия связей; настройки выбора проходят схема → холст → схема.
- Тесты: два и три направления, выбор правилом/моделью/владельцем, неизвестный маршрут, несколько совпадений, отсутствие совпадений, явный приоритет/умолчание, отмена владельцем и круговой проход.

**3.3 Возвраты, обратная связь и актуальность результатов.** *Закрывает: возвраты на ранний этап без потери причины и подстановки старых результатов.*
- Возврат использует маршрут 3.2. `maxLoops: 1..5` обязателен для перехода назад; переход вперёд без него. Лимит считается по совершённым обратным переходам конкретного маршрута за весь прогон, включая возобновления. Весь граф проверяется на циклы: любой цикл должен содержать ограниченный переход. Превышение лимита останавливает прогон причиной `loop_limit`.
- Причина возврата и выбранные ответы инициирующего шага передаются во вход нового захода целевого этапа отдельно от обычных ссылок на ранние этапы. S10 после возврата из S12 получает текущие Findings и Remaining Unknowns S12. Источник обратной связи фиксируется в записи; первый заход её не получает.
- Движок ведёт `visit` для каждого захода и фактические зависимости результатов от входов. Автор задаёт область пересмотра; изменение результата делает зависимые результаты недействительными. Обратная связь сохраняется для целевого захода, даже если результат её источника попал в область пересмотра. Старые результаты доступны в истории, но не выдаются как актуальные входы.
- `inputFor` берёт актуальный принятый результат. После провала или пропуска повторного этапа запрещён автоматический fallback на старый заход. Зависимый шаг без обязательного актуального входа не отправляется модели: требуется восстановление входа либо явное решение, предусмотренное схемой.
- До реализации зафиксировать представление обязательных входов и области пересмотра. Контроль актуальности включается со схемой возвратов; старые линейные схемы сохраняют прежнее поведение.
- Запись прогона хранит заходы, обратную связь, зависимости и состояния актуальности. Бюджет промпта проверяется на каждом заходе.
- Тесты: S12→S10 с передачей замечаний, лимит циклов, первый/повторный заход, недействительные зависимые результаты, провал и пропуск повторного этапа без старого fallback, обязательный вход, круговой проход. Зависимость: после 3.2.

**3.4 Controlled change — пересмотр зафиксированного результата.**
- Для CHG в S19/S25/S26/S28/S30 автор описывает: что пересматривается, какие этапы повторяются, какие gates и подтверждения обязательны, куда продолжить после пересмотра. Движок исполняет этот путь через маршруты и контролирует актуальность по 3.3.
- Для пути S19→S10→G1→S19 нужно явно сохранить точку продолжения и после повторной проверки вернуться к ней. Не проходить S14–S18 автоматически, если маршрут пересмотра этого не требует. Если изменение затронуло их входы, зависимые результаты должны быть пересчитаны до использования.
- До реализации выбрать контракт фиксированной точки продолжения или сохраняемой точки возврата; ограничения циклов применяются и к этому пути. Необходимые решения владельца не заменяются вердиктом модели.
- CHG не исключается из схемы автоматически. Остановка и новый запуск возможны только как явно выбранный автором процесс; при переносе результатов их актуальность должна быть проверена.
- Тесты: CHG с повторным gate и продолжением в заданной точке, провал gate, отказ владельца, обновление зависимых результатов, ограничение цикла и запись причины изменения.

### Волна 4 · человек и продолжение

**4.1 Этап, где результат вводит человек.** *Закрывает: внешняя работа (этап 25) и результат владельца (этапы 1, 13, 22, 30).*
- Схема: шаг `kind: "owner"` с `task` (что нужно предоставить). Моделей нет.
- Движок и страница: окно владельца показывает задание; владелец вводит текст или прикладывает файл; введённое становится принятым ответом шага с меткой «Владелец». Используются существующие окно и канал вопросов владельцу.
- Тесты: отмена, пустой ввод, использование результата следующим шагом.

**4.2 Продолжение прогона.** *Закрывает: «нет возобновления сохранённого прогона».*
- Движок: `run` принимает `resume` — полное состояние исполнения: схему прогона, текущий шаг и фазу его исполнения, заходы, принятые ответы и незавершённые попытки, выбранные маршруты, счётчики обратных переходов, обратную связь, зависимости и актуальность результатов, точку продолжения CHG, ответы и ожидаемые решения владельца, привязки участников к чатам. Одних ответов и номера следующего шага недостаточно.
- Продолжение использует сохранённую схему; изменения текущего холста не подменяют её. Если чат недоступен, требуется явное восстановление контекста или решение владельца, а не продолжение в чужом чате. Уже подтверждённые действия не запрашиваются повторно.
- Страница: действие «Продолжить прогон» для записи, остановленной владельцем, ошибкой или перезагрузкой. Попытки в состоянии `sent` и `unknown` не отправляются повторно вслепую: сначала вопрос владельцу («ответ мог прийти: проверить / отправить заново / пропустить»).
- Тесты: продолжение после остановки владельцем, после перезагрузки и с неопределённой попыткой; остановка внутри возврата, сохранение лимита циклов и недействительности результатов, продолжение CHG, ожидание владельца, недоступный чат и неизменность схемы прогона.

## 5. Приёмка

После каждой волны архитектура из 30 этапов (формат Design System) прогоняется на своём участке; закрытые строки вычёркиваются из раздела 5.2 и из этой таблицы:

| Волна | Участок архитектуры | Что должно работать |
| --- | --- | --- |
| 0 | S01–S02 | Задание первого этапа доходит до модели; порядок участников сохраняется |
| 1 | S01–S05, S13/S30 | Вход S03 из S01 и S02 выбором; адресные входы; результаты названы; на S05 владелец подтверждает; S02 требует минимум двух ответов; проверка обязательных полей при явном включении; реальный бюджет входа S13/S30 |
| 2 | S18–S20 | Два эксперта на одной модели в разных чатах; отдельный рецензент; кандидат возвращается исходному автору с адресными входами |
| 3 | S12→S10, G1–G4, S27, S29, CHG S19 | Выбор всех маршрутов; замечания доходят при возврате; старые зависимые результаты не используются; ограниченные циклы; CHG повторяет gate и продолжает в заданной точке |
| 4 | S25, длинный прогон и возвраты | Владелец приносит результат исследования; после перезагрузки восстановлены заходы, циклы, актуальность, ожидания владельца и привязки чатов |

**Вместимость полной схемы.** До закрытия плана собрать архитектуру целиком со всеми техническими шагами: роли, gates, выбор маршрутов и шаги владельца. 30 бизнес-этапов могут дать больше 30 шагов Basic. Проверить ограничение `toCanvas` в 50 раундов, явно определить, какие виды шагов учитываются, и при необходимости обоснованно изменить лимит с проверкой холста. Число технических шагов и запросов выводится из полученной схемы, а не предполагается заранее.

**Объём контекста.** На S13 и S30 проверить реальные документы, а после возврата — вход вместе с обратной связью. При нехватке бюджета нельзя молча обрезать или исключать данные: остановить отправку с понятной причиной. Если нужна подготовка сокращённого входа, это отдельный явный этап схемы, сохраняющий необходимые данные.

**Граница ответственности.** Автор задаёт бизнес-условия маршрутов (включая Q10 архитектуры), состав выходов, участников и область пересмотра. Не все Q1–Q10 блокируют разработку механики: названия, переводы и недостающие бизнес-описания остаются ответственностью автора. Неопределённые условия переходов нельзя выдумывать при генерации схемы.

Приёмка волны: тесты Basic зелёные (известные падения вне Basic перечислены в [basic-developer.md](basic-developer.md)), схема участка проходит `validate`, открывается на холсте, сохраняется и загружается без потерь.

## 6. Отложено и отклонено

- **Реестр версионируемых артефактов — отклонён.** Для Basic результат этапа и есть артефакт. Версии появятся через заходы (`visit`) в волне 3.3; название результата — `output.name`.
- **Именованные входные данные запуска — отложено.** Сейчас запуск принимает один текст задачи. Вернёмся, когда схемам понадобится несколько входов.
- **Ограничение объёма: число запросов выводится из схемы.** Для Design System это поле показывается автору как вычисленное; отдельной доработки движка не требует.

## 7. Как ставить задания исполнителям

- Одно задание — одна возможность из раздела 3 (например, «1.3 Обязательное число ответов»). Волны не смешивать.
- Все пути в заданиях задаются относительно корня текущего чекаута репозитория; абсолютные пути конкретного компьютера не переносить. Документы Basic находятся в `docs/Pipeline scenarios/`.
- В задании: ссылка на этот документ и номер пункта, перечень файлов (`disput/basic-schema.js`, `disput/custom-engine.js`, `results/stage-card.js`, `results.js`, тесты), критерий готовности из раздела «Тесты» пункта и из раздела 5.
- Проверка владельцем после каждого задания: diff, тесты Basic, круговой проход схемы через холст, обновлённые документы Basic и CHANGELOG, версия в `manifest.json` и `package.json`.
