# Basic: старт здесь

Для модели или человека, который впервые пришёл в проект. После чтения понятно, что такое Basic и схема, как идёт прогон, что и кем создаётся на странице и какой документ читать дальше. Здесь **единственное** описание прогона; остальные документы на него ссылаются.

## Что такое Basic (коротко)

- **Basic** — движок pipeline и его оболочка на странице. Это единственный pipeline, который развивается.
- Движок не знает про вкладки и DOM; страница отправляет запросы, принимает ответы и рисует карточки.
- **Pipeline = схема**: JSON с шагами (раунды и синтезы), моделями, заданиями, входами и политикой запуска.
- Схема, сохранённая пользователем, лежит в хранилище как **запись**: схема плюс данные холста, которые из неё выводятся.
- **Шаблон Default** (единственный встроенный; запускается движком Basic) собирается из кода (`disput/pipeline-presets.js`) и в хранилище не лежит; правки шаблона живут до перезагрузки страницы.
- В коде Basic называется `custom` (`disput/custom-engine.js`, `runCustomFromPage`).

Пример схемы (шаблон A из `basic-schema-guide.md`): один раунд, где три модели отвечают независимо, затем итоговый синтез одной моделью; политика запуска `auto` (шаги идут без остановки):

```json
{
  "schemaVersion": 1,
  "origin": "user",
  "run": { "policy": "auto" },
  "steps": [
    { "ref": "r1", "kind": "round", "models": [{ "name": "Claude" }, { "name": "GPT" }, { "name": "Gemini" }] },
    { "ref": "final", "kind": "synthesis", "models": [{ "name": "Claude" }] }
  ]
}
```

Где физически лежат pipelines: одна запись `llmComparatorPipelines` в `chrome.storage.local`, внутри — словарь `pipelines` «имя → запись», порядок списка и вспомогательные поля; подробно — в `basic-developer.md`, раздел «Где схема хранится физически».

## Что мы строим и зачем

- Движок можно менять и дополнять, не ломая уже созданные схемы.
- Поэтому схема хранит только явные отличия от умолчаний Basic; умолчания — контракт, формат схемы версионируется (`schemaVersion`).
- Схему может написать человек или модель по самодостаточной инструкции `basic-schema-guide.md`.
- Причины решений и правила совместимости — в `basic-developer.md`, раздел «Правила схемы и решения».

## Словарь

| Термин | Что это |
| --- | --- |
| Basic | Движок pipeline и его оболочка на странице. В коде — `custom`. |
| Схема | JSON, описывающий pipeline: шаги, модели, задания, вход, политику запуска, предел длины. |
| Запись | Pipeline в хранилище (`chrome.storage.local`, ключ `llmComparatorPipelines`): схема и данные холста. |
| Шаблон | Готовая схема из кода (`disput/pipeline-presets.js`); сейчас единственный — Default. В хранилище не лежит. |
| Шаг | Элемент схемы: раунд или синтез. |
| Раунд | Шаг, в котором модели отвечают на задачу (или на вход из предыдущих шагов). Ref: `r1`, `r2`… |
| Синтез | Шаг, в котором одна модель сводит ответы. Промежуточный — `synth:<id>`, финальный — `final`. |
| `ref` | Уникальный идентификатор шага в схеме: `r1`, `synth:<id>`, `final`. |
| Задача | Текст, который пользователь вводит в поле модератора при запуске. |
| Задание | Инструкция шага (поле `task`), которую получают все модели шага. Задание не равно задаче. |
| Принятый ответ | Ответ модели, который прошёл приёмку движка (`accept`): не пустой, не обрезан, не ошибка. |
| Запрос исправления | Повторный запрос в том же чате, если ответ не принят. Всего до 2 попыток. |
| Транспорт | Общая отправка запросов и приём ответов моделей через фон расширения и вкладки моделей. Одинаков для всех pipelines. |
| Метка доставки | Служебная метка, которую транспорт использует для подтверждения доставки. Ответ, состоящий только из неё, не принимается. |
| Журнал доставки | Журнал событий отправки (`MessageDelivery`). События Basic имеют имена `custom_*`. |
| Политика запуска | `run.policy`: `auto` — шаги идут без остановки; `manual` — владелец подтверждает каждый шаг. |
| Шаг управления | Проверка (`gate`), маршрут (`route`) или владелец (`owner`) — control-шаг схемы. На холсте — карточка после раунда или другого шага (добавляется в окне этапа: поле «Шаг после этого этапа»). Окно проверки — в `basic-windows.md`, «Карточка проверки (gate)». |
| Окно настроек | Окно редактирования: модели (двойной клик по блоку), раунда (клик по значку R1, R2…: роль, порядок, вход, задание, порог, владелец, выход), ▶ (общие значения для всех шагов), промежуточного синтеза (двойной клик по его блоку) и финального синтеза (двойной клик по значку Final; вход, порог, владелец, выход сверху окна). |
| Карточка ответа | Блок в ленте: один ответ модели с подписью `Basic · Раунд N` или `Basic · Синтез после раунда N`; при другом id участника добавляется `участник <id>`, со второго захода — `заход N`. |
| Строка прогона | Компактная строка в ленте для проверки, маршрута и перехода, а также для реестра артефактов (см. `basic-windows.md`, «Лента прогона»). Не ответ модели. |

## Как идёт прогон

### Картина целиком

```text
Задача (поле модератора; если поле пусто — название записи)
   │
   ▼
Страница: собирает шаги из схемы, проверяет схему, создаёт запись о прогоне,
          показывает задачу в ленте
   │
   ▼
Движок (CustomEngine.run), для каждого шага:
   собрать запрос каждой модели
   │
   ▼
   Страница (send): дописать ограничения
   │
   ▼
   Транспорт: доставить запросы в чаты моделей, получить ответы
   │
   ▼
   Страница: карточка ответа в ленте (на каждый непустой ответ)
   │
   ▼
   Приёмка и движок: принят? нет — запрос исправления (до 2 попыток)
   │
   ▼
   После шага: события журнала, вопросы [[ASK]], пауза для владельца
   │
   ▼
   Вход следующего шага = принятые ответы
   │
   ▼ (после последнего шага)
Страница: уведомление с причиной, запись о прогоне, холст
```

| Участник | Где в коде | Отвечает за | Не знает о |
| --- | --- | --- | --- |
| **Движок** | `disput/custom-engine.js`, `CustomEngine.run` | что отправлять, кому и в каком порядке; что принять; когда повторить; когда остановиться; какой вход у следующего шага | вкладок, DOM, карточек, холста |
| **Страница** | `results.js`, `runCustomFromPage` | сборка и проверка шагов; дописывание ограничений длины и дисциплины; вызов транспорта; карточки ответа; уведомление; холст; запись о прогоне; окна паузы и вопросов | того, принят ли ответ по существу: это решает движок по правилам приёмки |
| **Транспорт** | `runModelBatch` в `results.js`; фон расширения (сообщение `START_FULLPAGE_PROCESS`); вкладки моделей | доставка запроса в чат модели, метка доставки, получение ответа | шагов и задачи прогона |
| **Приёмка** | `disput/debate-response-acceptance.js`, `DebateResponseAcceptance.evaluate` | технический приём текста: обрыв, маркеры обрезки, незавершённое окончание | шагов, задачи и владельца |

Метка доставки (строка `[[AO-…]]`, которую добавляет `MessageDelivery.prepare`) нужна транспорту, чтобы подтвердить доставку и конец ответа модели. Движок её не видит.

### Прогон по шагам

1. **Задача введена.** Пользователь пишет задачу в поле модератора и запускает прогон. `window.runPipeline` вызывает `startDebateFromPage`; для шаблона с `runner: 'custom'` вызывается `runCustomFromPage({ task })`. Если поле пусто, задачей становится название записи (`moderatorEntryText || pipelineNameText`).
2. **Запуск.** `runCustomFromPage` строит схему со страницы (`buildBasicRun`: `basicSchemaFromPage`, затем `BasicSchema.validate` и `BasicSchema.assemble`). Политика запуска (`run.policy`), общий предел длины (`run.maxWords`) и строгая длина (`run.strictLength`) берутся один раз на весь прогон.
3. **Сборка и проверка схемы.** Два случая, в которых запроса нет:
   - схема с ошибкой: уведомление `Basic: схема не запущена. <место: причина>` (ошибка);
   - нет ни одного раунда с моделью: `Basic: выберите модели хотя бы в одном раунде.` (предупреждение).
4. **Запись о прогоне и холст.** Создаётся запись о прогоне (`CustomRunRecord.createRun`), задача появляется в ленте как сообщение модератора, холст переходит в режим прогона: все шаги `pending`.
5. **Движок.** Вызывается `CustomEngine.run` с функциями страницы: `send`, `accept`, `decide`, `askOwner`, `parseAsks`, `onRequest`, `onResponse`, `onEvent`. Движок решает, что отправлять, и больше ничего не знает о странице.
6. **Сборка запроса.** Для каждого шага движок собирает запрос каждой модели (`buildPrompt`, см. «Что получает модель»). Перед отправкой проверяется бюджет `maxPromptChars`; при превышении прогон останавливается с причиной `context_full`, и запрос не уходит.
7. **Отправка.** Страница передаёт `sendParticipants(requests, meta)`: отправка идёт по участникам (ID), каждый участник — в свою вкладку (см. `basic-developer.md`, раздел «Транспорт участников»). `composeCustomPrompts` дописывает особенность модели, инструкцию длины, требования к содержанию и свои строки. `runModelBatch` отправляет запросы через транспорт. Для каждого непустого ответа страница сразу создаёт карточку ответа, даже если ответ потом не будет принят.
8. **Оценка ответа.** Движок (`judge`) проверяет каждый ответ. Пустой текст не принимается (`empty`; `token_only`, если транспорт подтвердил ответ без текста). Непустой текст проверяется функцией `accept`, то есть `DebateResponseAcceptance.evaluate`.
9. **Повторы.** Не принятый ответ получает запрос исправления в том же чате, всего до `DEFAULT_ATTEMPTS = 2` попыток на шаг. Повторов нет, если владелец закрыл этап.
10. **После шага.** Движок отправляет `custom_step`. При политике подтверждения (и при `auto`, если у шага нет принятых ответов) вызывается `decide`: окно паузы. Затем принятые ответы разбираются на строки `[[ASK: …]]`, и вопросы уходят в окно «Вопрос владельцу» (`askOwner`).
11. **Вход следующего шага.** Движок выбирает вход по полю `input` шага: `none`, `previous` или `all` (см. «Частые вопросы»), либо список источников. Устаревший результат (пересмотренный переходом) не даёт ответов: `previous` и `all` его не берут, и более ранний ответ вместо него не подставляется. Ссылка `{ artifact, version }` берёт содержимое одного объявленного артефакта (`latest` — последняя актуальная версия линии, либо точная версия). Список берётся в своём порядке: ref шага — все принятые ответы шага по порядку участников; `{ step, participant }` — ответ одного участника. Каждый ответ подписан шагом, участником и заходом (`визит 1`). Обязательный источник (`required: true`) без принятого ответа останавливает прогон до первого запроса шага. Необязательный без ответа не даёт текста и не заменяется ближайшим ответом.

После последнего шага движок возвращает результат, страница закрывает запись о прогоне и холст и показывает уведомление с причиной. Подробности: раздел «Что видит пользователь в конце прогона».

### Что получает модель

Части запроса, их порядок и полный пример сборки — в `basic-schema-guide.md`, раздел 6. Если у шага есть `output`, в запрос добавляется блок «Формат ответа»: `form`, названия разделов и, для `json`, обязательные поля; блок входит и в собственный запрос модели (`promptTemplate`) и в предпросмотр. Метка доставки добавляется транспортом последней строкой и в запрос движка не входит.

### Ошибки до первого запроса

Прогон не начинается, если схема содержит то, что движок пока не исполняет или не может исполнить однозначно. Ошибка называет шаг (его `ref`, а не номер в отфильтрованном списке) и поле; ни один запрос не отправляется:

- `unsupported_kind` — вид шага, который движок не знает (раунд, синтез, проверка, маршрут и владелец исполняются);
- `unsupported_field` — `output.format` кроме `json`; `chat` не `continue` и не `new`; `chat: "new"` без транспорта по участникам; 
- `invalid_field` — маршрут без `select`, с `by` не `rule`/`model`/`owner`, с пустым или повторяющимся списком вариантов, с условием не в правиле или без него, с `conflict` вне правила, с моделью не одной или без задания; `output` не является объектом; `require` не `any`, `all` или целое число от 1 до числа участников; `owner` не `approve`; шаг владельца без `task` или с моделями; проверка без `criteria`, с `pass` не `all`/`any` или `onFail` не `stop`/`ask`/переход; переход (`onPass`, `onFail`) с лишним полем, без ровно одного из `goto`/`stop`/`return`, с `maxLoops` не от 1 до 5, пустой причиной `stop`, либо назад без `maxLoops`;
- `unknown_target` — `goto`, `resumeAt`, шаг в `invalidate` или выбор маршрута указывают на шаг, которого нет в исполняемом плане (например, выключенный);
- `unbounded_cycle` — цикл из переходов без ограниченного перехода (проверка `BasicSchema.graph`); в тексте ошибки — путь цикла;
- `invalid_input` — вход, который не является значением `none`, `previous`, `all` или списком; ревизия (`revisionOf`), которой нет во входе участника; у синтеза — только `previous`; источник в списке, который не является ref шага или `{ step, participant }`; участник, которого нет в шаге-источнике; шаг-источник не раньше этого шага;
- `participant_transport_required` — два участника одной модели в шаге без callback `sendParticipants`; страница его передаёт, поэтому при запуске со страницы не возникает;
- `participant_duplicate` — два участника в шаге с одним ID.

Продолжение (`resume`, движок): прогон идёт от сохранённой точки по схеме из снимка. Завершённые шаги не отправляются заново; принятые участники текущего шага остаются; счётчики переходов, стек, замечания и актуальность не сбрасываются; решение владельца, уже принятое и сохранённое, не спрашивается снова; открытое окно владельца спрашивается снова с теми же данными. Запрос, отправка которого не подтверждена (`unknown`), не уходит сам: владелец решает «отправить заново» (новая попытка) или «пропустить» (только для этой попытки; порог шага не обходит). Переход, уже применённый до перезагрузки, не применяется второй раз. Если в схеме продолжения нет шага сохранённого состояния — `resume_mismatch`; состояние без снимка — `resume_invalid`.

Ошибка `checkpoint_failed` (во время прогона) — состояние не сохранено; прогон прерывается с ошибкой, следующий запрос и переход не выполняются. Ошибка `provide_owner_required` (до запуска) — в схеме есть шаг владельца, а страница не передала окно ответа (страница передаёт окно текста, см. «Окна решений»). Ошибка `invalid_owner_result` (во время прогона) — ответ владельца не текст и не объект файла, файл без имени, MIME, размера или ссылки, либо `blob:` ссылка; прогон прерывается с ошибкой.

Ошибка `missing_content` (не причина остановки) возникает, когда текст принятого ответа, на который ссылается реестр, не найден в `getText`: прогон прерывается с ошибкой, а не продолжается с пустым документом.

### Приём ответа и повторы

Причины отказа (`CustomEngine.REASON_TEXT`) попадают в текст запроса исправления: «Твой предыдущий ответ {причина}. Дай ответ на задание полностью.». Исключение — причина `empty` (текста нет вообще, в том числе отказ транспорта): повтор отправляет тот же запрос заново, без исправления.

| Причина | Текст в исправлении | Когда возникает в Basic |
| --- | --- | --- |
| `empty` | пустой | ответ пуст, транспорт не подтвердил ответ (`judge`) |
| `token_only` | без текста | ответ пуст, но транспорт подтвердил ответ (`status` `SUCCESS`, `attribution` `verified`) (`judge`) |
| `truncation_marker` | оборван | в тексте `[...truncated]`, незакрытый блок кода или многоточие без завершения (`evaluate`) |
| `incomplete_ending` | оборван на середине | последняя строка длиннее трёх слов, без знака конца, не список и не заголовок, и `completion` не `complete` (`evaluate`) |
| `closed_by_owner` | раунд закрыт владельцем | транспорт закрыт владельцем (`closeReason: moderator_closed`) и текста нет (движок) |
| `too_long` | длиннее допустимого (с числом слов) | `output.strictLength: true` или `run.strictLength: true` (для шага без своего `strictLength`): слов больше предела модели, а без него — общего `run.maxWords` (`BasicOutput.checkAnswer`) |
| `missing_section` | не содержит раздел (с названием раздела) | заголовок из `output.sections` не найден ни в одной строке ответа; регистр не важен |
| `invalid_output` | не в формате ответа | `output.format: json`: ответ не один JSON-объект и не один блок ```json без текста вокруг |
| `missing_field` | без обязательного поля (с указателем) | поле из `output.requiredFields` отсутствует; `null` считается присутствующим |
| `missing_artifact` | без объявленного артефакта (с ID и указателем) | объявленный указатель не найден в ответе: ни один артефакт ответа не регистрируется |
| `invalid_route` | не назвал вариант маршрута | ответ модели маршрута не один JSON-объект `{"route": "<id>"}` с ID варианта (с перечнем допустимых); после повторов решает владелец |
| `no_verdict` | без вердикта | ответ проверки (`gate`) не заканчивается строкой «ВЕРДИКТ: ПРОШЁЛ» или «ВЕРДИКТ: НЕ ПРОШЁЛ», а при провале нет строки «НЕ ВЫПОЛНЕНО: …»; для JSON — нет `verdict` `pass`/`fail` или нет непустого `unmet` при `fail` (`BasicControl.verdictOf`) |

Причины `too_short` и `error_output` в пути Basic не возникают: пустой текст уже отсечён `judge`, а страница не передаёт проверку ошибок. Причины выхода (`too_long`, `missing_section`, `invalid_output`, `missing_field`, `missing_artifact`) проверяются после технической приёмки, в этом порядке; исправление называет конкретный раздел, указатель или предел. Принятые соседи не отправляются заново. `no_verdict` — пакет P06.

Правила повторов:

- Автоматически на шаг отправляются до 2 попыток: первый запрос и одно исправление (`DEFAULT_ATTEMPTS`).
- Исправление уходит тем моделям, которые не приняты, в тот же чат. Транспорт открывает новую страницу модели только при первой отправке в прогоне.
- Бюджет проверяется перед каждой отправкой, включая исправление. Превышение даёт `context_full` до отправки. Транспорт проверяет бюджет ещё раз, уже с меткой доставки.
- Повтор по решению владельца («Повторить») шлёт полный исходный запрос, а не исправление. Номера попыток продолжаются, так что после повтора на шаг может прийтись больше двух попыток.
- Каждая попытка записывается отдельно, предыдущая не переписывается (запись о прогоне).

### Продолжить прогон

Функция `resumeCustomFromPage` (`results.js`) продолжает последний прогон этого pipeline с сохранённого места. Она не берёт текущий холст: схема — та, с которой прогон начинался (`snapshot.schema`). Прогон без снимка (запись прежней версии, или прогон, не дошедший до первой точки сохранения) не продолжается: уведомление объясняет причину, запись остаётся для просмотра. Предложение продолжить показывается строкой ленты «Прогон остановлен…» с кнопкой «Продолжить» (`offerResumeLine`) после прогона, который не дошёл до конца (остановка, ошибка), если у записи есть снимок; кнопка в строке вызывает `resumeCustomFromPage` и после нажатия исчезает. Отдельной кнопки на панели нет. Файлы нового прогона сохраняются в его записи (до 1,5 МБ); если они не поместились, запись помечается и продолжить такой прогон нельзя — уведомление называет файлы. Привязка чата каждого участника записывается в запись прогона, пока идёт запрос (раз в секунду), поэтому остановка до первого ответа её не теряет; участник, который уже отправлял в этом прогоне и не имеет привязки, при продолжении получает отказ `participant_chat_lost`, а не чужую вкладку. После перезагрузки страницы строка с кнопкой не восстанавливается (не проверено, остаётся ли вообще текст строки в ленте). Запись из JSON Disput Flow (`customRun`) самодостаточна для просмотра, но продолжить прогон из файла нельзя: импорта записи прогона в интерфейсе нет.

Окна решений (общий компонент `results/choice-dialog.js`, `ChoiceDialog.ask`; отмена — `null` и остановка прогона `stopped`):

- **Неизвестный запрос** (отправка была в полёте при перезагрузке): «Проверить ответ» (только чтение чата участника, ничего не отправляется; найденный ответ проходит обычную приёмку, остальные остаются неизвестными и владельца спрашивают снова), «Отправить заново» или «Пропустить» (только эта попытка; порог шага не обходится). Ответ считается найденным, только если он заканчивается меткой доставки этого запроса; без метки проверка отвечает «нет ответа», с неизвестной меткой — «неоднозначно».
- **Выбор маршрута** (`by: owner`, или `conflict: owner`): по кнопке на каждый вариант, подпись — `label` варианта из схемы.
- **Ответ владельца** (шаг `owner`): текст в поле. Выбор файла пока не реализован: файловый ответ владельца страница не принимает, и окно не даёт его выбрать.

Окно «Продолжить» и вопросы паузы — см. «Пауза, вопросы и Stop».

### Пауза, вопросы и Stop

**Когда спрашивают владельца.** Политика `run.policy` (в коде `semiAuto`):

- `manual` (значение по умолчанию): окно паузы после каждого шага, кроме последнего шага, в котором набран нужный порог ответов и нет непринятых.
- `auto`: окно паузы только тогда, когда порог ответов шага (`require`, по умолчанию «любой принятый») не выполнен.

Подтверждение владельца (`owner: "approve"` на шаге): окно паузы после шага в любом режиме, в том числе в `auto` и на последнем шаге. Без решения или с недопустимым решением прогон завершается `no_decision`, даже когда ответы приняты. В `manual` это та же пауза шага, вторая не открывается. Вопросы `[[ASK]]` идут отдельно.

Порог (`require`): `any` — один принятый ответ; `all` — все включённые участники; число N — N принятых. Ниже порога «Продолжить» не предлагается; шаг решает владелец: повторить, пропустить или остановить. Принятые ответы не заменяют порог: без решения ниже порога прогон останавливается с `no_decision`.

**Окно паузы** (`askCustomDecision`):

| Ситуация | Текст окна | Кнопки | Результат |
| --- | --- | --- | --- |
| Есть принятые ответы | «<шаг>: принято N[ из M][, без ответа: модель (причина)]. Что дальше?» (M — порог шага) | «Продолжить» (`continue`); «Повторить без ответа» (`retry`, если есть непринятые); «Stop» (`stopped`) | шаг идёт дальше только с принятыми ответами |
| Порог не выполнен, принятые есть | то же окно с N из M; «Продолжить» не показывается (движок отвергает его ниже порога) | «Повторить» (`retry`); «Пропустить шаг» (`skip`); «Stop» (`stopped`) | ниже порога «продолжить» не выполняется: прогон завершится `no_decision` |
| Принятых нет | «<шаг>: нет принятых ответов (…). Что дальше?» | «Пропустить шаг» (`skip`); «Повторить» (`retry`); «Stop» (`stopped`) | пропущенный шаг ничего не передаёт дальше |

**Вопросы `[[ASK]]`.** Строка `[[ASK: вопрос || вариант 1 || вариант 2 [|| несколько]]]` в принятом ответе задаёт вопрос владельцу (до 3 вопросов, от 2 до 5 вариантов; разбор в `DebateStageMarkers`). Окно «Вопрос владельцу» даёт кнопки:

- «Ответить и продолжить» — нужен хотя бы один выбранный вариант, иначе появляется уведомление. Ответы попадают в запросы следующих шагов как «Ответы владельца на вопросы».
- «Продолжить без ответа» — идёт дальше без ответа и пишет событие `owner_answer` с `skipped: true`.
- «Позже» — идёт дальше без ответа, событие не пишется.

Инструкция о формате `[[ASK]]` моделям **намеренно не добавляется**: страница не передаёт её движку (поле «вопрос владельцу» из окон настроек удалено). Разбор строк `[[ASK]]` в принятых ответах при этом работает: чтобы модель задала вопрос, опишите формат в задании шага.

**Stop.** Есть три способа остановить прогон:

| Где нажат Stop | Причина в уведомлении | Что происходит |
| --- | --- | --- |
| Кнопка «Остановить Basic» на панели | `cancelled`, «остановлено пользователем» | прерывается текущий запрос; транспорт получает `CANCEL_PIPELINE_RUN`; фон останавливает процессы без закрытия вкладок (`closeTabs: false`) |
| «Stop» в окне паузы | `stopped`, «остановлено владельцем» | ничего не отправлено; вкладки не трогаются |
| Прерывание во время ожидания ответа или вопроса | `cancelled` | окно вопроса закрывается; прогон завершается |

Откат вкладок не делается: ответы остаются в ленте, вкладки моделей остаются открытыми. Прогон завершается с тем, что уже приняли: принятые ответы текущего шага сохраняются. Уведомление с причиной показывается в любом случае, холст получает `CANCELLED`, запись о прогоне закрывается с причиной, уведомление выводится как предупреждение.

Причины остановки (`CustomEngine.STOP_TEXT`):

| Причина | Текст | Когда |
| --- | --- | --- |
| `steps_done` | все шаги пройдены | все шаги прошли |
| `context_full` | промпт не помещается в бюджет | запрос больше предела до отправки |
| `stopped` | остановлено владельцем | «Stop» в окне паузы |
| `cancelled` | остановлено пользователем | Stop на панели или прерывание |
| `missing_input` | обязательный вход не получен, запрос не отправлен | обязательный источник списка без принятого ответа; адрес источника — в событии `custom_end` журнала (`stopDetail`) |
| `no_decision` | нет решения владельца, а порог шага не выполнен | решение отсутствует или не из предложенных вариантов; принятые ответы не заменяют порог |
| `route_not_found` | ни один вариант маршрута не подошёл, иначе не задан | правило маршрута без совпадений и без `otherwise` |
| `route_ambiguous` | подошло несколько вариантов маршрута | правило маршрута с несколькими совпадениями при `conflict: stop` (по умолчанию) |
| `invalid_route_input` | источник правила маршрута не читается как JSON | условие правила читает ответ, который не JSON; решение не принимается |
| `loop_limit` | лимит переходов исчерпан | переход, который уже сделан `maxLoops` раз, не совершается; `stopDetail` — ключ счётчика «ref:случай» (`onPass`, `onFail` или ID варианта) |
| `return_missing` | возврат без сохранённой точки продолжения | `return`, а стек продолжений пуст |
| `unsupported_input` | двоичный файл владельца не передаётся тексту модели; запрос не отправлен | вход шага ссылается на двоичный файл, который владелец передал (его имя и тип — в `stopDetail`) |
| `gate_failed` | проверка не пройдена | `onFail: stop` и вердикт проверки «не пройдена» (или шаг пропущен владельцем); невыполненные критерии — в `stopDetail` |

Ошибка вне движка не имеет причины из этой таблицы: страница пишет `Pipeline: error (…)` (ошибка), событие `custom_end` с `stopReason: 'error'`, запись о прогоне закрывается с `error`. В этом случае уведомления с причиной остановки нет.

### Что создаётся на странице

| Объект | Когда создаётся | Что внутри |
| --- | --- | --- |
| Сообщение модератора | сразу после записи о прогоне, до первого запроса | текст задачи |
| Карточка ответа модели | на каждый непустой ответ каждого захода, сразу после получения ответа, до приёмки | текст ответа; роль `Basic · Раунд N` или `Basic · Синтез после раунда N` (с `участник <id>` и `заход N`, если нужны); `pipelineRunId`, `pipelineRoundId` (`s<n>`, со второго захода `s<n>v<заход>`), id транспорта. Исправление того же захода (попытка 2 и далее) заменяет текст этой карточки, а не добавляет новую: в ленте один ответ модели на заход, и он тот, с которым прогон продолжается. Карточка сохраняет звёздочку и утверждение. Если исправления не было или оно не принято, карточка показывает последнюю попытку; первый непринятый текст остаётся в записи о прогоне |
| Уведомление | в конце, в том числе после Stop; не показывается при ошибке вне движка | `Basic: <причина>.` (информация при `steps_done`, иначе предупреждение); причина из `STOP_TEXT`; при отсутствии принятых ответов добавляется «Принятых ответов нет.» |
| Запись о прогоне | при старте; затем сохраняется по мере попыток (с задержкой около 600 мс) и при завершении | в `chrome.storage.local` под ключом `customRunRecord.<runId>`, индекс `customRunRecords.index`; ошибка записи в точке сохранения состояния останавливает прогон (`checkpoint_failed`), отложенная запись попыток только логируется |
| Холст | при старте (все шаги `pending`), во время прогона и в конце | статусы шагов и `lifecycle`, см. «Холст во время прогона» |

### Что видит пользователь в конце прогона

1. Результат прогона — карточки ответов последнего шага: принятые и непринятые ответы шага показаны карточками сразу после шага, так же как ответы любого другого шага.
2. Отдельной карточки итога нет: она повторяла бы те же принятые ответы.
3. В конце показывается уведомление `Basic: <причина>.` с текстом из `STOP_TEXT`; деталь остановки (`stopDetail`, например адрес `missing_input`) — в скобках после причины: информационное при `steps_done`, иначе предупреждение.
4. Если ни один шаг не принял ответ, к уведомлению добавляется «Принятых ответов нет.», например: `Basic: остановлено владельцем. Принятых ответов нет.`

Текст уведомления собирает `basicRunNotice` в `results.js`.

«Принятые ответы последнего шага» — это `result.answers`: принятые ответы последнего шага, у которого они есть. Пропущенный шаг и шаг без принятых ответов не учитываются, поэтому пустой список означает, что ни один шаг не принял ответ. Принятые ответы используются как вход следующего шага во время прогона. После прогона их видно в карточках шагов и в записи о прогоне.

### Холст во время прогона

Состояние холста: `customRunProgress` = `{ lifecycle, stages[{ plannedStageId, status }] }`.

- Статусы шага: `pending` (до запуска) → `running` (при каждой отправке шага) → `completed` (у шага есть принятые ответы или владелец пропустил шаг). Шаг без принятых ответов остаётся `running`, пока владелец не решит.
- `lifecycle`: `RUNNING` при старте; в конце `COMPLETED`, только при `steps_done`; при любой другой причине остановки `CANCELLED`; при ошибке вне движка `FAILED`.

Соответствие `ref` шага из схемы и id на холсте (`plannedIdOfRef` в `results.js`):

| `ref` в схеме | id на холсте | Пример |
| --- | --- | --- |
| `r<N>` (раунд) | `canvas-r<N>` | `canvas-r2` |
| `synth:<id>` (промежуточный синтез) | `<id>` — часть после `synth:` | `planned-working-synthesis-after-canvas-r1` |
| `final` (финальный синтез) | `planned-final-synthesis` | — |

### События журнала и запись о прогоне

Все события уходят в журнал доставки (`MessageDelivery.batchEvent`). Страница добавляет `pipelineRunId` ко всем событиям движка. Поле `pipelineRunId` — UUID прогона.

| Событие | Кто | Поля |
| --- | --- | --- |
| `custom_start` | движок, в начале | `semiAuto`, `maxAttempts`, `taskChars`, `steps[]` (`step`, `ref`, `label`, `order`, `input`, `models`) |
| `custom_answer` | движок, на каждый ответ каждой попытки | `step`, `label`, `model`, `attempt`, `input`, `accepted`, `reason`, `status`, `transportRequestId`, `promptChars` |
| `custom_step` | движок, когда шаг завершил попытки | `step`, `label`, `accepted` (число), `failed` (число) |
| `custom_decision` | движок, после ответа на окно паузы | `step`, `action` (`continue`, `retry`, `skip`, `stop`) |
| `custom_transition` | движок, при каждом переходе из `onPass`/`onFail`, маршрута и при остановке переходом | `from` (ref шага), `case` (`onPass`, `onFail`), `action` (`goto`, `return`, `stop`), `to` (ref шага), `count` (номер перехода по счётчику), `maxLoops`; при `stop` — `reason` |
| `custom_route` | движок, после выбора варианта маршрута | `step`, `ref`, `visit`, `case` (ID варианта или `otherwise`), `by` (`rule`, `model`, `owner`), `reason` (`rule`, `otherwise`, `conflict_first`, `conflict_owner`, `model`, `owner`, `invalid_route`) |
| `custom_owner` | движок, на каждый ответ владельца | `step`, `ref`, `visit`, `accepted` (`false` — ответ отклонён, владельца спрашивают снова), `reason` |
| `custom_unknown_check` | движок, при проверке ответа неизвестного запроса (кнопка «Проверить ответ») | `step`, `label`, `participant`, `attempt`, `status` (`found`, `no_answer`, `ambiguous`, `chat_unavailable`), `reason` |
| `custom_gate` | движок, после шага-проверки (`gate:<id>`) | `step`, `ref`, `pass` (итог вердиктов), `unmet` (невыполненные критерии), `rule` (`all` или `any`) |
| `custom_end` | движок, в конце; страница — при ошибке | `stopReason`, `steps` (число шагов с результатом); при ошибке — `stopReason: 'error'` и `error` |
| `owner_answer` | страница, на ответ или пропуск в окне вопросов | `stage` (подпись шага — при ответе и при пропуске), `answered`, `asked`; при пропуске `skipped: true` |

Идентификатор этапа транспорта — `custom:<runId>:s<n>` (`n` — номер шага, с единицы), на попытку — `custom:<runId>:s<n>:a<attempt>`.

**Запись о прогоне** (`disput/custom-run-record.js`, `CustomRunRecord`) хранит прогон целиком:

- задача и шаги;
- каждая попытка: шаг, модель, номер попытки, `retryOf`, `state` (`sent`, `done`, `not_sent` или `unknown`), запрос, входы с источниками, отправленный текст, ответ, принят ли он, причина и статус;
- `stopReason` и время начала и конца.
- Версия 2 (`version: 2`): реестр артефактов (`artifacts`: одна запись на версию, ссылка на текст ответа, без копии) и снимок состояния (`snapshot`) — схема, с которой запущен прогон, точка продолжения, визиты, маршруты, счётчики, стек, замечания, зависимости и ответы владельца. Снимок пишется до каждого внешнего действия (до запроса — с ID попытки), после ответа, до и после решения владельца, до перехода, после пересчёта актуальности и в конце прогона (checkpoint). В снимке — принятые ответы завершённых шагов (по ссылкам на тексты), принятые участники текущего шага, решения владельца, открытое окно владельца. Запись версии 1 читается и экспортируется, но без снимка не продолжается (`resumable: false`).
- Ключ попытки: шаг, участник, визит, номер попытки и фаза (ответ или маршрут). Завершённая попытка не переписывается.
- Привязки чатов участников (`chatBindings`: participantId → модель, шаг, визит, ID запроса транспорта) сохраняются в снимке, возвращаются после перезагрузки и не теряются при продолжении. Список без привязок читается как пустой объект.
- Тексты, на которые ссылаются попытки, реестр и снимок (поля `…Ref`), не удаляются при сохранении.

Тексты хранятся один раз, по отпечатку. Записи лежат в `chrome.storage.local` и ограничены 4 МБ: при переполнении удаляются самые старые прогоны целиком — до записи нового состояния, а если хранилище расширения отказывает по квоте (его занимают и другие данные расширения), старые прогоны удаляются по одному и запись повторяется; прогон, который не помещается даже один, останавливается ошибкой `checkpoint_failed` с размером записи. После перезагрузки попытка, отправленная, но не завершённая, получает состояние `unknown` и никогда не отправляется повторно. В JSON-экспорте диагностики Disput Flow запись попадает в поле `customRun`, журнал доставки — в поле `delivery`.
