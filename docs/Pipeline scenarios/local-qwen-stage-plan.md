# Локальная Qwen 3.5 как стадия пайплайна: программа внедрения

Дата: 2026-11-13. Основание: три опроса (21 ответ GPT, Claude, Qwen, Z.ai, Kimi, Gemini, DeepSeek, Perplexity) об использовании локальной Qwen 3.5 (Ollama, `qwen3.5:4b-mlx` / `qwen3.5:9b-mlx`, http://127.0.0.1:11434) в оркестраторе. Экспорт опросов: `Downloads/Saved sessions/Применение локальной Qwen 3.5 LLM.json`.

## Выводы анализа

На чём сошлись почти все модели (≥6 из 8):

1. **Локальная модель — не источник фактов и не автор итогового текста.** Её работа: извлекать, сжимать, классифицировать, разбирать в JSON, проверять по источнику, форматировать. Факты приходят только из входного текста или от облачной модели.
2. **Стадия — типизированный узел с контрактом**: вход и выход по схеме (JSON), детерминированный валидатор на коде, один повтор при провале, затем эскалация. Свободного текста между стадиями нет.
3. **Режим инференса**: `think:false` всегда, кроме проверочных стадий на 9B (бюджет рассуждений ≤1.5–2K токенов). Фиксированный `num_ctx` (4B — 8K), жёсткий `num_predict` на каждую стадию, `keep_alive` 15–60 мин, прогрев одним пустым вызовом, отмена через разрыв запроса.
4. **Одна резидентная модель.** Первая версия — только 4B. 9B подключается после статистики: только для классов задач, где она чинит ≥30% провалов 4B (правило Kimi). Пинг-понг 4B↔9B внутри одного прогона запрещён: перезагрузка весов 2–15 с.
5. **Проверка по источнику, а не «по знаниям»**: каждое утверждение с дословной цитатой, цитата сверяется кодом подстрокой; вердикты `supported / contradicted / not_in_source / unknown`; «не знаю» — валидный ответ. Числа, даты, имена, отрицания при сжатии передаются дословно.
6. **Пайплайн корректен без локальной модели**: у каждой локальной стадии есть обход (код-эвристика или прямой путь в облако). Выключенная Ollama не ломает прогон.

Главные расхождения и принятые решения:

- *Черновик локально → доработка в облаке*: отвергнуто (большинство против — облако якорится на ошибках черновика, а облачное сообщение тратится полностью в любом случае). Допустим только скелет без фактов.
- *Self-consistency (2–3 локальных прогона)*: отвергнуто — ошибки малой модели коррелируют, это ложная уверенность.
- *Эмбеддинги отдельной моделью*: отложено — сначала кодовые методы (точный поиск, BM25), эмбеддер только после замера прироста.
- *Vision (скриншоты вкладок)*: только как fallback, когда DOM недоступен; при конфликте чисел побеждает DOM. Отложено на поздний этап.

## Как это ложится на Basic

Принцип проекта сохраняется: приложение не принимает решений, этапы — запрос модели, User или действие приложения, маршрут выбирает человек. Локальная модель входит **как обычная модель — участник раунда**, которого автор схемы ставит в нужное место. Движок (`CustomEngine`) не меняется: он не знает про вкладки и точно так же не будет знать про Ollama.

Готовая инфраструктура, которую переиспользуем:

| Что нужно по анализу | Что уже есть в Basic |
| --- | --- |
| JSON-контракт стадии | `output.format: json`, `output.requiredFields`, `output.sections` |
| Один repair при провале | запрос исправления в том же чате, `DEFAULT_ATTEMPTS = 2` |
| Эскалация при провале | окно решения User (повторить / пропустить / Stop) |
| Вердикт проверки | приёмка `invalid_audit_verdict`, роль аудита |
| Журнал стадий | события `custom_answer`, `custom_step` с `promptChars`, `attempt`, `reason` |
| «Чат» участника для исправлений | привязки чатов участников; для локального участника — история сообщений прогона в памяти |

Задел уже написан в копии «AutoOrchestr Qwen Local» (ветка `experiment/qwen-local-hint`): `disput/local-model.js` (окно `LocalModel`: `post` на `/api/chat`, выбор модели, правило `declarativeNetRequest` для заголовка Origin), `results/local-model-select.js`, вкладка Local LLM, тесты. Этап 1 — перенос и доработка этого модуля, а не написание с нуля.

## Этапы внедрения

Порядок — по соотношению эффект/усилия, согласованному всеми тремя опросами: транспорт → контракт → первые стадии → метрики → выбор модели → остальное.

### Этап 1. Транспорт «Qwen Local» — локальный участник раунда

Локальная модель появляется в списке моделей холста как участник «Qwen Local». Страница маршрутизирует его запросы не во вкладку, а в Ollama.

- Перенести из копии `disput/local-model.js` (ядро: `post`, выбор модели, `allowOwnOrigin`) в основной чекаут; в `manifest.json` добавить `http://127.0.0.1:11434/*` и `declarativeNetRequestWithHostAccess`.
- Точка маршрутизации — транспорт страницы (`results.js`, путь `sendParticipants` / `runModelBatch`): участник с моделью «Qwen Local» уходит в `LocalModel.post`, остальные — как раньше, через фон и вкладки. Движок и схема не меняются.
- Параметры вызова: `think:false`; `num_ctx` 8192; `num_predict` из предела шага (`maxWords` → токены, по умолчанию 1024); `temperature` 0.2; `keep_alive` «15m»; `format` — JSON-схема, когда у шага `output.format: json`.
- Прогрев: при старте прогона, в схеме которого есть «Qwen Local», — один пустой вызов (загрузка весов до первого шага).
- Ответ транспорта совместим с приёмкой: метка доставки дописывается в хвост ответа локально, статус `SUCCESS`, `completion: complete` — весь существующий конвейер приёмки и исправлений работает без изменений.
- Исправления «в том же чате»: история сообщений участника копится в памяти прогона и передаётся в `/api/chat` целиком; блоки рассуждений в историю не попадают.
- Stop и отмена: разрыв fetch (AbortController) по «Остановить Basic» и решению User.
- Ollama не отвечает → отказ участника `not_sent` с ясной причиной («локальная модель недоступна»), дальше обычное окно решения User. Никакой тихой подмены.

Готово, когда: схема с раундом из «Qwen Local» проходит прогон целиком — карточка ответа, приёмка, исправление, запись о прогоне, экспорт кнопкой Basic; при выключенной Ollama прогон останавливается штатно.

### Этап 2. Контракт стадии

- Шаблоны заданий для локальных стадий — фиксированный текст со слотами (не свободная формулировка): инструкция, затем помеченный блок данных. Данные страницы и чужие ответы — в блоке «данные», инструкции — вне его (защита от инъекций из текста).
- Выход всегда по `output`: `json` + `requiredFields` для разборов и вердиктов; обычный текст с `sections` — для дайджестов.
- Правило цитат: утверждение в выходе локальной стадии сопровождается дословной цитатой источника; проверка цитаты — поиск подстроки в приёмке выхода (код, не модель). Вывод с сущностью (число, имя), которой нет в источнике, не принимается.
- Повтор: существующий запрос исправления с текстом причины; после двух попыток — существующее окно User. Отдельного механизма эскалации не строим.

Готово, когда: стадия с невалидным JSON получает исправление и принимается со второй попытки; подделанная цитата отклоняется.

### Этап 3. Первые три стадии в схемах

Выбраны те, где локальная модель окупается в наших прогонах (облачное сообщение = десятки секунд + квота + лимит вставки):

1. **Дайджест раунда** — одна «Qwen Local» между облачными раундами: сжимает принятые ответы предыдущего раунда до заданного объёма (экстрактивно: отобрать и процитировать, не пересказывать; числа и имена дословно). Прямая борьба с `context_full` и лимитами вставки в веб-UI. Окупается, когда вход следующего раунда превышает ~2–4K токенов.
2. **Разбор ответа в JSON** — извлечение из облачного ответа структуры (список тезисов, таблица сравнения, поля опросника) для следующих шагов или реестра артефактов.
3. **Проверка по источнику** — раунд-аудит: сверить утверждения облачного ответа с входным документом, вердикт `supported / contradicted / not_in_source / unknown` по каждому, с цитатами. Решение по вердикту принимает User шагом `owner`, как и сейчас.

Для каждой стадии — готовый блок схемы в `basic-schema-guide.md` (пример с заданием, `output` и входами), чтобы схему с локальной стадией могла написать модель по существующей инструкции.

Готово, когда: эталонная схема «облачный раунд → дайджест → облачный синтез → локальный разбор» проходит на реальной задаче, и дайджест сокращает вставку минимум вдвое без потери чисел и имён (проверка кодом по списку сущностей источника).

### Этап 4. Телеметрия и метрики

- В события `custom_answer` локального участника добавить тайминги Ollama: `load_duration`, `prompt_eval_count`, `eval_count`, `total_duration`.
- Считать по экспорту прогона: доля локальных ответов, принятых с первой попытки; p50/p95 времени стадии; сэкономленные облачные сообщения (сколько раундов стали локальными); доля эскалаций к User.
- Пороги из анализа для контроля: стадия окупается, если экономит ≥0.3 облачного вызова в среднем; время локальной стадии не больше времени, которое она экономит.

Готово, когда: по JSON кнопки Basic видно время и исход каждой локальной стадии без дополнительных инструментов.

### Этап 5. Выбор 4B/9B по данным

- Собрать golden set из существующих записей прогонов: 30–60 реальных входов для трёх стадий этапа 3, включая ловушки «ответа нет в источнике».
- Вечерний прогон 4B против 9B (и `think` on/off для проверки по источнику) скриптом по `/api/chat`; сравнение — кодом по контрактам (валидность JSON, цитаты, вердикты), не на глаз. Задел — `qwen-compare` из копии.
- Решение по правилу: класс стадии остаётся на 4B, если отстаёт от 9B менее чем на 5 п.п. при двукратной скорости; 9B включается для класса, только если чинит ≥30% провалов 4B. Резидентной остаётся одна модель; выбранная для стадии пишется в задание схемы, не переключается на лету.

### Этап 6. Дежурные функции вне схем

Наблюдение за зависшими вкладками, за модальными окнами и подсказки User на шаге `owner` (уже в копии: `createStallWatch`, `observeTab`, `ownerHint`) — отдельная линия, не стадии пайплайна. Переносится после этапов 1–4 отдельным решением: сначала наблюдение и журнал без действий, как решено 2026-11-09.

### Этап 7. Отложенное — только после замеров этапов 4–5

- Vision: скриншот вкладки модели как fallback, когда детектор ответа сломан (чтение состояния страницы, поиск поля ввода). Кроп по месту, длинная сторона ~1024 px.
- Сжатие длинной истории прогона в карточки фактов.
- Спекулятивная подготовка следующей стадии, пока облако отвечает (только лёгкие вызовы 4B: GPU делит память с браузером).
- Эмбеддинги отдельной моделью — только если точный поиск и BM25 измеримо не хватают.

## Чего не делать (антипаттерны из всех трёх опросов)

- Локальные ответы «из головы»: факты, оценки, фактчек облака без опоры на текст источника.
- Итоговый текст пользователю от локальной модели; переписывание облачного ответа свободным текстом.
- `think:true` по умолчанию и на стадиях, где ждут первый результат.
- Две резидентные модели или смена модели внутри прогона.
- Цепочка из многих локальных вызовов там, где хватает одного с общей JSON-схемой; LLM там, где справится код (regex, обрезка, точный поиск).
- Тихая подмена облачного ответа локальным при недоступности облака.
- Передача блоков рассуждений или сырых DOM-дампов в историю чата.

## Риски

1. **9B на 16 ГБ рядом с браузером** — все 7 моделей первого опроса сомневаются. Ответ: первая версия только 4B, 9B — по golden set.
2. **`think:false` может протекать** в отдельных сборках Ollama (DeepSeek). Ответ: приёмка режет вывод по контракту; проверить на этапе 1.
3. **Малая модель путает «противоречит» и «нет в источнике»** (Kimi). Ответ: ловушки в golden set до включения стадии проверки в рабочие схемы.
4. **Качество дайджеста**: потеря критичной детали хуже, чем длинный вход. Ответ: контроль сущностей кодом (этап 3) и обход — при провале передавать исходный текст.
