# Локальная Qwen 3.5 как стадия пайплайна: программа внедрения

Дата: 2026-11-13, уточнено по совместному разбору с Codex 2026-11-13. Основание: три опроса (21 ответ GPT, Claude, Qwen, Z.ai, Kimi, Gemini, DeepSeek, Perplexity) об использовании локальной Qwen 3.5 (Ollama, `qwen3.5:4b-mlx` / `qwen3.5:9b-mlx`, http://127.0.0.1:11434). Экспорт опросов: `Downloads/Saved sessions/Применение локальной Qwen 3.5 LLM.json`.

## Принципы

1. **Локальная модель — не источник фактов и не автор итогового текста.** Её работа: извлекать, сжимать, разбирать в JSON, проверять по источнику. Факты — только из входного текста или от облачной модели.
2. **Стадия — обычный участник раунда Basic** с выходом по контракту шаблона; провал решается существующими механизмами (исправление, окно решения User). Автоматических fallback и развилок нет — Basic линеен.
3. **Режим инференса**: `think:false`; завершение проверяется по ответу сервиса (`done_reason`); жёсткий `num_predict`; `keep_alive`; отмена разрывом запроса. Одна резидентная модель — 4B; 9B — только по результатам сравнения на наших задачах.
4. **Никакого молчаливого усечения**: консервативный предел полного запроса с резервом, при превышении — явный отказ до отправки. Точный расчёт токенов из символов не заявляется; настройка `num_ctx` на этап пользователю не выдаётся.
5. **Пилот — один сценарий с подтверждённым потребителем.** Польза доказывается сравнением прогона с локальным этапом и без него: качество итога, общее время (с прогревом и исправлениями), число вмешательств User. Синтаксически правильный JSON пользы не доказывает.

## Как это ложится на Basic

Маршрут выбирает человек, приложение решений не принимает: локальная модель входит как обычный участник раунда, движок не меняется. Переиспользуем готовое, с честными границами:

| Нужно для локальной стадии | Что есть в Basic | Граница |
| --- | --- | --- |
| Контракт выхода | `output.format: json`, `output.requiredFields` | `requiredFields` проверяет только наличие полей; `sections` с `json` несовместимы. Типы и допустимые значения задаёт JSON-схема Ollama `format`, которую поставляет шаблон стадии |
| Один повтор при провале | запрос исправления в том же чате, `DEFAULT_ATTEMPTS = 2` | «тот же чат» локального участника — история сообщений по `participantId` в пределах прогона; новый прогон её не наследует; восстановление из записи прогона — пункт проверки реализации |
| Эскалация | окно решения User (повторить / пропустить / Stop) | новых окон и обязательных остановок не добавляем |
| Журнал и запись | события `custom_*`, запись о прогоне, экспорт Basic | локальный участник обязан попадать в карточки, события, запись и экспорт наравне с облачным |

Существующий аудит (`parseAuditVerdict`: только `pass` / `issues_found`) не расширяем; сценарий проверки по источнику, если будет выбран, — обычный JSON-раунд с результатами по утверждениям и проверкой своего шаблона.

Задел — копия «AutoOrchestr Qwen Local» (ветка `experiment/qwen-local-hint`): `disput/local-model.js` (`post` на `/api/chat`, выбор модели, правило `declarativeNetRequest` для Origin), выбор модели в интерфейсе, тесты. Переносится ядро; `excerpt` для подсказок в обработку артефактов не переносится. Текущий `post` возвращает только текст — доработка: вернуть `done_reason` и тайминги.

## Этапы

### Этап 1. Транспорт «Qwen 4B» — локальный участник раунда

- Перенести ядро `disput/local-model.js` из копии; в `manifest.json` — `http://127.0.0.1:11434/*` и `declarativeNetRequestWithHostAccess`.
- Маршрутизация в транспорте страницы (`results.js`, путь `sendParticipants` / `runModelBatch`): участник «Qwen 4B» уходит в `LocalModel`, остальные — как раньше. Движок и формат схемы не меняются. Карточки, события журнала доставки, запись о прогоне, экспорт и Stop (разрыв fetch) работают для локального участника как для обычного.
- Честное завершение: `done_reason` из ответа Ollama первичен; исчерпание `num_predict` (`length`) — обрыв, идёт в существующую приёмку как незавершённый ответ, не `SUCCESS`. Метка доставки дописывается только после непустого завершённого ответа — как адаптация к существующему конвейеру приёмки и исправлений.
- Параметры вызова: `think:false`; `num_predict` с запасом от предела слов шага (слова и токены — разные величины); `temperature` 0.2; `keep_alive` 15m; `format` — JSON-схема шаблона при `output.format: json`.
- Предел запроса: консервативный предел полного запроса (вход + инструкция + история + резерв на выход), при превышении — явный отказ до отправки, штатная остановка. Без молчаливой обрезки.
- Доступность до расходования облачных запросов: если в схеме есть «Qwen 4B», при старте прогона — проверка Ollama (она же прогрев); не отвечает → прогон не начинается, уведомление по образцу «выберите модели». Отказ посреди прогона → `not_sent` («локальная модель недоступна») и обычное окно решения User.

Готово, когда: схема с раундом «Qwen 4B» проходит прогон целиком (карточка, приёмка, исправление, запись, экспорт Basic); при выключенной Ollama прогон не начинается с ясным уведомлением; `done_reason: length` приводит к исправлению, а не к принятию обрыва.

**Состояние 2026-11-13: этап 1 реализован в копии «AutoOrchestr Qwen Local» (ветка `experiment/qwen-local-hint`, версия 2.81.1036), по решению владельца — не в основном чекауте.** Покрыто unit-тестами (включая `length` → обрыв, недоступность Ollama, Stop, предел запроса); живой прогон с Ollama ещё не выполнялся — он совмещается с выбором пилотного сценария (этап 3). Известные границы: история участника не переживает перезагрузку страницы (отказ `participant_chat_lost`, новый чат работает); входные файлы участнику не передаются (файлы шага/участника останавливают прогон до старта); кнопка модели есть только на `pipeline_panel.html`.

### Этап 2. Контракт шаблона стадии

Каждый шаблон стадии — тройка: текст задания (фиксированный, со слотами; данные страницы и чужие ответы в помеченном блоке — снижение риска инъекций, не гарантия), блок `output`, JSON-схема для Ollama `format`. Проверка смысла привязана к конкретному шаблону; универсального языка контрактов не строим. Правило цитат: `supported` / `contradicted` — с дословной цитатой, проверяемой кодом подстрокой; `not_in_source` / `unknown` — без цитаты (доказательство отсутствия не выдумывается).

### Этап 3. Первый рабочий сценарий

**Первый полезный сценарий предстоит подтвердить на записи реального прогона.** Основание выбора: что User делал вручную, какие данные уже были у приложения, какой результат потребляет следующий этап или User. Кандидаты (одна строка, не три поставки): дайджест раунда против лимитов вставки; разбор облачного ответа в JSON для названного потребителя; проверка утверждений по источнику. В просмотренных экспортах прогонов остановок `context_full` нет, поэтому дайджест обоснования по умолчанию не имеет; правдоподобный, но лишний вердикт проверки может отвлечь User — польза любого кандидата доказывается только сравнением по п. 5 принципов.

Для выбранного сценария — готовый блок схемы в `basic-schema-guide.md`, чтобы схему с локальной стадией могла написать модель по существующей инструкции.

### Этап 4. Телеметрия

В события локального участника — `done_reason` и тайминги Ollama (`load_duration`, `prompt_eval_count`, `eval_count`, `total_duration`). По экспорту прогона видно: исход и время каждой локальной стадии, доля принятых с первой попытки.

### Этап 5. Выбор 4B/9B по данным

После подтверждённого сценария: golden set из записей реальных прогонов (включая ловушки «ответа нет в источнике», если выбран сценарий проверки), прогон 4B против 9B скриптом по `/api/chat` (задел — `qwen-compare` из копии), сравнение кодом по контракту шаблона. 9B — только если 4B сценарий не тянет; резидентной остаётся одна модель, выбор фиксируется в схеме.

### Этап 6. Дежурные функции вне схем

Наблюдение за зависшими вкладками и модальными окнами, подсказки User, чтение скриншота вкладки при сломанном детекторе ответа (`createStallWatch`, `observeTab`, `ownerHint` из копии) — отдельная линия, не стадии пайплайна. Переносится отдельным решением: сначала наблюдение и журнал без действий, как решено 2026-11-09.

## Чего не делать (отвергнуто при анализе и совместном разборе)

- Факты «из головы» локальной модели; фактчек облака без опоры на текст источника; итоговый текст пользователю от локальной модели.
- Черновик локально → доработка в облаке: облако якорится на ошибках черновика, а облачное сообщение тратится полностью в любом случае.
- Self-consistency (несколько локальных прогонов с голосованием): ошибки малой модели коррелируют.
- `think:true` по умолчанию; две резидентные модели; смена модели внутри прогона.
- Автоматический fallback «при провале взять исходный текст» — в линейном Basic нереализуем без развилок; провал решает User существующими окнами.
- Требование «все числа и имена дословно при двукратном сжатии» — внутренне противоречиво; сохранение чисел, отрицаний и условий — инструкция шаблона, качество проверяется сравнительными прогонами.
- LLM там, где справится код; цепочка локальных вызовов там, где хватает одного.

## Риски

1. **9B рядом с браузером не влезает в память** — первая версия только 4B.
2. **`think:false` может протекать** в отдельных сборках Ollama — проверить на этапе 1; контракт выхода режет лишнее.
3. **Малая модель путает «противоречит» и «нет в источнике»** — ловушки в golden set до включения сценария проверки в рабочие схемы.
4. **Цитата доказывает происхождение, не правильность вывода** — потерю отрицания, условия или единицы ловит только сравнение итогов прогонов, поэтому пилот без сравнения «с/без» не считается подтверждённым.
