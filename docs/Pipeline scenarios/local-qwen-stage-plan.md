# Локальная Qwen 3.5 как стадия пайплайна: программа внедрения

Дата: 2026-11-13. Основание: три опроса (21 ответ GPT, Claude, Qwen, Z.ai, Kimi, Gemini, DeepSeek, Perplexity) об использовании локальной Qwen 3.5 (Ollama, `qwen3.5:4b-mlx` / `qwen3.5:9b-mlx`, http://127.0.0.1:11434). Экспорт опросов: `Downloads/Saved sessions/Применение локальной Qwen 3.5 LLM.json`.

## Принципы (согласие почти всех моделей опросов)

1. **Локальная модель — не источник фактов и не автор итогового текста.** Её работа: извлекать, сжимать, разбирать в JSON, проверять по источнику. Факты — только из входного текста или от облачной модели.
2. **Стадия — узел с контрактом**: выход по схеме, валидатор на коде, один повтор при провале, затем решение User. Утверждения — с дословными цитатами источника; «не знаю» (`not_in_source`, `unknown`) — валидный ответ. Числа, даты, имена — дословно.
3. **Режим инференса**: `think:false`; фиксированный `num_ctx`; жёсткий `num_predict`; `keep_alive`; прогрев; отмена разрывом запроса. Одна резидентная модель — 4B; 9B — только по результатам сравнения на наших задачах (этап 5).
4. **Пайплайн корректен без локальной модели**: выключенная Ollama останавливает прогон штатно, а не ломает его.

## Как это ложится на Basic

Принцип проекта сохраняется: маршрут выбирает человек, приложение решений не принимает. Локальная модель входит **как обычная модель — участник раунда**; движок не меняется. Переиспользуем готовое:

| Нужно для локальной стадии | Уже есть в Basic |
| --- | --- |
| JSON-контракт выхода | `output.format: json`, `output.requiredFields`, `output.sections` |
| Один повтор при провале | запрос исправления в том же чате, `DEFAULT_ATTEMPTS = 2` |
| Эскалация | окно решения User |
| Вердикт проверки | приёмка `invalid_audit_verdict`, роль аудита |
| Журнал стадий | события `custom_answer`, `custom_step` |

Задел — копия «AutoOrchestr Qwen Local» (ветка `experiment/qwen-local-hint`): `disput/local-model.js` (`post` на `/api/chat`, выбор модели, правило `declarativeNetRequest` для Origin), выбор модели в интерфейсе, тесты. Этап 1 — перенос, не написание с нуля.

## Этапы

### Этап 1. Транспорт «Qwen Local» — локальный участник раунда

- Перенести ядро `disput/local-model.js` из копии; в `manifest.json` — `http://127.0.0.1:11434/*` и `declarativeNetRequestWithHostAccess`.
- Маршрутизация в транспорте страницы (`results.js`, путь `sendParticipants` / `runModelBatch`): участник «Qwen Local» уходит в `LocalModel.post`, остальные — как раньше. Движок и формат схемы не меняются.
- Параметры: `think:false`; `num_ctx` 8192; `num_predict` из предела шага (по умолчанию 1024); `temperature` 0.2; `keep_alive` 15m; `format` — JSON-схема при `output.format: json`. Прогрев пустым вызовом при старте прогона со схемой, где есть «Qwen Local».
- Совместимость с приёмкой: метка доставки дописывается в хвост локально, статус `SUCCESS`, `completion: complete` — конвейер приёмки и исправлений работает без изменений. «Тот же чат» для исправлений — история сообщений участника в памяти прогона.
- Stop — разрыв fetch. Ollama не отвечает → `not_sent` («локальная модель недоступна») и обычное окно решения User.

Готово, когда: схема с раундом «Qwen Local» проходит прогон целиком (карточка, приёмка, исправление, запись, экспорт Basic); при выключенной Ollama прогон останавливается штатно.

### Этап 2. Контракт стадии

- Задания локальных стадий — фиксированный шаблон со слотами: инструкция отдельно, данные (текст страницы, чужие ответы) в помеченном блоке. Защита от инъекций из данных.
- Проверка цитат кодом: дословная цитата ищется подстрокой в источнике; не нашлась — ответ не принят, идёт исправление.

Готово, когда: невалидный JSON чинится исправлением со второй попытки; подделанная цитата отклоняется.

### Этап 3. Первые три стадии в схемах

Выбраны по месту, где локальная модель окупается в наших прогонах (облачное сообщение = десятки секунд + квота + лимит вставки):

1. **Дайджест раунда** — между облачными раундами: сжать принятые ответы предыдущего раунда до заданного объёма экстрактивно (отобрать и процитировать, не пересказывать). Прямая борьба с `context_full` и лимитами вставки в веб-UI.
2. **Разбор ответа в JSON** — извлечение структуры из облачного ответа для следующих шагов или реестра артефактов.
3. **Проверка по источнику** — раунд-аудит: вердикт `supported / contradicted / not_in_source / unknown` по каждому утверждению, с цитатами; решение принимает User шагом `owner`.

Для каждой — готовый блок схемы в `basic-schema-guide.md`, чтобы схему с локальной стадией могла написать модель по существующей инструкции.

Готово, когда: эталонная схема «облачный раунд → дайджест → облачный синтез» проходит на реальной задаче, и дайджест сокращает вставку минимум вдвое без потери чисел и имён (сверка кодом по списку сущностей источника).

### Этап 4. Телеметрия

В события `custom_answer` локального участника — тайминги Ollama (`load_duration`, `prompt_eval_count`, `eval_count`, `total_duration`). По экспорту прогона должно быть видно: исход и время каждой локальной стадии, доля принятых с первой попытки, насколько дайджест сократил вставку.

### Этап 5. Выбор 4B/9B по данным

Golden set из существующих записей прогонов: 30–60 реальных входов трёх стадий, включая ловушки «ответа нет в источнике». Прогон 4B против 9B скриптом по `/api/chat` (задел — `qwen-compare` из копии), сравнение кодом по контрактам. 9B включается только для стадии, где 4B ошибается заметно чаще; резидентной остаётся одна модель, выбор фиксируется в схеме, на лету не переключается.

### Этап 6. Дежурные функции вне схем

Наблюдение за зависшими вкладками и модальными окнами, подсказки User, чтение скриншота вкладки при сломанном детекторе ответа (`createStallWatch`, `observeTab`, `ownerHint` из копии) — отдельная линия, не стадии пайплайна. Переносится после этапов 1–4 отдельным решением: сначала наблюдение и журнал без действий, как решено 2026-11-09.

## Чего не делать (отвергнуто при анализе опросов)

- Факты «из головы» локальной модели; фактчек облака без опоры на текст источника; итоговый текст пользователю от локальной модели.
- Черновик локально → доработка в облаке: облако якорится на ошибках черновика, а облачное сообщение тратится полностью в любом случае.
- Self-consistency (несколько локальных прогонов с голосованием): ошибки малой модели коррелируют.
- `think:true` по умолчанию; две резидентные модели; смена модели внутри прогона.
- LLM там, где справится код (regex, обрезка, точный поиск); цепочка локальных вызовов там, где хватает одного с общей JSON-схемой.

## Риски

1. **9B рядом с браузером не влезает в память** — первая версия только 4B.
2. **`think:false` может протекать** в отдельных сборках Ollama — проверить на этапе 1; контракт выхода режет лишнее.
3. **Малая модель путает «противоречит» и «нет в источнике»** — ловушки в golden set до включения стадии проверки в рабочие схемы.
4. **Дайджест теряет критичную деталь** — сверка сущностей кодом; при провале дальше идёт исходный текст.
