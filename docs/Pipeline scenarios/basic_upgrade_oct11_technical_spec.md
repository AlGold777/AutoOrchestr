## 1. Результат работы

Basic должен исполнять архитектурную методику: адресные входы, несколько документов одного ответа, независимые участники одной модели, проверка выхода, подтверждение владельца, gates, выбор маршрутов, возвраты с замечаниями, controlled change и продолжение сохранённого прогона.

Старые схемы продолжают работать. Исключение — исправление явно заданного `task` при `input: none` (0.1 плана). Не переписывать транспорт других pipelines, не добавлять бизнес-описания за автора и не угадывать условия маршрутов.

30 бизнес-этапов могут быть представлены несколькими техническими шагами каждый. Gate и выбор маршрута — разные операции. Реестр артефактов находится внутри записи прогона; содержимое хранится в результатах один раз.

## 2. Сколько агентов и почему

Нужно **7 ролей: 6 исполнителей и 1 интегратор приёмки**. Это 7 ответственных за участки, а не 7 одновременных процессов. Максимум полезного параллелизма — 3 агента после фиксации общих контрактов. При ограничении среды в 4 слота вместе с координатором это также допустимо.

| Агент | Участок | Основные файлы | Карточка задания |
| --- | --- | --- | --- |
| A01 | Схема, валидация, сборка и совместимость | `disput/basic-schema.js` | [A01](basic-upgrade-agents/A01-schema.md) |
| A02 | Данные движка, выход, приёмка, реестр | `disput/custom-engine.js`, чистые вспомогательные модули | [A02](basic-upgrade-agents/A02-data-engine.md) |
| A03 | Участники и транспорт чатов | адаптер Basic в `results.js`, транспорт при необходимости | [A03](basic-upgrade-agents/A03-participants-transport.md) |
| A04 | Gate, маршрутизация, циклы, CHG | `disput/custom-engine.js`, чистые вспомогательные модули | [A04](basic-upgrade-agents/A04-routing.md) |
| A05 | Запись прогона, человек, checkpoint и resume | `disput/custom-run-record.js`, движок и адаптер страницы | [A05](basic-upgrade-agents/A05-record-resume.md) |
| A06 | Холст, настройки, предпросмотр, Save/Import/Export | `results.js`, `results/stage-card.js`, вёрстка страницы | [A06](basic-upgrade-agents/A06-canvas-ui.md) |
| A07 | Интеграция, документация, итоговая приёмка | тесты интеграции, документы Basic, архитектурные fixtures | [A07](basic-upgrade-agents/A07-integration.md) |

Два агента не редактируют одновременно один файл. `custom-engine.js`: A02 → A04 → A05. `results.js`: A03 → A05 → A06. A01 остаётся владельцем `basic-schema.js`; другие агенты передают ему запросы на уточнение контракта, не меняют файл самостоятельно. Версию и CHANGELOG меняет один агент для текущего самостоятельного изменения.

Разбиение мельче создаст больше конфликтов в общих файлах. Разбиение крупнее заставит одного исполнителя одновременно менять схему, транспорт, страницу и восстановление, затруднив проверку.

## 4. Общий контракт схемы

### 4.1 Совместимость

- `schemaVersion: 1` сохраняется: добавляются необязательные поля и виды шагов, поддержка старых значений не удаляется.
- Неизвестные поля остаются ошибками с полным путём, включая вложенные объекты.
- Умолчания Basic берутся только из `BasicSchema.DEFAULTS`. Не заводить вторую копию старых умолчаний в UI или движке.
- Отсутствующее поле сохраняет прежнее поведение; явно заданное значение сохраняется даже при совпадении с умолчанием. Пустой список ссылок — ошибка; `input: none` — явный пустой вход.
- Проверять ссылки по полному `schema.steps` до удаления выключенных участников/шагов из исполняемого плана. Сохранять источник и исходный индекс шага. Owner и route без моделей не удалять фильтром `models.length`.
- Любое поле проходит validate → assemble → normalizeSteps → настройки/холст → Save → Import → schema без потери смысла.
- Старые `r1..rN`, `synth:<id>`, `final` сохраняются. Новые виды: `gate:<id>`, `route:<id>`, `owner:<id>`; ID содержит латинские буквы, цифры, `_`, `-`, непустой. `final` остаётся последним шагом. К нему допустим переход вперёд, но обычная ссылка на его результат запрещена.
- Старое ограничение 50 относится к раундам. Gate, route, owner и synthesis в этот счётчик не включать. Если архитектурный fixture требует больше 50 раундов, A07 фиксирует фактическое число и обоснование изменения лимита; не повышать заранее.

### 4.2 Шаг и участник

У шага сохраняются существующие поля. Добавляются `output`, `require`, `owner`, `chat`; для gate — `criteria`, `pass`, `onFail`, `onPass`; для route — `select`; для owner — контракт ввода из раздела 8.

`models[].id`: непустой ID, уникален внутри шага. Без поля ID равен `name`. Один явно заданный ID между шагами означает одного участника; его `name` должен совпадать. Разные ID одной модели — разные участники. Проверка совпадения модели по ID не должна ломать старые схемы без явных ID.

`models[].input`: тот же формат, что у шага. Если задан, полностью заменяет общий вход участника; данные предыдущих участников последовательного раунда остаются отдельным блоком «ответы до тебя». В параллельном раунде этот блок пуст. Для независимости и полного исключения чужих ответов использовать параллельный порядок и новый чат.

`require`: `any` по умолчанию, `all` или целое 1..число включённых участников выполняемого шага. Выключенные не учитываются. При выключенном целом шаге сохранить настройку; проверять числовой порог при включении. Gate дополнительно применяет `pass` к вердиктам принятых проверяющих.

`owner: approve`: после достаточного числа принятых ответов необходимо подтверждение владельца даже в auto и на последнем шаге. Отсутствие/невалидность решения — `no_decision`. В manual одна пауза, а не две. `[[ASK]]` остаётся отдельным содержательным каналом.

`chat`: `continue` по умолчанию или `new`, применяется к каждому участнику. Continue означает чат participant ID, new — новый чат при новом заходе шага; повтор исправления внутри захода продолжает этот новый чат, не создаёт следующий.

### 4.3 Вход: точный JSON

JSON-примеры здесь и ниже — фрагменты контрактов; ссылки в них должны быть объявлены в полной схеме. Их нельзя запускать как самостоятельный pipeline.

`input` — существующая строка `none`, `previous`, `all` либо непустой массив источников. Для synthesis строковые none/all по-прежнему запрещены; массив разрешён. Источник в массиве:

```json
[
  "r1",
  { "step": "r2", "participant": "expert-B", "required": true },
  { "artifact": { "step": "r3", "participant": "expert-A", "id": "map" },
    "version": "latest", "required": true },
  { "artifact": { "step": "r3", "participant": "expert-A", "id": "map" },
    "version": { "step": "r3", "participant": "expert-A", "visit": 1 }, "required": false }
]
```

- Строка этапа означает все его принятые ответы в порядке участников. Объект `step/participant` — только ответ указанного участника. Объект artifact — только конкретный документ.
- `required` по умолчанию false, чтобы сохранить поведение старых ссылок на выключенные шаги. Отсутствующий необязательный источник не даёт текста. Обязательный источник без актуального результата останавливает отправку: `missing_input`, с адресом. Запрос модели не отправлен.
- `version: latest` означает последнюю актуальную версию выбранной линии артефакта; объект версии — точный адрес. Для artifact поле version обязательно, чтобы модель не угадывала.
- Обычные источники должны быть определены раньше шага-потребителя. Дубликат полного адреса в массиве — ошибка, даже если запись различается только required.
- Порядок массива сохраняется. Авторство, шаг и visit присутствуют в подписи источника. Отсутствующий ответ не заменяется ближайшим успешным.
- Поле participant проверяется среди объявленных участников источника, в том числе выключенных. Не объединять источники строкой с двоеточиями.
- Перед первым запросом валидатор проверяет существование шага, участника и объявления артефакта; во время исполнения — наличие версии, содержимого и актуальность.

## 5. Выход, приёмка и простой реестр

### 5.1 Output

```json
{
  "output": {
    "name": "Результаты аудита",
    "form": "Сформируй исправленную карту и замечания",
    "sections": ["Карта", "Замечания"],
    "strictLength": true
  }
}
```

`form` — инструкция. `sections` — непустые строки; каждый заголовок ищется как подстрока строки без учёта регистра. `strictLength` использует индивидуальный `maxWords`, иначе `run.maxWords` через DEFAULTS. Ровно предел разрешён. Счёт слов — непустые части после разделения по пробельным символам; один общий helper для тестов/движка.

Структурированный режим включается `output.format: json`; обязательные поля задаются `output.requiredFields` массивом JSON Pointer к полям ответа. Отсутствующее значение отличается от null; null считается присутствующим полем. Не проверять семантику данных этим механизмом. `requiredFields` разрешены только с format json. Поддерживается JSON Pointer с ~0/~1; запрещать сегменты `__proto__`, `prototype`, `constructor` при обходе и не изменять объекты.

При format json весь ответ — один JSON-объект. Допускается один внешний блок ```json ... ``` без текста вокруг; не извлекать «похожий JSON» из произвольной прозы. `sections` при json запрещены: не смешивать текстовые заголовки с проверкой полей. Требования к именованным документам задаются artifacts.

Порядок приёмки: техническая accept → длина → JSON/поля или sections → выделение артефактов → для gate вердикт. До полного успеха ответ не становится рабочим входом и не регистрирует артефакты.

Причины отказа: `missing_section`, `too_long`, `invalid_output`, `missing_field`, `missing_artifact`, `no_verdict`. Каждая причина содержит конкретный заголовок/указатель. Обычный повтор сохраняет уже принятых участников и повторяет только неудавшихся. Принятый ответ в текущем заходе не отправляется заново через retry.

### 5.2 Объявление нескольких артефактов

```json
{
  "output": {
    "name": "Аудит карты",
    "format": "json",
    "requiredFields": ["/correctedMap", "/auditFindings"],
    "artifacts": [
      { "id": "map", "name": "Corrected Map", "pointer": "/correctedMap" },
      { "id": "findings", "name": "Audit Findings", "pointer": "/auditFindings" }
    ]
  }
}
```

- В текстовом режиме один артефакт может ссылаться на весь ответ: `pointer: ""`. Для нескольких артефактов нужны format json и разные указатели на существующие поля. Не выделять документы эвристикой по заголовкам.
- ID уникален среди объявлений одного выхода, но одинаковый ID у разных авторов не означает один документ. Адрес: step + participant + artifact ID.
- Все объявленные артефакты обязательны. Необязательные отдельные документы пока не добавлять: необходимости в этом запросе нет.
- Строковое значение указателя передаётся как текст; объект/массив — JSON.stringify без потери полей. Указатель на null допустим как содержимое, если бизнес-контракт не требует иного.
- Для доработки документа на другом шаге объявление может иметь `revisionOf`: artifact-ссылка из 4.3. Она должна присутствовать во входе автора; новая версия наследует линию исходного артефакта. Без revisionOf начинается новая линия. Нельзя присоединять результат к чужой линии без явно заданной ссылки схемы. Начало линии идентифицируется адресом первого объявления; версия — адресом фактического создателя и visit.

### 5.3 Запись реестра

```json
{
  "id": "map", "name": "Corrected Map",
  "lineage": { "step": "r8", "participant": "author-A", "id": "map" },
  "source": { "step": "r8", "participant": "author-A", "visit": 1 },
  "content": { "answerRef": "<ссылка CustomRunRecord.texts>", "pointer": "/correctedMap" },
  "valid": true,
  "inputs": ["<точные адреса использованных версий>"]
}
```

Реестр хранится в record.artifacts массивом; отдельного хранилища нет. Текст ответа уже хранится в record.texts, копию выделенного документа не записывать. Для просмотра/входа разрешать указатель к исходному ответу. В памяти движка допускается кэш разобранного JSON, в сохранённой записи он не нужен.

Ключ записи включает линию и адрес версии. Регистрация идемпотентна: повторное сохранение того же принятого ответа не создаёт вторую версию. Отвергнутая попытка не создаёт запись. До циклов visit всегда 1.

Latest выбирается по порядку регистрации в текущем прогоне среди актуальных версий линии, а не по сравнению visit разных этапов. Два автора — две линии. Недействительная конкретная версия доступна для истории, но не как рабочий вход. Нет актуальной версии — missing_input для required; иначе пустой источник, без старого fallback.

## 6. Gate и маршрутизация

### 6.1 Gate

Gate — самостоятельный `kind: gate`, ref gate:<id>. Модели — проверяющие; criteria — непустой список строк. Вход общий/индивидуальный работает как в round. Порядок parallel; pass all по умолчанию или any. Require регулирует достаточность ответов, pass — итог их вердиктов; недостаточное require не позволяет объявить gate успешным.

Текстовый ответ заканчивается `ВЕРДИКТ: ПРОШЁЛ` или `ВЕРДИКТ: НЕ ПРОШЁЛ`. При провале перед последней строкой — `НЕ ВЫПОЛНЕНО: ...`. Для JSON-выхода gate используются поля verdict: pass/fail и unmet: список строк (непустой при fail); текстовые маркеры в этом режиме не требуются. Это позволяет gate одновременно выпускать именованный документ.

onFail: stop по умолчанию или ask сохраняют поведение плана. onPass отсутствует — следующий шаг. Совместимый сокращённый переход `{goto, maxLoops}` допускается в onPass/onFail и нормализуется в action из 6.3. Gate с этим переходом не имеет второго локального выбора маршрута; следующий самостоятельный route исполняется только при обычном продолжении.

### 6.2 Самостоятельный шаг маршрута

```json
{
  "ref": "route:audit", "kind": "route", "models": [],
  "input": [{"artifact":{"step":"r29","participant":"reviewer","id":"report"},"version":"latest","required":true}],
  "select": {
    "by": "rule",
    "cases": [
      {"id":"close","when":{"source":0,"pointer":"/route","op":"eq","value":"close"},"action":{"goto":"r26","maxLoops":2}},
      {"id":"revise","when":{"source":0,"pointer":"/route","op":"eq","value":"revise"},"action":{"goto":"r28","maxLoops":2}}
    ],
    "otherwise": {"goto":"r30"}
  }
}
```

Route можно вставлять после любого этапа, gate или owner. Это исполняемый шаг без собственного бизнес-артефакта; выбранный маршрут сохраняется в журнале. Не подменять им gate.

`select.by`: rule/model/owner. Cases — непустой список с уникальными ID и action. Для rule у каждого case обязательное when. Для model/owner when запрещён: варианты описываются полем label, непустым текстом. Model имеет ровно одного включённого участника в models и непустой task; rule/owner имеют models: [].

Rule condition: `{source: <индекс разрешённого входа>, pointer: <JSON Pointer>, op: eq|in|exists, value?: ...}`. source индексирует разрешённые элементы после раскрытия источников; для правил использовать точные participant/artifact-ссылки, а не ссылку на весь многоответный шаг. Eq — рекурсивное сравнение JSON-значений без преобразования типов (порядок ключей объекта не важен, порядок массива важен); in — членство в непустом массиве JSON-значений; exists — наличие поля, value запрещён. Missing поле не совпадает eq/in. Вложенный pointer применим только к корректному JSON-значению источника; непарсируемый источник даёт invalid_route_input до выбора, а не otherwise. Составные условия: `{all:[conditions]}` или `{any:[conditions]}`, непустые; смешивать ключи атомарного и составного условия запрещено. Не eval и не пользовательский JS.

Ноль совпадений: выполнить otherwise, если задан; иначе stop route_not_found. Несколько: по умолчанию stop route_ambiguous. Явное `select.conflict: first` выбирает первый подходящий case в порядке списка; это записывается в журнал. Для явного разрешения владельцем `conflict: owner` вызывает окно выбора только совпавших вариантов. Rule по умолчанию conflict stop.

Model получает вход, labels и разрешённые case ID; возвращает ровно JSON `{"route":"<id>"}`. Неизвестный ID/невалидный JSON — отказ invalid_route и обычный повтор. После исчерпания попыток — решение владельца, без произвольного fallback. Owner выбирает ID; отмена останавливает, отсутствие/невалидность решения — no_decision. Otherwise не подменяет ошибочный ответ модели.

### 6.3 Action

Action — ровно один из `{goto: ref}`, `{stop: reason}`, `{return: true}`; у return дополнительно допустим maxLoops, у stop дополнительные поля запрещены. Goto может дополнительно содержать maxLoops, feedback, invalidate, resumeAt. Stop reason — непустая строка; журнал сохраняет её. Return разрешён только при сохранённой точке продолжения; пустой стек — return_missing.

Feedback — массив источников из 4.3, но текущий/более поздний относительно целевого шага источник разрешён: он уже исполнился в текущем пути. Все feedback разрешаются в точные версии ДО перехода и недействительности; нельзя ссылаться на ещё не выполненную версию. В новом заходе цель получает блок «Замечания, вызвавшие возврат», отдельно от обычного входа. Далее этот блок не рассылается всем шагам автоматически.

Invalidate — список ref результатов, которые автор явно требует пересмотреть. Движок добавляет транзитивно зависимые результаты/артефакты по фактически использованным версиям входов. При обратном goto целевой результат обязательно пересматривается, даже без invalidate. Связанная feedback сохраняется как историческое основание доработки; не становится актуальным документом от одного факта передачи.

ResumeAt — ref шага, к которому вернуться после исправления; сохраняется в стеке продолжений. Например S19→S10 с resumeAt S19, затем после G1 action return. Если resumeAt ведёт назад относительно return-шага, лимит maxLoops требуется на return-маршруте; у return разрешено maxLoops. Вложенные пересмотры используют стек, а не одну глобальную переменную.

Перед входом в новый заход пересматриваемые и зависимые версии становятся valid false; история не удаляется. Не считать весь диапазон шагов между источником и целью автоматически недействительным: учитывать зависимости и явную область. После пропуска/провала пересчёта прежний результат не возвращается в latest.

### 6.4 Циклы и счётчики

- Для любого перехода к раннему или текущему ref maxLoops — целое 1..5; отсутствующий лимит — ошибка схемы. Значение ограничивает число фактических переходов этого маршрута, не число посещений всего шага.
- Return с динамической целью проверяется на цикл консервативно по допустимым resumeAt. Если цель может быть ранней/текущей, нужен maxLoops.
- Ключ счётчика: ref выбирающего шага + case ID или otherwise/onPass/onFail. После reload ключи и значения сохраняются.
- При достижении лимита следующий переход не совершается, причина loop_limit. Существующий успешный результат текущего шага остаётся в истории.
- Validate проверяет полный граф, включая неявный линейный переход и все return-цели. Каждый возможный цикл должен содержать ограниченное ребро; проверять, что граф после удаления ограниченных рёбер ацикличен.
- Visit увеличивается при новом исполнении шага, но не при техническом повторе ответа и не при resume внутри того же захода. Повторное выполнение завершённого шага разрешено только переходом, создающим новый visit.

## 7. Интерфейсы движка и транспорта

Движок остаётся независимым от DOM/chrome. Чистые операции входов, output, реестра, условий и графа допускается вынести в небольшие модули `disput/basic-*.js`; A01/A07 согласуют имена и подключение. Не переписывать движок целиком ради разделения файлов.

**Хранение текстов между движком и записью.** Добавить синхронные callbacks `putText(text) → textRef` и `getText(textRef) → text`. Страница привязывает их к `record.put` и `CustomRunRecord.textOf`; движок не обращается к chrome/storage. После успешной приёмки сначала putText ответа, затем запись артефактов с этим answerRef. Если callbacks отсутствуют в автономном тестовом запуске, использовать внутренний словарь texts с теми же ссылками и вернуть его вместе с состоянием. При resume словарь/record уже восстановлен до разрешения inputs. Missing textRef — ошибка missing_content, а не пустой успешный документ. A02 реализует применение callbacks, A05 — привязку к сохраняемой записи и сериализацию.

**Snapshot: минимум формы.** `state = {schema, taskRef, runSettings, pc, visits, current, routes, loopCounters, continuationStack, feedback, dependencies, artifacts, ownerAnswers, pendingOwner, chatBindings}`. Pc — ref следующего действия, null только при завершении; current — `{stepRef, visit, phase, accepted, pending}`. Phase имеет значения input/send/judge/decision/asks/transition/done. Attempts и texts сохраняются в записи рядом со state. Каждый helper меняет явно свой участок; нельзя строить resume повторным запуском всего run с одним стартовым индексом. Сохранять фазу и исход намерения перехода так, чтобы повторное применение не инвалидировало новые результаты и не увеличило counter второй раз.

Сохранить текущий `send(models, promptsByModel, meta)` для старых схем. Для явных participant ID добавить callback `sendParticipants(requests, meta)`: requests — массив `{participantId, modelName, prompt, chat, stepRef, visit, attempt}`; результат — словарь по participantId с прежней структурой результата приёмки. Если новый callback отсутствует, legacy-send допустим лишь при уникальных modelName; два участника одной модели требуют явной ошибки participant_transport_required.

Meta содержит phase: answer/route, stepRef, visit. Gate использует answer; selector модели — route. OnRequest/OnResponse сохраняют прежние аргументы и дополнительно передают participantId/stepRef/visit/phase; A05 использует эти поля для уникального ключа попытки. Retry хранит participant ID и продолжает тот же чат. Нельзя превращать ID участника в имя провайдера для START_FULLPAGE_PROCESS.

`chooseRoute({stepRef, visit, choices, reason})` возвращает разрешённый ID или null. `provideOwnerResult({stepRef, visit, task, output})` возвращает текст либо объект ссылки на сохранённый файл; `checkpoint(state)` — Promise, сохраняющий состояние, ошибка не проглатывается. При наличии callback движок вызывает его в точках раздела 8.2 и ждёт завершения; страница передаёт snapshot и изменения реестра в record. Snapshot обновляется до checkpoint, а внешнее действие — после. При отсутствии callback автономный тестовый запуск остаётся допустимым, но не объявляет сохранённый resume. AbortSignal прерывает все ожидания; поздние ответы окна после Stop игнорируются.

Исследование A03 обязательно: проверить START_FULLPAGE_PROCESS, runModelBatch и выбор tab/request ID. Если отдельный чат по ID нельзя надёжно выбрать, реализовать минимальное расширение транспорта; показать конкретный отсутствующий механизм. Не заменять два независимых чата одним чатом и не имитировать независимость только текстом запроса. Две вкладки одной модели могут обслуживаться последовательно, если транспорт не умеет параллельное выделение: независимость означает отсутствие общего контекста, а не обязательную одновременность отправки.

## 8. Человек, хранение и возобновление

### 8.1 Owner-step

`{ref:"owner:evidence", kind:"owner", task:"...", models:[], input:..., output:...}`. Не требуется хотя бы один round для валидного pipeline, если есть выполняемый owner/gate/route. Иначе исследования и документы владельца невозможно представить самостоятельно.

Owner вводит текст или файл. При текстовом вводе применить output-проверки и регистрацию артефактов. Для файла сохранить доступное содержимое в хранилище прогона/существующем файловом механизме, включая MIME, имя и размер; не сохранять blob: URL как единственное содержимое. Двоичный файл не выдавать как текст следующей модели: передавать через существующий механизм вложений. Если транспорт такого входа не поддерживает, явная остановка unsupported_input, без потери файла. Ссылка реестра должна разрешаться после reload.

Пустой результат не принят. Отмена — stopped, Stop — cancelled. Owner-step не отправляет запрос модели. Owner approve не заменяет создание содержательного документа; эти операции различаются.

### 8.2 Запись и checkpoint

Новая запись прогона version 2; это версия записи, не schemaVersion. Чтение и экспорт version 1 сохраняются. Старой записи без полного checkpoint не обещать resume: оставить просмотр и объяснить отсутствие состояния.

Snapshot содержит: schema, taskRef, settings запуска, program counter по ref, visitByRef, текущую фазу и принятую часть outcome, маршруты и counters, continuationStack, feedback, exact input dependencies, artifacts, ownerAnswers, pending owner interaction, chatBindings, attempts. Тексты — в texts по ссылкам, а не копии в snapshot.

Ключ попытки включает stepRef + participantId + visit + attempt + phase. Не связывать две попытки разных заходов старым ключом step|model|attempt. Завершённая попытка не перезаписывается. При reload sent становится unknown.

Serialize обязан помечать как используемые все textRef/answerRef, на которые ссылаются реестр, checkpoint, файлы и обратная связь; иначе существующая очистка texts удалит необходимые данные. Export включает реестр, версии, snapshot и разрешаемые ссылки; не терять источники и visit.

Checkpoint сохраняется до внешней отправки (с намерением/идентификатором попытки), после её результата, до/после принятия решения владельцем, перед переходом, после изменения актуальности, при Stop. Ошибка сохранения останавливает дальнейшие внешние действия: checkpoint_failed. Повторное сохранение идемпотентно. Не использовать только нынешний debounce 600 мс как гарантию восстановления.

### 8.3 Resume

Используется schema из snapshot, а не текущий холст. Завершённые шаги не отправляются заново; внутри незавершённого захода сохраняются принятые участники. Число попыток и лимиты циклов не сбрасываются.

Unknown/sent требуют решения: проверить наличие ответа / отправить заново / пропустить. «Проверить» использует сохранённый request/tab ID и обычную приёмку; отсутствие доказанного ответа не означает успех. Повтор получает новую попытку и связь retryOf. Пропуск применяется к конкретной неопределённой попытке, не обходит require.

Чат недоступен — восстановить контекст явно из сохранённых входов и ответов либо спросить владельца; не привязываться к произвольной вкладке той же модели. Уже принятое подтверждение владельца не спрашивается снова. При незавершённом подтверждении окно открывается снова с теми же данными.

## 9. Холст и UI

- Старый холст и его кнопки сохраняются. Новые участники, gate/route/owner и их позиции представлены явно, не маскируются под обычный синтез.
- У новых схем канонический порядок редактирования — упорядоченные шаги схемы; видимые стеки/вставки — проекция. Не хранить новую механику только в DOM или в JSON, который UI потом молча заменяет старой сборкой.
- A01 расширяет toCanvas/toSettings, A06 — обратную сборку basicSchemaFromPage, recordFromSchema, installBasicSchema и окна. Новые control-steps могут стоять подряд; старое ограничение synthesis между round не применять к gate/route/owner.
- Новые поля редактируются структурированными контролами; допустимо отдельное компактное окно control-step. Графический редактор языка условий не нужен: простой список условий source/pointer/op/value и вариантов маршрута достаточен.
- Предпросмотр знает, что runtime-ответов нет: метки источников, а не вымышленные документы. Модель задания и исходный текст не меняются от просмотра.
- В ленте подписи: этап, участник/роль, visit; реестр открывает именно содержимое выбранного артефакта. Недействительность видна в истории; ошибку required input показать с адресом.
- Round-trip равенство сравнивает явные поля схемы, порядок участников и источников, route cases, revisionOf. Не сравнивать только число раундов.

## 11. Git, версии, документация и завершение

Перед работой читать AGENTS.md и git status. Не reset/clean чужие изменения. Для реализации отдельные ветки codex/basic-<участок>; обмен только проверенными коммитами, без автоматического merge в main. Владение файлами соблюдать даже в разных worktrees.

Каждая самостоятельная кодовая правка: код + необходимые тесты + соответствующие документы Basic + docs/CHANGELOG.md + одинаковая актуальная версия корневых manifest.json/package.json и связанных версионных файлов, найденных в текущем проекте. Не менять manifests вложенных независимых приложений по совпадению имени файла. Версию брать из состояния после предыдущего принятого коммита, не резервировать одинаковый номер нескольким агентам.

По AGENTS.md commit поручается Haiku. Если эта модель недоступна, явно сообщить и выполнить локальный commit самостоятельно, как уже делалось в этой сессии. Не подменять её другой моделью без объяснения.

Документы Basic описывают только уже реализованное поведение. Настоящее ТЗ и план могут описывать будущее с явным статусом. A07 обновляет карту документации и фиксирует закрытые пункты плана; нерешённые условия бизнеса не помечаются исправленными.

Пакет принят, когда: проверены позитивные/негативные сценарии, сохранены старые схемы, круговой проход без потерь, выполнены нужные тесты, документы и версия актуальны, изменение закоммичено. Итоговый отчёт: commit, что работает, команды проверок, оставшиеся ограничения и отдельно неподтверждённые сценарии реального транспорта.
