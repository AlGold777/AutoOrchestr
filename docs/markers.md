# Маркеры в ответах моделей

Перечень маркеров, которые **сейчас работают** в коде. Ничего не предлагает и
не вводит. Сверено с основным каталогом проекта, версия расширения **2.81.611**.
Ссылки на строки относятся к ней.

## 1. Сводка

| Маркер | Кто пишет | Кто читает | Что делает |
|---|---|---|---|
| `[[AO-xxxxxx]]` метка доставки | Модель, по инструкции в конце промпта | `shared/message-delivery.js`, `background/dispatch-coordinator.js` | Доказывает, что ответ принадлежит именно этому запросу и закончен |
| `[[ASK: вопрос]]` | Модель, по инструкции этапа | `disput/stage-markers.js` | Просит ответ владельца; пауза запуска и диалог |
| `[[VERDICT: pass\|issues_found]]` | Модель на проверочном этапе | `disput/stage-markers.js` | Итог проверки: есть ли блокирующие замечания |
| `<<<RESPONSE <nonce> <имя> START>>>` и `…END>>>` | Код, не модель | `shared/judge-prompt-builder.js` | Границы чужих ответов внутри промпта судьи |
| `<<<RESPONSE legacy <имя> START>>>` и `…END>>>` | Код, не модель | `results.js`, `background/evaluation-manager.js` | То же в прежнем формате |

Других маркеров вида `[[…]]` в коде нет. Остальной служебный текст (например,
`<<<…>>>` без слова `RESPONSE`) маркером не считается.

## 2. Метка доставки `[[AO-xxxxxx]]`

**Формат.** `[[AO-` + 6 символов + `]]`. Символы из алфавита
`abcdefghjkmnpqrstuvwxyz23456789`. При чтении регистр не различается
(`shared/message-delivery.js`, `TOKEN_RE`).

**Как попадает в промпт.** К каждому промпту добавляется абзац:
`Последней строкой ответа напиши только метку [[AO-xxxxxx]]`. Метка своя на
каждый запрос каждой модели. Хранится по `transportRequestId`, поэтому
подготовка нового запроса не отменяет метку запроса, который ещё выполняется.

**Как читается ответ.**

| Состояние | Условие | Что происходит |
|---|---|---|
| `verified` | В ответе есть метка этого запроса | Ответ принят как доставленный |
| `missing` | Метки нет | Ответ показывается с пометкой «Без метки доставки» (`attributionState: unproven`). Галочка в карточке заменяет пометку решением пользователя (`user_verified`) |
| `foreign` | Есть метка, но другого запроса | Ответ считается устаревшим и **не показывается** (`stale_dropped`) |
| `untracked` | Для запроса метка не зарегистрирована | Служебные теги вырезаются, остальное без изменений |

Основное доказательство принадлежности ответа — `transportRequestId`
(`shared/transport-contract.js`). Метка дополнительная.

**Что метка даёт завершению ответа:**
- текст с меткой этого запроса считается **завершённым**; его принудительная
  фиксация — успех, а не «неполный» (`answerHasDeliveryToken`,
  `background/dispatch-coordinator.js:443`);
- при отложенном неопределённом финале ответ с меткой фиксируется через 5 с
  тишины, без метки — через 30 с (`docs/message-delivery.md`);
- пока пакет открыт, ответ без метки (возможно, обрезанный) заменяется
  ответом того же запроса с меткой (`unproven_replaced`);
- при проверке ответа признак «обрыва по концовке» (`incomplete_ending`) не
  применяется, если транспорт признал ответ `complete`
  (`disput/debate-response-acceptance.js:43`).

**Что вырезается из текста** (`MessageDelivery.clean`):
- метки `[[AO-…]]`;
- строка с инструкцией «Последней строкой ответа напиши только метку»;
- разделители `<<<RESPONSE … START|END>>>`;
- хвост после метки на той же строке до 40 символов, не содержащих `[` и
  перевода строки (например, время `8:55pm`, которое дописывает Le Chat);
- Для HTML-ответов вырезаются метки и разделители.

Остальной текст ответа не переписывается.

## 3. Маркер вопроса `[[ASK: вопрос]]`

**Формат.** Отдельная строка `[[ASK: текст вопроса]]`.

**Где добавляется инструкция.** В промпт каждого этапа шаблона, у которого
есть собственное задание (`stage.instruction`, `results.js:6478`). Текст
инструкции: если для продолжения нужен ответ владельца, который нельзя придумать
за него (цель, приоритет, ограничение, выбор между вариантами), добавь
отдельной строкой `[[ASK: вопрос]]`, не больше 3 строк, за владельца не
отвечай, нет вопросов — строку не добавляй. Строки пишутся до метки доставки и
не оформляются кодом или цитатой.

**Правила разбора** (`disput/stage-markers.js`, `parse`):
- маркер должен занимать строку целиком; допустимо лёгкое оформление по краям:
  пробелы, `*`, `_`, `-`, `•`;
- регистр слова `ASK` не важен;
- строки внутри блоков кода (``` и ~~~) и строки цитат, начинающиеся с `>`,
  — данные, маркер на них не срабатывает;
- маркер посреди строки с другим текстом не распознаётся;
- пустой вопрос игнорируется;
- вопрос обрезается до 400 символов;
- повторы (без учёта регистра) схлопываются;
- принимается не больше 3 вопросов на ответ, остальные отбрасываются молча.

**Что происходит дальше:**
1. Исполнитель этапа разбирает каждый принятый ответ
   (`disput/debate-stage-executor.js:210`) и собирает `asks` этапа вместе с
   участником, который задал вопрос.
2. Оркестратор сохраняет их в `stage.asks` (`disput/debate-orchestrator.js:771`).
3. Если у выполненного этапа есть вопросы, запуск встаёт на паузу с причиной
   `ask` (`debate-orchestrator.js:938`). Приоритет причин пауз: этап не
   отработал (`stage_failed`) → `ask` → ворота (`gate`) → «после каждого
   этапа».
4. Страница показывает диалог «Вопрос владельцу» (`results/owner-ask.js`):
   под каждым вопросом поле для **свободного текста**.
5. Три кнопки: «Ответить и продолжить», «Продолжить без ответа», «Позже».
   Первые две снимают паузу, «Позже» закрывает диалог и паузу не снимает.
   «Ответить и продолжить» без единого ответа не принимается. Сохраняются
   только вопросы, на которые дан непустой ответ.
6. Ответы превращаются в строки `Ответ владельца на вопрос «…»: …` и
   попадают в промпты следующих этапов как «Текущее указание человека»
   (`OwnerAsk.toInstruction`, `results.js:6248`).

Телеметрия: события `run_paused` и `owner_answer` (сколько вопросов задано и
сколько отвечено).

## 4. Маркер итога проверки `[[VERDICT: pass|issues_found]]`

**Формат.** Отдельная строка `[[VERDICT: pass]]` или
`[[VERDICT: issues_found]]`. Пробелы внутри значения заменяются подчёркиванием,
регистр не важен.

**Где добавляется инструкция.** Только в этапы с целью `critique`,
`verification` или `evidence_review`. В конце проверки модель пишет
`pass`, если блокирующих замечаний нет, и `issues_found`, если они есть.

**Правила разбора:** те же, что у `[[ASK]]` (отдельная строка, не в коде и не
в цитате). Дополнительно:
- значение вне списка попадает в `invalid` и не считается вердиктом;
- при нескольких допустимых строках в одном ответе действует последняя.

**Объединение участников этапа** (`combineVerdicts`): если хотя бы один дал
`issues_found`, итог этапа `issues_found`; иначе, если был `pass`, итог
`pass`; иначе вердикта нет (`null`).

**Что происходит дальше.** Вердикт сохраняется в `stage.verdict` и
передаётся в описание паузы (`ask` и `gate`). Страница использует его только
для текста уведомления в точке ворот: «Проверка нашла блокирующие замечания»
или «Проверка: замечаний нет». Автоматического ветвления сценария по
вердикту в оркестраторе я не нашёл.

## 5. Разделители ответов для судьи

В промпте судьи ответы моделей оборачиваются так
(`shared/judge-prompt-builder.js:61`):

```
<<<RESPONSE <nonce> <имя модели> START>>>
текст ответа
<<<RESPONSE <nonce> <имя модели> END>>>
```

`nonce` создаётся для каждого промпта судьи. Прежний формат использует слово
`legacy` вместо `nonce`. При очистке ответа вырезаются только разделители со
словом `RESPONSE` в обоих форматах, в том числе в виде `&lt;&lt;&lt;…&gt;&gt;&gt;`.
Остальное содержимое вида `<<<…>>>` (код, шаблоны) сохраняется.

## 6. Порядок элементов в конце промпта этапа

1. Задание этапа.
2. Инструкция про `[[ASK]]`, а на проверочном этапе — и про `[[VERDICT]]`.
3. Строка про метку доставки с `[[AO-…]]` — последней.

Модель, соответственно, пишет строки `[[ASK]]` и `[[VERDICT]]` **до** метки
доставки, а метку — последней строкой.

## 8. Чего нет

- Отдельного «паспорта ответа» в коде нет. Метаданные принятого ответа
  собираются из `transportRequestId`, `dispatchId`, статуса завершённости
  (`complete` / `partial` / `failed` / `cancelled`) и состояния метки.
- Маркеров начала ответа, формата JSON-блока или номеров утверждений в
  коде нет.
- Ответ владельца на `[[ASK]]` вводится текстом; выбора из вариантов и
  комментария к варианту в диалоге нет.
