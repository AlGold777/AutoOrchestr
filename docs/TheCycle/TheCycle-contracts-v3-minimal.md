# TheCycle — минимальные контракты v3 (P2)

Редакция 1.0, проект для приёмки GPT, 28.11.2026. Основание: утверждённый генплан v3, §§3.1–3.4 и §§4.2–4.3. SHA кода: `9bf39a13`, версия 2.81.1154. Это спецификация этапов P3–P6, не код. Не вводит графовую БД, второй движок, отдельных агентов и универсальные метрики. Код проверяет форму и допустимость переходов; смысловую достаточность проверяют разрешённые методы задачи.

## 0. Главное решение: где живёт знание

Новых хранилищ IndexedDB нет, `DB_VERSION` остаётся 1. Знание записывается **в пакеты цикла** (`packets`, ключ `researchId + cycleId`) необязательным полем `knowledge`. Решения владельца между циклами — в `research.state`, как уже сделано для `budgetHistory`. Накопительное состояние знаний — детерминированная свёртка (`fold`) этих записей по порядку циклов; единственной сохранённой копии у него нет.

Почему так:
- Старые исследования и копии читаются без миграции: нет поля `knowledge` — пустая дельта, пустое состояние.
- Копия, восстановление и `activeIsNewer` работают по тем же хранилищам; добавляется только учёт новых полей.
- Журнал остаётся первичным и неизменным; ошибка свёртки чинится пересчётом, а не правкой данных.

Формат версионируется полем `knowledgeFormat` (сейчас 1). Читатель, встретивший формат новее известного, **отказывает** кодом `KNOWLEDGE_FORMAT_UNSUPPORTED` и не искажает данные. Несовместимое изменение требует миграции либо безопасного чтения старого (ARCH-013: сейчас миграции нет, есть явный отказ).

**Чтение существующих исследований и копий.** Исследования без `knowledge` читаются как есть: знания пусты, итоговый статус прежний. Знания из прежних текстовых отчётов аналитика задним числом не извлекаются и проверенными не объявляются. Копии `thecycle-idb-snapshot` v1 читаются прежним путём; в новых копиях `knowledgeFormat` проверяется вместе со схемой.

## 1. Задача (§3.1)

`TaskSpec`: `taskVersion` (целое с 1), `text`, `requirements[]` (`id`, `text`, `closeCondition`), `constraints`, `successCriteria`, `standardRef` (§4), `authorizedBy: "OWNER"`, `createdAt`, `supersedes`.
- Версию задачи меняет только решение владельца; запись в `research.state.taskVersions`. Модель может предложить правку, принять — нет.
- Смена версии помечает затронутые обязательства и утверждения `NEEDS_REASSESSMENT`, не стирает их.
- Неоднозначность — `assumptions[]` (`id`, `text`, `affects[]`); допущения видны в финале.

## 2. Накопительное состояние (§3.1)

Запись добавляется в `packet.knowledge` объектом `KnowledgeDelta`:

| Запись | Поля |
|---|---|
| `Obligation` | `id`, `taskVersion`, `requirementRef` либо `derivedFrom` + `derivationReason`, `status`: `OPEN`, `CLOSED`, `WITHDRAWN`, `closeBasisRefs[]` |
| `Claim` | `id`, `rev`, `statement`, `status`: `CANDIDATE`, `SUPPORTED`, `DISPUTED`, `REFUTED`, `INSUFFICIENT`; `conditional` (гипотеза), `basisRefs[]`, `dependsOn[]` (`claimId:rev`), `scope`, `origin` (`role`, `model`, `cycleId`), `statusReason` |
| `Basis` | `ref` (адрес первичного свидетельства: `cycleId`, `runId`, `eventId`, выдержка или хэш), `provenance` (`model`, `role`, `isolation`), `kind`: `MODEL_ANSWER`, `EXPERT_CONFIRMATION`, `REPRODUCIBLE_CHECK`, `OWNER_EVIDENCE`, `partial` (флаг) |
| `Contradiction` | `id`, `claimRefs[]`, `status`: `OPEN`, `RESOLVED`, `ACCEPTED_LIMIT`, `basisRefs[]` |
| `MethodEntry` | `cycleId`, `method`, `expectation`, `outcome` (после результата), `rejectionReason` |

Правила переходов (проверяет код; `fold` отклоняет дельту целиком с кодом ошибки):
1. Новая запись — `rev=1`; изменение — `rev+1` с тем же `id`; прежние ревизии не удаляются.
2. Смена статуса `Claim`, закрытие `Obligation`, разрешение `Contradiction` требуют основание в той же дельте или ссылку на существующее. Иначе `KNOWLEDGE_NO_BASIS`.
3. Ссылки (`basisRefs`, `dependsOn`, `requirementRef`) указывают на существующие записи и пакеты не позже текущего цикла. Иначе `KNOWLEDGE_BAD_REF`.
4. Пустой ответ, обрыв, молчание, отсутствие ссылки, снижение уверенности и необоснованное несогласие статус **не меняют**. Возражение по существу — `DISPUTED` с основанием возражения; прежнее основание не удаляется.
5. Пересмотр статуса при утрате применимости, надёжности или достаточности источника допустим, с причиной.
6. Смена ревизии утверждения помечает зависимые (`dependsOn`) `NEEDS_REASSESSMENT`. Полнота обнаружения неизвестных зависимостей не заявляется.
7. Модельные утверждения остаются `CANDIDATE`, пока основание не достигло уровня стандарта (§4). Запись в реестр достоверности не создаёт.
8. Частичные принятые ответы сохраняются как `Basis` с флагом `partial`; повторная отправка ради них не нужна.

Код **не** проверяет смысловую истинность, силу основания и эквивалентность прозы — это делает процедура проверки (§4).

## 3. Проекция контекста (§3.2)

`ProjectionManifest` хранится вне промпта (в пакете цикла-потребителя, `knowledge.projection`): `included[]`, `excluded[]` (`ref`, `reason`), `originalsAvailable`, `truncated` (для каждой усечённой записи). Отбор — по исходным требованиям, открытым вопросам, актуальности и значимости оснований, не только по новизне. Усечённое свидетельство не выдаётся за полное. Перед закрытием значимых обязательств проекция сверяется с состоянием; при расхождении — диагностика, не молчаливое закрытие. Переполнение — код `CONTEXT_OVERFLOW` и безопасная пауза либо обоснованное изменение проекции; повышение бюджета вызовов переполнение не лечит (подтверждено на коде: ARCH-001). Лимиты и способ сжатия нормой документа не являются.

## 4. Стандарт достаточности, результат, статус (§3.4)

`SufficiencyStandard`: `version`, `level`: `EXPERT_SUPPORTED` либо `FORMALLY_VERIFIED`; `requiredChecks[]`; `independence`: `NOT_REQUIRED`, `DIFFERENT_MODEL`, `FRESH_SESSION`, `BLIND`; `coverage` (все требования либо перечисленные); `reachabilityNote`. Фиксируется **до первого расхода**, в `research.state.standards` с версией.
- Достижимость проверяется при доступных моделях, инструментах, правах и бюджете. Недостижимо — потолок сообщается, исследование без разрешения владельца на изменённые условия не стартует.
- Смена стандарта — новая версия, основания переоцениваются; критерий скрытно не снижается.

Результат — три независимых поля:
- `execution`: `COMPLETED`, `PAUSED`, `STOPPED`, `BUDGET_EXHAUSTED`, `FAILED`;
- `coverage`: доля закрытых требований исходной задачи и список незакрытых;
- `level`: `NONE`, `CANDIDATE`, `EXPERT_SUPPORTED`, `FORMALLY_VERIFIED`, `DISPUTED`, `INSUFFICIENT`.

`VERIFIED_SOLUTION` допустим только при выполнении всех условий: достигнут уровень стандарта, покрытие требований подтверждено, существенные противоречия разрешены, финал прослеживается к проверенным версиям утверждений (§5), независимость соответствует стандарту. Иначе — вычисленный статус без этого слова. `COMPLETE` модели — предложение; статус вычисляет контроллер. При неполноте, недостижимости или недостаточном обосновании по умолчанию — возобновляемая пауза с лучшим результатом и причиной. Необратимое закрытие неполного — явное действие владельца. Принятие владельцем — отдельное поле, доказательность не повышает.

`VerificationRecord` (расширение существующей записи): `claimSet` (`id:rev`), `taskVersion`, `standardVersion`, `procedureRef`, `sources[]`, `assumptions[]`, `verdict`, `checks[]`, `isolation` (§6). Новая ревизия утверждения делает запись неприменимой к ней.

## 5. Итоговая публикация (§3.4)

`FinalPublication`: `text`, `composedFrom[]` (`claimId:rev`, хэш фрагмента), `unverifiedParts[]` (новые выводы, смысловые изменения, обобщения, условия). Композиция неизменённых утверждений перепроверки не требует. Хэш и ссылки удостоверяют идентичность фрагмента, не смысл пересказа; совпадение `claimId` не объявляет прозу эквивалентной. Непроверенное помечается.

## 6. Изоляция проверяющего (§3.4)

`IsolationObservation`, пишется кодом из наблюдаемого: `model`, `modelVersion` (если видна), `role`, `newSession` (новая вкладка/чат), `contextManifest` (что передано: исходная задача, проверяемый объект, чужая аргументация — да/нет), `blind`. Скрытое состояние провайдера не утверждается. Если изоляция недостижима или не подтверждена данными, результат не получает уровня, требующего независимости. Чувствительные идентификаторы и содержимое в общие артефакты не попадают.

## 7. Ресурсы (§3.3)

`ResourceLedger` в `research.state` (расширяет `budgetHistory`): `limit` владельца, `forecast`, `actual` по категориям `work`, `analyst`, `verify`, `extra`; расход `UNKNOWN` — неопределённость, не ноль. Резерв на проверку и завершение выделяется заранее. Бюджет — верхний предел, не цель. Недоступные показатели провайдеров помечаются неопределёнными.

## 8. Прогресс и управляющее решение (§3.3)

`ProgressAssessment` в решении аналитика: `verdict`: `PROGRESS`, `STAGNATION`, `REGRESSION`, `UNKNOWN`; `observations[]` — ссылки на изменение состояния (закрытое требование, новый обоснованный вывод, снятое противоречие, исключённый метод, сужение неопределённости). Структурная дельта — сигнал, не доказательство пользы. Политика задачи (`maxReassessments`, допустимые действия при стагнации) задаётся **до запуска**; единого N нет. При отсутствии обоснованного продвижения — конечное число переоценок, смена метода либо пауза/остановка. Возврат к методу знания, журнал и бюджет не откатывает.

## 9. Восстановление и совместимость (§§4.2–4.3)

- На том же снимке, который активируется, проверяются: байтовая и логическая целостность; доказательное замыкание (каждое основание из `knowledge` есть в копии, иначе отказ, активная база остаётся); `knowledgeFormat`; отсутствие потери более поздних данных (`activeIsNewer` сравнивает и знание).
- Логическая целостность: сейчас `validate` в `restore-service.js` не проверяет ссылки (`lastCommittedPacket`, `activeRunId`, `resultEventId`) и `usedCalls ≤ maxCalls` — REL-002, воспроизведено; закрывается в этом контракте как обязательные проверки restore.
- Восстановленный статус относится к восстановленному состоянию; точка восстановления и возможный утраченный хвост сообщаются; текущим `VERIFIED_SOLUTION` без достаточных оснований не объявляется.
- Право отправки не восстанавливается вместе с данными: правила UNKNOWN, `no replay` и C-13 не меняются.
- Рост размера: полный снимок допустим в измеренных пределах; измерения — P8.

## 10. Что не определено и не назначается

Графовая БД; отдельные агенты ролей; универсальные метрики прогресса; единый порог стагнации; лимиты проекции и способ сжатия; способ формальной проверки (определяется стандартом задачи); разбиение на модули и общий модуль двух путей копирования (ARCH-008/010/012 — решение при реализации P3).

## 11. Решения владельца до P3

1. Принять решение «знание — в пакетах, свёртка по порядку, без новых хранилищ IDB» (§0). Альтернатива — отдельное хранилище и подъём `DB_VERSION` с миграцией; не рекомендуется.
2. Подтвердить на первом шаге уровни стандарта `EXPERT_SUPPORTED` и `FORMALLY_VERIFIED`; формальная — только где есть детерминированный метод.
3. Подтвердить паузу вместо принудительного завершения при недостатке обоснования (§4).
4. Целевая граница автономности G4 (A1 или A2) — после спайка, отчёт `TheCycle-P2-verification.md`.

## P3. Как реализован §2 (уточнения при реализации)

Код: `disput/thecycle/knowledge.js` (`fold`, `applyDelta`, `applyTaskVersion`), запись — `state-store.decide`, проверка при восстановлении — `restore-service.validate`. Тесты: `tests/thecycle-knowledge.test.js`, `tests/thecycle-knowledge-store.test.js`.

- Аналитик может приложить к решению ключ `knowledge` (дельта). Она проверяется свёрткой со всеми прежними пакетами и записывается в `packet.knowledge` пакета, который оценивается, в той же транзакции, что и решение. Недопустимая дельта отклоняется целиком: решение проходит, в пакет пишется `knowledgeRejected {code, message}`; пауза не наступает.
- Всякая запись имеет `rev` (с 1). Основание (`Basis`) имеет собственный `id`; утверждения и обязательства ссылаются на него по `id` (`basisRefs`, `closeBasisRefs`).
- Допустимость переходов: смена статуса утверждения требует новое основание этого цикла; `SUPPORTED`/`REFUTED` — только основание вида `EXPERT_CONFIRMATION`, `REPRODUCIBLE_CHECK` или `OWNER_EVIDENCE` и не частичное; ответ модели даёт максимум `DISPUTED`. Прежние основания не удаляются. Обязательство из постановки (`requirementRef`) модель не снимает (`KNOWLEDGE_OWNER_ONLY`). Новое обязательство возникает `OPEN`.
- Версию задачи вносит владелец в `research.taskVersions` (`[{taskVersion, atCycle}]`): затронутое помечается `needsReassessment`, не стирается. Интерфейса владельца для этого пока нет — он нужен к P6.
- Коды отказа: `KNOWLEDGE_SHAPE_INVALID`, `KNOWLEDGE_FORMAT_UNSUPPORTED`, `KNOWLEDGE_NO_BASIS`, `KNOWLEDGE_WEAK_BASIS`, `KNOWLEDGE_BAD_REF`, `KNOWLEDGE_REV_INVALID`, `KNOWLEDGE_OWNER_ONLY`. При восстановлении — `RESTORE_KNOWLEDGE_INVALID`, `RESTORE_KNOWLEDGE_UNSUPPORTED`.
- Не сделано в P3 (по плану): показ накопленного состояния аналитику и проекция контекста (P4), стандарт достаточности и связь с итоговым статусом (P6). Промпт аналитика пока не просит `knowledge`, поэтому дельты появятся после P4.

## P4. Управление контекстом

- Что видит аналитик: проекция накопленного состояния (код `knowledge.projection`). Порядок важности: открытые обязательства, утверждения (сначала помеченные на пересмотр, спорные, кандидаты, затем поддержанные), открытые противоречия, частичные данные. Знания получают не больше 40% свободного места, рабочий цикл — не больше 20% лимита.
- Что не влезло, не пропадает молча: в тексте строка «не показано записей: N», в журнале (`CONTEXT_READY.context.knowledge`) — `{shown, omitted}`.
- Сводка последнего рабочего цикла при нехватке места сокращается с пометкой «показано N из M», `CONTEXT_READY.context.summaryTruncated = {from, to}`. Полные ответы остаются в журнале и доступны по ссылкам `cycle=N step=N model=…`.
- Пауза `CONTEXT_UNAVAILABLE` остаётся только когда шаблон со знаниями не оставляет под сводку 500 знаков: это ошибка настройки лимита, а не рост исследования.
- Завершение: `COMPLETE` проверяет форму (не смысл): дельта допустима, открытых обязательств нет. Иначе пауза `KNOWLEDGE_REJECTED` или `OBLIGATIONS_OPEN`.
- Старая копия: восстановление идёт в новую базу и не затирает активные знания; копия без знаний читается как пустое состояние.

## P5. Управление исследованием

- Код только считает; суждение о пользе остаётся за моделью. Блок «ДИНАМИКА ИССЛЕДОВАНИЯ» в промпте аналитика: циклы, подряд продолжений без изменений знаний, смены стратегии, остаток вызовов и резерв, история стратегий (ожидалось → знания менялись / не менялись).
- Продвижение — наблюдаемый сигнал: новая или изменённая по статусу/тексту запись, основание, закрытие обязательства. Смена `rev` без содержательных изменений продвижением не считается.
- Остановка: `CONTINUE` при трёх подряд циклах аналитика без изменений знаний (последний — текущий) → пауза `STAGNATION` с лучшими кандидатами и открытыми обязательствами; возобновление начинает отсчёт заново. Допустимы `CHANGE_STRATEGY`, `VERIFY`, `COMPLETE`, `WAIT_OWNER`. Условие — в реестре есть записи.
- Смена стратегии: ожидание `expected` фиксируется; та же схема, применявшаяся ранее, отклоняется (`STRATEGY_REPEATED`), пока знания с её завершения не изменились. Лимит смен — 5.
- Резерв: 2 вызова на проверку и завершение. Новая схема не должна его занимать; `CONTINUE` с реестром при остатке меньше резерва + 2 → пауза `BUDGET_RESERVE`. Автоматического повтора нет.

## P6. Верификация и завершение

- `verifies` (только при `COMPLETE`, ≤64 знаков) — id утверждения реестра, на которое опирается финал.
- При доказанной проверке и непустом реестре `VERIFIED_SOLUTION` требует: утверждение есть, статус SUPPORTED, нормализованный текст равен проверенному `claim`. Нарушение — пауза `VERIFICATION_MISMATCH` (возобновляемая, причина в `detail.errors`).
- Независимость `FRESH_TAB_OTHER_MODEL` принимается, только если по отчётам циклов ответила ровно назначенная модель, не участвовавшая в рабочих циклах и у аналитика-источника; иначе `UNPROVEN`, причина в `downgrades`.
- Без реестра знаний привязка финала не проверяется (ограничение).
