# Запрос на создание схемы по виду задачи (шаблон)

Шаблон запроса модели для схемы определённого вида. Пустой блок «ПРОДУКТОВАЯ ЧАСТЬ» заполняется текстом из ограждения в файле [task-types/<вид>.md](task-types/) — например, [research.md](task-types/research.md). Остальное — техническая часть [общего запроса](basic-model-request.md): вместо его раздела «Как проектировать процесс» здесь продуктовая часть и «Общие правила процесса». При правке технической части общего запроса меняйте её и здесь.

````
Задание: спроектировать процесс под реальную задачу и записать его как схему Basic в строгом формате JSON.

О приложении.
Это расширение для браузера. Пользователь ставит задачу, а приложение отправляет её сразу нескольким нейросетевым чатам (ChatGPT, Gemini, Claude и другим), собирает ответы и передаёт их дальше по схеме. Схема — список шагов сверху вниз. Шаги выполняются строго по порядку, ветвлений, возвратов назад и условий нет.

ПРОДУКТОВАЯ ЧАСТЬ


ОБЩИЕ ПРАВИЛА ПРОЦЕССА
— Запрос модели приложение собирает из задачи User, задания этапа (или личного задания участника), выбранных входов, роли и служебных требований. `spec` и описательные поля (`title`, `goal`, `quality`, `rules` шага, `description` артефакта) сохраняют замысел процесса для человека, который читает схему на холсте; в запрос они не переносятся. Все требования, которые должна выполнить модель, повторите в `task` соответствующего этапа; проверяемые приложением требования к формату задавайте через `output`.
— Независимость определяется историей участника, а не названием модели или ролью. Другой участник того же провайдера с отдельным чатом может дать независимое предложение. Смена роли автора на «проверяющий» не делает его проверку независимой: для отдельной проверки нужен участник, который не писал проверяемый документ; для независимых предложений участники не должны заранее видеть ответы друг друга. `chat: "new"` начинает без прежней истории, но нужные материалы и проверяемый документ придётся передать заново; отдельный чат уменьшает влияние прежнего контекста, но не гарантирует правильность ответа.
— Для каждого этапа: `title` — название; `goal` — что этап даёт процессу; `task` — задание, ожидаемый выход и критерии; `input` — необходимые входы, только из более ранних шагов; `output` — выход, при необходимости именованный артефакт и `revisionOf` для новой версии; по необходимости `quality` — критерий завершения и `rules` — ограничения этапа (это поля для человека: нужное модели повторите в `task`).
— Если обязательный источник (`required: true`) не дал принятого результата, прогон останавливается до отправки запросов этапа. Версии и происхождение ответов приложение записывает само; технические повторные попытки при непринятом ответе тоже выполняет само.
— Содержательные суждения делают модель (`round`) или User (`owner`). Проверка — обычный раунд с конкретными критериями в `task`; если замечания можно применить без решения человека, следующий раунд дорабатывает результат сам. Вердикт «прошло» не включает условный переход. Условных переходов, автоматического пропуска этапов и циклов «до успеха» нет: доработку и повторную проверку записывайте отдельными последующими этапами.
— Документ попадает в чат участника один раз. Если участник уже получил документ или сам его написал, на следующих его этапах не подавайте документ во `input` снова: напишите в `task` ссылку по названию («используй «Карту экранов» из этого чата») и поставьте `"input": "none"` или подайте только новое — замечания, ответ User. Документ передаётся снова только тому, кто его ещё не видел (другому участнику или после `chat: "new"`), и только когда появилась новая версия (правка User, доработка).
— Коротко объясните выбранное взаимодействие участников в `description` и во втором пункте после JSON; поля `why` в Basic нет.

ЗАПИСЬ СХЕМЫ. Переведите сценарий в JSON по правилам ниже.

Как работает приложение (на этом строится схема).
1. Постоянный чат участника. Модель (`name`, например Claude), участник (`id`, например claude-author) и его переписка — разные вещи. По умолчанию один участник продолжает свой чат между шагами в пределах прогона; помнит только материалы и ответы своего чата. Два участника Claude работают в отдельных чатах, историю друг друга не видят. Одинаковый `id` в следующем шаге означает того же участника; новая роль или подпись не создаёт новый чат. Адреса переписок и ID вкладок приложение хранит само: в схему их не пишите. Ссылка на шаг в `input` вставляет в запрос ПОЛНЫЙ текст ответов этого шага, каждый раз заново; передавайте участнику только нужные материалы, которых ещё нет в его текущем чате. При `chat: "new"` прежняя история участника в новый чат не переносится: нужные материалы передайте через `input` заново.
2. Приложение само ничего не понимает и не решает. Оно рассылает запросы, собирает ответы, подставляет нужные ответы в следующие запросы, показывает документ User и ждёт его ответа. Условий по тексту ответа оно не вычисляет и не читает слов «прошло» или «не прошло». Если нужна проверка, её делает модель, а её ответ читает User или следующая модель.
3. Приложение само дописывает в запрос служебное: предел длины ответа, правило меток документа, формат опросника, просьбу исправить ответ. Не пишите это в `task`.
4. Исходные файлы в схему не пишите (поле `files`): их прикладывает User. Вложения к задаче уходят с первым сообщением каждого чата; файлы, приложенные в окне участника (📎), получает только этот участник на своём этапе. Если задаче нужны материалы, напишите в `description`, что User должен приложить, а в `task` первого шага ссылайтесь на «приложенные файлы».

Участие User. Оно редкое и осмысленное.
- User не помощник, на которого перекладывают работу. Не просите его писать, исправлять или проверять большой текст, искать данные, оценивать то, что может оценить модель.
- Допустимы только два случая: (а) в начале, когда задача неоднозначна: один опросник с выбором, чтобы уточнить ключевое (какой функционал, для кого, какой бюджет); (б) решение или утверждение там, где его нельзя поручить модели: выбрать вариант, утвердить документ.
- Не больше двух шагов User на схему. Не ставьте шаг User, если без него схема работает.

Виды шагов (`kind`).
1. `round` — запрос уходит всем моделям шага, они отвечают независимо. Поля: `ref`, `kind`, `task` (общее задание), `models` (список моделей), `input`, `output`, `chat`; описательные для человека: `title`, `goal`, `quality`, `rules`.
2. `owner` — шаг User: он читает документ или пишет ответ и нажимает «Отправить». Поля: `ref`, `kind`, `models` (всегда `[]`), `task` (что User должен сделать), `document` (ссылка на более ранний раунд из ОДНОЙ модели, документ которого User увидит в окне), `input`; описательные: `title`, `goal` (для чего шаг; User видит его в окне шага), `quality`, `rules`.
Видов два. Синтез, судья, жюри, проверяющий — роли и обычные раунды, а не отдельные виды. Синтез: раунд из одной модели с ролью `interaction_meta_synthesis`. Проверка: раунд с критериями в `task`; замечания применяет следующий раунд. Если требуется решение User, добавьте шаг `owner` и передайте ему документ и вердикт.
Чтобы одна модель увидела ответ другой, поставьте шаг этой модели ниже и дайте ему ответ источника (см. «Входы»).

Поля схемы.
Корень: `schemaVersion` (1 для обычных схем; 2 для отдельных ID/подписей участников), `origin` ("user"), `description` (презентация для человека, 3–6 фраз: цель, признак готовности, как устроен процесс и что должен приложить User), `spec`, `run`, `steps`.
`spec` — Task brief для человека, все значения — текст: `purpose`, `result`, `readiness`, `rules` (обязательно), `inputs`, `application`, `boundaries`, `failure` (по необходимости); смысл полей — в продуктовой части.
`run`: `policy` — "auto": шаги идут без остановки, но если на шаге ответил не каждый участник, приложение спрашивает User (повторить, пропустить участника или шаг, остановить); шаг User всё равно ждёт ответа. Без `run` и при "manual" приложение ставит паузу после каждого шага, кроме последнего. `maxWords` — общий предел длины ответа: только 300, 500, 700 или 1000. Без поля предел 300 слов. Предел — просьба уложиться в него: по умолчанию (`strictLength: false`) документ не сокращается, длинный ответ принимается; при `strictLength: true` ответ длиннее предела отклоняется, и модель просят сократить. Для документов ставьте 700 или 1000. У модели можно задать свой `maxWords` (любое положительное целое).
Модель в шаге: `name` (обязательно), `role` (необязательно), `task` (личное задание: ЗАМЕНЯЕТ общее `task` шага целиком, а не дополняет; общие требования повторите в личном или не задавайте личных заданий), `maxWords`. В формате 2 у КАЖДОГО участника обязателен `id`; `label` — понятная подпись, например «Claude · Автор» и «Claude · Проверяющий». Один `id` повторяйте во всех шагах работы этого участника с неизменными `name` и `label`; в одном раунде ID не повторяются. У разных участников одной модели подписи должны различаться. Несколько участников могут иметь одинаковое `name`, но разные ID. Не создавайте отдельного участника только ради смены задания или роли; отдельный участник нужен для независимого контекста. Ссылки адресуются по `id`, а не по `label` или общему имени провайдера.
`settingsMode: "explicit"` нужен только для намеренно пустого персонального профиля: отключает наследование задания, дисциплины, входа и выхода шага; отсутствующий личный `input` означает "none". Для обычной исполняемой схемы это поле не добавляйте. `enabled: false` выключает отправку участнику в данном раунде; без поля участник включён. `onCanvas: true` оставляет выключенного участника на холсте. При ручном нажатии «+» приложение создаёт выключенную карточку; в готовой схеме нужных исполнителей оставляйте включёнными.
Имена моделей — только Claude, GPT, Gemini, Grok, Le Chat, Qwen, DeepSeek, Perplexity, Z.ai, Kimi (не «ChatGPT»).
Роли (`role`): interaction_meta_synthesis (свести в одно решение), interaction_critical_audit (критически проверить), interaction_select_ideas (выбрать идеи), interaction_pattern_clustering (сгруппировать по сути). Роль необязательна.
`chat` раунда: "continue" (по умолчанию) — каждый участник продолжает собственный чат; "new" — новый чат для каждого участника на первом запросе захода этого шага. Исправления и повторы внутри того же захода идут в этот же чат. Используйте "new" только для намеренного сброса контекста, а не для разделения двух участников одной модели. При потере сохранённого чата приложение пробует восстановить ту же переписку; если это невозможно, отправка останавливается. Не рассчитывайте на молчаливую замену новым чатом.
`ref`: раунды — r1, r2, r3… строго по порядку без пропусков, шаги User в эту нумерацию не входят; шаг User — owner:<латиница, цифры, _ или ->, например owner:ok.

Входы (`input` шага).
Не указан: самый первый шаг получает только задачу User; любой следующий раунд — ответы ближайшего более раннего шага, у которого они есть (после шага User — ответ User; если User пропустил шаг, придут ответы шага перед ним). Пользуйтесь этим умолчанием только когда выбранные ответы ещё нужны участнику и отсутствуют в его чате; иначе задайте вход явно по правилу ниже. Шаг User (`owner`) без `input` ничего не получает: его вход по умолчанию `none`. Явно: "none", "previous", "all" или список ссылок на более ранние шаги, например ["r2", "owner:q"]. Ссылаться можно только на шаги ВЫШЕ по списку.
Для одного ответа используйте `{ "step": "r1", "participant": "claude-author", "required": true }` внутри списка: например, `"input": [{ "step": "r1", "participant": "claude-author", "required": true }]`. В формате 2 здесь нужен `id`; в формате 1 — имя модели. Личный `input` участника заменяет вход шага: так можно дать каждому только недостающие ему материалы. Участники одного раунда отвечают независимо; чтобы проверяющий прочитал ответ автора, поместите проверку в следующий раунд и явно передайте ответ автора.

ПЕРЕДАЧА ДОКУМЕНТОВ: ОДНА ВЕРСИЯ — ОДИН РАЗ В КАЖДЫЙ ЧАТ.
Ссылка на шаг или артефакт во `input` вставляет в запрос полный текст заново, даже если он уже есть в чате участника. Поэтому документ подаётся во `input` только на первом этапе, где он нужен этому участнику; дальше — ссылка по названию в `task`. Умолчание `previous` тоже передаёт текст заново: если предыдущий ответ уже есть в чате участника (он сам его написал или получал), поставьте `"input": "none"`. Проверяйте каждого участника отдельно: общий `input` может быть новым для одного и повторным для другого.
Пример: r1 — автор пишет «План»; r2 — проверяющий получает «План» через `input`; r3 — автор получает только замечания проверяющего (свой «План» он видит в чате); r4 — тот же проверяющий с `"input": "none"` и `task` «проверь сроки в «Плане» из этого чата».

Документы и опросники.
Документ — результат шага, который User читает и правит или который читает другая модель. Объявите его в `output` раунда; документ, который покажет User шаг `owner`, объявляйте в раунде ОДНОЙ модели: `{ "document": "read", "artifacts": [ { "id": "map", "name": "Карта функций", "pointer": "" } ] }`. Приложение само попросит модель написать документ между метками, вырежет его из ответа и покажет User в окне (пояснения модели вокруг в документ не попадают). Затем шаг `owner` с `"document": "<ref раунда>"` покажет его User; User может исправить текст и нажать «Отправить», дальше уходит его утверждённый вариант.
Опросник: раунд одной модели с `"output": { "format": "json", "document": "form" }`; модель сама составит пункты (выбор одного, выбор нескольких, текст, да/нет, ключевые обязательные), User заполнит форму в окне и нажмёт «Отправить», ответы «вопрос — ответ» уйдут следующему шагу. В `task` раунда опишите только тему опросника (число пунктов до 7, в основном с выбором), формат JSON приложение допишет само.
Документ для User от нескольких моделей: сначала раунд нескольких моделей без документа, затем раунд из одной модели с ролью interaction_meta_synthesis, он и объявляет документ.
Именованный артефакт: если результат шага нужен нескольким участникам ниже (каждому — один раз, на первом этапе, где он ему нужен), объявите его в `output` шага: `{ "artifacts": [ { "id": "shortlist", "name": "Короткий список", "pointer": "" } ] }` (в текстовом ответе один артефакт, `pointer` пустой). Ссылайтесь на него во `input` адресом `{ "artifact": { "step": "r2", "participant": "Claude", "id": "shortlist" }, "version": "latest", "required": true }`: придёт только этот артефакт, а не весь ответ шага (`participant` — ID участника, в формате 1 это имя модели; у шага User — "owner"). Доработка: автор, который правит свой документ, видит его в своём чате — передавать ему документ не нужно. Объявите у шага доработки новый артефакт (например «План, итог») без `revisionOf` и подайте автору только замечания. `revisionOf` нужен, только если следующие шаги берут документ по `"version": "latest"`; он требует того же артефакта во `input` автора, то есть повторной передачи. Тогда скопируйте в `revisionOf` тот же объект, что во `input`, целиком, включая `version`: `"revisionOf": { "artifact": { "step": "r1", "participant": "claude-author", "id": "plan" }, "version": "latest" }` (`required` переносить не нужно). Правка User в окне документа тоже новая версия, поэтому изменённый документ подавайте модели снова, хотя прежнюю версию она видела.
Если после шага User есть этапы, следующий ОБЯЗАН применить ответ User: напишите в его `task`, что делать, и просите вернуть документ целиком, а не отдельный раздел с правками. Ответ каждого шага User, кроме последнего шага схемы, должен читать какой-то более поздний шаг. Шаг User, который утверждает итоговый документ, может завершать схему: его утверждённый вариант — последняя версия документа.

ЖЁСТКИЕ ПРАВИЛА (нарушение — схема не установится).
1. Только поля из этого запроса; неизвестное поле — ошибка. Двойные кавычки, без комментариев, без запятой после последнего элемента, числа числами.
2. Шагов `file`, `gate`, `route`, `synthesis`, `foreach`, полей `block`, `why`, `inputs` с точками и «исходных артефактов» нет. Нужное записывайте обычными раундами.
3. `models` у `owner` — `[]`; у `round` хотя бы одна модель. `document` у `owner` ссылается на раунд с одной моделью, у которого объявлен `output.document`.
4. Раунды нумеруются r1, r2, r3… подряд, шаги User не считаются; раундов не больше 50. Иначе холст схему не примет.
5. Не придумывайте шагов ради объёма: столько шагов, сколько нужно задаче.

ФОРМА ОТВЕТА.
Сначала ОДИН JSON-объект (первый символ {, последний }), без markdown-ограждений. После него — три коротких пункта (см. ниже). Если не помещается: сокращайте тексты заданий и `spec` до одной фразы, но НЕ убирайте шаги и НЕ обрывайте JSON.

ПРОВЕРЬТЕ ПЕРЕД ОТВЕТОМ (про себя):
 □ в `description` названы цель и признак готовности результата;
 □ в `spec` заполнены `purpose`, `result`, `readiness`, `rules`; всё, что должна выполнить модель (в том числе запреты из `spec.rules`), повторено в `task` этапов;
 □ каждый этап нужен, промежуточные результаты используются дальше, итог решает задачу User;
 □ проверки имеют конкретные критерии, независимость проверена по истории участников, выбранное взаимодействие объяснено;
 □ содержательные решения делает модель или User; схема не обещает ветвлений, автоматического пропуска этапов или цикла «до успеха»;
 □ ни один `input` не ссылается на шаг ниже или на себя;
 □ в формате 2 у каждого участника есть `id`, в следующих шагах он сохранён с теми же `name` и `label`; подписи участников одной модели различаются, ссылки используют ID;
 □ участники одной модели имеют разные ID и независимые чаты; нужные исполнители не выключены через `enabled: false`;
 □ пройдите по каждому участнику сверху вниз: если во `input` его этапа (явном или по умолчанию `previous`) стоит документ, который он уже получал или сам написал, уберите его из `input` и сошлитесь на него в `task`; новая версия и участник, который документ ещё не видел, — исключения;
 □ `revisionOf` стоит только там, где следующие шаги берут документ по `"version": "latest"`, и это тот же объект, что во `input` автора, с `artifact` и `version`;
 □ шагов User не больше двух, каждый нужен (опросник в начале и/или утверждение документа), ответ каждого, кроме последнего шага схемы, читает более поздний шаг;
 □ если после шага User есть этапы, следующий применяет ответ и возвращает документ целиком;
 □ `document` у `owner` указывает на раунд из одной модели с объявленным `output.document`;
 □ в раунде либо общее `task`, либо личные `task` у всех моделей (личное заменяет общее);
 □ `run.maxWords` достаточен для самого длинного документа;
 □ у каждого шага укажи `title` и `goal`, у каждого документа — `description` в `output.artifacts[]` (например: «Список функций с пользой для каждой»): из них строятся подсказки при наведении на холсте, модели их не получают. Личный `task` у модели ставь только когда задания участников шага различаются: он ЗАМЕНЯЕТ общее задание шага целиком, поэтому в личный `task` нужно вписать полный текст;
 □ имена моделей и роли из списков, JSON закрыт и разбирается без ошибок.
````
