# Продуктовая часть запроса: Изменение архитектуры

**Когда выбирать.** Есть работающая система с готовой архитектурой, и решено изменить её часть: заменить компонент, изменить интерфейс или модель данных, перенести ответственность, разделить или объединить модули. Итог — предложение об изменении: целевое состояние части, влияние на остальную систему, путь перехода, откат и проверка.
**Когда не подходит.** Система строится с нуля — [Проектирование](solution-design.md). Ещё не решено, какой из вариантов изменения выбрать, и нужен только выбор — [Выбор решения](decision.md). Изменение спроектировано, нужен только план работ — [Планирование](planning.md).
**Опыт прогонов.** Отдельных прогонов такого вида не было; текст — гипотеза, проверяется первым прогоном.

Это продуктовая часть запроса на создание схемы. Текст из ограждения вставляется в блок «ПРОДУКТОВАЯ ЧАСТЬ» [шаблона запроса по виду задачи](<../basic-model-request-typed.md>); техническая часть и общие правила процесса уже есть в шаблоне.

````
ВИД ЗАДАЧИ: ИЗМЕНЕНИЕ АРХИТЕКТУРЫ
User получает предложение об изменении части существующей системы: почему её меняют, какой она станет, что это затронет в остальной системе, как перейти от текущего состояния к целевому, не ломая работающее, как откатиться и как проверить результат. Отличие от проектирования: система уже есть, и главная работа — не сломать то, что меняться не должно.

Работайте как бизнес-консультант: сначала поймите задачу и выберите метод, потом проектируйте процесс. Продуктовый слой схемы — `description`, `spec`, `title` и `goal` этапов, описания артефактов — читает человек на холсте; модели получают задание этапа (`task`) и его входы. Всё, что должна выполнить модель (требования к результату, критерии, запреты), перенесите в `task` соответствующего этапа.

1. ПОСТАНОВКА (Task brief → `spec`)
Выясните из задачи User:
— что меняем: какая часть системы, где проходят её границы;
— причина: какая проблема у текущего решения и по какому измеримому признаку будет видно, что изменение её решило;
— текущее состояние: как устроена изменяемая часть и с чем она связана — по материалам User (описание архитектуры, код, схемы, документация);
— что меняться не должно: внешние контракты, поведение для пользователей, данные, принятые решения — неизменные условия;
— допустимое: можно ли нарушить обратную совместимость, допустим ли простой, нужен ли период совместной работы старого и нового;
— ограничения: сроки, команда, технологии, нормы.
Запишите:
— `spec.purpose` — что меняем, почему и по какому признаку будет видно, что проблема решена;
— `spec.result` — предложение об изменении с целевым состоянием, картой влияния, путём перехода, откатом и планом проверки;
— `spec.readiness` — проверяемые признаки, например: «текущее состояние описано по материалам User, пробелы помечены; перечислены неизменные условия; у каждой затронутой части и интерфейса названо, как именно они меняются; каждый шаг перехода оставляет систему рабочей и имеет откат; план проверки включает регрессию затронутого и критерии приёмки; рассмотрен вариант минимального изменения»;
— `spec.rules` — неизменные условия, ограничения совместимости и простоя, запрет описывать текущую систему по догадкам;
— по необходимости: `spec.inputs` — материалы о текущей архитектуре; `spec.boundaries` — что в задачу не входит (в том числе переделка остальной системы); `spec.failure` — главные риски: пропущенный потребитель изменяемой части, неработоспособный промежуточный шаг, невозможный откат.
Модели знают о системе только то, что им передали. Попросите User приложить описание архитектуры и нужные фрагменты кода; если их нет — опросник в начале о границах части, её связях и неизменных условиях.

2. МЕТОД
— Порядок: текущее состояние → проблема и цель → варианты целевого состояния → выбор → анализ влияния → путь перехода → проверка. Текущее состояние фиксируется первым и одинаково для всех следующих этапов: варианты и влияние строятся на нём, а не на представлениях каждого участника.
— Минимальное изменение: среди вариантов всегда есть минимальный, решающий проблему с наименьшим затрагиванием системы. Если выбран более крупный, причина названа. Переделка соседних частей «заодно» — отдельная задача.
— Анализ влияния: кто использует изменяемую часть (модули, интерфейсы, данные, внешние потребители), что у каждого изменится и что для этого нужно. Отдельно — поведение, которое может измениться незаметно: порядок событий, время ответа, ошибки, хранение данных.
— Переход: по шагам, каждый из которых оставляет систему рабочей; где нужно — период совместной работы старого и нового; миграция данных; точка отката у каждого шага. Переход «одним махом» допустим, только если User согласился на такой риск.
— Независимость: если жизнеспособных вариантов несколько, их предлагают несколько участников независимо. Предложение ведёт один автор.
— Проверка: участник, не писавший предложение, ищет пропущенных потребителей, нарушенные контракты и неизменные условия, неработоспособные промежуточные шаги, невозможный откат; плюс одна строка premortem: «что сломается у тех, кто пользуется этой частью сейчас».
— Глубина: по охвату влияния и обратимости. Проверку на работающей системе модели не выполняют: она оформляется планом проверки с критериями приёмки.

3. СМЫСЛОВАЯ МОДЕЛЬ И АРТЕФАКТЫ
Сущности: изменяемая часть → причина и цель → текущее состояние → неизменное условие → вариант → целевое состояние → потребитель (зависимая часть) → интерфейс или контракт → влияние → шаг перехода → точка отката → проверка → риск.
Связи: каждый потребитель связан с изменяемой частью через интерфейс; влияние описывает, что у потребителя меняется; каждый шаг перехода сохраняет неизменные условия и имеет точку отката; проверка покрывает целевое состояние и каждого затронутого потребителя.
Артефакт «Предложение об изменении архитектуры»:
— обязательные блоки: причина и цель с признаком успеха; текущее состояние изменяемой части и её связи (по материалам, пробелы помечены); границы изменения и неизменные условия; варианты, включая минимальный, и выбор с причиной; целевое состояние; карта влияния (потребитель или интерфейс — что меняется — что сделать); совместимость; путь перехода по шагам с точками отката; миграция данных (если есть); план проверки — регрессия затронутого и критерии приёмки; риски с мерами; открытые вопросы; журнал отклонённых замечаний;
— доказательства: утверждения о текущей системе опираются на материалы User с указанием, откуда взято; догадки помечены;
— готовность: у каждого потребителя в карте влияния есть действие, у каждого шага перехода — откат;
— подача: резюме изменения и главные риски в начале, подробности ниже.

4. ТИПОВОЙ ПРОЦЕСС
Обязательны требования к качеству результата — раздел 3 и `spec.readiness`. Состав этапов зависит от размера и риска задачи: ниже — полный процесс для сложной задачи. Для небольшой задачи достаточно автора и одной проверки, а иногда одного этапа. Независимые варианты нужны, когда есть несколько жизнеспособных подходов; шаг User — только когда остаётся решение, которое нельзя поручить модели.
1) Опросник (по необходимости) — границы части, неизменные условия, допустимость простоя и нарушения совместимости.
2) Текущее состояние — один участник по материалам User описывает изменяемую часть, её связи и потребителей; пробелы помечает, а не додумывает.
3) Варианты (если подходов несколько) — несколько участников независимо, на основе описания текущего состояния; минимальный вариант обязателен.
4) Предложение — один автор: выбор с причиной, целевое состояние, карта влияния, путь перехода с откатом, план проверки.
5) Аудит влияния — участник, не писавший предложение, по критериям раздела 2; замечание: где, что не так, почему, как исправить.
6) Правка — автор вносит принятое, отклонённое записывает в журнал с причиной, возвращает предложение целиком.
7) User (если остаётся его решение: принять риск, простой, отказ от совместимости) — решает и при необходимости правит текст.
8) Итог (если был шаг User) — автор выполняет указания User и возвращает предложение целиком.

5. УЧАСТИЕ USER
— В начале: материалы о текущей архитектуре; причина изменения и неизменные условия, если их нет в задаче.
— В конце: решения, которые нельзя поручить модели, — допустимый риск, простой, нарушение совместимости.

6. ЧАСТЫЕ ОШИБКИ
— Текущая система описана по догадкам, а не по материалам User.
— «Заодно» переделывается вся система вместо изменяемой части.
— Пропущены потребители изменяемой части; контракты меняются молча.
— Переход одним шагом, без рабочих промежуточных состояний и без отката.
— Проверяется только новая часть, без регрессии затронутого.
— Причина изменения не измерима, и неясно, решена ли проблема.

7. ПРОВЕРЬТЕ
□ в `spec.purpose` названы изменяемая часть, причина и признак успеха;
□ неизменные условия и запрет догадок о текущей системе вписаны в `task` этапов;
□ текущее состояние фиксируется до вариантов и передаётся следующим этапам;
□ минимальный вариант рассмотрен;
□ у каждого потребителя есть действие, у каждого шага перехода — откат;
□ если предложение проверяется, это делает участник, который его не писал;
□ шаг User есть, только если остаётся его решение.
````
