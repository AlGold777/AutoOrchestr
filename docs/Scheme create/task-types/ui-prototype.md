# Продуктовая часть запроса: Прототип интерфейса

**Когда выбирать.** Есть идея приложения, сайта или функции, и нужно быстро получить кликабельный прототип интерфейса, чтобы пройти главный сценарий пользователя и увидеть, понятен ли он. Итог — один файл HTML, который открывается в браузере, и короткая инструкция, как его открыть.
**Когда не подходит.** Нужны концепция продукта, состав первой версии и метрики или работающий продукт с данными и сервером — [Разработка продукта](product-development.md). Нужна спецификация устройства решения — [Проектирование](solution-design.md).
**Опыт прогонов.** Отдельных прогонов такого вида не было; текст — гипотеза, проверяется первым прогоном.

Это продуктовая часть запроса на создание схемы. Техническая часть — [общий запрос](<../basic-model-request.md>); при сборке этот текст встаёт в блок «ПРОДУКТОВАЯ ЧАСТЬ» [шаблона](<../basic-model-request-typed.md>).

````
ВИД ЗАДАЧИ: ПРОТОТИП ИНТЕРФЕЙСА
User получает кликабельный прототип: один файл HTML (разметка, стили и скрипт внутри), который открывается в браузере без установки, сервера и интернета и позволяет пройти главный сценарий пользователя от первого экрана до результата. Данные вымышленные, сервера и хранения нет: прототип показывает, как пользователь движется по экранам, а не как устроена система.

Работайте как бизнес-консультант: сначала поймите задачу и выберите метод, потом проектируйте процесс. Продуктовый слой схемы — `description`, `spec`, `title` и `goal` этапов, описания артефактов — читает человек на холсте; модели получают задание этапа (`task`) и его входы. Всё, что должна выполнить модель (требования к результату, критерии, запреты), перенесите в `task` соответствующего этапа.

1. ПОСТАНОВКА (Task brief → `spec`)
Выясните из задачи User:
— пользователь: кто он и в какой ситуации пользуется продуктом;
— главный сценарий: с чего пользователь начинает, какого результата достигает, какие решения принимает по пути; один главный сценарий, при необходимости один-два дополнительных;
— устройство: телефон, планшет или компьютер — от этого зависят размеры экранов и навигация;
— что проверяет прототип: где пользователь может запутаться, понятны ли названия и порядок шагов;
— ограничения: стиль, язык, обязательные элементы, образцы, если User их приложил;
— что не входит: регистрация, оплата, настройки и всё, чего нет в главном сценарии.
Запишите:
— `spec.purpose` — пользователь, его задача и что проверяет прототип;
— `spec.result` — кликабельный прототип одним файлом HTML и инструкция, как его открыть;
— `spec.readiness` — проверяемые признаки, например: «главный сценарий проходится кликами от первого экрана до результата без тупиков; на каждом экране понятно, что делать дальше, и есть путь назад; все кнопки сценария работают, остальные помечены как неактивные; тексты интерфейса написаны для пользователя, без заглушек; файл открывается в браузере без интернета и установки»;
— `spec.rules` — один файл без внешних библиотек и обращений к сети; вымышленные данные; только экраны сценария;
— по необходимости: `spec.boundaries` — что не делаем (сервер, вход, оплата); `spec.failure` — риск, что прототип не поместится в один ответ модели: тогда сокращаются экраны, а не обрывается код.
Если неясны пользователь, главный сценарий или устройство — опросник в начале.

2. МЕТОД
— От сценария к экранам: сценарий → шаги пользователя → экраны → элементы и переходы → тексты интерфейса → код. Сначала определяется карта экранов, потом пишется код.
— Операции: описание сценария, карта экранов и переходов, тексты интерфейса, программирование прототипа, проверка прохождением сценария.
— Независимость: разные варианты карты экранов полезны, когда сценарий можно построить по-разному (например, пошаговый мастер или один экран). Код пишет один автор: файл не собирают из частей разных моделей или этапов.
— Объём: прототип должен поместиться в один ответ модели, обычно 3–7 экранов. Если не помещается — убираются второстепенные экраны, а не дробится код.
— Проверка: участник, не писавший код, проходит сценарий по коду шаг за шагом: какие элементы на экране, куда ведёт каждая кнопка, нет ли тупиков, совпадает ли с картой экранов; ищет ошибки, из-за которых файл не откроется или переход не сработает. Модель не открывает файл в браузере: её проверка — чтение кода, а не запуск; пройти прототип кликами User может, открыв файл после схемы.
— Удобство оценивается по сценарию: число шагов, понятность названий, видна ли следующая цель. Реакции пользователей не выдумываются.

3. СМЫСЛОВАЯ МОДЕЛЬ И АРТЕФАКТЫ
Сущности: пользователь → цель → сценарий → шаг → экран → элемент (кнопка, поле, список) → переход → состояние экрана (пусто, заполнено, ошибка) → текст интерфейса → вымышленные данные.
Связи: каждый шаг сценария выполняется на экране; каждая кнопка сценария ведёт на экран или меняет состояние; у каждого экрана есть вход и выход.
Артефакты:
— «Карта экранов» (когда её проверяют до кода): экраны с назначением, элементами и переходами; путь главного сценария по экранам;
— «Прототип»: один файл HTML целиком, готовый к сохранению; в начале файла — комментарий с названием и списком экранов;
— «Как открыть»: две-три строки — сохранить как файл .html, открыть в браузере, с какого экрана начать и какой сценарий пройти;
— готовность: выполнены признаки из `spec.readiness`;
— подача: код целиком, без сокращений вроде «остальное без изменений».

4. ТИПОВОЙ ПРОЦЕСС
Обязательны требования к качеству результата — раздел 3 и `spec.readiness`. Состав этапов зависит от размера и риска задачи: ниже — полный процесс для сложной задачи. Для небольшой задачи достаточно автора и одной проверки, а иногда одного этапа. Независимые варианты нужны, когда есть несколько жизнеспособных подходов; шаг User — только когда остаётся решение, которое нельзя поручить модели.
1) Опросник (по необходимости) — пользователь, главный сценарий, устройство.
2) Сценарий и карта экранов — один автор; если сценарий можно построить по-разному, сначала несколько участников независимо предлагают карты, затем автор выбирает и сводит.
3) Проверка карты (для сложного сценария) — участник, не писавший карту: тупики, лишние шаги, непонятные названия.
4) Прототип — один автор пишет файл целиком по карте экранов. В `task`: карта экранов, один файл без внешних библиотек и сети, вымышленные данные, все переходы сценария рабочие, код целиком.
5) Проверка кода — участник, не писавший код, проходит сценарий по коду и возвращает замечания: экран, элемент, что не так, как исправить.
6) Правка — автор вносит замечания и возвращает файл целиком вместе с инструкцией «Как открыть».

5. УЧАСТИЕ USER
— В начале: пользователь, сценарий и устройство, если их нет в задаче; образцы, если они есть.
— По ходу: выбор между вариантами карты экранов — только если они различаются по замыслу.
— Проверять код и править тексты интерфейса User не должен.

6. ЧАСТЫЕ ОШИБКИ
— Код пишется до того, как определены сценарий и экраны.
— Прототип пытается охватить весь продукт, не помещается в ответ и обрывается.
— Файл собран из частей разных моделей или этапов: стили и переходы не сходятся.
— Внешние библиотеки и обращения к сети: файл не открывается без интернета.
— Заглушки вместо текстов; кнопки сценария, которые никуда не ведут.
— Чтение кода выдано за проверку в браузере.
— Код возвращается фрагментами вместо файла целиком.

7. ПРОВЕРЬТЕ
□ в `spec.purpose` названы пользователь, его задача и что проверяет прототип;
□ главный сценарий и карта экранов определены до этапа кода;
□ требования «один файл, без сети, вымышленные данные, код целиком» вписаны в `task` этапа прототипа;
□ код пишет один автор;
□ если код проверяется, это делает участник, который его не писал, проходя сценарий;
□ итог — файл целиком и инструкция «Как открыть»;
□ шаг User есть, только если остаётся его решение.
````
