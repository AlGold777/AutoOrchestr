3. Вопросы 12.1–12.10

12.1. MediaPipe + кинематическая оптимизация. Пригодно для мобильного прототипа, но не обеспечивает доказанную абсолютную метрическую точность.

12.2. Кандидаты — локтевой угол, относительная конфигурация плеча и корпуса, наклон корпуса. Ненадёжны: пронация предплечья, осевые вращения отдельных костей, положение ракетки, точный контакт.

12.3. Базовая горизонтальная система фиксируется по стойке; вращения частей тела вычисляются на каждом кадре относительно базы.

12.4. Confidence точек + чувствительность к ракурсу + residual fitting + калиброванное распределение ошибок. Одного visibility недостаточно.

12.5. Предварительно σ ≤ 7° и P95 межракурсного расхождения ≤ 12°. Подтвердить контрольной выборкой.

12.6. Без IMU оценивать вертикаль по стойке с неопределённостью. При неоднозначности отключать зависящие от неё метрики.

12.7. После первичной реконструкции и до расчёта метрик, с сохранением сырых данных. Сглаживать без фазового сдвига и без прохождения через длительные пропуски.

12.8. Скелет и орбитальная камера на штатном Canvas. Цель — 60 fps; испытать перекрытия, порядок отрисовки и нагрузку.

12.9. Три телефона, синхронизация, калибровочная мишень, триангуляция, тест одного удара с разных ракурсов.

12.10. Заменить эвристические confidence, независимое сглаживание координат, фиксированные пороги и проверку только через σ. Сохранить мобильный Pose Landmarker до появления доказанно лучшего совместимого кандидата.

4. Самая сильная идея

View-Invariance Certificate — сертификат межракурсной устойчивости каждой отдельной метрики.

Во время разработки строится эмпирическая карта ошибок по ракурсам, типам перекрытия и фазам смэша. На устройстве система оценивает, попадает ли текущая метрика в проверенную область качества, и только тогда формулирует отклонение.

Это выполнимо без обучения крупной нейросети. Уникальность относительно OnForm, Hudl, Sportsbox и SwingVision не подтверждена — сравнительный аудит их текущей реализации не проведён.

7. Допущения и компромиссы

Главный компромисс: надёжные, ограниченные 3D-метрики вместо обещания полного метрически точного цифрового двойника.

Худшие свойства: при плохом ракурсе система может не обнаружить ошибку; без ракетки нет точного момента контакта; абсолютные координаты в метрах остаются модельной оценкой; 360° не создаёт отсутствующую информацию о скрытых частях тела.

Не проверено: реальные скорости и потребление памяти на iOS/Android, ошибка глубины на смэшах, корректность всех преобразований координат MediaPipe, качество IK, покрытие интервалов, коммерческие условия каждой версии распространяемых бинарных компонентов.

Итоговое решение: архитектура пригодна для начала реализации с обязательными воротами после этапа 0. Если межракурсная ошибка M1–M3 превышает установленные пределы, выпуск соответствующих диагностических статусов блокируется. Подмена отсутствующей достоверности визуально убедительной 3D-анимацией недопустима.

Для каждого спортсмена нормировать длины сегментов; сравнивать локальные углы и фазовые признаки, а не расстояния между абсолютными координатами. Различную ведущую руку учитывать зеркальным преобразованием.

Теоретически:
\[
\angle(Ra,Rb)=\angle(a,b)
\]

Но ошибки оценённой глубины зависят от ракурса. Применять калиброванный интервал ошибки \(q_i\), рассчитанный на независимых межракурсных наблюдениях.
d = abs(metricStudent - metricCoach)

if d + q <= T: IN_RANGE
else if d - q > T: DEVIATION
else: UNCERTAIN


\(T\) — предварительный порог практического различия; \(q\) включает ошибку обоих видео. Для STRONG_DEVIATION использовать отдельно откалиброванный более высокий порог.

DTW ограничить фазами движения. Максимум высоты запястья — предварительный якорь, не доказанный момент контакта с мячом. Без ракетки точный контакт недоступен.

Разница телосложения: нормализация устраняет единицы масштаба, но не физиологические различия подвижности. Поэтому отклонение от тренера не объявляется автоматически технической ошибкой.

3. Ответы 12.1–12.10
12.1. Для MVP — монокулярная root-relative 3D-поза с кинематической оптимизацией. Абсолютно метрическая реконструкция из одного видео без масштабирующей информации не гарантируется.

12.2. Проверять M1–M3. M4–M5 экспериментально. Осевые вращения плечевой/локтевой системы, кисть и ракетка недостаточно наблюдаемы.

12.3. Базовая система координат фиксируется по стойке; локальные вращения сегментов обновляются каждый кадр.

12.4. Использовать видимость, reprojection residual, непрерывность, перекрытия и распределение межракурсной ошибки. Confidence модели не считать калиброванной вероятностью метрической точности.

12.5. Предварительно σ ≤ 7° и P95 ≤ 12°, затем подтверждение на новых игроках.

12.6. Без IMU оценивать вертикаль по стойке и изображению; при неоднозначности M3 — UNCERTAIN.

12.7. Сглаживать после обнаружения выбросов, совместно с кинематической оптимизацией, не размывая фазовые пики.

12.8. Для скелета достаточно Canvas и собственной 3D-проекции. Полная поверхность тела не нужна для текущих метрик.

12.9. Три камеры, калибровка, синхронизация, триангуляция и контрольная выборка.

12.10. Заменить эвристические пороги, раздельное сглаживание координат и некалиброванную надёжность; сохранить мобильный базовый движок до доказательства преимущества альтернативы.
4. Самая сильная идея
View-Invariance Certificate: для каждой метрики система хранит калиброванную область ракурсов и условий видимости, при которых ошибка допустима. Показывать DEVIATION только внутри этой области; за её пределами — UNCERTAIN.

Публичная документация Onform описывает 2D-наложения и скелетный трекинг, а Sportsbox — сравнение двух 3D-аватаров. Аналогичный сертификат качества там не документирован; его фактическое отсутствие у конкурентов не подтверждено.

7. Итог: приоритеты и ограничения
1. Межракурсная достоверность — главный риск: ошибка реконструкции превышает полезное различие техники.
2. Калиброванная неопределённость — риск: слишком много результатов UNCERTAIN.
3. Кинематическая оптимизация — риск: подавление реального быстрого движения.
4. Единый мобильный движок — риск: скорость и память слабых Android.
5. Вращаемый 3D-скелет — риск: пользователь воспринимает оценку как измеренную реальность.
Главный компромисс: лучше три проверенные метрики, чем полный цифровой двойник с недоказанной точностью.

Худшие свойства: невозможность восстановить скрытые суставы достоверно при некоторых ракурсах; отсутствие точной ориентации ракетки и момента контакта; условный метрический масштаб; возможное отсутствие диагностического результата.

Непроверено: производительность на целевых устройствах, межракурсная точность на паделе, калибровка вероятностей, соответствие координатных систем, окончательная совместимость и лицензирование поставляемых бинарных артефактов.

1. Захват
Стабилизация видео выключена (на iOS — режим .off, на Android — CONTROL_VIDEO_STABILIZATION_MODE_OFF). Электронная стабилизация кропит и деформирует кадр, и связь «гравитация ↔ изображение» ломается. Поддержка на устройствах — не подтверждено.
Параметры камеры по кадрам записываются в файл-спутник: фокусное расстояние и главная точка. Для iOS это матрица камеры в AVFoundation, для Android — LENS_INTRINSIC_CALIBRATION (оба имени из памяти, не подтверждено). Без них перспектива в оптимизации неверна.
Каждый кадр получает метку времени сенсора. Гравитация медленная, поэтому сдвиг до 50 мс на уровне ориентации не критичен. Если камера и датчик на разных часах (источник меток UNKNOWN), берётся ближайший отсчёт, статус SYNC_APPROX.
Гироскоп нужен для ручной съёмки: поворот камеры по кадрам берётся из датчика.
Режим ультраширокого объектива не используется (дисторсия вне модели).
2. Распознавание
Модель выбирается по результату 20-кадрового замера на первом запуске: ≤ 40 мс → уровень A (heavy, GPU/NPU-делегат); ≤ 100 мс → B (full); иначе → C (lite). Пороги — PROVISIONAL.
Сохраняются 2D, world, visibility, presence без отсечения порогами. Отсечение делается позже, чтобы можно было пересчитать.
Выбор человека касанием и трекинг по непрерывности рамки — как у автора.
На уровне A второй проход по зеркальному кадру даёт ансамбль из 2 оценок для оценки разброса. Это дороже вдвое. Выигрыш — не измерен, решается в фазе 0.
3. Реконструкция
Вход: 2D-ключевые точки, переведённые в лучи камеры (через параметры камеры), world-оценка MediaPipe как слабый приор, гравитация по кадрам.
Параметры: положения 19 суставов на кадр в системе «вертикаль — гравитация» плюс длины костей на клип (инициализация — медиана).
Стоимость:
E = Σ w·ρ_Huber(reproj) + α‖X − X_mp‖² + β(‖bone‖ − L)² + γ·joint_limits + δ(t)‖∇²X‖² + ε·stance_foot
joint_limits: гиперразгибание колена и локтя недопустимо, диапазоны сгибания берутся из биомеханических справочников (числа не подтверждено).
δ(t) ∝ 1/(1 + скорость запястья): сглаживание ослабляется в момент удара и не гасит пик.
stance_foot: опорная стопа лежит на плоскости пола (нормаль = гравитация) и неподвижна, пока скорость мала. Это даёт физическую правдоподобность.
Масштаб: абсолютные метры без роста человека не определяются. Углы масштаба не требуют; скорости выражаются в длинах корпуса в секунду.
Неопределённость: приближение Лапласа — ковариация суставов равна (JᵀJ)⁻¹ в решении. Затем 64 выборки из гауссианы дают распределение каждой метрики. Лаплас занижает разброс, поэтому масштаб ковариации подгоняется так, чтобы 90%-интервал покрывал межракурсную разницу в 85–95 % случаев (раздел 7).
Уровень C: без оптимизации, как у автора (world + гравитация + длины костей), с пометкой «упрощённый режим». Метрики M2 и M3 только с датчиком; M1 скрыта.
4. Хранение (.p3d v2)
Заголовок JSON: schema, profile=padel.smash.v2, engineInfo{bundleSha256, solverVer, limitsVer}, tier, intrinsics, fps, vertical=SENSOR|ESTIMATED.
Сырой слой: на кадр 33×(x,y)+33×(x,y,z) в float16 и 66 байт vis/pres в uint8 ≈ 400 Б. На 240 кадров ≈ 96 КБ.
Расчётный слой: на кадр 19×3 float16 + 19 лог-σ в uint8 ≈ 130 Б. На 240 кадров ≈ 31 КБ.
Итого: ≈ 130 КБ до сжатия.
Пересчёт: из сырого слоя без видео, когда меняется версия решателя или ограничений. Версии сравниваются по семантике: при смене мажорной версии показывается предупреждение и запускается пересчёт. Если сырой слой от другой модели MediaPipe — пересчёт только из видео.
5. Сравнение
Система тела: гравитация берётся по кадрам, потому что камера может двигаться. Азимут корпуса — один раз на клип по стойке. Вращение таза относительно корпуса считается по кадрам, иначе вращение в ударе «съедается» нормализацией.
Метрики: углы в родительской системе сустава (локоть, плечо относительно корпуса, колено), наклон корпуса к гравитации. Длины костей и рост в них не входят.
Перенос на тело ученика: призрак эталона строится по углам тренера, применённым к длинам костей ученика. Различия пропорций не дают ложного рассогласования.
Время: три якоря (момент загрузки руки, tA, завершение), линейная деформация между ними, DTW внутри сегментов в полосе Сакое–Чиба.
Вердикт:

  Δ = θ_you − θ_ref                      # средние распределений
  σΔ = sqrt(σ_you² + σ_ref² + σ_cal(d,az)²)
  T  = z·sqrt(σ_view² + σ_retest²)       # z = 1,64
  deviation        если |Δ| − T > 1,28·σΔ
  strong deviation если |Δ| − 2T > 1,28·σΔ
  uncertain        если σΔ > T/1,5 или видимость < 60 %

σ_view берётся из межракурсной калибровки, σ_retest — из повторов одного игрока. σ_cal(d,az) — поправка от доли сегмента вдоль оси камеры d и азимута. Все числа — PROVISIONAL.

Режимы: с собой (основной), с тренером, прогресс.
6. Показ
Холст без 3D-движка: проекция в общем ядре, кватернионная орбита с инерцией, кнопки Front/Side/Back/Top и «Match camera». Последняя ставит камеру орбиты в азимут съёмки, и скелет ложится на видео по подобранной камере.
Кости рисуются капсулами с сортировкой по глубине. Неопределённость показывается эллипсом: проекция 1σ-эллипсоида ковариации сустава.
Пара — рядом или наложением с призраком эталона. Один общий таймлайн в деформированном времени, покадровый шаг, замедление 0,25×.
Почему не 3D-движок: одинаковые пиксели на обеих платформах и нет зависимости от SceneKit. Утверждение автора, что Apple объявила SceneKit устаревшим, не подтверждено.
Постоянная подпись: «Estimated 3D from a single camera».
7. Проверка

Подробности — в ответах 12.5 и 12.9 и в таблице проверки ниже.

Ответы на вопросы 12.1–12.10

12.1. Для конца 2026 года лучший доступный на устройстве способ — не одна сеть, а связка: 2D-детектор + датчик гравитации + параметры камеры + пакетная оптимизация с ограничениями. Тяжёлые сети-сетки (SAM 3D Body) точнее по вращениям костей, но по [S2] не помещаются на телефон. Это ограничение носителя, а не качества метода.

12.2. Надёжно (после прохождения порога 12.5): сгиб локтя; наклон корпуса к гравитации при vertical=SENSOR. Условно: подъём плеча, сгиб колена опорной ноги. Не измеряются: пронация, кисть, ракетка (трекинга нет), внутреннее/внешнее вращение плеча (вращение вокруг оси кости в 33 точках не определено), разворот корпуса вокруг вертикали (сильная зависимость от глубины).

12.3. Гравитация — на каждый кадр (камера может двигаться). Азимут корпуса — один на клип. Вращения таза и корпуса внутри удара — относительные, по кадрам. Фиксировать полный поворот на каждый кадр нельзя: вращение в ударе исчезает.

12.4. Надёжность — не флаг, а число: σ метрики = Лаплас-ковариация + калиброванная поправка σ_cal(d,az). Дискретный статус получается порогами. Критерий корректности — покрытие: 90%-интервал должен покрывать межракурсное расхождение в 85–95 % случаев (диаграмма надёжности).

12.5. Критерий автора σ ≤ 7° слишком мягкий. При σ_view = 7° разница двух ракурсов одной и той же техники имеет σΔ ≈ 9,9°. Доля ложных отклонений при пороге 15° — 2·(1 − Φ(15/9,9)) ≈ 13 % (расчёт мой, на нормальном приближении). Мой критерий: σ_view ≤ 5° при T = 15°, что даёт σΔ ≈ 7,1° и ≈ 3,4 % ложных отклонений. Дополнительно 95 % пределы согласия (Bland–Altman) между парой ракурсов ≤ ±10°, верхняя граница доверительного интервала по кластерному бутстрепу по игрокам. Все числа — PROVISIONAL, фиксируются до прогона.

12.6. Без датчика вертикаль берётся из двух независимых оценок: стойка до замаха (линия «середина стоп → середина плеч», усреднённая) и вертикальные линии сцены (стойки забора, стены; поиск точки схода). Они сливаются по весам. Корректность проверяется на собственных клипах: датчик скрывается, расчётная вертикаль сравнивается с записанной. Допуск: медиана ≤ 3°, 95-й перцентиль ≤ 8° (PROVISIONAL). При превышении vertical=ESTIMATED, M3 и риск-паттерн — UNDETERMINED.

12.7. До оптимизации — только отбраковка выбросов по visibility и ограничение скорости. Сглаживание внутри оптимизации через член δ(t), ослабленный в момент удара. После — только для показа, с нулевой фазой. Метрики берутся из оптимизированной позы, а не из отфильтрованного ряда. Срез частот для показа подбирается в фазе 0 по минимуму σ_view; диапазон 8–15 Гц — рабочая гипотеза, не подтверждено.
Для запрета подсказок (А2): качество определяется азимутом камеры. Оно оценивается постфактум и выражается ростом σ в статусах, а не гейтом перед съёмкой.

12.8. Холст Canvas с капсулами, глубиной по сортировке и эллипсами неопределённости. Производительность: 33 точки, ~35 сегментов, два скелета — нагрузка мала. Цель ≤ 4 мс на кадр, измеряется в фазе 3.

12.9. Межракурсная проверка (см. таблицу проверки). Дорогого оборудования не нужно.

12.10. Заменить: (1) порог σ ≤ 7° (13 % ложных отклонений); (2) DTW по метрикам на выравнивание по якорям с DTW внутри; (3) фиксированный порог max(15°, 2σ) на порог из данных; (4) метрики как числа на метрики как распределения; (5) покадровое сглаживание на оптимизацию с приором; (6) тезис «M1–M3 не зависят от азимута» — верно лишь при корректной глубине, а ошибка глубины как раз зависит от азимута; (7) «ось камеры» для d: система осей worldLandmarks не подтверждена (в материале помечено NEEDS FACT), проверка в фазе 0.

Худшие свойства решения:

Лаплас-неопределённость занижает разброс, и без калибровки на данных ей верить нельзя.

Для вращений костей вокруг оси решения нет.

Ответы 12.1–12.10

12.1. Лучший практичный способ — монокулярные world landmarks MediaPipe + гравитация датчика + система тела; тяжёлые mesh-модели точнее, но не проходят on-device/лицензии. Точность не подтверждена.

12.2. Надёжно: сгиб локтя, подъём плеча, наклон корпуса к гравитации, сгиб колена. Плохо: разворот плеч/таза, пронация, кисть, ракетка, скручивание позвоночника — глубина шумит.

12.5. Достаточно σ между ракурсами ≤7° и доля LOW ≤20% на штатных клипах; это провизорно и фиксируется до прогона.

12.6. Без датчиков вертикаль — по вектору «середина стоп → середина плеч» в стойке, усреднённо; статус ESTIMATED, M3 LOW, риск-паттерн UNDETERMINED.

12.7. Сглаживать offline, zero-phase, после удаления выбросов; не сглаживать через разрыв >3 кадров; сырые данные хранить отдельно.

12.8. Рисовать 2D-проекцию скелета на Canvas, орбитальная камера, 33 точки, толщина/прозрачность как глубина; 60 fps; без SceneKit/Filament.

12.9. Качество доказывать 3 телефонами одновременно: межракурсная σ, триангуляция как эталон, повтор с намеренной ошибкой, паритет платформ.

Пояснения
Захват. Частота 60 fps достаточна для смэша (длительность ~200–400 мс). 120 fps на флагманах даёт запас по временному разрешению. Гравитация пишется в файл-спутник (JSON) с метками времени, интерполяция линейная.
Распознавание. MediaPipe Pose Landmarker — единственный бесплатный вариант с метрическими 3D-координатами (worldLandmarks в метрах, начало в тазу). Модель heavy точнее на размытых кадрах, но требует флагман (iPhone 13+, Pixel 7+). На слабых устройствах — модель full или lite с предупреждением LOW_ACCURACY. RTMPose используется только когда MediaPipe даёт visibility < 0.5 на ключевых точках (плечо, локоть, запястье) — это резерв, не основной путь.
Реконструкция. Отличие от варианта автора — кинематические ограничения:
Длины костей фиксируются как медиана по клипу (как у автора).
Добавляются угловые ограничения суставов (локоть: 0–160°, плечо: анатомические пределы).
Фильтр Калмана с моделью скелета: состояние — позиции и скорости суставов, наблюдения — MediaPipe, модель перехода — прямая кинематика с ограничениями.
Это убирает «дребезг» и физически невозможные позы, особенно при низкой видимости.
Хранение. Protocol Buffers вместо JSON даёт 20–30% меньший размер и быстрее парсинг. Float16 достаточен для координат в метрах (точность ~0.1 мм). Версия модели сохраняется, чтобы при обновлении MediaPipe можно было пересчитать.
Сравнение. Метрики считаются в системе тела, как у автора. Отличие — более строгая оценка неопределённости:
Для каждого сегмента считается не только d = |v · camAxis| / |v|, но и ковариация из фильтра Калмана.
Если ковариация позиции сустава > 0.05 м — метрика LOW, даже если d < 0.8.
Это даёт более честную оценку надёжности.
Показ. Рендеринг через Canvas (не SceneKit/RealityKit) — правильно, так как SceneKit устарел (не подтверждено для 2026, но тенденция ясна). Глубина передаётся толщиной линий (близкие — толще) и прозрачностью (далёкие — прозрачнее). Это работает одинаково на iOS и Android.
Проверка. Межракурсная согласованность — правильный подход. Добавляю тест на временную стабильность: один и тот же игрок делает 10 ударов подряд, метрики должны иметь σᵢ ≤ 5° (внутри одного ракурса).

Ответы на вопросы 12.1–12.10
12.1. Лучший способ получить метрическое 3D-движение.
MediaPipe Pose Landmarker с worldLandmarks — единственный бесплатный вариант с метрическими координатами и лицензией Apache 2.0. Альтернативы:
WHAM/SMPL — точнее, но исследовательская лицензия, требует GPU (не подтверждено коммерческое использование).
Apple Vision 3D — только iOS, нет паритета.
Триангуляция с нескольких камер — не подходит для мобильного приложения.
12.2. Какие величины измерять надёжно.
Надёжно: M1 (подъём плеча), M2 (сгиб локтя), M3 (наклон корпуса) — при vertical = SENSOR.
Ненадёжно: M5 (разворот корпуса) — сильно зависит от глубины; пронация, кисть, ракетка — MediaPipe не даёт точных вращений мелких сегментов.
12.3. Система координат тела: один раз или каждый кадр.
Один раз на клип по стойке до замаха. Если пересчитывать каждый кадр, вращение корпуса в ударе «съедается» нормализацией, и M3 (наклон корпуса) теряет смысл.
12.4. Оценка надёжности метрики.
Три фактора:
Видимость точек (visibility ≥ 0.5, presence ≥ 0.5).
Чувствительность к глубине: d = |v · camAxis| / |v| > 0.8 → LOW.
Ковариация позиций из фильтра Калмана > 0.05 м → LOW.
12.5. Согласованность между ракурсами.
Достаточно σᵢ ≤ 7° (стандартное отклонение метрики между 3 ракурсами) и доля LOW ≤ 20% на стандартных клипах. Обоснование: 7° — это ~12% от типичного диапазона углов; если σᵢ > 10°, метрика бесполезна для сравнения.
12.6. Вертикаль без датчиков.
Оценка по стойке: направление «середина стоп → середина плеч» в кадрах готовности, усреднённое. Допущение: камера примерно вертикальна. Статус vertical = ESTIMATED, M3 и риск-паттерн получают LOW.
12.7. Сглаживание.
Офлайн, нулевой фазы (Butterworth 4-го порядка, частота среза 6 Гц), отдельно по осям. Разрывы > 3 кадров не сглаживать. Сырые данные хранятся отдельно для повторной обработки.
12.8. Показ 3D-движения.
Canvas-based рендеринг (SwiftUI / Compose), орбитальная камера, глубина через толщину/прозрачность линий. Плюсы: одинаковая картинка на обеих ОС, нет зависимости от устаревающих 3D-движков, нагрузка минимальна.
12.9. Проверка качества без дорогого оборудования.
Межракурсная согласованность (3 телефона, один удар). Дополнительно: тест на временную стабильность (10 ударов подряд, σᵢ ≤ 5° внутри ракурса). Это не требует мокапов или motion capture.
12.10. Что заменить в плане автора.
Добавить фильтр Калмана с кинематическими ограничениями (§5.5).
Явно использовать NPU-ускорение (§5.2).
Учитывать ковариацию для оценки неопределённости (§5.8).
Уточнить определение tA с проверкой пика скорости (§5.6).

1.3. Реконструкция

Вертикаль по гравитации-спутнику (vertical=SENSOR); для импорта — оценка по стойке (ESTIMATED) с пониженной надёжностью M3. Идея выравнивания по гравитации совпадает с линией GVHMR (gravity-view coordinates, 2024) — это подтверждённый исследованиями ход, а не самодеятельность.
aiartweekly

Система тела фиксируется один раз на клип по стойке (таз, up=−g, right=бёдра, forward=up×right) — автор прав; изменений нет.

Критично: worldLandmarks — относительная глубина с началом в тазу, не абсолютные метры (GitHub issue #6034). Поэтому: масштаб клипа калибруется так, чтобы длина цепочки «таз→макушка» в условной вертикальной стойке равнялась доле роста пользователя (≈0,52·рост, поправка подбирается калибровкой, PROVISIONAL). Метрика M2 (локоть) масштабно-инвариантна, M1/M3 — тоже угловые; метрические величины (высота запястья в метрах) показываются только при успешной привязке.
github

Физическая правдоподобность: нуль-фазовое сглаживание (Savitzky–Golay / Butterworth вперёд-назад) на сырых world-точках → прямая кинематика с медианными длинами костей → детектор контакта стоп (скорость лодыжки ≈ 0 в горизонтальной плоскости пола) → принудительная нулевая скорость опорной стопы и фиксация плоскости пола. Это убирает дрожание по вертикали и «плавание» таза — главный визуальный артефакт монокулярного 3D.

Левша — зеркалирование эталона в 3D, как у автора.

1.4. Хранение

PoseTrack3D: кадр = 33×(x,y,z,visibility,presence) float16 + 2D-точки + гравитация-кватернион + engineInfo{модель, версия, калибровочный профиль}. Клип 4 с / 60 к/с ≈ 100–150 КБ (float16). Сырые точки и сглаженные — раздельно; повторный расчёт метрик по сырым — одна кнопка, повторный инференс — только при смене модели (с предупреждением несравнимости, как у автора R3-08).

1.5. Сравнение (главная проблема)

Независимость от ракурса достигается не словами, а конструкцией:

Метрики — только углы между сегментами тела в 3D (M1, M2, M3-полный и его сагиттальная/фронтальная составляющие). Азимут камеры исключён поворотом в систему тела; телосложение исключено тем, что углы безразмерны.

Неопределённость — числом, не словами: для каждого кадра σ метрики оценивается распространением дрожания: σ_точек оценивается по высокочастотному остатку после RTS-сглаживания в окне ±70 мс, далее Монте-Карло (100 возмущённых проходов по окну) → 90% ДИ угла. Угол с долей длины сегмента вдоль оси камеры d>0,8 помечается LOW (порог автора сохраняю).

Порог находки: T_i = max(15°, 3·σ_i(калибровка)), статусы: in range / deviation / strong / uncertain / n/a — без цифр (PC-030).

Числовой тест независимости (K2): межракурсная согласованность — один физический удар, 3 телефона синхронно (90°/45°/135°, синхронизация хлопком), σ между ракурсами ≤ 7° и согласование статусов ≥ 95% для допуска метрики в интерфейс (пороги фиксируются до прогона).

12.1. Лучший способ конца 2026: быстрый переносимый покадровый движок (MediaPipe heavy) + офлайн-оптимизационный 3D-лифт с физическими ограничениями и привязкой масштаба по росту; полносеточный HMR на телефоне нежизнеспособен (даже ускоренный — 8 к/с на RTX 6000 Ada ).

12.2. Надёжно: M2 (сгиб локтя), M1, M3-полный при SENSOR, тайминги фаз, высота запястья в длинах корпуса. Ненадёжно монокулярно: M5 (разворот плечи/таз, чувствителен к глубине), пронация, кисть, ракетка — остаются скрытыми.

12.6. Без датчиков: вертикаль = усреднённое «стопы→плечи» в стойке + согласованность с осью кадра; статус ESTIMATED, M3 и риск-паттерн понижаются; альтернатива — оценка гравитации из модели (как в GVHMR ) — «не подтверждено» переносимостью.
