4. Окончательный вариант

padel.smash.v2: 3D-подсистема анализа смэша

Принципы. Метрики — углы в 3D в системе тела. Числа пользователю не показываются (решение владельца): только статусы in range / deviation / strong deviation / uncertain / not available и исходы FULL / PARTIAL / INDETERMINATE. 3D — оценка по одной камере, подпись «Estimated 3D from a single camera» постоянна. Все числа — PROVISIONAL до фазы 0.

Что нового относительно 2022–2024 (K4).

Сенсорное слияние: гравитация, ориентация и параметры камеры покадрово вместо вертикали кадра.
Неопределённость как калиброванная величина σ_i с проверкой покрытия и областью применимости; вне неё вердикта нет.
Перенос углов тренера на кости ученика.
Опциональная пакетная оптимизация, включается только при измеренном выигрыше.
Независимая 3D-проверка: ручная разметка плюс триангуляция ChArUco, офлайн-судья SAM 3D Body (при допустимой лицензии).

Базовый детектор (BlazePose GHUM, бандл float16 2023-04) — решение до 2024 года. Оставлен потому, что это единственный проверенный вариант с 3D-выходом на устройстве. Тяжёлые альтернативы не проходят по размеру, лицензии и паритету [6], [10].

Б.1 Захват
1080p, 60 к/с (120, где устройство даёт при 1080p); 30 к/с допускается с флагом LOW_FPS. Объектив 1×, ультраширокий не используется. Подсказок и проверки кадра нет.
Стабилизация выключена там, где API позволяет (имена параметров NEEDS FACT). Если нет, флаг STAB_UNKNOWN и расширение σ по матрице устройств (Т10).
Метки времени каждого кадра (PTS).
Файл-спутник: гравитация, кватернион ориентации, гироскоп, 50 Гц по умолчанию ≈ 8 КБ на 4 с. 100 Гц только если фаза 0 покажет выигрыш; доступность на средних Android NEEDS FACT.
Движение камеры: определяется по датчикам (гироскоп, акселерометр), не по оптическому потоку (стёкла и сетка корта ненадёжны). Тест на 10 клипах реального корта в фазе 0.
Синхронизация: смещение часов камеры и датчика берётся из таблицы по модели устройства (фаза 0; стабильность NEEDS FACT), иначе SYNC_APPROX. В SYNC_APPROX к σ_orient добавляется ω_max·Δt_bound (50 мс по умолчанию, PROVISIONAL). При 30°/с и 50 мс это 1,5°. Бюджет ≤ 1°.
Intrinsics покадрово, где доступны; иначе номинальное поле зрения и флаг INTRINSICS_NOMINAL.
Импорт без датчиков: vertical = ESTIMATED.
Б.2 Распознавание
MediaPipe Pose Landmarker, Tasks API, режим VIDEO, один бандл на обеих платформах. Выход: 33 точки 2D, 33 worldLandmarks (метры, начало в центре таза [1]), visibility, presence без отсечения при записи. Входы: детектор 224², ландмарк 256², float16 (официальная страница Google).
Версия MediaPipe 1.2.0 от 28.10.2026 [4]; совместимость мобильных артефактов (Maven/SPM) NEEDS FACT. Размеры бандлов: lite ≈ 5,5 МБ, full и heavy измерить скачиванием.
Делегат CPU/GPU/NPU выбирается замером (GPU не всегда быстрее CPU [8]); NNAPI не планируется (устарел с Android 15 [3]). Использует ли Tasks Core ML — NEEDS FACT.

Б.3 Реконструкция

Метрическое 3D (определение). world MediaPipe — оценка модели в метрах [1], не измерение глубины. Её метрическая шкала проверяется в Т9. Пользователь метров не видит; метрика нужна для нормировки на длину корпуса и показа.

Ось и вертикаль. Конвенция осей worldLandmarks (по вторичному источнику [5] y вниз, z к камере) проверяется в фазе 0 обратной проекцией. До проверки правило d > 0,8 не применяется, действует правило видимости.

База (ядро v1, по плану §5.5).

Пропуски: visibility или presence < 0,5 → null.
Сглаживание: офлайн, нулевой фазы; срез по данным фазы 0 по минимуму σ_view при ограничении на срезание пика; через разрыв > 3 кадров не сглаживается.
Длины костей: медиана по надёжным кадрам, направления сохраняются, прямая кинематика от таза.
Левша: зеркалирование эталона.

Опциональный оптимизатор (включается по воротам фазы 0, если σ_view падает относительно базы и время укладывается в бюджет). Минимизируется Σ w·ρ_Huber(reproj) + α‖X − X_mp‖² + β(‖bone‖ − L)² + γ·joint_limits + δ(t)‖∇²X‖², где δ(t) слабеет у пика скорости запястья. Размерности: 19 суставов × кадр + длины костей. Бюджет считается на 240 кадров (весь клип 4 с); окно оптимизации ±1,5 с (≈ 180 кадров) — подмножество; запасное окно ±0,75 с. stance_foot по умолчанию выключен; включается только при подтверждённом контакте, фаза полёта (обе лодыжки поднимаются над плоскостью пола) его отключает. joint_limits: числовые диапазоны NEEDS FACT. Реализация: сначала Kotlin 2.4.21 [11]; если > 20 с на среднем устройстве, окно сужается либо ядро переносится на C++ (лицензия библиотеки NEEDS FACT; порт Ceres/g2o проверяется в фазе 1).

Неопределённость: σ_i² = σ_cov² + σ_sys² + σ_t². σ_cov = λ_cal · σ̂² · (JᵀWJ)⁻¹ (вариант без оптимизатора — по шуму остатка), λ_cal подгоняется по покрытию на независимых игроках. σ_sys² — превышение наблюдаемой ошибки над σ_cov² по стратам (d, азимут, дистанция); оценивается как максимум межракурсной оценки и оценки против ручной 3D-истины. σ_t = |dθ/dt|·δt, δt — разброс локализации tA (старт 1 кадр). Для углов — дельта-метод; Монте-Карло с n = 512 только для нелинейных метрик.

Б.4 Хранение (.p3d v2)
Заголовок: схема, профиль, SHA-256 модели, версии ядра и ограничений, уровень, источник intrinsics, статус синхронизации, источник вертикали, конвенция осей.
Кодирование: world и fitted — int16, шаг 0,1 мм (±3,27 м от таза); 2D — uint16; visibility и presence — uint8. float16 не используется (шаг ≈ 0,98 мм на [1; 2) м).
Размер: сырой слой 396 Б/кадр ≈ 95 КБ на 240 кадров; расчётный 133 Б/кадр ≈ 32 КБ; итого ≈ 127 КБ + спутник ≈ 8 КБ. Сжатие zstd — NEEDS FACT.
Сырой слой не перезаписывается. Пересчёт метрик без видео, если модель та же. При смене бандла только из видео. Сравнение результатов разных бандлов без пересчёта запрещено.
Б.5 Сравнение

Система тела (контракт). Начало: pelvis = середина бёдер. Ось up против гравитации. Ось right = проекция вектора «левое бедро → правое бедро» на горизонтальную плоскость, усреднённая по кадрам стойки до замаха. Ось forward = up × right. Фиксируется один раз на клип. Правая тройка и зеркалирование проверяются золотыми векторами (одинаковые на iOS и Android до 0,1°).

Событие tA. Максимум высоты запястья бьющей руки над shoulderMid вдоль up в длинах корпуса. Проверка: пик скорости запястья в окне ±150 мс, иначе STRIKE_UNCERTAIN. tA вне 10–90% клипа: STRIKE_NOT_FOUND → INDETERMINATE.

Метрики. Окно tA ± 70 мс, значение — медиана допустимых кадров. M1 подъём плеча; M2 сгиб локтя; M3 наклон корпуса к up (полный) и его составляющие вперёд-назад и вбок. M4, M5 считаются и хранятся, в интерфейсе скрыты.

Надёжность метрики. UNAVAILABLE, если видимость < 60% кадров окна или < 3 кадров. LOW (то есть uncertain), если d > 0,8 (после проверки осей), либо для M3 при vertical = ESTIMATED, либо область вне калибровки.

Риск-паттерн. Изменение M3 относительно медианы кадров стойки > 30°, по гравитации; при vertical ≠ SENSOR статус UNDETERMINED.

Время. База: DTW с якорем tA, полоса Сакое–Чиба, признаки M1–M3 и высота запястья (план §5.9). Метрики от DTW не зависят. Три якоря и линейная деформация — экспериментальные, только для показа.

Вердикт. Δ = θ_you − θ_ref (знак даёт направление словами). u² = σ_you² + σ_ref² (ρ = 0, консервативно). T — порог на метрику, стартовый пол 15° (план), уточняется по Т3. Порядок проверки:

not available (UNAVAILABLE / UNDETERMINED);
strong deviation: |Δ| − z·u > 2T;
deviation: |Δ| − z·u > T;
in range: |Δ| + z·u ≤ T;
иначе uncertain.

Начальное z = 1,645; подбирается по Т2 так, чтобы эмпирическая доля ложных deviation на границе |Δ_true| = T была ≤ 5%. Арифметика: при T = 15° и u = 7° in range достижим только при |Δ| ≤ 3,5°, deviation только при |Δ| > 26,5°. Поэтому достижимость вердиктов проверяется отдельно (Б.7).

Исходы. FULL: ≥ 2 метрики с надёжностью OK. PARTIAL: 1. INDETERMINATE: 0, либо STRIKE_NOT_FOUND, либо SUBJECT_LOST в окне.

Режимы. «С собой» — основной (своё прошлое видео). «С тренером» — только если у обоих клипов надёжность метрик OK; углы тренера применяются к длинам костей ученика; различия подвижности не называются ошибкой («отличается от эталона»). «Прогресс» — тот же расчёт по ряду клипов, тренд статусов.

Б.6 Показ
Общая проекция в ядре, холсты SwiftUI Canvas и Compose Canvas. SceneKit soft-deprecated с WWDC25 [2]; RealityKit — отдельная задача.
Капсулы костей с сортировкой по глубине; ненадёжные точки тусклые и пунктирные; сетка и тень пола.
Орбитальная камера 360°, Front / Side / Back / Top, «Match camera». Вид сзади — достроенная моделью, не наблюдавшаяся геометрия; подпись и пунктир это показывают.
Наложение: два скелета в одном нормированном масштабе и общем времени, рядом или поверх; замедление 0,25× / 0,5×, покадровый шаг, петля вокруг tA; видео синхронно со своим 2D-скелетом.
Эллипсы 1σ — опционально, без цифр; допустимость — вопрос владельцу.
Цель ≤ 4 мс/кадр, 60 к/с: не подтверждено.
Б.7 Проверка качества

Три обычных телефона, шахматная мишень ChArUco, OpenCV 4.14.0 [7].

Данные.

Пилот (8–10 игроков × 10 смэшей × 3 ракурса, фаза 0).
Полный набор: 15–30 игроков + 2–3 тренера; ракурсы 90° / 45° / 135°, синхронизация хлопком или вспышкой плюс подбор подкадрового сдвига.
20 клипов «как снимает пользователь»: с рук, 30 к/с, частично вне кадра.
Страты по дистанции (включая > 4 м; ограничение карточки модели «до ≈ 4 м» — вторичный источник [12]) и по росту и сложению (рост измеряется рулеткой).
Игроки калибровки и проверки не пересекаются.

Тесты.

Т1 — межракурсное σ_i по метрике; допуск метрики в интерфейс: σ_i ≤ 7° и доля LOW ≤ 20% (план §9.2; необходимое условие, не достаточное), пределы Бланда–Альтмана, кластерный бутстреп по игрокам.
Т2 — «один удар, два ракурса» как «ученик и тренер»: доля ложных deviation ≤ 5%.
Т3 — 10 обычных и 10 намеренно ошибочных ударов; уточнение T.
Т4 — покрытие 90%-интервалов 85–95% по стратам; достижимость: доля вердиктов, отличных от uncertain, ≥ 60% (если нет, показывается меньше метрик, R3-10 плана).
Т5 — ручная 2D-разметка суставов M1–M3 на подвыборке кадров в трёх видах; триангуляция даёт 3D-истину, независимую от детектора. Выполняют внешние асессоры; межразметчиковое согласие на 10% перекрытия.
Т6 — вертикаль без датчика (датчик скрывается): медиана ≤ 3°, P95 ≤ 8°.
Т7 — паритет: ядро (золотые векторы до 0,1°); сквозной на одном видео (метрики ≤ 1°, статусы ≥ 95%, план §9.5). Релаксация только по замеру и решению владельца.
Т8 — повтор 10 ударов: оценка вариативности игрока, не тест системы.
Т9 — масштаб: длины костей world против триангуляции и роста.
Т10 — матрица устройств: стабилизация, intrinsics, кроп.
Сдвиг окна tA на ±1–3 кадра для σ_t.

Б.9 Ответы на 12.1–12.10
12.1. Лучший способ на устройстве: детектор MediaPipe, гравитация и параметры камеры из датчиков, база по плану, опциональная пакетная оптимизация с ограничениями. Тяжёлые сети-сетки не для телефона [6]. Абсолютная метрическая точность не гарантирована; проверяется Т9.
