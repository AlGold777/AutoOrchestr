# Задание на живой прогон Basic

Скопируйте этот документ в `docs/Run/Test_run/<имя>_<yyyy-mm-dd>[_HH-mm]/notes/run-brief.md`. Сохраните общий регламент, заполните часть 2 и передайте агенту весь документ. Относительные пути ниже указаны от корня репозитория.

Условия части 2 уточняют общий регламент для конкретного запуска. Прямые указания владельца и `AGENTS.md` имеют приоритет. При расхождении со справочниками `docs/Run/` порядок работы задаёт это задание; технические детали проверяются по справочникам и текущему коду. Заполненный документ сам по себе не даёт разрешения отправлять запросы моделям.

## Часть 1. Общий регламент

### Цель и роли

Цель — проверить движок Basic на реальной задаче, найти препятствия и сохранить доказательства. Завершение прогона и качество полученного документа оцениваются отдельно.

- Ведущий — единственный оператор обычного Chrome: готовит и запускает прогон, наблюдает, обрабатывает окна и сбои, ведёт журнал, сохраняет результаты. Один Chrome — один прогон одновременно. Владельца к рутинным действиям не привлекает.
- Проверки, разбор результатов и коммиты делегируются по `AGENTS.md`: GPT — агентам `gpt-6-luna`, `reasoning_effort: high`; Claude — Haiku 5.5 (`model: haiku`). Четыре направления разбора можно выполнять очередями с учётом лимита агентов. Живым Chrome одновременно управляет только ведущий.
- Модели на сайтах — участники схемы; выбор модели субагента их не заменяет. Отправку запросов через интерфейс моделей субагентам не поручать.
- Разработчик исправляет дефекты отдельно, методолог переносит уроки схем. Если нужно взаимодействие с другими сессиями, их адресаты и поручения указываются в части 2; исторические имена и ID не использовать автоматически.

### Перед запуском

1. Прочитать `AGENTS.md`, `docs/Agents/agent-onboarding.md`, `docs/Agents/agent-extension-pages-spec.md`; затем `docs/Run/model-modes.md`, `docs/Run/run-procedure.md`, раздел об окнах в `docs/Agents/agent-live-test.md`, `docs/Platform specifics/README.md`, `environment.md` и файлы участвующих провайдеров, `docs/Agents/basic-issues-registry.md`. Управление обычным Chrome — `docs/Agents/agent-real-chrome-control.md`; селекторы панели — `docs/Agents/agent-extension-page-control.md`.
2. Проверить разрешение владельца в чате: конкретная схема, точный `task.txt`, число запусков и допустимые повторы. Старое разрешение в примере задания не действует на новый прогон. Недостающие условия допуска выяснить до отправки.
3. Проверить `git status --short`, ветку и версию основного чекаута `/Users/restart/Documents/GitHub/AutoOrchestr`. Не включать чужие изменения в свои коммиты. Схема и задача должны быть валидированы и сохранены коммитом; зафиксировать проверяемую версию и наличие незакоммиченного кода расширения, не выдавая его за состояние коммита.
4. Создать папку прогона с `schema/`, `artefacts/`, `exports/`, `notes/`. Для новой попытки сохранить отдельные результаты, не перезаписывать прошлые. Сверить схему с задачей: этапы, обязательные входы, ограничения объёма и критерии готовности должны согласовываться.
5. Проверить доступные инструменты и нужные вкладки Chrome. `docs/Run/tools/js.sh` выбирает последнюю вкладку по фрагменту URL: до действия убедиться, что адресат однозначен. Режимы читать именно на вкладках, которые получат запросы; прежняя проверка другой вкладки не подтверждает режим. Участие и режимы брать из `docs/Run/model-modes.md` с уточнениями части 2. Если точного режима нет, этот справочник разрешает ближайший доступный по названию с записью в отчёт; если часть 2 запрещает переключения, ничего не менять и записать неподтверждённое состояние.
6. Убедиться, что другой прогон не идёт, экран разблокирован и защищён от сна (`caffeinate -dimsu -t 7200 &`; продлить при необходимости). Выполнить `bash docs/Run/tools/preflight.sh` и оценить каждый пункт: скрипт только выводит состояния и закрывает окно телеметрии, его код завершения не означает готовность всех моделей.
7. Сверить версию `manifest.json` с реально загруженной (`extension-version.js`, затем телеметрия). Если нужна перезагрузка, выполнять её до прогона на нужном расширении; `reload-extension.js` содержит фиксированный ID. После перезагрузки обновить вкладки моделей и панель. `refresh-model-tabs.applescript` обновляет все подходящие вкладки, включая неучаствующие: сначала проверить область действия.

### Импорт и запуск

Скрипты находятся в `docs/Run/tools/`. Сгенерировать импорт командой `python3 docs/Run/tools/make-import-scripts.py <schema.json> <task.txt> "<имя pipeline>" <временная папка этого запуска>`.

Через `docs/Run/tools/js.sh` последовательно выполнить `paste.js`, `name.js`, передавая полные пути к файлам из созданной временной папки; прочитать и закрыть информационное окно «Схема установлена… OK». Отчёт проверки сверить со списком ожидаемых предупреждений из части 2: новые замечания разобрать до запуска. Затем выполнить из той же папки `select.js`, `task.js`, проверить выбранную схему, полный текст задачи, `any-modal.js` и `run-state.js` из `docs/Run/tools/`.

Запускать только кнопкой `#debate-run-toggle-btn` (`run-click.js`) после проверки её текущего действия и отсутствия активного прогона. Зафиксировать время старта и идентификаторы прогона. Повторно нажимать запуск без проверки состояния нельзя.

### Наблюдение и решения

- Каждые 20 секунд проверять `any-modal.js` и `run-state.js`; ход и длины ответов — `model-cards.js`. Любое видимое окно прочитать и обработать, неизвестное — по тексту и кнопкам. Не фокусировать и не прокручивать вкладки без диагностической необходимости.
- Молчание дольше 120 секунд — повод читать состояние и страницу модели: `document.hidden`, поле ввода, кнопки, узлы ответа, баннеры. По умолчанию предел ожидания одной попытки — 10 минут от отправки; отличия задаются в части 2. При явном лимите, CAPTCHA или неверной странице необязательную модель пропустить без ожидания предела.
- Неполный раунд сначала сверить с DOM страниц моделей. Если ответ уже есть, сохранить доказательства и выполнить ручной сбор Get it двойным кликом по индикатору статуса нужной модели (`.status-indicator[data-llm-name]`); не путать с `.api-indicator`, который открывает телеметрию. Проверить, что собран ответ именно из вкладки участника текущего прогона, и сверить приём движком. Только после сверки DOM и ручного сбора рассматривать «Повторить»: он может отправить новый запрос, а получение готового ответа не гарантирует (M-20). По умолчанию допускается не более одного ручного повтора на участника в этапе, если он разрешён в части 2.
- Необязательного участника пропустить через «Пропустить участника» и продолжить. У обязательного — сначала диагностика и получение уже готового ответа, затем разрешённый повтор. Если модель всё равно выбыла, сохранить причину, пропустить участника и продолжить с оставшимися без ожидания владельца. `input.required: false` означает необязательность источника следующего этапа, а не автоматический пропуск модели. Если движок сам остановится на отсутствующем обязательном входе (`missing_input`), зафиксировать этот исход и сохранить результаты; не подменять вход выдуманными данными и не запускать прогон заново без разрешения.
- Окно «Ответ User» заполнять самостоятельно только в пределах решений, делегированных в части 2. Записывать, что ответил оператор. Новые предпочтения владельца и отсутствующие факты не выдумывать; если без них нельзя продолжить, сохранить состояние и обозначить, какое решение требуется.
- `NO TAB` сначала проверить по списку вкладок и адресам: отсутствие совпадения не доказывает потерю прогона. При реальной потере состояния, перезагрузке расширения или блокировке экрана сохранить доступную диагностику; данные затронутого прогона не считать подтверждением исправности транспорта. Перезапуск — только в пределах отдельного разрешения владельца.
- Пока прогон идёт, расширение не перезагружать, правки в основной чекаут не доставлять. Каждое ручное действие записывать с временем в `notes/action-log.md`, отделяя его от действий движка.

### Находки и завершение

1. Новую находку в тот же ход внести в `docs/Agents/basic-issues-registry.md`: версия, этап, модель, время, наблюдение и источник доказательств. Сначала проверить существующие записи и нумерацию; наблюдение и предположение различать. Новое поведение платформы добавить в `docs/Platform specifics/<провайдер>.md`. Сообщение другой сессии отправлять, если это поручено владельцем в части 2 или чате.
2. Делать не больше трёх выгрузок «Basic» за прогон, включая финальную; для обычного наблюдения использовать карточки и состояние. Финальную выгрузку сохранить в `exports/`, итог и контроль — в `artefacts/`. После экспорта закрыть телеметрию и панель загрузок доступным инструментом. Скрипт `docs/Run/tools/dismiss-downloads-bubble.sh` работает в описанной среде только из вкладки Terminal приложения, не из Bash; перед кликом сверить положение значка загрузок, после — проверить снимком, что панель закрыта. Чужие загрузки не трогать.
3. Заполнить `notes/run-report.md` по `docs/Run/run-report-template.md`. Отдельно указать ход (завершён / частичный с пропусками / остановлен), действительность данных среды и качество итога по критериям части 2 (прошло / не прошло / не проверено).
4. Делегировать четыре направления разбора: транспорт и завершение; логика, запросы и приёмка; интерфейс и окна; качество итога относительно «готово, когда» схемы. Передать версию, схему, задачу, экспорт, журнал действий и критерии. Ведущий сохраняет полученные отчёты в `notes/analysis-*.md`, уроки — в `notes/lessons-for-handbook.md`; возможность аналитиков записывать файлы не является условием разбора. Для отдельных worktree использовать актуальную базу и правила `AGENTS.md`; общим Chrome аналитики не управляют.
5. Исправления проверять воспроизводящим тестом и независимым разбором. Живую проверку проводить по отдельному разрешению; без неё писать «исправлено тестом, живьём не проверено». Закрывать дефект после подтверждения обоими способами.
6. Каждое законченное изменение сохранить отдельным коммитом через субагента своей платформы: перечислить точные пути, разрешить только git-команды, не включать чужие файлы. Доставить в основной чекаут по `agent-onboarding.md`. При изменении кода поднять связанные версии и обновить документацию; документы без кода версию расширения не меняют. Перезагрузка после доставки только при отсутствии активного прогона.
7. Владельцу сообщить кратко: проверенная версия, статус прогона, качество результата, основные находки и пути к отчёту и итогу. Уведомить другие сессии о завершении, если это поручено в части 2.
