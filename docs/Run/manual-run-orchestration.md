# Ручной прогон: как оркестрировать отправку, обход вкладок и сбор ответов

Читать вместе с [manual-run.md](manual-run.md) (регламент координатора) и [model-modes.md](model-modes.md). Здесь описан порядок работы с вкладками — тот же, что в приложении (расширение AutoOrchestr). Если `manual-run.md` и этот документ расходятся в порядке отправки и обхода вкладок, действует этот документ.

Ты работаешь вместо расширения. Расширение делает то же самое кодом; ты — через браузерные инструменты. Поэтому ниже сначала то, как это устроено в приложении, потом — что делаешь ты.

## 1. Главное

1. **Шаг схемы — это пакет.** Шаг `round` отправляется всем своим моделям сразу. Не по одной с ожиданием ответа, а всем, затем ждём всех. Следующий шаг начинается, когда ответы всего пакета приняты (или участник выбыл по правилам).
2. **Отправка — по очереди, генерация — параллельно.** Запросы уходят в порядке схемы, строго один за другим: за раз активна одна вкладка. Ответа ты не ждёшь: отправил модели А, подтвердил отправку, перешёл к Б. Пока ты отправляешь Б, А уже пишет ответ.
3. **После отправки всем — обход вкладок по кругу** в том же порядке: проверить, что генерация идёт, подержать вкладку в фокусе, прокрутить.
4. **Ответ забираешь по готовности каждой модели**, не по готовности всех: закончила — собрать сразу (прокрутка до начала ответа, чтение, запись на диск), потом ждать остальных.
5. **Автономно.** Владельца в процессе нет. Не спрашивай «продолжить?». Остановка после одной модели или одного шага — ошибка (см. §10).

## 2. Как это устроено в приложении

```text
Схема (schema.json)
  └─ шаг (round / owner), порядок строго по схеме
       └─ пакет: все модели шага → один запуск в фоне (runModelBatch → START_FULLPAGE_PROCESS)
            ├─ Раунд 0  открыть/привязать вкладки моделей (новые — по одной, пауза 1 с)
            ├─ Раунд 1  отправка: по одной модели, по очереди, в порядке схемы
            ├─ Раунд 2  проверка отправки: обход в том же порядке, ремонт неушедших
            ├─ Раунд 3  сбор: для ещё не готовых — визит, прокрутка, запрос ответа
            └─ Раунд 4  ждать, пока все модели пакета не придут к исходу
       └─ приёмка каждого ответа → до 2 запросов исправления в том же чате
       └─ вход следующего шага = принятые ответы
```

Порядок моделей берётся из схемы в момент старта и в ходе пакета не меняется. Последовательны именно отправка (Раунд 1) и обход (Раунды 2 и 3). Генерация у моделей идёт одновременно.

### Раунд 1: как приложение отправляет одну модель

Для каждой модели, по очереди:

1. Вкладка модели выводится на передний план и получает фокус.
2. Пауза **2 с** перед отправкой (`ROUND1_BEFORE_SEND_MS`).
3. Вставка текста в поле ввода целиком (не по символам) и событие `input`, чтобы редактор принял текст.
4. Ожидание активной кнопки отправки (до ~3 с). Не включилась — повтор вставки тремя способами (paste, порции `insertText`, то же с «толчком»); не помогло — отправка не состоялась (`send_not_taken`).
5. Нажатие кнопки или клавиши отправки (у провайдера свой порядок, §9).
6. Подтверждение отправки: в беседе появился собственный запрос (с меткой), поле очистилось, виден Stop. Очередь держится не дольше 8 с в ожидании признака вставки или отправки; дальше приложение идёт к следующей модели, а подтверждение дожидается отдельно.
7. Фокус остаётся на вкладке ещё **5 с** (`ROUND1_POST_SEND_MS`), затем переход к следующей модели.

Ответа в Раунде 1 никто не ждёт.

Бюджеты подтверждения отправки: GPT 15 с; Gemini, Claude, Grok, Le Chat, Qwen, Z.ai 20 с; DeepSeek 22 с; Perplexity 12 с. Повторы отправки: до 4 попыток, паузы 0,5 / 0,8 / 3 / 8 с; для Grok, Qwen, DeepSeek, Z.ai — осторожнее: 2 / 2,5 / 5 / 9 с.

### Раунд 2: проверка отправки

Обход в порядке схемы. Подтверждённую модель повторно не посещают. Неподтверждённой — визит 5–8 с (до двух) и ремонт: перевставить, «толкнуть» поле пробелом, отправить. Бюджет обхода: `max(45 с, число моделей × 8 с)`, на модель не больше ~7 с. Бюджет вышел — оставшиеся не проверяются, их подтверждение ловится позже.

### Раунд 3 и ожидание: сбор

- Ещё не готовой модели — один визит 5–8 с, прокрутка вниз, запрос ответа.
- Пока пакет открыт, приложение обходит ещё не готовые модели по кругу: первый обход через 7 с, на вкладке ~3 с с прокруткой, между вкладками ~1,5 с.
- Окно активных визитов: **60 с** после отправки (обычный профиль) и **90 с** (длинный). Потом приложение вкладки не трогает и ждёт пассивно до предела генерации: **450 с** обычный, **900 с** длинный (Perplexity в исследовательском режиме — до 540 с). Это предел автоматики, а не остановка модели: страница продолжает генерировать, ответ можно забрать позже вручную («Get it»).
- Квота фокуса: не больше 20 с чужой вкладки в любом 60-секундном окне, затем пауза 15 с.
- Отложенные визиты: через 15, 45 и 90 с после отправки, если признаков жизни нет.
- Визит — не доказательство прогресса. «Модель жива» — это рост текста, Stop на странице, метка конца. То, что ты зашёл во вкладку, ничего не доказывает.

### Конец и сбор ответа: прокрутка до начала

Когда ответ закончен (§6), приложение готовит страницу к чтению. Это и есть прокрутка до начала ответа:

1. **Вниз до конца беседы.** До 8 проходов: найти прокручиваемый контейнер беседы, поставить низ, подождать 150 мс, сравнить высоту и хвост текста; два одинаковых замера подряд на самом низу — готово. Есть кнопка «к последнему сообщению» — нажать. У ChatGPT лента может быть `column-reverse` (низ = `scrollTop` 0).
2. **Проход вверх к началу последнего ответа.** Страницы рисуют часть блоков (диаграммы, таблицы, код) только когда они попали в окно. Шаг вверх по 0,6 высоты окна, после каждого шага пауза, пока DOM не затихнет (250 мс, потолок 600 мс); идти, пока начало последнего ответа не окажется в окне. Ответ не найден — не больше 3 шагов.
3. **Заглушки.** Каждый ещё не отрисованный блок («Загрузка диаграммы…», `aria-busy`, пустой `role=status`) подвести в центр окна и подождать до 1,5 с.
4. **Вернуться вниз.** Второй проход — только если изменились высота, число блоков или число заглушек.
5. **Читать ответ.** Бюджет всего прохода — 10 с на модель (при ручном сборе 8 с), не больше двух проходов.

«Последний ответ» — тот, что ниже всех на странице (по `getBoundingClientRect`), а не последний в DOM: у DeepSeek виртуальный список монтирует узлы в любом порядке. Сообщение пользователя, блоки размышлений и боковые панели в ответ не входят.

Вкладка в фоне (`document.hidden`) — ленивые блоки не рисуются, проход не работает. Сначала вывести вкладку на передний план (подождать до 1,5 с), потом проходить.

## 3. Что делаешь ты: порядок действий на каждый шаг

Для шага схемы с моделями `M1 … Mn` (порядок — как в схеме).

**Фаза А. Подготовка (быстро).**
1. Собери запрос каждой модели: задание шага + входы из принятых ответов прошлых шагов (по `step-plan.md`) + директивы из `manual-run.md` §6.4 и §8.1 (метка `КОНЕЦ-ОТВЕТА`, «без встречных вопросов»). Запросы сохрани в `notes/` до отправки.
2. Для каждой модели найди или открой вкладку (reuse / fresh из плана). Новые вкладки открывай по одной с паузой 1 с. Прочитай режим модели на странице (`mode_verified`).
3. Проверь, что экран не заблокирован и вкладки не скрыты (`document.visibilityState`).

**Фаза Б. Отправка, по очереди.** Для i = 1…n:
1. Активируй вкладку Mi, проверь `document.visibilityState === 'visible'`.
2. Пауза 2 с.
3. Вставь запрос целиком (больше 3000 символов — через буфер или `insertText`, `manual-run.md` §5.2), событие `input`.
4. Дождись активной кнопки (до 3 с); нет — «толчок» пробелом, повторная вставка.
5. Отправь способом провайдера (§9).
6. Подтверди отправку: в беседе появился твой запрос, поле пусто, виден Stop или спиннер. `chat_url` запиши, когда адрес сменился на постоянный.
7. Побудь на вкладке 5 с и **переходи к M(i+1)**. Ответа не жди.
8. Не подтвердилась за бюджет провайдера — один повтор (§7). Не вышло — пометь «не ушла», иди дальше, вернёшься в фазе В.

Фаза Б закончена, когда каждая модель подтверждена или помечена «не ушла». Время отправки каждой запиши.

**Фаза В. Контрольный проход (Раунд 2).** Один обход по порядку: у каждой модели видно, что идёт генерация. Подтверждённую достаточно прочитать, без долгой стоянки на вкладке. Для «не ушла» — визит 5–8 с, ремонт (перевставить, толкнуть, отправить), максимум два захода. Не удалось — модель недоступна, каскад подмены (`manual-run.md` §7.2).

**Фаза Г. Ожидание и обход.** Цикл, пока есть неготовые модели:
1. Читай состояние **каждой** неготовой вкладки без вывода на передний план (скрипт во вкладке по её `tabId`): есть ли Stop, длина текста последнего ответа, есть ли метка `КОНЕЦ-ОТВЕТА`, баннер лимита или ошибки, `document.hidden`. Период ~10–15 с.
2. В первые 60 с после отправки каждой модели (90 с в режиме Long) делай обходы с фокусом: порядок схемы, на вкладке 3–6 с с прокруткой вниз, между вкладками ~1,5 с, не больше 20 с чужого фокуса в минуту.
3. Потом вкладку активируй только по причине: состояние не читается или `document.hidden`; текст не растёт 60 с при видимом Stop; кандидат на конец (Stop исчез, метка есть) — пора собирать; отложенные визиты на 15 / 45 / 90 с, если признаков жизни нет. Визит 5–8 с, с прокруткой; потом вернись к тому, что делал.
4. Выходи из цикла по пределу (§7). Нулевой рост текста в первые 120–180 с у думающих моделей (High Reasoning, DeepThink) — норма.

**Фаза Д. Сбор, по готовности каждой модели.** Как только модель закончила (§6):
1. Активируй вкладку, выведи на передний план.
2. Вниз до стабильного низа.
3. Проход вверх к началу последнего ответа, заглушки, возврат вниз (§2, образец скрипта — §5).
4. Прочитай ответ (разметка из DOM; кнопка Copy — для сверки, `manual-run.md` §8.4) и **сразу сохрани** в `exports/<step_ref>_<model_id>.md`.
5. Запиши строку в `notes/platform-log.md`.
6. Вернись в цикл ожидания, если остались неготовые.

Не откладывай сбор готовой модели до конца пакета: ответ на странице можно потерять (перезагрузка, ограничение чата).

**Фаза Е. Приёмка и закрытие шага.**
1. Проверь каждый сохранённый ответ по §6. Принят — очищенный вариант в `artefacts/` (`manual-run.md` §8.4).
2. Не принят — запрос исправления в **том же чате**, до 2 раз: коротко назови, что не так («ответ оборван, продолжай с места обрыва…», «ответ пуст, дай итог целиком»). Он идёт теми же фазами Б–Д, но для одной модели.
3. Модель выбыла — подмена по каскаду (`manual-run.md` §7.2) или пропуск необязательной. Запиши `что изменено → почему`.
4. Все обязательные приняты — шаг закрыт, вход следующего шага = принятые ответы. **Сразу иди к следующему шагу**, без отчёта и вопроса.
5. Шаг `owner` выполняешь сам: решение и причина в одну строку в `notes/owner_decisions.md`.

После последнего шага — итоговый документ, `run-report.md`, пополнение `Platform specifics`.

## 4. Пример для трёх моделей (шаг r1: Claude, GPT, DeepSeek)

```text
t=0     Фаза А. Запросы собраны, вкладки найдены, режимы прочитаны.
t=10    Б1. Claude: фокус, 2 с, вставка, отправка, подтверждено в t=24, +5 с.
t=34    Б2. GPT: фокус, 2 с, вставка, отправка, подтверждено в t=46, +5 с.
t=56    Б3. DeepSeek: фокус, 2 с, вставка, отправка, подтверждено в t=75, +5 с.
t=82    В. Контрольный проход: у всех трёх идёт генерация. Ремонта нет.
t=82…   Г. Чтение состояния всех трёх каждые ~10–15 с. Первые 60 с каждой модели — обход
        с фокусом по кругу Claude → GPT → DeepSeek.
t=190   GPT: Stop исчез, метка есть, три проверки подряд. Д: вкладка GPT, вниз, вверх к началу
        ответа, вниз, чтение, запись exports/r1_gpt.md.
t=240   Claude готов — тот же сбор.
t=410   DeepSeek (DeepThink) готов — тот же сбор.
t=420   Е. Приёмка трёх ответов, шаг закрыт, начинается r2.
```

Отправка трёх моделей занимает около полутора минут; ответы приходят в порядке готовности. Схема «отправил → дождался ответа → следующая модель» заняла бы сумму всех трёх генераций, так делать не нужно.

## 5. Образец скрипта сбора (прокрутка до начала ответа)

Запускай во вкладке модели, когда она видима. Селектор ответов `answerSel` бери из `docs/Platform specifics/<провайдер>.md` и `selectors/<провайдер>.config.js`. Без него скрипт делает 3 шага вверх и возвращает `stoppedBy: 'unknown_cap'`.

```js
(async (answerSel) => {
  const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
  if (document.visibilityState !== 'visible') return { ok: false, reason: 'page_hidden' };

  // самый большой прокручиваемый контейнер беседы
  const scrollers = [...document.querySelectorAll('main, main *')].filter((n) => {
    const s = getComputedStyle(n);
    return /(auto|scroll)/.test(s.overflowY) && n.scrollHeight - n.clientHeight > 4 && n.clientHeight > 200;
  });
  scrollers.sort((a, b) => b.clientHeight * b.clientWidth - a.clientHeight * a.clientWidth);
  const sc = scrollers[0] || document.scrollingElement;
  const reverse = getComputedStyle(sc).flexDirection === 'column-reverse'; // низ = scrollTop 0
  const bottom = () => sc.scrollTo({ top: reverse ? 0 : sc.scrollHeight, behavior: 'instant' });
  const atBottom = () => (reverse
    ? Math.abs(sc.scrollTop) <= 4
    : sc.scrollHeight - sc.clientHeight - sc.scrollTop <= 4);
  const sig = () => `${sc.scrollHeight}:${(sc.innerText || '').length}:${(sc.innerText || '').slice(-120)}`;

  // 1. вниз до стабильного низа: до 8 проходов, два одинаковых замера подряд
  let prev = '', same = 0;
  for (let i = 0; i < 8 && same < 2; i++) {
    bottom(); await sleep(150);
    const s = sig();
    same = (atBottom() && s === prev) ? same + 1 : 0;
    prev = s;
  }

  // 2. вверх к началу ПОСЛЕДНЕГО ответа (тот, что ниже всех на странице)
  const lastAnswer = () => (answerSel
    ? [...document.querySelectorAll(answerSel)]
        .sort((a, b) => b.getBoundingClientRect().bottom - a.getBoundingClientRect().bottom)[0] || null
    : null);
  const startVisible = () => {
    const a = lastAnswer();
    if (!a) return false;
    const r = a.getBoundingClientRect(), c = sc.getBoundingClientRect();
    return r.top >= c.top && r.top <= c.bottom;
  };
  const step = sc.clientHeight * 0.6;
  const maxSteps = answerSel ? 60 : 3;
  const t0 = Date.now();
  let steps = 0, stoppedBy = 'answer_top';
  while (!startVisible()) {
    if (steps >= maxSteps) { stoppedBy = answerSel ? 'budget' : 'unknown_cap'; break; }
    if (Date.now() - t0 > 10000) { stoppedBy = 'budget'; break; }
    sc.scrollBy({ top: -step, behavior: 'instant' }); // вверх: и обычная, и column-reverse лента
    steps++;
    await sleep(300); // пауза на дорисовку
  }
  const a = lastAnswer();
  if (a) a.scrollIntoView({ block: 'start', behavior: 'instant' });

  // 3. заглушки: подвести к центру и подождать до 1,5 с
  const holders = [...document.querySelectorAll('[role=status],[aria-busy=true]')].filter((n) =>
    /загрузк|diagram|mermaid|render/i.test(`${n.getAttribute('aria-label') || ''} ${n.textContent}`)
    && !n.querySelector('svg,img,canvas,pre'));
  for (const h of holders) { h.scrollIntoView({ block: 'center', behavior: 'instant' }); await sleep(1500); }

  // 4. назад вниз
  bottom(); await sleep(300);
  return { ok: true, steps, stoppedBy, placeholders: holders.length, answerFound: !!a };
})(null /* сюда селектор ответов провайдера, строкой */);
```

Это образец логики. Селектор ответов и поведение `column-reverse`-ленты проверь на странице. Скрипт прокручивает, но не читает и не отправляет; ответ читается отдельным вызовом после него.

## 6. Конец ответа и приёмка

**Ответ закончен**, когда выполнено всё:
- нет Stop (или он стал «Отправить»), нет потокового курсора (`_animating`);
- последняя строка ответа — `КОНЕЦ-ОТВЕТА`;
- длина текста не меняется **3 проверки подряд по 3 с**.

Нет метки — ответ оборван, дожатие по `manual-run.md` §6.4. Метка стоит, но перед ней только строка состояния («Проверил и уточнил…», короче 300 символов, без содержания) — это не ответ.

**Ответ принят**, если он:
- не пуст и не является эхом запроса;
- не строка состояния, не сообщение об ошибке, лимите, «Повторить»;
- не оборван (метка на месте, нет обрыва на полуслове и незакрытого блока кода);
- относится к этому запросу, а не остался от прошлого шага в продолженном чате (твой запрос виден в последнем ходе пользователя прямо над ответом).

Короткий содержательный ответ с меткой («Замечаний нет.») принят. Не принят — запрос исправления в том же чате, до 2 раз (§3, фаза Е).

Технический отказ (вкладка, лимит, ошибка страницы) не ошибка модели и не идёт в оценку её качества.

## 7. Сбои и повторы

| Симптом | Действие | Бюджет |
|---|---|---|
| Кнопка отправки неактивна | «толчок» пробелом, повторная вставка (paste → `insertText` порциями → с «толчком») | ~3 с на способ; потом считай, что отправка не состоялась |
| Не подтвердилась отправка | сначала прочитать страницу: запрос мог уже уйти; потом один повтор | бюджет провайдера (§2); дубль не отправлять |
| Поле обрезает текст | эскалация `manual-run.md` §5.3 (файл, декомпозиция) | — |
| Вкладка скрыта (`document.hidden`) | активировать, проверить экран | сразу |
| Текст не растёт 60 с при видимом Stop | визит 5–8 с, прокрутка вниз; ещё 60 с | думающие модели: 120–180 с без роста — норма |
| Генерация «зависла» | **не жать F5**; открыть тот же чат в соседней вкладке (`manual-run.md` §6.3) | один раз |
| Лимит, вход, оплата | участник недоступен, каскад подмены | сразу |
| Пусто на готовой странице | вниз, вверх к началу, вниз, читать заново | 2 попытки |
| Предел ожидания | PARTIAL: забрать, что есть, пометить «неполный» | 450 с обычный, 900 с длинный профиль; Perplexity до 540 с; общий лимит шага 20 мин (`manual-run.md` §2) |
| «Покинуть страницу?» | «Остаться» | — |

Автоматика приложения не нажимает Stop на странице по пределу: страница может дописать ответ позже. Перед тем как закрыть модель как PARTIAL, один раз выполни полный сбор (фаза Д): ответ мог уже дойти.

## 8. Что записывать

- `notes/action-log.md` — строка на каждое действие с временем: отправка модели (подтверждена или нет, способ), контрольный проход, каждый визит (кто, сколько секунд, причина), сбор (модель, шаги прокрутки, `stoppedBy`, длина), приёмка (принят или причина отказа), решение шага `owner`.
- `notes/platform-log.md` — поля из `manual-run.md` §9 плюс `send_to_confirm_sec`, `visits_total`, `collect_stopped_by`.
- Новые наблюдения о платформах — в `docs/Platform specifics/<провайдер>.md` с датой.

## 9. Отправка у провайдеров: ловушки

Полные записи — в [Platform specifics](<../Platform specifics/README.md>). Коротко:

| Модель | Что учесть при отправке |
|---|---|
| ChatGPT | пока промпт стоит в поле, отправка не подтверждена; итог — по метке в хвосте блока; ход — цепочка блоков, строки «Проверил…» — не ответ |
| Claude | запрос ~16 тыс. символов не принимается (кнопка disabled); лимит аккаунта «Сброс в HH:MM»; Retry от прошлых ходов — не конец |
| Gemini | Ctrl+Enter первой стратегией; при заблокированном экране пустые попытки |
| DeepSeek | бюджет отправки 22 с; ложные отказы на скрытой вкладке; возможный дубль от клика; режимы DeepThink и поиск проверять на странице |
| Perplexity | исследовательский режим идёт минуты (до 540 с); эхо запроса как ответ; вложенные `.prose` — брать внешний блок |
| Qwen | Ctrl+Enter только без видимой кнопки; ждать активную кнопку 1,5 с; не залогинен — недоступен |
| Grok | на macOS отправка через Cmd+Return, не Ctrl+Enter |
| Le Chat | Ctrl+Enter первой |
| Z.ai | кнопка, иначе `requestSubmit` или Enter |

## 10. Типичные ошибки

- **Остановиться после одной модели и спросить «продолжить?».** Шаг не закончен, пока не приняты ответы всего пакета. Владельца в прогоне нет.
- **Отправить одной модели и ждать её ответа, не трогая остальных.** Отправлять всем по очереди, ждать всех вместе.
- **Вставлять в несколько вкладок без смены фокуса.** Отправка идёт по одной вкладке за раз, в активной.
- **Считать визит признаком жизни.** Жизнь — рост текста, Stop, метка.
- **Читать ответ сразу после конца, без прокрутки.** Сначала вниз, вверх к началу ответа, заглушки, вниз; потом чтение.
- **Брать «последний в DOM» вместо «ниже всех на странице».**
- **Не сохранить ответ на диск сразу.**
- **Нажать F5 на зависшей вкладке.**
- **Идти дальше, не проверив приёмку.** Следующий шаг получает только принятые ответы.
- **Работать при заблокированном экране.** Данные недействительны (`Platform specifics/environment.md`).
