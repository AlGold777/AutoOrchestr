## Метод и границы

Исполнены настоящие `content-scripts/attachment-handler.js`,
`results/attachments.js` и `background/dispatch-retry.js` в Node VM.
Страница моделировалась через JSDOM, загрузка через bridge и storage заменялись
управляемыми имитациями. В проверках вложений сокращены интервалы ожидания:
settle 50 мс, poll 2 мс, timeout 100 мс. Селекторы и стратегии провайдеров взяты
из действующих конфигураций. Для реестра управлялись часы и момент ответа storage.

Проверки доказывают поведение модулей в указанных условиях. Настоящие страницы
провайдеров не открывались, реальные запросы и файлы не отправлялись.
Шесть новых дефектов ниже отделены от дополнительного ограничения срока хранения.

## TR-09 · Одна карточка файла подтверждает загрузку двух файлов

Места: `content-scripts/attachment-handler.js:601`, `748`, `758`, `1351`.

Считается количество DOM-элементов, совпавших с селекторами, а не количество
различимых загруженных файлов. У GPT карточка и вложенная кнопка удаления
дают два совпадения.

Воспроизведение: запрос содержит `a.txt` и `b.txt`. После bridge на странице
появляется только:

```html
<div data-testid="attachment">a.txt<button aria-label="Remove file">x</button></div>
```

Результат: `success: true`, `uploadedCount: 2`, `failedFiles: []`.
Доказательства самого обработчика: `currentCount: 2`, `filenameEvidenceCount: 1`.
Отсутствие `b.txt` не мешает успеху, поскольку достаточно счётчика селекторов.
GPT проверяет только `result.success` (`content-scripts/content-chatgpt.js:1175`).

## TR-10 · Текст ошибки загрузки становится доказательством успешной загрузки

Места: `content-scripts/attachment-handler.js:625`, `754–758`.

Поиск имени файла охватывает текст всей страницы и не различает карточку файла,
сообщение об ошибке или обычное упоминание.

Воспроизведение: запрошен `a.txt`, после попытки загрузки появился только текст
`Upload failed: a.txt`. Ни карточки, ни файла в input нет.

Результат: `success: true`, `delivered: true`, `uploadedCount: 1`.
Доказательства: `currentCount: 0`, `inputFileCount: 0`, `filenameEvidenceCount: 1`.
Таким образом, ошибка провайдера может открыть проверку, которая должна блокировать
отправку запроса без вложения.

## TR-11 · Защита Perplexity от исчезающих признаков загрузки не включается

Места: `content-scripts/attachment-handler.js:235`, `522–568`, `761–763`.

В конфигурации Perplexity задано `persistentEvidenceRequired: true`, но
`resolveConfig` не переносит это поле в итоговую конфигурацию. Проверяющая функция
получает `undefined` и разрешает использовать признак загрузки, который уже исчез.

Воспроизведение: после bridge появилась карточка `a.txt`; наблюдение успело её
увидеть, затем карточка исчезла до истечения settle. В момент успеха страница пуста.

Результат: `success: true`, `uploadSettled: true`, `ready: true`.
Доказательства: `currentCount: 0`, `inputFileCount: 0`, `filenameEvidenceCount: 0`.
Это потеря действующей настройки, а не отсутствие задуманного ограничения.

## TR-12 · Непригодное вложение исключается из пакета без ошибки пакета

Места: `content-scripts/attachment-handler.js:506–519`, `1050`, `1351–1352`.

`hydrateAttachments` отфильтровывает элементы без имени/данных или с ошибкой
декодирования. Затем ожидаемое число вложений определяется по оставшимся файлам.
Успех не сравнивается с исходным числом запрошенных вложений.

Воспроизведение: два элемента — корректный `a.txt` и `{name: 'b.txt'}` без base64.
На странице подтверждён только `a.txt`.

Результат: `success: true`, `uploadedCount: 1`, `failedFiles: []`, хотя запрошено
два файла. Проверка подтверждает дефект обработки неполного входного пакета;
частота появления таких пакетов в обычном UI не установлена.

## TR-13 · Ошибка чтения файла в панели не останавливает отправку

Места: `results/attachments.js:113–126`, `results.js:21401–21420`.

Ошибка FileReader записывается только в консоль. `buildAttachmentPayload`
успешно возвращает массив без этого файла. Вызывающий обработчик отправляет
возвращённый массив фону без проверки, сколько файлов пользователь прикреплял.

Воспроизведение: в UI выбран `required.txt`; FileReader возвращает ошибку чтения.
Действующий модуль возвращает `[]`, уведомлений пользователю нет, исключения нет.
Путь отправки в `results.js` затем использует этот массив как `attachments`.

В отличие от TR-12, данные теряются ещё до поступления в браузерный адаптер.

## TR-14 · Поздняя загрузка реестра стирает новую подтверждённую отправку

Места: `background/dispatch-retry.js:81–89`, `109–119`, `311`.

При загрузке модуля асинхронно читается сохранённый реестр. После чтения текущая
Map безусловно очищается и заменяется прочитанными данными. Операции регистрации
и подтверждения не ждут окончания загрузки.

Воспроизведение: задержать первоначальное чтение storage; зарегистрировать и
подтвердить `during-bootstrap`; затем завершить чтение старым пустым снимком.

Результат: до завершения чтения `isDispatchConfirmed` возвращает `true`, после —
`false`. Повторная регистрация того же идентификатора возвращает `{ok: true}`.
В репозитории не найдено ожидания `loadDispatchIdRegistry` перед использованием
реестра: первоначальный вызов запущен без await.

Доказана потеря защиты именно в реестре. Повторная физическая отправка через всю
систему не воспроизводилась: там существуют дополнительные проверки состояния.

## Дополнительное наблюдение: срок защиты не отсчитывается от подтверждения

Места: `background/dispatch-retry.js:7`, `34–43`, `109–128`.

Подтверждение записывает `confirmedAt`, но очистка проверяет исходный `ts` регистрации.
Воспроизведение: зарегистрировать запрос, подтвердить за 1 мс до окончания 15 минут,
сдвинуть часы ещё на 2 мс. Подтверждение уже исчезло; повторная регистрация разрешена.

Это подтверждённое ограничение срока защиты. Сам по себе выбранный TTL не доказывает
дублирующую отправку в полном процессе; наблюдение не приравнивается к такому сбою.
