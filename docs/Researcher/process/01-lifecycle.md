# Жизненный цикл задачи

Один порядок для любой задачи. Каждый этап — схема Basic из [../basic/schemas/](../basic/README.md). Этап пройден, когда выполнены его ворота.

| Этап | Схема | Что на выходе | Ворота |
| --- | --- | --- | --- |
| Э0 Карточка задачи | `1-task-card` | Карточка задачи | Поля 3 и 4 не пусты; проверяющий не нашёл непроверяемого признака решения |
| Э1 Предполёт | `2-preflight` | Журнал отказов, итог пробы знания | Задача не «сгорела»; способ проверки отличает верное от ложного; у каждого простого подхода записана точка отказа |
| Э2 Настройка | `3-setup` | Диагноз, конфигурация `C0`, пороги, страница ратификации, `core/lock.json` | Владелец подписал ядро; хеши записаны; якорь отправлен |
| Э3 Исследование | `4-cycle` | Записи циклов, карта вопроса, сводки | Идёт до стоп-правила или решения владельца |
| Э4 Перестройка | `5-rebuild`, `6-rebuild-verdict` | Новая конфигурация или откат, запись библиотеки | Суд вынесен; исход записан |
| Э5 Периодика | `7-calibration`, `8-audit`, `10-polygon` | Два числа проверяющих, отозванные выводы, задачи полигона | По расписанию из ядра |
| Э6 Выход | `9-exit` | Итог, пакет воспроизведения, пост-мортем | Итог проверен; финальный якорь отправлен |

Рецензия методологии (`11-methodology-review`) проводится один раз до первой задачи и после каждого пост-мортема, который меняет методологию.

## Э0. Карточка задачи

1. Интервьюер задаёт владельцу вопросы по девяти полям опросником.
2. Составитель собирает карточку; владелец правит её в окне.
3. Проверяющий ищет пустые и непроверяемые поля.
4. Владелец утверждает.

Если сегодня проверять нечем, первой задачей становится постройка проверки: в поле 3 записываются известные частные случаи и архив прошлых неудач, ведущая валюта — В3.

## Э1. Предполёт

До настройки, чтобы настройка шла против настоящих отказов, а не выдуманных.

1. **Проба знания.** Все модели состава в новых чатах отвечают на задачу в открытую. Критерий сгорания записан в запросе.
2. **Проверка способа проверки.** Способ из поля 3 прогоняется на заведомо верном и заведомо ложном случае.
3. **Три простых подхода** при одном и том же малом бюджете: одиночное длинное рассуждение; перебор ответов нескольких моделей с отбором; стандартный метод области.
4. **Журнал отказов.** Для каждого подхода — шаг, артефакт и причина отказа; пометка, проверено ли, что это не ошибка исполнения.

Если простой подход решил задачу — система не нужна; владелец записывает это и останавливается.

## Э2. Настройка

1. **Пробы барьера** — три пробы стадии А.
2. **Диагноз** — два диагноста независимо, затем свод: конкурирующие гипотезы о барьере и различающий тест.
3. **Конфигурация `C0`** — сборщик берёт методологию, карточку, журнал отказов и диагноз. Каждый приём адресует записанную точку отказа. Всё, чего нет в методологии, помечается расширением; расширений не больше, чем разрешено карточкой.
4. **Взлом правил** — модель другой группы ищет, как исполнитель мог бы законно обойти правила.
5. **Страница ратификации** — одна страница для владельца: хеши, бюджет по этапам, пороги с процедурой задания, kill-критерии, чем проверяется центральная гипотеза.
6. **Подпись.** Владелец записывает пороги, запечатывает свои ожидания, собирает `core/lock.json`, начинает `journal/chain.txt`, отправляет якорь.

До этапа Э3 проверяющие проходят калибровку (`7-calibration`): без двух чисел вердикты не засчитываются.

## Э3. Исследование

Цикл — [02-cycle.md](02-cycle.md). После каждого цикла владелец сохраняет экспорт, дописывает цепочку, обновляет пакет. Стоп-правила — [03-stop-rules.md](03-stop-rules.md). Непрерывный режим — [04-endless-mode.md](04-endless-mode.md).

## Э4. Перестройка

Запускается решением владельца по предложению из очереди карты.

1. `5-rebuild`: сборщик пишет новую конфигурацию и перечень изменений; проверяющий изменение сверяет; владелец подписывает.
2. Испытание: запуски `4-cycle` по плечам — [../methodology/03-change-operator.md](../methodology/03-change-operator.md), §5.
3. `6-rebuild-verdict`: судья, библиотекарь, решение владельца.

## Э5. Периодика

| Что | Когда | Схема |
| --- | --- | --- |
| Калибровка проверяющих | До Э3; при смене модели; при новой версии корпуса | `7-calibration` |
| Аудит принятых выводов | Раз в период из карточки | `8-audit` |
| Красная команда | Перед принятием перестройки классов B–D; после смены модели; раз в период | `8-audit` |
| Задачи полигона | До первого испытания; при исчерпании набора | `10-polygon` |
| Посевы | По порогу `seed_rate` | [../verification/03-control.md](../verification/03-control.md), §3 |
| Пересмотр правил проверки | Раз в период из карточки | [../system/04-core.md](../system/04-core.md), §6 |

## Э6. Выход

1. Проверка новизны: поиск предшествующих работ и тест редукции.
2. Итог в одном из шести конечных состояний.
3. Проверка итога: каждое утверждение итога ведёт к вердикту.
4. Пакет воспроизведения: итоговая конфигурация, последняя строка цепочки, отпечатки моделей, версия ядра.
5. Пост-мортем: что из методологии и библиотеки сохранить, что изменить. Изменение методологии — операция владельца и новая рецензия.
6. Если назначен внешний наблюдатель и заявляется статус выше S1 — вскрытие финального набора.

Kill переноса: ноль приёмов и перестроек, сохранивших силу на задачах следующего проекта, означает «самообучение не подтверждено».
