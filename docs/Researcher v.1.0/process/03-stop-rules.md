# Стоп-правила и пороги

Число без способа его задания не принимается. Пороги записываются в `core/thresholds.json` на этапе Э2, до первого цикла, и после этого меняются только операцией над ядром.

## 1. Стоп-правила

Проверяет докладчик в каждой сводке по записям цикла и карте. Сработало — строка «СТОП: <код>» и тревога.

| Код | Правило | Что дальше |
| --- | --- | --- |
| `STOP_KILL` | Наступил kill-критерий карточки | Этап Э6 |
| `STOP_BUDGET` | Любая из четырёх единиц бюджета исчерпана | Этап Э6 или операция над ядром |
| `STOP_LOSS` | Израсходована доля `stop_loss`, прироста нет ни в одной валюте | Этап Э6 |
| `STOP_STAGNATION` | Сработал T1, а `k_rebuilds` перестроек подряд не дали прироста | Смена диагноза барьера; если уже менялся — Э6 |
| `STOP_RUNAWAY` | Расход растёт, валюты стоят `k_stagnation` циклов, триггер не записан | Владелец |
| `STOP_QUALITY` | Три вердикта «неясно» подряд; или два независимых вердикта противоречат и не разрешены за два цикла; или предсказания перестали подтверждаться | Владелец |
| `STOP_DEADLINE` | Истёк срок кандидата в выразимость, на котором держится ведущая валюта | Смена диагноза |
| `STOP_CRITERIA` | Агент предложил изменить критерий успеха, kill или порог | Донесение владельцу; цикл продолжается с прежним ядром |
| `STOP_ROUTE` | Два цикла подряд без заявки; или запечатанные ожидания владельца дважды расходятся со сводкой | Владелец |
| `STOP_HARD` | Жёсткое нарушение | Ветка заморожена до решения владельца |

Разрешённые действия при застое задачи: сузить задачу (операция над ядром), сменить приём (перестройка), вернуть владельцу с отчётом (Э6). Других нет.

## 2. Флаг ручной проверки

За `tripwire_n` циклов не было ни признанной ошибки, ни отката, ни пересмотра диагноза — владелец сверяет записи с экспортами сам. Обязанности производить провал нет.

## 3. Как задаётся каждый порог

| Порог | Способ |
| --- | --- |
| `k_stagnation` | `k` циклов стоят не больше доли бюджета, которую владелец готов потерять без прироста |
| `m_repeat` | Наименьшее число повторов, при котором совпадение кода провала уже не случайно при измеренной частоте этого кода |
| `k_diversity` | Равно `k_stagnation` |
| `prediction_floor` | Доля подтверждений наивных предсказаний, измеренная в предполёте, плюс минимальный интересный отрыв |
| `meta_quota` | Замер по первым двум циклам с перестройкой; запись до третьего |
| `min_config_life` | Число циклов на одну полную проверку гипотезы при заявленной цене |
| `k_rebuilds` | Сколько перестроек владелец готов оплатить вперёд |
| `tripwire_n` | Число циклов, за которое при заявленной частоте перестроек ожидается хотя бы одна ошибка или откат |
| `quarantine_cycles` | Не меньше `min_config_life` |
| `trial_pairs` | По измеренному шуму и минимальному интересному эффекту: [../verification/04-evaluation.md](../verification/04-evaluation.md), §4 |
| `emergency_floor` | Просадка, после которой остатка бюджета не хватит на откат и один полный цикл |
| `stop_loss` | Доля бюджета, при которой ещё остаётся резерв на один полный цикл проверки и выход |
| `reserve_share` | Сколько владелец готов тратить на направления без текущих показателей |
| `checker_detect_min`, `checker_false_max` | По цене пропуска ложного вывода в этой задаче. После калибровки меняется проверяющий, а не порог |
| `seed_rate` | Чтобы за период между окнами решений ожидалось не меньше трёх посевов |
| `closed_set_access_limit` | Число обращений, после которого долю набора можно восстановить по ответам |
| `external_view_every` | Не реже одного раза на `k_stagnation` циклов |

Пока замеров нет (первые циклы), порог записывается как «временный до цикла N» с датой пересмотра; пересмотр — операция над ядром.

## 4. Бюджет

Четыре единицы: запросы к моделям, запуски проверок, часы расчёта, минуты владельца. Считаются с первого цикла; секретарь журнала записывает расход цикла, докладчик — остаток.

Сравнение с простыми подходами — только при равном бюджете во всех четырёх единицах.
