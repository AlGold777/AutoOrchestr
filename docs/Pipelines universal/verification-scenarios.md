# Universal Engine — проверка готовности

Версия комплекта: **0.1.0**. Статус: **проект проверок, исполнение не подтверждено**.
Основа: [концепция](README.md) и [JSON Schema](contracts.schema.json).

## Общие условия

Каждый сценарий запускается на одном и том же ядре. Предметные типы, правила,
адаптеры и граф задаются конфигурацией. Для воспроизводимой проверки используются
управляемые ответы моделей и адаптеров; проверка настоящего провайдера отдельно
подтверждает транспорт, но не заменяет проверки семантики движка.

Для каждого запуска сохраняются паспорт и поправки, версии сценария и контрактов,
входные снимки, аудит контекста, ответы и проверки, принятые изменения, состояния
критериев, расход бюджета, отпечатки и причины переходов. Восстановление проверяется
по устойчивому хранилищу после потери памяти процесса.

Готовность означает прохождение положительных и отрицательных ветвей всех шести
сценариев. Сейчас описаны требования; ни один сценарий этим документом не объявлен
пройденным. Проверка JSON Schema подтверждает только структуру примеров.

| ID | Проверяемое свойство | Наблюдаемый результат |
| --- | --- | --- |
| UE-01 | Полный архитектурный процесс выражается сценарием | Все 30 этапов и ворота представлены без предметных условий внутри ядра |
| UE-02 | Минимальная конфигурация | Один этап, одна модель, результат принят без судьи |
| UE-03 | Параллельное выполнение | Независимые ответы объединены по контракту без судьи |
| UE-04 | Человек и полномочия | Ожидание, одобрение, поправка и продолжение имеют проверяемую связь |
| UE-05 | Доработка и прогресс | Успех, регрессия и отсутствие прогресса различаются |
| UE-06 | Прерывание и восстановление | Нет двойной фиксации; неизвестный внешний эффект не повторяется вслепую |

## UE-01. Архитектурный пайплайн как предметный сценарий

**Исходные данные:** версия архитектурного комплекта v2.2.4,
[описание этапов](<../Automation GPT комплект Документов/process/stages.json>),
[переходов](<../Automation GPT комплект Документов/process/control-flow.json>) и
[ворот](<../Automation GPT комплект Документов/process/gates.json>).

**Ход:** загрузить предметный пакет с архитектурными типами и валидаторами; выполнить
путь 1–30 с ветвлениями, независимыми исполнителями, вопросами владельцу,
свидетельствами и человеческой проверкой там, где это требует исходный процесс.

**Приёмка:** существует полная таблица «исходное требование → узел/правило/проверка»;
все ворота вычислены по актуальным подтверждениям; итоговые результаты представлены
версионируемыми артефактами. Удаление предметного пакета не требует изменения ядра.
Промежуточный запуск только этапов 1–5 не закрывает UE-01.

**Отрицательные ветви:** пустой ответ при обязательном результате; недостижимое
условие активации; недостаточное число независимых моделей; отсутствие обязательного
свидетельства; попытка изменить одобренную цель. Ни одна ветвь не должна завершиться
успехом или скрытым обходом ворот. Противоречия исходного комплекта разрешаются
явно в таблице соответствия, а не случайным выбором одного из документов.

**Доказательства:** таблица соответствия, граф, журнал каждого перехода и проверки
ворот, версии всех входных и итоговых результатов.

## UE-02. Один этап с одной моделью

**Исходные данные:** задача выдать короткую строку; один исполнитель-модель;
программная проверка формата; без судьи и модератора.

**Ход:** собрать ограниченный контекст, выполнить один вызов, проверить строку и
зафиксировать результат. Примеры паспорта и этапа приведены ниже.

**Приёмка:** ровно один вызов модели, один принятый результат, обязательный критерий
`PASSED`, завершение. Внутренний валидатор формата не является вызовом инструмента.
Движок не добавляет обязательных ролей и раундов.

**Отрицательные ветви:** пустая строка, отсутствующий результат, результат сверх
ограничения, чужой идентификатор попытки. Результат отвергается; при лимите в один
вызов задача завершается ошибкой без автоматической второй генерации.

**Доказательства:** полный контекст, счётчик вызовов, ответ, протокол валидации,
единственная запись фиксации.

## UE-03. Параллельная работа без судьи

**Исходные данные:** три модели независимо предлагают варианты; сценарий требует
два успешных ответа от различных моделей; агрегация сохраняет принятые варианты
как набор со ссылками на источники. Проверки структуры выполняет программа.

**Ход:** все исполнители получают одинаковый входной снимок, без ответов соседей.
Ответы сохраняются отдельно по мере поступления. После кворума и проверок агрегат
фиксируется атомарно. Поведение оставшейся ветви задаётся заранее: поздний ответ
остаётся в журнале, не изменяя уже принятый агрегат.

**Приёмка:** корректный агрегат получен без судьи; одна неуспешная ветвь не отменяет
достижимый кворум. Уже принятые ответы не запрашиваются повторно.

**Отрицательные ветви:** два ответа одной модели вместо двух независимых моделей;
недостаточный кворум; утечка ответа соседней ветви; конфликт версий; дубликат ответа.
Проверить также конфигурацию с пятью исполнителями и другим кворумом без изменения
кода ядра. Повторяющаяся ошибка одной ветви при улучшении других критериев не должна
автоматически объявлять весь процесс зацикленным.

**Доказательства:** аудит изоляции контекста, происхождение ответов, расчёт кворума,
одна фиксация агрегата и учёт поздних событий.

## UE-04. Человек, одобрение и поправка

**Исходные данные:** действующий паспорт ревизии 1 и этап, которому нужны данные
человека. Отдельно предлагается увеличение бюджета за пределы паспорта.

**Ход:** сохранить вопрос и точку продолжения; при ответе на обычный вопрос
продолжить в той же ревизии. Для расширения бюджета сформировать поправку с автором
и основанием. Только решение назначенного человека активирует ревизию 2.

**Приёмка:** исходный паспорт и поправка неизменяемы; каждая попытка ссылается на
исполненную ревизию. Одобрение оформлено до использования нового бюджета.
Результат старой незавершённой попытки после активации ревизии 2 сохранён для
аудита, но не принят автоматически. При отказе действует прежний паспорт, если
задача остаётся выполнимой; иначе она остаётся остановленной с указанной причиной.

**Отрицательные ветви:** поддельное одобрение модели; ответ другого человека;
повтор того же решения; ответ на устаревший вопрос; изменение критериев без
поправки. Ожидание ответа не является циклом; достижение общего срока задачи
завершает ожидание по политике срока.

**Доказательства:** обе ревизии паспорта, поправка, проверенное решение, история
вопросов, привязка попыток и инвалидация зависимых оценок.

## UE-05. Цикл «реализация ↔ тесты»

**Исходные данные:** реализация функции и три заранее заданных критерия поведения
`C1`, `C2`, `C3`. Модель предлагает изменения, инструмент выполняет тесты.
Контрольная точка — завершённая проверка тестов после очередной реализации;
промежуточный вызов автора не расходует окно отсутствия прогресса.
Порог отсутствия прогресса — 3 попытки, повторения состояния — 2.

**Положительная ветвь:** `[FAILED, FAILED, FAILED] → [PASSED, FAILED, FAILED] →
[PASSED, PASSED, FAILED] → [PASSED, PASSED, PASSED]`. Каждое улучшение подтверждено
тестами актуальной версии реализации; последняя точка завершает задачу.

**Регрессия:** после изменения кода связанные оценки становятся `UNVERIFIED` до
новой проверки. Переход `[PASSED, FAILED, FAILED] → [FAILED, PASSED, FAILED]`
не считается улучшением и не сбрасывает окно отсутствия прогресса.
Возврат затем к `[PASSED, FAILED, FAILED]` также не считается новым улучшением:
сравнение выполняется с сохранённой опорной точкой, а не только с предыдущей попыткой.

**Повторяемый цикл:** реализация возвращается в состояние A после B; в одной
контрольной точке повторяется тот же семантический отпечаток без улучшения.
После порога движок выполняет `on_stall` и показывает повторившиеся ошибки.

**Разные хеши без прогресса:** модель меняет код или пояснения в каждой попытке,
но набор критериев не улучшается. Срабатывает независимый предел в 3 попытки.
Увеличение объёма кода, новая формулировка и перестановка тестов не считаются успехом.

**Отрицательные ветви:** повторная доставка прежнего отчёта не считается новой
попыткой; новая реализация не наследует старый `PASSED`; одинаковый текст ошибки
при изменившейся версии внешней зависимости не доказывает цикл. Блокированное
ожидание не расходует окно улучшения, но учитывается общий срок.

**Доказательства:** версии кода, полные отчёты тестов, векторы критериев, правила
нормализации, отпечатки, счётчики, причина продолжения или остановки.
Этот сценарий обязателен для проверки доработки; сходные циклы могут встречаться
и в исследованиях либо редактировании текста.

## UE-06. Прерывание и восстановление

**Исходные данные:** устойчивое хранилище, параллельные ответы и адаптер внешнего
действия с управляемым исходом. Сравнение с непрерванным запуском выполняется по
принятым результатам и эффектам; технические события восстановления могут отличаться.

| Место сбоя | Ожидаемое восстановление |
| --- | --- |
| После получения одного параллельного ответа | Принятый ответ сохранён; повторяются только недостающие допустимые вызовы |
| После проверки, до локальной фиксации | Нет частичных изменений; предложение повторно проверено перед фиксацией |
| После фиксации, до подтверждения отправителю | Повтор события не создаёт новую версию результата и не запускает следующий этап второй раз |
| После сохранения намерения, до подтверждённого внешнего эффекта | Проверяется журнал и стратегия адаптера; отсутствие локального ответа не доказывает отсутствие эффекта |
| После внешнего эффекта, до сохранения ответа | Сверка либо тот же действующий ключ дедупликации; подтверждённый эффект не повторяется |
| Неизвестный эффект без безопасного способа сверки | Пауза для человека с описанием неизвестного исхода и риска повторения |

**Приёмка:** счётчики бюджета и попыток, версии паспорта, прогресс и точка продолжения
сохраняются после перезапуска. Восстановление не расширяет права и не обнуляет лимиты.
Инструмент с `manual` не повторяется автоматически. Проверка решения о повторе
различает «эффекта не было», «эффект уже был» и «исход неизвестен».

**Отрицательные ветви:** просроченная гарантия дедупликации; чужой ключ операции;
двойная доставка; конфликт ревизий; повторное одобрение; потерянный ответ после
эффекта. Ни один случай не должен создавать ложное сообщение об однократном
выполнении внешнего действия.

**Доказательства:** журнал намерений и результатов, состояния до и после перезапуска,
фактическое число внешних эффектов, принятые версии артефактов, история сверки.

## Структурные примеры для JSON Schema

Ниже — три структурно полных примера. Одинаковые нулевые хеши служат заполнителями:
перед исполнением все ссылки должны разрешаться в зарегистрированные определения
с настоящими хешами. Эти примеры не являются готовым исполняемым сценарием и не
подтверждают подлинность одобрений. Ревизия паспорта 2 в примере поправки должна
быть создана отдельно из ревизии 1 с указанным изменением.
