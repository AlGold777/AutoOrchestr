# Руководство по эксплуатации

Что делает владелец руками. Команды выполняются в папке задачи. Путь к папке системы задаётся один раз в начале сеанса:

```bash
R="/Users/restart/Documents/GitHub/AutoOrchestr/docs/Researcher v.2.0"
```

## 1. Подготовка задачи

1. Создать папку задачи по [../data/README.md](../data/README.md), §3.
2. Пройти Э0 и Э1: схемы `1-task-card`, `2-preflight`. Утверждённую карточку сохранить в `core/task-card.txt`, журнал отказов — в `runs/`. Если в журнале отказов стоит «заявлено решение: проверить» — проверить заявленное решение способом из карточки до следующего шага.
3. Пройти Э2: схема `3-setup`. В поле задачи — карточка, журнал отказов и выдержка библиотеки: записи `library/rebuilds/` и `library/pits/` с тем же типом барьера, если они есть. Подписанную страницу ратификации сохранить; числа порогов перенести в `core/thresholds.txt`; конфигурацию — в `config/C0.txt`.
4. Собрать выжимку ядра `core/extract.txt`: поля карточки и пороги, переписанные дословно. Она входит в каждый пакет без изменений.
5. Записать свои ожидания по ключевым вехам в `core/sealed-test.txt`.
6. Собрать `core/lock.json`: суммы из §2.
7. Начать цепочку (§3) и отправить наблюдателю первую строку (§4).

## 2. Суммы для замка

Файл:

```bash
shasum -a 256 core/task-card.txt core/thresholds.txt core/extract.txt config/C0.txt
```

Папка — сумма от списка сумм её файлов:

```bash
(cd "$R/prompts" && find . -type f | sort | xargs shasum -a 256 | shasum -a 256)
```

Так же считаются `"$R/basic/schemas"` и `"$R/methodology"`.

В замке нет ничего, что меняется по ходу работы: ни счётчиков обращений к закрытым наборам, ни чисел калибровки. Они записываются событиями журнала (§3).

## 3. Цепочка журнала

Первая запись после ратификации — ссылается на замок:

```bash
f=0001_3-setup_2026-11-16.json; echo "1 $(date -u +%FT%TZ) $f $(shasum -a 256 "journal/$f" | cut -d' ' -f1) $(shasum -a 256 core/lock.json | cut -d' ' -f1)" >> journal/chain.txt
```

Каждая следующая — после каждого запуска схемы, имя файла своё:

```bash
f=0002_4-cycle_2026-11-17.json; echo "$(($(wc -l < journal/chain.txt)+1)) $(date -u +%FT%TZ) $f $(shasum -a 256 "journal/$f" | cut -d' ' -f1) $(tail -n 1 journal/chain.txt | shasum -a 256 | cut -d' ' -f1)" >> journal/chain.txt
```

В цепочку идёт каждый запуск, в том числе остановленный и неудачный: выгрузка сохраняется, какой бы она ни была. Запуск, которого нет в цепочке, — дыра в журнале; номер цикла в разделе «ХОД» идёт подряд, пропуск виден.

Событие без выгрузки — операция над ядром, решение владельца, посев, обращение к закрытому набору, числа калибровки, запись перед испытанием — записывается так же: содержание кладётся в текстовый файл `journal/NNNN_<вид>_<дата>.txt`, строка цепочки ссылается на него.

Проверка цепочки — каждая строка должна ссылаться на сумму предыдущей:

```bash
awk 'NR>1{c="sed -n " NR-1 "p journal/chain.txt | shasum -a 256"; c | getline h; close(c); split(h,a," "); print (a[1]==$5 ? "строка " NR " сходится" : "РАЗРЫВ в строке " NR)}' journal/chain.txt
```

Проверка одного файла: `shasum -a 256 journal/<имя>` и сравнение с четвёртым полем его строки.

`chain.txt` только дописывается. Ошибочная строка не стирается: следующей строкой записывается исправление.

Цепочка показывает, что записанное не менялось после якоря. Она не показывает, что записано всё: запуск, который владелец не выгрузил, цепочка не увидит.

## 4. Якорь

После каждой новой строки цепочки — коммит `journal/chain.txt` в удалённый репозиторий, к которому у внешнего наблюдателя есть доступ на чтение. Первую строку и последнюю строку каждого окна решений — ещё и письмом наблюдателю. Отправка наружу — действие владельца.

```bash
tail -n 1 journal/chain.txt
```

## 5. Один цикл

1. Сверить выжимку ядра с замком:

```bash
shasum -a 256 core/extract.txt
```

Сумма обязана совпасть с записанной в `core/lock.json`. Не совпала — цикл не запускается.

2. Собрать `state/package.txt`: `core/extract.txt` без изменений, раздел «ХОД», конфигурация, карта; записи, которые запросил координатор прошлого цикла ([../data/README.md](../data/README.md), §4). Проверить длину:

```bash
wc -m state/package.txt
```

Больше 14 000 — цикл не запускается: сначала сжать карту по [../methodology/01-methodology.md](../methodology/01-methodology.md), §9. Свёрнутое переносится в `state/map-archive.txt`.

3. Запустить `4-cycle`, вставив пакет в поле задачи.
4. Если нужен посев — подложить его в пакет или в ответ ручного задания ([../verification/03-control.md](../verification/03-control.md), §3) и записать об этом в свой файл посевов.
5. На шаге ручного задания — запустить код исполнителя или ответить «нет». Ленту с заявкой до отправки не открывать.
6. В окне решений — прочитать сводку и оба донесения, исправить карту, дописать решение.
7. Сохранить выгрузку в `journal/`, дописать цепочку, закоммитить якорь.
8. Сохранить записи цикла в `journal/records/`, утверждённую карту — в `state/map.txt`.
9. Посчитать расход по выгрузке (`usage.requestsSent` — отправленные запросы без шага User) и обновить раздел «ХОД». Запрос, про который неизвестно, ушёл ли он, считается потраченным: номер следующего цикла; остаток запросов (минус число карточек ответов), запусков проверок, своих минут.

## 6. Перестройка

1. Диагност назвал триггер, решение — перестраиваться. Собрать задачу схемы `5-rebuild`: пакет цикла; ответ диагноста целиком; выдержка библиотеки — записи `library/rebuilds/` с тем же триггером или барьером и все откаты текущей задачи; при T7 — своя заметка «взгляд извне».
2. Запустить `5-rebuild`. На шаге выбора назвать предложение и пункт контрольного изменения. Номер пункта:

```bash
echo $(( 0x$(tail -n 1 journal/chain.txt | shasum -a 256 | cut -c1-8) % 8 + 1 ))
```

Для классов C и D вместо `8` — `18`. Пункт совпал по сути с выбранным предложением — следующий по порядку.

3. Подписанные конфигурации сохранить как `config/C<n>.txt` и `config/C<n>к.txt`.
4. Имена плеч. Номер перестановки:

```bash
echo $(( 0x$(tail -n 1 journal/chain.txt | shasum -a 256 | cut -c1-8) % 6 ))
```

| Остаток | А | Б | В |
| --- | --- | --- | --- |
| 0 | прежняя | новая | контрольная |
| 1 | прежняя | контрольная | новая |
| 2 | новая | прежняя | контрольная |
| 3 | новая | контрольная | прежняя |
| 4 | контрольная | прежняя | новая |
| 5 | контрольная | новая | прежняя |

5. До первого плеча записать событием в цепочку: суммы обеих конфигураций; предсказание и показатель; наименьший интересный эффект; число циклов на плечо; ключ плеч.
6. Если шум в задаче ещё не измерен или после замера принималась перестройка — измерить: действующая конфигурация дважды с одного пакета тем же числом циклов; сводки сохранить.
7. Собрать пакеты плеч: одинаковые ядро, «ХОД» и карта; раздел конфигурации — прежний, новый, контрольный. Прогнать `4-cycle` по плечам. Для испытания на зачётном наборе каждое обращение записать событием журнала `closed_set_access`.
8. Результат, на котором держится исход предсказания, запустить самому: вердикт о перестройке не опирается на результат без запуска владельца.
9. Запустить `6-rebuild-verdict`: в поле задачи — предсказание и условие отката из предложения; сводки циклов каждого плеча под именами А, Б, В, без названий конфигураций; шум. Вынести вердикт по правилу в окне.
10. Подтверждено — `C<n>` действует, работа продолжается с карты её плеча. Откат — действует прежняя и карта её плеча; яму перенести в карту. Расход всех плеч списать в разделе «ХОД». Запись — в `library/rebuilds/`.

Пока идёт испытание, второе не начинается.

## 7. Сбои

| Сбой | Что делать |
| --- | --- |
| Модель не получила запрос | Это сбой расширения, а не модели: повторить шаг; не помогает — чинить расширение. Модель не заменять |
| Модель получила запрос и не ответила; роль не одна | Пропустить; секретарь запишет неполный шаг |
| Неизвестно, ушёл ли запрос | Не повторять вслепую: сначала открыть вкладку модели и посмотреть, есть ли запрос и ответ. Basic для этого предлагает «Проверить ответ» |
| Не ответила единственная модель роли | Повторить шаг; если не помогает — остановить прогон, заменить модель в сборщике схем, пересобрать |
| Ответило меньше двух проверяющих | Цикл неполный: статус не повышается; заявка повторяется в следующем цикле |
| Не ответил экспериментатор, секретарь журнала или контролёр | Цикл недействителен: остановить, повторить цикл с тем же пакетом. Остановленный запуск — тоже в цепочку |
| Ответ не в формате JSON дважды | То же, что «не ответил» |
| `context_full` до отправки | Ответы длиннее пределов или пакет длиннее 14 000 знаков: сжать карту, повторить цикл |
| `missing_input` | Обязательный источник без ответа: повторить шаг-источник |
| Прогон остановлен посреди цикла | «Продолжить» в ленте; заявка остаётся прежней |
| Провайдер сменил модель | Калибровка заново; незаконченные испытания недействительны; запись в цепочку |
| Потеряна `state/map.txt` | Взять карту из последней выгрузки цикла в `journal/` |
| Цепочка не сходится | Остановить работу; найти первую расходящуюся строку; всё после неё — репетиция, пока расхождение не объяснено записью |
| Не отвечает ни один проверяющий | Тревога; циклы не запускаются: без проверки они дают только гипотезы |

## 8. Смена запросов, состава и схем

1. Править текст в `"$R/prompts/"` или состав в `"$R/basic/build-schemas.mjs"`.
2. Пересобрать из корня проекта: `node "docs/Researcher v.2.0/basic/build-schemas.mjs"`. Сборка откажет, если новая расстановка моделей нарушает пары независимости.
3. Заново импортировать изменённые схемы в Basic.
4. Пересчитать суммы папок в `core/lock.json`, увеличить версию ядра, записать событие `core_change` в цепочку.

Результаты до и после смены напрямую не сравниваются. Смена модели у проверяющего требует новой калибровки.

## 9. Остановка и выход

Сработало стоп-правило или принято решение «стоп»: запустить `9-exit` с пакетом последнего цикла и перечнем вердиктов из `journal/records/`. Утверждённый итог — в `out/final.txt`, пост-мортем из ленты — рядом. Последняя строка цепочки — финальный якорь.

## 10. Расписание

| Что | Когда |
| --- | --- |
| Окно решений | После каждого цикла; не чаще одного окна в день при нескольких циклах подряд |
| Якорь | Коммит — после каждой строки цепочки; письмо — каждое окно решений |
| Калибровка | После первого цикла наладки и до первой настоящей задачи; при смене модели; при пополнении корпуса |
| Аудит и красная команда | Раз в период из карточки; перед вердиктом о перестройке |
| Повтор запуска владельцем | При аудите: выборка результатов с происхождением «инструмент модели» |
| Контроль дрейфа | Раз в период из карточки |
| Пересмотр правил проверки | Раз в период из карточки |
| Смена скрытых правил контроля | Раз в период из карточки |
