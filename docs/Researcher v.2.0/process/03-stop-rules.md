# Стоп-правила и пороги

Число без способа его задания не принимается. Пороги записываются в `core/thresholds.txt` на этапе Э2 и входят в выжимку ядра.

## 1. Стоп-правила

Проверяет докладчик в каждой сводке по записям цикла и карте. Сработало — строка «СТОП: <код>» и тревога.

| Код | Правило | Что дальше |
| --- | --- | --- |
| `STOP_KILL` | Наступил kill-критерий карточки | Этап Э6 |
| `STOP_BUDGET` | Любая из трёх единиц бюджета исчерпана | Этап Э6 |
| `STOP_LOSS` | Израсходована доля `stop_loss`, прироста нет ни в одной валюте | Этап Э6 |
| `STOP_STAGNATION` | Сработал T1, а `k_rebuilds` перестроек подряд не дали прироста | Смена диагноза барьера; если уже менялся — Э6 |
| `STOP_RUNAWAY` | Расход растёт, валюты стоят `k_stagnation` циклов, триггер не записан | Владелец |
| `STOP_QUALITY` | Три вердикта «неясно» подряд; или два независимых вердикта противоречат и не разрешены за два цикла; или предсказания перестали подтверждаться | Владелец |
| `STOP_DEADLINE` | Истёк срок кандидата в выразимость, на котором держится ведущая валюта | Смена диагноза |
| `STOP_CRITERIA` | Агент предложил изменить критерий успеха, kill или порог | Донесение владельцу; цикл продолжается с прежним ядром |
| `STOP_NO_RUN` | Три цикла подряд без результата, полученного запуском | Владелец: проверки неисполнимы без него |
| `STOP_ROUTE` | Два цикла подряд без заявки; или запечатанные ожидания владельца дважды расходятся со сводкой | Владелец |
| `STOP_HARD` | Жёсткое нарушение | Ветка заморожена до решения владельца |

Разрешённые действия при застое задачи: сменить приём (перестройка), вернуть владельцу с отчётом (Э6), закрыть задачу и открыть более узкую. Других нет.

## 2. Флаг ручной проверки

За `tripwire_n` циклов не было ни признанной ошибки, ни отката, ни пересмотра диагноза — владелец сверяет записи с экспортами сам. Обязанности производить провал нет.

## 3. Как задаётся каждый порог

Пороги трёх видов. Вид определяет, когда число можно вписать.

**Выбор владельца** — число следует из того, чем владелец готов рисковать. Вписывается при подписи.

| Порог | Способ |
| --- | --- |
| `k_stagnation` | `k` циклов стоят не больше доли бюджета, которую владелец готов потерять без прироста |
| `k_rebuilds` | Сколько перестроек владелец готов оплатить вперёд |
| `meta_quota` | Какую долю бюджета владелец готов отдать перестройкам; пересматривается один раз после второй перестройки по замеру |
| `stop_loss` | Доля бюджета, при которой ещё остаётся резерв на один полный цикл проверки и выход |
| `reserve_share` | Сколько владелец готов тратить на направления без текущих показателей |
| `checker_detect_min`, `checker_false_max` | По цене пропуска ложного вывода в этой задаче; записываются с размером выборки, на которой будут мериться. После калибровки меняется проверяющий, а не порог |
| `trial_pairs` | Число пар на полигоне по таблице знакового критерия: [../verification/04-evaluation.md](../verification/04-evaluation.md), §4 |
| `closed_set_access_limit` | Число обращений, после которого долю набора можно восстановить по ответам |

**Замер** — число берётся из прогонов. Пока замера нет, порог подписывается как «временный до цикла N».

| Порог | Способ | Откуда замер |
| --- | --- | --- |
| `m_repeat` | Наименьшее число повторов, при котором совпадение кода провала уже не случайно при измеренной частоте этого кода | Первые циклы задачи |
| `prediction_floor` | Доля подтверждений наивных предсказаний плюс наименьший интересный отрыв | Предполёт и первые циклы |
| `min_config_life` | Число циклов на одну полную проверку гипотезы | Первый цикл наладки |
| `tripwire_n` | Число циклов, за которое при измеренной частоте перестроек ожидается хотя бы одна ошибка или откат | Первые перестройки |
| `emergency_floor` | Просадка, после которой остатка бюджета не хватит на откат и один полный цикл | Цена цикла из первого цикла наладки |
| `seed_rate` | Чтобы за период между окнами решений ожидалось не меньше трёх посевов | Число шагов цикла |

**Производные** — считаются из других порогов и на странице ратификации печатаются формулой.

| Порог | Формула |
| --- | --- |
| `k_diversity` | Равно `k_stagnation` |
| `quarantine_cycles` | Не меньше `min_config_life` |
| `external_view_every` | Не реже одного раза на `k_stagnation` циклов |

Временный порог заменяется постоянным один раз, в названном цикле, записью `core_change` в журнале. Постоянный порог внутри задачи не меняется.

Признак решения, способ проверки и kill-критерии внутри задачи не меняются вовсе. Если они оказались неверны — задача закрывается итогом «остановлено» и открывается новая, со своей карточкой и своим журналом: результаты двух задач не складываются.

## 4. Бюджет

Три единицы: запросы к моделям, запуски проверок, минуты владельца. Считает владелец по выгрузке прогона: запросы — по числу карточек ответов, включая повторные попытки. Остаток он пишет в раздел «ХОД» пакета; модели остаток не считают, а только читают.

Сравнение с простыми подходами — только при равном бюджете во всех трёх единицах.

Цена одного цикла — 20 запросов и один запуск проверки; перестройка с тремя плечами по три цикла — 190 запросов; замер шума — ещё 120. Бюджет задачи подписывается после первого цикла наладки, когда эти числа измерены, а не оценены.
