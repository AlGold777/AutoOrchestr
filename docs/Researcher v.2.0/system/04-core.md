# Ядро и замок

Система может менять свой метод. Поэтому она не должна менять то, чем этот метод проверяется: изнутри «починить проверку» и «подогнать проверку» неразличимы.

## 1. Что входит в ядро

| Элемент | Что случится, если отдать его в изменяемый слой |
| --- | --- |
| Карточка задачи: цель, признак решения, чем проверяем, ограничения | Система объявит решённой более лёгкую задачу |
| Критерии успеха и провала, kill-критерии | Провал будет переопределён как успех |
| Пороги стоп-правил и триггеров | Остановка и перестройка станут делом удобства |
| Правила проверки: предсказание до проверки, слепая проверка, происхождение результата, пары независимости | Вывод будет подтверждать сам себя |
| Запросы и приёмы исполнителя проверки, проверяющих, секретарей, контролёров и счётчиков | Перестройка перепишет то, чем система себя проверяет |
| Правило вердикта о перестройке и каталог контрольных изменений | Перестройка будет принята по удобному правилу |
| Правила статусов и меток утверждений | Гипотеза станет «фактом» без проверки |
| Простые подходы для сравнения и правило равного бюджета | Сравнение будет выиграно выбором слабого соперника |
| Закрытые наборы: зачётный, финальный, корпус порч, посевы | Система выучит ответы вместо способа |
| Журнал и учёт бюджета | Неудобные записи исчезнут |
| Проверка новизны и пробы знания | Пересказ известного пройдёт как открытие |
| Полномочия ролей и запреты | Автор назначит себе проверяющего |
| Правило внешних действий: только через владельца | Необратимое действие без человека |

Всё остальное — изменяемый слой.

## 2. Как ядро защищено на Basic

| Защита | Как работает |
| --- | --- |
| Порядок шагов | Заявка с предсказанием — отдельный шаг раньше проверки. Запись прогона участникам недоступна |
| Слепой вход | Проверяющий получает только запись заявки — без утверждения и гипотезы — и сырой результат явным списком входов. Текста задачи у него нет: это свойство движка, проверенное по коду и приёмочным тестом 7 |
| Новый чат | Шаги проверки и подтверждения идут в новом чате: истории автора там нет |
| Ядро только на чтение | Выжимка ядра — файл `core/extract.txt`; его сумма в замке. В пакет он входит без изменений; перед циклом владелец сверяет сумму одной командой. Ответ модели изменить её не может |
| Независимость ролей | Пары ролей, которые одна модель играть не может, проверяет сборщик схем |
| Закрытые наборы вне схем | Лежат в папке владельца `sealed/`, ни к одному шагу не прикладываются целиком |
| Финальный набор у внешнего наблюдателя | Владелец его не видит до вскрытия |
| Хеши | `core/lock.json` хранит SHA-256 карточки, порогов, выжимки ядра, конфигурации, запросов, схем и закрытых наборов |

## 3. Журнал и цепочка хешей

Первичная запись — экспорт прогона Basic (JSON кнопки Basic). После каждого запуска схемы, в том числе остановленного, владелец:

1. Сохраняет экспорт в `journal/NNNN_<схема>_<дата>.json`.
2. Дописывает строку в `journal/chain.txt`:

```
<номер> <дата-время UTC> <имя файла> <SHA-256 файла> <SHA-256 предыдущей строки chain.txt>
```

Команды — в [../operations/02-runbook.md](../operations/02-runbook.md), §3. Первая строка ссылается на SHA-256 файла `core/lock.json`.

Журнал только дописывается. Исправление — новая запись со ссылкой на исправляемую.

**Внешний якорь.** Каждая новая строка `chain.txt` уходит туда, где владелец не может её переписать: коммит в удалённый репозиторий, который читает внешний наблюдатель. Первая строка и последняя строка каждого окна решений — ещё и письмом. Без якоря цепочку может пересобрать сам владелец, и постороннему она ничего не доказывает.

**Что цепочка доказывает.** Записанное не менялось после якоря. Она не доказывает, что записано всё: запуск, который владелец не выгрузил, в неё не попадёт. Номер цикла в пакете идёт подряд, и пропуск виден, но закрыть это полностью может только расширение, когда научится сохранять каждый заход само.

Без цепочки прогон считается репетицией.

## 4. Запись предсказания до проверки

1. Экспериментатор выдаёт заявку `H#`: утверждение, процедура, что считается «за» и «против», предсказание, наивное предсказание, ставка уверенности.
2. Заявка — артефакт своего шага из трёх частей. Исполнитель проверки получает только процедуру. Проверяющие получают запись заявки — условия «за» и «против», предсказание, наивное предсказание — и сырой результат. Утверждение и гипотеза лежат в заметке автора; её получает только секретарь журнала.
3. Вердикт `V#` ссылается на `H#`. Вердикт без более ранней заявки в том же прогоне недействителен.
4. После шага заявки её текст не меняется. Уточнение — новая заявка с новым номером; прежняя закрывается статусом «отозвана».

Предсказание принимается, если в нём есть числовой интервал, знак сравнения или конкретный дискретный исход и если оно отличается от наивного.

## 5. Операция над ядром

Ядро меняет только владелец. Внутри задачи меняется не всё.

| Что | Можно ли менять внутри задачи |
| --- | --- |
| Признак решения, способ проверки, kill-критерии | Нет. Если они неверны — задача закрывается итогом «остановлено» и открывается новая; результаты двух задач не складываются |
| Порог, подписанный как «временный до цикла N» | Один раз, в названном цикле |
| Постоянный порог | Нет |
| Запросы, схемы, состав, методология, корпус порч | Да; результаты до и после напрямую не сравниваются |

Порядок операции:

1. Причина записана: что изменилось в мире, а не в удобстве.
2. Новая версия документа ядра сохранена рядом со старой.
3. Пересчитан `core/lock.json`; версия ядра увеличена.
4. В журнал дописана строка с типом `core_change`, старым и новым хешем.
5. Отмечено, какие результаты получены при прежнем ядре. Результаты до и после напрямую не сравниваются; статусы, которые опирались на изменённый элемент, сбрасываются до S0 и проверяются заново.
6. Якорь отправлен.

Если владельца нет, ядро заморожено. Агент, предложивший изменить ядро, получает нарушение `V_CORE_WRITE`; предложение уходит владельцу как донесение.

Просьба владельца «смягчить критерий» в окне решений циклом не исполняется: критерий внутри задачи не меняется.

## 6. Пересмотр правил проверки

Ядро — единственная часть, которую система не улучшает, и в нём тоже бывают ошибки. Раз в период, записанный в карточке, владелец пересматривает правила проверки по свидетельствам журнала:

- посевы, которые никто не поймал;
- порчи, пропущенные всеми проверяющими;
- выводы, отозванные аудитом;
- проверки, которые владелец выполнял вручную, потому что способа не было.

Каждое изменение — операция по §5. Новые виды порч добавляются в корпус; проверяющие калибруются заново на выборке, куда входят новые элементы. Корпус только пополняется: элемент, который проверяющие не ловят, из него не убирается.

## 7. Расход закрытых наборов

Каждое обращение к закрытому набору сообщает о нём немного сведений. Поэтому:

- у каждого набора есть предел обращений, записанный в `core/lock.json`;
- обращение — событие журнала `closed_set_access`: кто, зачем, какая часть набора. Счётчик — число таких событий; в замке его нет, замок после подписи не меняется;
- набор, исчерпавший предел, переводится в открытые и заменяется новым;
- финальный набор вскрывается один раз.

## 8. Состав `core/lock.json`

Формат — [../data/schemas/core-lock.schema.json](../data/schemas/core-lock.schema.json). Поля: версия ядра; хеши карточки задачи, файла порогов, выжимки ядра, конфигурации `C0`, папок `prompts/`, `basic/schemas/` и `methodology/`, каждого закрытого набора; пределы обращений; имя внешнего наблюдателя; дата ратификации. Счётчиков и чисел калибровки в замке нет: они — события журнала.
