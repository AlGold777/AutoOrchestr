# Человек

## 1. Кто есть кто

| Человек | Что делает | Чего не делает |
| --- | --- | --- |
| Владелец | Ставит задачу, подписывает ядро, решает в окне решений, утверждает перестройки, выполняет ручные задания, ведёт цепочку хешей | Не выносит научных вердиктов, не правит записи задним числом |
| Внешний наблюдатель | Держит финальный набор, получает якоря журнала, вскрывает финальный набор один раз, может подать свои задачи | Не участвует в настройке и не знает устройства конфигурации |

Внешний наблюдатель — человек, который систему не строил. Без него прогон не претендует на статус выше S1 и на заявление «система учится».

## 2. Окно решений

Владелец видит сводку ([../data/schemas/digest.schema.json](../data/schemas/digest.schema.json)), донесения контролёра и очередь решений. Окно — одно в день; в непрерывном режиме — раз в N циклов.

Допустимые решения:

| Решение | Что происходит |
| --- | --- |
| Продолжать | Следующий цикл с обновлённым пакетом |
| Перестройка | Запуск этапа Э4 по выбранному предложению |
| Ручное задание выполнено | Сырой результат прикладывается к следующему циклу |
| Правка карты | Владелец исправляет карту; правка — запись в журнале |
| Операция над ядром | По [04-core.md](04-core.md), §5 |
| Стоп | Этап Э6 |

Карточка в очереди решений — четыре строки: что предлагается; на чём проверено; что изменится; чем откатить. Плюс срок и вариант по умолчанию, который действует, если владелец не ответил. Вариант по умолчанию всегда безопасный: не внедрять, не закрывать, не тратить.

## 3. Владелец как исполнитель

Ручное задание — измерить, достать данные, запустить то, что модель не может, оценить вслепую. Процедура приходит без гипотезы: владелец не знает, какой исход «нужен». Ответ записывается с классом R1 или R2, если приложен первичный артефакт, и проходит слепую проверку наравне с остальными.

## 4. Шлюз для слов владельца

| Что сказал владелец | Как записывается |
| --- | --- |
| Данные с первичным артефактом | Факт R1/R2, обязательна проверка |
| Догадка, идея, «попробуйте так» | Гипотеза R5: заявка, предсказание, слепая проверка |
| Изменение цели, критерия, порога | Операция над ядром |
| «Продолжать вопреки проверке» | Волевое решение: записывается, уроком о мире не становится, в испытаниях перестроек как доказательство не участвует |

Серия волевых решений одного типа — вход диагносту метода.

## 5. Проверка владельца

Владелец — часть системы и проверяется так же, как остальные.

| Проверка | Как |
| --- | --- |
| Запечатанный тест | До прогона владелец записывает свои ожидания по ключевым вехам и запечатывает хешем в `core/lock.json`. Расхождение сводки с запечатанным ожиданием — строка сводки |
| Слабое предложение | Раз в период в очередь решений подкладывается заведомо слабое предложение перестройки из `sealed/seeds/`. Принял — событие в журнале и повод сократить права автоматического принятия |
| Два числа | На корпусе порч владелец размечает выборку вслепую: доля найденных порч и доля ложных срабатываний. Хранятся в `core/lock.json` рядом с числами проверяющих |
| Минуты | Время владельца считается с первого цикла и входит в бюджет |

Слабые предложения готовит внешний наблюдатель или модель из служебной группы в отдельном прогоне; владелец их содержания заранее не видит.

## 6. Тревоги

Владельца зовут сразу, не дожидаясь окна:

- жёсткое нарушение;
- контролёр дважды сообщил об одном и том же, а координатор дважды не учёл;
- сработало стоп-правило;
- нужен выход за пределы системы: покупка, публикация, запрос к людям;
- все модели одной группы не отвечают.

В Basic тревога — последняя строка ответа контролёра или докладчика «ТРЕВОГА: <код>»; в режиме по шагам владелец видит её в окне решений, в непрерывном — на ближайшем чекпоинте. Мгновенной остановки по тревоге в Basic пока нет ([../process/04-endless-mode.md](../process/04-endless-mode.md), §4).

Сбой вкладки, капча, истёкшая сессия тревогой не считаются: шаг повторяется или пропускается по [05-roles.md](05-roles.md), §4.

## 7. Что владелец обязан понимать перед подписью ядра

1. Чем проверяется решение сегодня и чем оно не проверяется.
2. Какой исход останавливает работу.
3. Сколько запросов, проверок, часов расчёта и своих минут он готов потратить.
4. Что после подписи критерии не меняются без операции над ядром.
5. Что центральная гипотеза проверяется тем, что действительно есть в конфигурации, а не тем, что обещано.
