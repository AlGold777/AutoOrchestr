# Выжимка из отчётов расширения

Схема: **Disput Flow → Extract внутри расширения → проверка готовой выжимки моделью.**
Числа и сопоставления считает `shared/report-digest.js`. Модель читает результаты;
она не пересчитывает времена, медиану и накопительные `waitedMs` по тексту.

## Extract

На вкладке Disput выберите `transport` рядом с **Extract**. Скачиваются два файла
из одного снимка после удаления секретов, с одинаковой датой в именах:

- `Disput Flow YYYYMMDD_HH-MM.json` — полный исходный отчёт.
- `extract_transport_YYYYMMDD_HH-MM.md` — читаемая выжимка.

Структурированные таблицы и счётчики (`schemaVersion: 2`) вычисляются внутри
расширения для построения Markdown; отдельный JSON выжимки не скачивается.

Командная строка и внешние процессы для Extract не нужны. `Only problems` относится
только к отображению и выключен по умолчанию. Шапка выжимки содержит `sourceFile`,
`debateRunId`, `DIGEST_VERSION` и параметры сжатия. Алгоритм имеет отдельную версию
`2.0.0`; версия расширения в `metadata` относится к производителю исходной телеметрии.

## Контракт данных

- Время `t` — секунды от **исходного** `stageExecutions[0].actual.startedAt`, точность 0.001.
  Порядок этапов и их индексы сохраняются. `+st` и `+sub` хранятся в таблице запроса;
  в хронологии используется одно `t`.
- `null`, отсутствие поля (`state: missing`), пустая строка, пустой массив и нулевой
  счётчик различаются. Исходные значения имеют пути; формулы находятся в `calculations`.
- Все пути JSON полные. Markdown использует обратимые префиксы **E[N] = events[N]**
  и **J[N] = delivery.journal[N]**, объявленные в шапке. `QN.dK` — dispatch K запроса N
  из карты идентификаторов. Отсутствующий шаг обозначается `not recorded`.
- Попытка — транспортный запрос. Привязка идёт по `requestId`, затем `dispatchId`;
  запасная привязка по этапу и модели помечается. `pipelineRoundId` — колонка для
  проверки, он не становится ключом привязки. Чужой dispatch сохраняет своего владельца.
- `tabId` приводится к строке. Карта сохраняет токен, batch_start, свои и чужие dispatch,
  записанные раунды и их исходные пути.
- `correlationQuality` и `provenance` считаются отдельно. Правило экспортёра для
  `incomplete` — наличие событий с качеством корреляции, отличным от `exact`.
  `legacy_adapter` сам по себе не является причиной `incomplete`. Полный список событий
  без раунда находится в `quality.eventsWithoutRound.paths`.

## Три уровня хронологии

1. **Все запросы**, без фильтра проблемных: первый стабильный текст и обнаружение
   завершения, длины, accepted, финалы, счётчики дублей/wrong_card/displayed/ручных записей,
   задержки и пути. Один терминальный финал может иметь несколько исходных записей.
2. **Общая шкала этапа** для обеих моделей: dispatch_started, submitted, focus, tab,
   navigation. Эти записи не повторяются в переходах отдельного запроса.
3. **Переходы запроса и фон**: first_text, первое TEXT_STABLE и изменения длины/статуса/
   dispatch, обнаружение завершения, completion_terminal, терминальная группа, финал доставки,
   STAGE_FAILED, ручные восстановления и отклонения. Фон представлен счётчиками безопасных
   групп с первой/последней записью; все пути участников группы остаются в JSON.

Группы различаются по запросу, dispatch, статусу, причине, значимым полям и атрибуции.
Возврат к прежней длине после изменения — новый переход. Нулевая длина не отбрасывается.
Временные счётчики опроса и выборочные hit/miss/rate SELECTOR_STATS не являются ключами
группировки; исключения перечислены в `compression.ignoredGroupingFields`.
Нет ограничения в 160 строк. `coverage` показывает количество представленных записей,
записей в общей шкале и число строк групп, без скрытой обрезки.

`FINALIZATION_DECISION` и `MODEL_FINAL` могут образовать пару только при одинаковых
request/dispatch/status/completionReason, совместимых известных длинах и интервале не более
50 мс. Оба пути, обе метки, обе точки измерения длины и интервал сохраняются. Поля
`foregroundMsUsed`, `focusSwitchesUsed`, `doneReason`, `durationMs` показаны как
**зарегистрированные значения**, без причинной интерпретации.

## Остальные таблицы

- Этапы: длительность, пауза, правильная медиана. LONG: `durationMs > 3 × median`
  **или** `durationMs > 120000`. Совместное наличие success и записей failure показывается
  с путями; оно само по себе не объясняет последовательность восстановления.
- Длины: одинаковые delivery/journal значения объединяются в отображении, оба пути
  остаются. Колонки ревизий и stale появляются только при наличии записей.
- Ручные действия, отказы старта, фокус, записи вне окна прогона, проверка фрагмента
  следующего сохранённого промпта. Накопительные ожидания отказов не складываются.
- Диагнозы: в сводке группировка по code/reasonCode, в приложении все отдельные
  диагнозы с исходными путями, отсортированные по severity. D1/D2 — ссылки на группы.
- Сравнения: только одноимённые величины с одинаковой областью счёта. События fallback,
  терминальные записи и уникальные запросы с forced completion — три отдельных счётчика.
- Доставка: только пакеты и problems; отправки и модераторские события не повторяются.
  Отдельных разделов 15/16 нет, integrity и dispatchAttempts находятся в сводке данных.

Фрагмент в `prepared.prompt` подтверждает наличие фрагмента в сохранённом подготовленном
промпте. Он не доказывает отправку и передачу полного ответа. Отсутствие события не доказывает
отсутствие действия; позднее событие не доказывает продолжение генерации; фокус между первым
текстом и финалом не доказывает непрерывную печать. Длительность блокировки неизвестна без
начала/конца блокировки. Эти оговорки приведены один раз в шапке Markdown.

## Запрос модели

Приложите `.md`, при необходимости также структурированный JSON и исходный Disput Flow.

```text
Тебе дан Transport extract, сформированный внутри расширения. Числа уже посчитаны.
Не пересчитывай их и не добавляй отсутствующих значений. Не чини и не советуй.

Для каждого запроса опиши цепочку одной-тремя строками:
отправка → наблюдение текста → решения завершения → принятие/отклонение → восстановление → финал.
Используй таблицу запросов, общую шкалу этапа и переходы; ссылайся на путь и t.
Затем перечисли расхождения одноимённых величин и пробелы доказательств.
Не смешивай счётчики событий, терминальных записей и уникальных запросов.

Каждое утверждение помечай:
[факт] — зарегистрированное значение с путём;
[вычисление] — вычисленное значение с формулой;
[гипотеза] — объяснение, не следующее прямо из данных;
[недостаточно данных] — проверить по выжимке нельзя.
Наличие фрагмента в prepared.prompt не доказывает отправку или передачу полного ответа.
```

## Прогоны

С 2.81.575 телеметрия держит максимум два прогона **в памяти страницы**. Поздняя запись
сохранённого неактивного прогона не переключает activeRunId. Вытеснённые прогоны не создаются
заново поздними событиями. Запись истории в chrome.storage и восстановление остаются отключёнными.
