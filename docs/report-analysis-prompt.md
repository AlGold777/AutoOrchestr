# Проверка выжимки транспорта

Схема работы: Disput Flow → Extract в расширении → проверка фактов моделью.
Расчёты выполняет `shared/report-digest.js`; модель читает готовый результат.

## Получение файлов

На вкладке Disput выберите transport и нажмите Extract. Из одного снимка скачиваются
ровно два файла с одинаковым временем в имени:

- `Disput Flow YYYYMMDD_HH-MM.json`: исходная телеметрия с журналом доставки.
- `extract_transport_YYYYMMDD_HH-MM.md`: компактная сводка со ссылками на исходный JSON.

Отдельный JSON выжимки не скачивается. Внутренние таблицы имеют schemaVersion 3,
DIGEST_VERSION 3.8.0. Версия в metadata относится к производителю исходного отчёта.
Only problems влияет на отображение вкладки, экспорт содержит весь доступный снимок.
Командная строка для Extract не используется.

## Идентичность и единицы

- `correlation.transportRequestId` — канонический идентификатор запроса; requestId —
  совместимый псевдоним. Dispatch идентифицирует отправку, stageAttemptId — попытку этапа.
  Эти количества не равны по определению. Batch-событие не считается отдельной отправкой модели.
- Привязка: запрос, затем dispatch, затем однозначная пара этап/модель. Неоднозначная
  пара остаётся unassigned. Чужой dispatch сохраняет первоначального владельца.
- pipelineRoundId используется для проверки, а не как самостоятельный ключ привязки.
  tabId нормализуется в строку. Карта сохраняет токены, batch_start и исходные полные ID.
- null, отсутствие поля, пустая строка, пустой массив, false и 0 различаются.
- `t`: секунды от stageExecutions[0].actual.startedAt с точностью 0.001. Если начало
  первого этапа вытеснено лимитом событий (startedAt=null, deviation missing_stage_start),
  база берётся из первой доступной записи в порядке: runOutcome.startedAt,
  delivery.diagnosis.batches[0].at, events[0].sourceTimestamp, delivery.journal[0].at.
  Шапка называет выбранный путь и причину запасной базы; st для такого этапа считается от
  batch_start.at запроса и не печатается, когда равен t. Порядок этапов сохраняется. +st и +sub появляются только в таблице запросов;
  нулевой +sub при submitted не повторяется. Граница прогона берётся из runOutcome,
  а не из начала первого этапа. После границы дополнительно показан +end.
- sourceTimestamp и receivedAt — разные часы производителя и коллектора.
  delivery.journal.at — время панели; delivery.ms отсчитывается от prepared.
  Эти определения и зарегистрированные изменения режима сохраняются в metadata.

## JSON: контракт телеметрии

Отчёт schemaVersion 2 содержит события schemaVersion 6. Известные идентификаторы,
ожидаемая/входящая идентичность, доказательства рендера и предоставленные причинные
ссылки проходят диагностический адаптер без потери нулей и null.

`metadata.dataCompleteness` оценивает корреляцию событий; область оценки указана
в dataCompletenessBasis. `completeness` отдельно сообщает доступность плана,
идентичности, доказательств отображения и остановки наблюдателя. provenance считается
отдельно: legacy_adapter сам по себе не означает неполноту. Один run ID не делает
событие конкретного запроса точно привязанным.

`integrity.checks` различает checked, not_checked и insufficient_data. Пустые массивы
предупреждений не означают выполненную проверку. Проверка часов ограничена опережением
sourceTimestamp относительно receivedAt на 5000 мс; синхронизация часов не доказана.
Без терминала прогона completedAt=null, последнее наблюдение — отдельное lastObservedAt.

`collection` содержит известные принятые/вытесненные события, лимит и фильтрацию адаптера.
Неизвестный исходный объём источника остаётся null. delivery.collection отдельно сообщает
предел журнала и пропущенные подробности переключений фокуса. Исходные записи остаются
в JSON; сжатие применяется к представлению MD.

При отсутствии фиксированного execution plan expectedStages=null; completedStages
считается по фактически наблюдавшимся этапам. `planning` сохраняет авторские ревизии
динамического плана и соответствия stageInstanceId/plannedStageId/planRevisionId.
Ожидания отдельного этапа берутся из явно связанной ревизии, без подстановки всей
последней ревизии в исторический этап и без угадывания будущего количества этапов.

ANSWER_COLLECTED.accepted=null означает сбор до решения движка.
ANSWER_ACCEPTANCE_DECIDED фиксирует фактический verdict, причину, идентичность и доказательство
текста движка. Старые файлы с постоянным accepted=false нельзя трактовать как всеобщий отказ.

Observer stop — отдельный факт, с временем и причиной остановки, не синоним терминала модели.
Рендер главной карточки и pipeline-карточки содержит контекст страницы, тип карточки,
ожидаемый/наблюдаемый ID, измерения текста и outcome. Наличие отдельных наблюдений не
доказывает полного покрытия всех исторических путей.

## Текст и происхождение промпта

Длины — UTF-16 code units. promptArtifact описывает полный обёрнутый промпт до сохранения
фрагмента: fullLength, storedLength, storageLimit, truncated, версия нормализации и хеш.
answerArtifacts.raw включает транспортные метки; cleaned описывает MessageDelivery.clean.
Текст движка и rendered_text имеют отдельные представления. Хеши считаются до обрезки
существующим AnswerProofNormalization. Сопоставлять длины можно только с учётом представления;
удаление метки не является потерей ответа.

PROMPT_COMPILED и prepared.promptLineage сохраняют ID выбранных входов, их provenance,
нормализованные доказательства, fingerprint компилятора и зарегистрированные преобразования.
`promptIdentityProven` требует совпадения хеша и версии нормализации на submitted.
Область этой проверки — dispatch_command: она сопоставляет подготовленный промпт с аргументом
подтверждённой команды отправки, а не проверяет DOM редактора провайдера.

В derived delivery не повторяются полные prompt/answer: preparedPath и journalPath
ссылаются на delivery.journal. Фактические разделы:
delivery.diagnosis.sends/batches/problems/moderator/rejections/matrix и delivery.journal.

## Markdown — страховочный предел 250 000 байт UTF-8

С 3.8.0 предел не является целью проектирования: реальные прогоны (в том числе 10 моделей × 4 этапа)
помещаются целиком, с хронологией. Предел защищает только от патологического ввода.

Генератор 3.8 строит MD непосредственно из исходного JSON. Старый MD не читается.
Это компактные таблицы и хронология отклонений, а не полная хронология с новым кодированием.

- Все запросы: этап, модель, раунд, requestId, dispatch, вкладки и batch source;
  первые отправка/текст/TEXT_STABLE/COMPLETION_DETECTED, принятие движком,
  длины собранного ответа и доставки, счётчики и задержки финализации.
- Все терминальные группы: время, исходные метки и пути, статус/причина, AL/EL/EAL,
  интервал группы и зарегистрированные foregroundMs/focusSwitches/doneReason/durationMs.
  Подряд идущие одиночные группы одного dispatch с одинаковыми статусом, причиной и
  doneReason и без других зарегистрированных значений занимают одну строку (все пути и
  ряд длин сохранены).
- Хронология запросов (раздел 6): по каждому запросу в порядке времени, в заголовке время
  отправки; одно время `t` на запись, записи в пределах 50 мс на одной строке, повторы — ×N
  с первым и последним источником, любое изменение статуса, причины, длины, dispatch или
  привязки — отдельная запись. Нулевая длина стабильного текста и чужая привязка видны;
  записи после конца прогона помечены `[after run end]`. Включено всё, кроме явного шума
  (список NOISE_LABEL в генераторе: PING_TRANSPORT_ERROR, status, Panel output update failed,
  SELECTOR_STATS, SCRIPT_REINJECT_SKIPPED_ACTIVE_RUN, Finalization deferred/defer bypassed,
  ANSWER_GENERATING, ANSWER_CARD_RENDER_EVALUATED, Response ignored (pipeline control),
  DUPLICATE_FINAL_REJECTED, displayed, prepared, PROMPT_COMPILED, TURN_RESOLUTION,
  LEGACY_TIMELINE_EVENT, text_progress, Terminal success deferred, dispatch:command_accepted),
  рутинных наблюдений и рутинных терминалов. Неизвестная метка попадает в хронологию, а не
  в счётчики. Вмешательства автоматизации (dispatch:bottom_nudge, TAB_VISIT_SHORT,
  FORCED_VISIT_SHORT_RETRY, terminal_deferred/deferral_ended, Terminal status upgraded)
  видны у запроса с временем. Доказательства SUCCESS_TERMINAL — в разделе 4 (`ct:`),
  рутинные терминалы — в разделе 5, dispatch/submitted/tab/navigation — в разделе 4 и
  источнике. Запросы без отклонений перечислены одной строкой. В режиме aggregated
  вместо хронологии остаётся группировка по метке.
- Фокус (раздел 10): итоги, таблица по запросам (переключения до отправки, между отправкой
  и первым текстом, между первым текстом и финалом, после финала, источники) и полный
  список переключений по времени с запросами, которые в этот момент находятся в интервале
  first_text→финал доставки («others printing»). Интервал не доказывает непрерывную печать.
- Факты о длинах и отображении: диапазон/нули стабильного текста, число групп,
  наблюдения до отправки/совпадения длины с предыдущим запросом, число результатов
  отрисовки по запросу; одна таблица результатов отрисовки на весь прогон с первым и
  последним источником.
- Ручные действия (записи одного этапа и модели в пределах 1 с — одно действие), отказы
  старта, фокус, записи вне окна прогона, проверки фрагментов промптов (строки только для
  найденных совпадений, остальное — одной строкой на результат), группы диагнозов, сверки
  и пакеты доставки; проблемы focus_* свёрнуты в одну строку с путями. Пустой раздел
  пишет явный ноль («0 refusals…», «0 records…»), а не пустую таблицу.
- Фон — это все группы запроса, не попавшие в хронологию, один раз на весь прогон. В MD нет словарей G/V/C/I/L,
  копий evidence, полного списка диагнозов и всех промежуточных опросов.

Полная хронология, все промежуточные хеши и изменения идентичности, artifacts,
prompt lineage и детали диагнозов остаются в исходном JSON. Внутренние структурированные
факты Extract также сохраняются; MD ссылается на записи через E/J/S/B.
Непривязанные ошибки выводятся отдельно с причиной и адресами E/J. Статистика вытеснения
содержит минимум/максимум всех наблюдений, включая пики перед сбросом; крайние источники
выбираются по времени, а не по порядку появления групп.
Если нет ни одной записи времени для базы, t не вычисляется; — обозначает неизвестное время, а не ноль.

Размер проверяется в общем браузерном генераторе (рассчитан на реальные прогоны, см. выше), в байтах UTF-8, перед скачиванием MD.
Если таблицы превышают бюджет, генератор автоматически переходит к `mode=aggregated`:
ошибки агрегируются по метке с числом сочетаний статуса/причины; длинный свободный текст ручных действий
представлен явно помеченным превью с исходной длиной и ссылкой на JSON. Идентификаторы,
решения о принятии, числа и терминальные поля в таблицах не обрезаются.
Если и это превышает бюджет, `mode=overview` содержит общие счётчики, решения о принятии,
терминальные статусы и самые частые метки ошибок. Число показанных групп и остаток объявлены;
полные таблицы запросов и причины доступны в исходном JSON. Уровень агрегации виден в шапке.
Критические категории выводятся отдельной обязательной таблицей с полными счётчиками:
отказ этапа, нарушения корреляции, расхождения состояния, отказ доставки ответа,
неотправленный запрос/потеря контекста, терминальный отказ и зарегистрированная высокая
важность. Они учитывают также терминальные записи и ошибки этапа без привязки к модели.
В ограниченной таблице меток критические события идут первыми; частота служит вторичным
критерием. Даже если меток больше лимита, счётчик каждой критической категории сохраняется.
Каждый участник терминальной пары учитывается под собственной меткой и своим путём.
`terminal_failure` требует MODEL_TERMINAL_COMMITTED или completion_terminal с ошибочным
статусом; промежуточные ERROR/RECOVERABLE_ERROR не доказывают терминальный отказ.
Зарегистрированная важность берётся из event.severity, включая события без известных
меток ошибок и без привязки к запросу. Severity участвует в группировке наблюдений;
отсутствие поля и null сохраняются отдельно от значений high/critical.
Размер обзорного уровня ограничен числом групп и длиной превью независимо от числа запросов.
Превышение бюджета больше не отменяет скачивание MD и не вызывает ошибку Extract.

## Запрос проверяющей модели

Проверь выжимку транспорта. Используй только зарегистрированные факты и расчёты из MD;
для уточнения обращайся к исходному Disput Flow JSON по указанным путям.
Разделяй факт, вычисление, гипотезу и недостаточность данных. Не пересчитывай вручную
медиану и времена, не складывай накопительные waitedMs. Учитывай область integrity.checks,
качество привязки, разные представления текста и пределы сохранённых фрагментов.
Не приписывай отсутствующим полям значения и не выдавай отсутствие события за отсутствие действия.

## Хранение текущего прогона (2.81.585)

Pipeline хранит журнал движка, контрольные снимки и курсор публикации в памяти
страницы с начала прогона. Они не занимают localStorage и доступны для экспорта
и Pause/Continue, пока страница открыта. После перезагрузки архив прогона
не восстанавливается. Защита владения остаётся общей: lease в хранилище,
BroadcastChannel и navigator.locks. При создании прогона удаляются старые
ключи disputOrchestratorV2:*:events/snapshots/published; lease и настройки сохраняются.
