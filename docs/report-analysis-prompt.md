# Проверка выжимки транспорта

Схема работы: Disput Flow → Extract в расширении → проверка фактов моделью.
Расчёты выполняет `shared/report-digest.js`; модель читает готовый результат.

## Получение файлов

На вкладке Disput выберите transport и нажмите Extract. Из одного снимка скачиваются
ровно два файла с одинаковым временем в имени:

- `Disput Flow YYYYMMDD_HH-MM.json`: исходная телеметрия с журналом доставки.
- `extract_transport_YYYYMMDD_HH-MM.md`: самостоятельная выжимка.

Отдельный JSON выжимки не скачивается. Внутренние таблицы имеют schemaVersion 3,
DIGEST_VERSION 3.0.0. Версия в metadata относится к производителю исходного отчёта.
Only problems влияет на отображение вкладки, экспорт содержит весь доступный снимок.
Командная строка для Extract не используется.

## Идентичность и единицы

- `correlation.transportRequestId` — канонический идентификатор запроса; requestId —
  совместимый псевдоним. Dispatch идентифицирует отправку, stageAttemptId — попытку этапа.
  Эти количества не равны по определению. Batch-событие не считается отдельной отправкой модели.
- Привязка: запрос, затем dispatch, затем однозначная пара этап/модель. Неоднозначная
  пара остаётся unassigned. Чужой dispatch сохраняет первоначального владельца.
- pipelineRoundId используется для проверки, а не как самостоятельный ключ привязки.
  tabId нормализуется в строку. Карта сохраняет токены, batch_start и исходные полные ID.
- null, отсутствие поля, пустая строка, пустой массив, false и 0 различаются.
- `t`: секунды от stageExecutions[0].actual.startedAt с точностью 0.001.
  Порядок этапов сохраняется. +st и +sub появляются только в таблице запросов;
  нулевой +sub при submitted не повторяется. Граница прогона берётся из runOutcome,
  а не из начала первого этапа. После границы дополнительно показан +end.
- sourceTimestamp и receivedAt — разные часы производителя и коллектора.
  delivery.journal.at — время панели; delivery.ms отсчитывается от prepared.
  Эти определения и зарегистрированные изменения режима сохраняются в metadata.

## JSON: контракт телеметрии

Отчёт schemaVersion 2 содержит события schemaVersion 6. Известные идентификаторы,
ожидаемая/входящая идентичность, доказательства рендера и предоставленные причинные
ссылки проходят диагностический адаптер без потери нулей и null.

`metadata.dataCompleteness` оценивает корреляцию событий; область оценки указана
в dataCompletenessBasis. `completeness` отдельно сообщает доступность плана,
идентичности, доказательств отображения и остановки наблюдателя. provenance считается
отдельно: legacy_adapter сам по себе не означает неполноту. Один run ID не делает
событие конкретного запроса точно привязанным.

`integrity.checks` различает checked, not_checked и insufficient_data. Пустые массивы
предупреждений не означают выполненную проверку. Проверка часов ограничена опережением
sourceTimestamp относительно receivedAt на 5000 мс; синхронизация часов не доказана.
Без терминала прогона completedAt=null, последнее наблюдение — отдельное lastObservedAt.

`collection` содержит известные принятые/вытесненные события, лимит и фильтрацию адаптера.
Неизвестный исходный объём источника остаётся null. delivery.collection отдельно сообщает
предел журнала и пропущенные подробности переключений фокуса. Исходные записи остаются
в JSON; сжатие применяется к представлению MD.

При отсутствии фиксированного execution plan expectedStages=null; completedStages
считается по фактически наблюдавшимся этапам. `planning` сохраняет авторские ревизии
динамического плана и соответствия stageInstanceId/plannedStageId/planRevisionId.
Ожидания отдельного этапа берутся из явно связанной ревизии, без подстановки всей
последней ревизии в исторический этап и без угадывания будущего количества этапов.

ANSWER_COLLECTED.accepted=null означает сбор до решения движка.
ANSWER_ACCEPTANCE_DECIDED фиксирует фактический verdict, причину, идентичность и доказательство
текста движка. Старые файлы с постоянным accepted=false нельзя трактовать как всеобщий отказ.

Observer stop — отдельный факт, с временем и причиной остановки, не синоним терминала модели.
Рендер главной карточки и pipeline-карточки содержит контекст страницы, тип карточки,
ожидаемый/наблюдаемый ID, измерения текста и outcome. Наличие отдельных наблюдений не
доказывает полного покрытия всех исторических путей.

## Текст и происхождение промпта

Длины — UTF-16 code units. promptArtifact описывает полный обёрнутый промпт до сохранения
фрагмента: fullLength, storedLength, storageLimit, truncated, версия нормализации и хеш.
answerArtifacts.raw включает транспортные метки; cleaned описывает MessageDelivery.clean.
Текст движка и rendered_text имеют отдельные представления. Хеши считаются до обрезки
существующим AnswerProofNormalization. Сопоставлять длины можно только с учётом представления;
удаление метки не является потерей ответа.

PROMPT_COMPILED и prepared.promptLineage сохраняют ID выбранных входов, их provenance,
нормализованные доказательства, fingerprint компилятора и зарегистрированные преобразования.
`promptIdentityProven` требует совпадения хеша и версии нормализации на submitted.
Область этой проверки — dispatch_command: она сопоставляет подготовленный промпт с аргументом
подтверждённой команды отправки, а не проверяет DOM редактора провайдера.

В derived delivery не повторяются полные prompt/answer: preparedPath и journalPath
ссылаются на delivery.journal. Фактические разделы:
delivery.diagnosis.sends/batches/problems/moderator/rejections/matrix и delivery.journal.

## Markdown

1. Все запросы, включая успешные: первые TEXT_STABLE/COMPLETION_DETECTED, accepted и решения,
   явно названные счётчики, интервалы задержек терминальных групп.
2. Одна общая шкала этапа: dispatch_started, submitted, SUBMIT_CONFIRMED, focus, tab,
   navigation обеих моделей. submitted и подтверждение не подменяют друг друга.
3. Хронология запроса: первые наблюдения и изменения состояния; фон — группы со счётчиками,
   первой/последней точками. Изменения длины, статуса, dispatch и значимых полей не теряются.
   Чередование разных моделей не дробит одну устойчивую последовательность; возврат к
   прежнему состоянию сохраняется отдельным переходом.

Нет лимита в 160 строк. Coverage сообщает показанные и исходные записи.
Временные счётчики опроса и sampled SELECTOR_STATS hit/miss/rate не являются ключами;
точные исходные значения доступны по реестру путей. Поля, различающие группы,
показываются в состоянии или словаре V. Недостающая длина в selector summary не объявляется
переходом реального текста к null.

FINALIZATION_DECISION и MODEL_FINAL объединяются только при совместимых запросе, dispatch,
статусе, причине, длинах и интервале до 50 мс. Все исходные метки, длины и пути остаются
в одном терминальном реестре; остальные таблицы используют ссылки QN.TK. Зарегистрированные
foregroundMsUsed/focusSwitchesUsed/doneReason/durationMs не имеют причинной интерпретации.

Шапка объявляет E/J/S/B/P, QN.DK, QN.TK, G, V и сокращения меток событий.
Реестр G содержит все адреса членов группы: диапазон 1..3 означает 1,2,3;
1..13/4 означает 1,5,9,13. Эти ссылки полностью восстанавливаются без отдельного JSON выжимки.
Динамически указана доступность полей; старые ограничения перечисляются только когда применимы.

Оговорки общие для всего документа. Ручные действия показаны с временем и подробностями;
все journal kinds не выдаются за действия пользователя. Ожидания отказов накопительные,
их нельзя складывать; elapsedFromBatchMs не доказывает длительность блокировки.
Обнаружение фрагмента prepared.prompt не доказывает отправку или передачу полного ответа.
Без подтверждённой зависимости следующий наблюдавшийся этап обозначается кандидатом.

Диагнозы сгруппированы в сводке, индивидуальные строки с путями — в приложении.
Сравниваются только одноимённые величины одной области; события, записи и запросы считаются
отдельно. Пакеты сохраняют runMode/skipped/adopted, а повторные problems ссылаются на разделы
фокуса и отказов. Основные разделы имеют непрерывную нумерацию 1–15.

## Запрос проверяющей модели

Проверь выжимку транспорта. Используй только зарегистрированные факты и расчёты из MD;
для уточнения обращайся к исходному Disput Flow JSON по указанным путям.
Разделяй факт, вычисление, гипотезу и недостаточность данных. Не пересчитывай вручную
медиану и времена, не складывай накопительные waitedMs. Учитывай область integrity.checks,
качество привязки, разные представления текста и пределы сохранённых фрагментов.
Не приписывай отсутствующим полям значения и не выдавай отсутствие события за отсутствие действия.
