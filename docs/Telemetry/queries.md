# Запросы к модели по телеметрии

Телеметрия больше не строит отчёты и дайджесты. Экспорт (`Telemetry → ↓`) отдаёт сырые события прогона, а разбор делает модель по запросу под проблему. Файл прикрепляется к сообщению, запрос вставляется текстом. Если проблема в одной модели, сначала выбрать её в фильтре `Platform`.

Для pipeline Basic есть отдельный файл прогона (`Disput → Basic`) и свой запрос — раздел «Прогон Basic» в конце.

## Профили экспорта

Список рядом с кнопкой `↓` выбирает, что попадёт в файл. По умолчанию `Raw (all)`: все события (до 3 МБ). Для типичных задач есть сжатые профили, в которые уже вписана задача для модели, так что запрос можно не набирать:

| Профиль | Для чего |
|---|---|
| Prompt not sent | запрос не дошёл до модели или не подтверждён |
| End of generation | окончание генерации определено рано или поздно |
| Which answer is last | принят не тот (старый, чужой) ответ |
| Truncated answer | зафиксирован успех, а текст неполный |

В сжатом файле поля короткие: `t` — мс от `startTs`, `p` — модель, `l` — метка, `v` — уровень, `d` — details, `m` — meta, `n` — число подряд идущих повторов. Задачи ниже остаются для сырого файла и для проблем, которых профили не покрывают.

## Как читать файл

- `events` идут по времени; `platform` — модель, `label` — что произошло, `level` — важность, `details` и `meta` — подробности.
- `meta.dispatchId` — один запрос к модели; `meta.runSessionId` — один прогон.
- Файл содержит события всех волн текущего прогона и сохраняется после перезагрузки страницы и расширения; очищается при старте нового прогона.
- Лог ограничен (4000 событий / 3 МБ), при длинном прогоне начало может быть вытеснено. Чего нет в файле, то «не зафиксировано», а не «не было».
- Часть меток закреплена и переживает вытеснение: `PROMPT_*`, `DISPATCH_BASELINE_CAPTURED`, `FINALIZATION_DECISION`, `MODEL_FINAL`, ошибки.

## Общая шапка запроса

> К сообщению приложен JSON сырых событий телеметрии расширения (формат `telemetry-raw/1`). Опирайся только на события из файла и называй метки и `ts`, на которые опираешься. Чего в файле нет, пиши «не зафиксировано». Не строй догадок о причинах, которых события не показывают. Ответ: (1) вывод в одном предложении, (2) цепочка событий с `ts` в порядке времени, (3) чего не хватило для уверенного вывода.

Дальше добавляется одна из задач.

## Задачи

**Обрезанный ответ** (зафиксирован SUCCESS, а текст явно неполный). Найди `MODEL_FINAL` для модели `<M>` и `FINALIZATION_DECISION` перед ним. Покажи, какие причины приняли ответ. Проверь `ANSWER_TEXT_STABLE`, `ANSWER_COMPLETE_DETECTED`, `ANSWER_LENGTH_DECREASED`, `ANSWER_PARTIAL_ON_TIMEOUT`, `ANSWER_COMPLETE_TIMEOUT`. Был ли ответ принят по таймауту или по стабильности текста, и был ли признак завершения от самой модели.

**Ложный успех** (система решила «готово», а ответ продолжил расти). Сравни `ts` решения (`FINALIZATION_DECISION`, `MODEL_FINAL`) с последним `ANSWER_GENERATING` и с `POST_TERMINAL_ANSWER_OBSERVED` и `ANSWER_LENGTH_DECREASED` для той же модели. Насколько позже решения появились признаки генерации.

**Старый ответ** (принят текст от предыдущего запроса). Для модели `<M>` найди `DISPATCH_BASELINE_CAPTURED` текущего `dispatchId`, затем `STALE_BASELINE_ANSWER_IGNORED`, `ANSWER_DELIVERY_REJECTED`, `RECOVERY_STALE_BASELINE_REJECTED`. Совпадает ли принятый ответ с базовым (по длине и хэшу в `meta`), и кто его принял.

**Нет доставки** (ответ получен, но не оказался в нужной карточке). Проследи `dispatchId` от `DISPATCH_SEND` до `MODEL_FINAL`; найди `ANSWER_DELIVERY_REJECTED` и причину в `meta` (ожидаемый и пришедший `dispatchId`, вкладка, прогон).

**Prompt не вставился.** Для модели `<M>` покажи `PROMPT_INSERTION_CONFIRMED` / `PROMPT_INSERTION_FAILED` текущего `dispatchId` и стадии `PROVIDER_DISPATCH_STAGE_OBSERVED` перед ними. На какой стадии остановилось и что сказано в `details`.

**Prompt не отправлен.** Для модели `<M>` покажи `PROVIDER_SUBMIT_METHOD_OBSERVED`, `PROMPT_SUBMITTED_ACCEPTED`, `PROMPT_SUBMITTED_UNCONFIRMED`, `RECOVERY_BLOCKED_SUBMIT_UNCONFIRMED`. Было ли подтверждено, что запрос ушёл, каким способом отправки и что делала система после.

**Долгий хвост** (текст давно стабилен, а система ждала). Для модели `<M>` найди момент последнего изменения длины текста (`ANSWER_TEXT_STABLE`, `ANSWER_GENERATING`), момент `ANSWER_COMPLETE_DETECTED` и момент `MODEL_FINAL`. Сколько прошло между ними и что удерживало финализацию (`FINALIZATION_DECISION`, `ROUND4_FORCE_FINAL`, барьеры).

**Общий разбор прогона.** Для каждой модели одной строкой: когда отправлен запрос, когда пришёл первый признак ответа, когда финализировано, чем закончилось. Затем отдельно перечисли события с `level` `error` и `warning`.

## Прогон Basic

Файл `Basic <дата>.json` (вкладка Disput → Basic), формат `basic-telemetry/3`, состав — [telemetry.md](telemetry.md), раздел «Basic: JSON прогона». Фильтры окна на этот файл не влияют. Запрос:

> К сообщению приложен JSON прогона Basic (формат `basic-telemetry/3`). Опирайся только на файл и называй пути полей, на которые опираешься (`rounds[i].participants[j]`, `customRun.attempts[k]`, `delivery.diagnosis.sends[n]`, `delivery.journal[n]`, `telemetry.events[n]`). Чего в файле нет, пиши «не зафиксировано». Не строй догадок о причинах, которых файл не показывает.
> 1. По `rounds` для каждого шага и визита одной строкой: шаг, исход (`outcome`), длительность, ожидание User; затем по участникам — `outcome` и `reason`.
> 2. Для каждого участника с исходом не `accepted`: его попытки в `customRun.attempts` (по `ref`, `participant`, `visit`) с `state`, `reason`, `status`, `trigger`; по `transportRequestId` — отправка в `delivery.diagnosis.sends` (`result`) и события в `delivery.journal` и `telemetry.events`. Где оборвалась цепочка: запрос не ушёл, отправка не подтверждена, ответа нет, ответ не принят.
> 3. Отдельно: `delivery.diagnosis.problems`, а также `delivery.unassigned` и `telemetry.unassigned` с `selectionReason`.
>
> Ответ: (1) вывод в одном предложении, (2) разбор по пунктам 1–3, (3) чего не хватило для уверенного вывода.

Текст запроса и ответа конкретной попытки — `customRun.attempts[k].sentPrompt` и `answer`.
