## 1. Цель и границы

Пользователь должен иметь возможность по JSON кнопки **Basic** восстановить для каждого шага: какой участник, с каким входом, в какой чат и почему получил запрос; когда запрос действительно отправлен; какой ответ получен и принят; кто инициировал повтор; что происходило во время ожидания User; чем закончился шаг.

Исполнение должно сохранять уже полученные результаты при остановке, восстанавливать правильные чаты и показывать ответы разных участников раздельно. Телеметрия фиксирует факты; она не управляет отправкой и не подменяет приёмку движка.

Область: Basic (`custom` в коде), общая доставка в части идентификации событий и хранения журнала, экспорт Basic, существующая лента и холст. Не переделывать другие pipelines, транспорт целиком, формат схемы, выбор моделей, правила приёмки, интерфейс настроек. Новые кнопки, фильтры и настройки хранения не нужны. Бинарные вложения в телеметрию не копировать.

Словарь: **шаг** — `round` или `owner`; **участник** — `models[].id`, при отсутствии ID имя модели; **модель** — провайдер; **попытка** — запрос участника внутри шага и визита; **волна** — часть запросов, отправляемая страницей отдельным пакетом. Два участника одной модели — разные чаты и ответы.

## 3. Обязательные инварианты

1. Полная идентичность попытки: `runId + stepRef + participantId + visit + attempt + phase`. Сохраняемый `attemptKey` остаётся локальным прогону ключом CustomRunRecord; между модулями используется пара `runId + attemptKey`. Ключ карточки (`cardKey`): `runId + stepRef + participantId + visit`. Исправление получает новый attemptKey, но отображается на прежнем cardKey. Новые поля ID не вычислять из текста роли или подписи карточки.
2. `transportRequestId` связывает конкретную транспортную отправку. До её создания и при чтении чата он может отсутствовать. `dispatchId`, `tabId` и имя модели не являются его взаимозаменяемыми синонимами.
3. Подготовка запроса, подтверждённая отправка, возврат текста и приёмка — разные факты. Существующий `sentAt` старых записей не переименовывать задним числом в доказанное время отправки.
4. Принятый результат завершённой волны не исчезает из-за остановки другой. Отправка следующей волны не начинается до успешного checkpoint результатов предыдущей.
5. Завершённая попытка не переписывается повтором; повтор — новая попытка со ссылкой на исходную. Повторное уведомление о том же результате не создаёт новый артефакт или новую приёмку.
6. Неизвестное остаётся неизвестным. Если идентичность конфликтует или отсутствует, не выбирать последнюю модель, ближайшее время или похожий текст.
7. Ошибка телеметрии не запускает запрос, не принимает ответ и не делает автоматический повтор. Ошибка обязательного checkpoint по-прежнему останавливает исполнение.
8. JSON Basic не зависит от Platform/Only problems. События другого доказанного прогона не входят в события выбранного.

## 5. Технические требования по пакетам

### A. B01 — сохранение чатов при остановке

**Файлы:** `results.js`, при необходимости `disput/custom-run-record.js`. Ориентиры: `checkpointRecord`, финальный `CustomRecord.setSnapshot`, `refreshParticipantChats`, `filesNeeded`, `resumeCustomFromPage`.

- Вынести сборку сохраняемого состояния в одну локальную функцию страницы. И checkpoint, и финальное сохранение используют её.
- Состояние движка сохраняет позицию и результаты; для маршрутизации использовать актуальные полные `chatBindings` страницы, а не заменять их сокращённой картой движка.
- Сохранить поля `modelName`, `stepRef`, `visit`, `transportRequestId`, `tabId`, `requestId`, `stageAttemptId`, `chatVisit`, `attachedChatVisit`, если они известны. Не подставлять неизвестным полям значения от другого участника.
- Не терять `pendingOwner`, уже принятые ответы и текущие `pending` при финальном сохранении. При ошибке продолжения не оставлять старый `stopReason` единственным описанием новой ошибки.
- Старый снимок с неполной привязкой продолжать по текущим строгим правилам; не угадывать чат и не открывать замену автоматически.

**Приёмка:** остановить прогон перед следующим шагом, очистить только фоновую карту привязок, продолжить. Используется сохранённый tabId своего участника; существующая вкладка/чат соседа не выбирается; потерянная вкладка даёт явный отказ. Файлы не прикрепляются повторно к чату с подтверждённой загрузкой. Снимок после финала содержит те же известные поля привязки, что перед ним.

### B. B02 — результаты отдельных волн

**Файлы:** `disput/custom-engine.js`, `results.js`. Ориентиры: `attempt`, `sendParticipants`, `sendWave`.

- Добавить необязательный async callback `meta.onWaveResult(byParticipant)` в контракт `sendParticipants`. Старый автономный адаптер, возвращающий общий `byParticipant`, остаётся поддержанным.
- После каждого завершившегося `sendWave` страница передаёт результат callback и **await** его завершение перед следующей группой/волной. При Stop после получения результата сначала сохранить этот результат, затем остановить дальнейшие отправки.
- Движок использует одну функцию приёмки результата и для callback, и для общего возврата. Она обновляет `outcome`, попытки через `onResponse`, артефакты и `inFlight`; затем выполняет checkpoint. Уже обработанные ID не обрабатываются повторно при общем возврате.
- Callback принимает только участников текущей попытки. Повторное уведомление с тем же результатом идемпотентно; конфликтующее повторное уведомление не заменяет принятый результат, сохраняется как диагностический конфликт.
- При AbortError после обработанных волн их результаты остаются. Запрос с возможной отправкой и без доказанного результата остаётся неизвестным по текущему протоколу восстановления. Для ещё не начатой волны фиксировать `not_sent` с причиной `cancelled_before_dispatch`, убрать её участников из pending неизвестных; при продолжении они отправляются как `resume_unsent` без окна разрешения неизвестной отправки. Если такой участник имел подготовленную запись попытки, её сохранить как not_sent, а фактическую отправку оформить новой попыткой со ссылкой на неё. Граница «не отправлено» берётся из явного факта до внешнего вызова, а не из отсутствия submitted-события.
- Ошибка checkpoint из callback не превращается в обычный ответ транспортной ошибки и не разрешает следующую волну. Новых автоматических повторов после Stop нет.
- Не менять семантику раунда: он ждёт всех участников; раннее сохранение A не разрешает запуск следующего шага до решения по B.

**Приёмка:** A ответил в волне 1, B прерван после возможной отправки в волне 2 — A имеет `done`, текст и фактический verdict; при продолжении A не отправляется заново, B обрабатывается штатным разрешением неизвестного исхода. Если остановка произошла до запуска волны B, он not_sent и при продолжении не вызывает окно неизвестной отправки. Повтор rejected-A не пересылает accepted-B. Повторный callback не создаёт второй артефакт. Проверить остановку между волнами, внутри второй волны, ошибку checkpoint и остановку до первой отправки.

### C. B03 — карточки участников

**Файлы:** `results.js`; `results/stage-card.js` только если требуется передача структурной идентичности. Ориентиры: `sendWave`, `resolveDebateFeedMeta`, `setDebateCardRound`, `matchesDebateCardRound`, `resolveSingleDebateAnswerCard`, `appendPostTerminalAnswerRevision`, сохранение/восстановление ленты.

- Передавать `participantId`, `stepRef`, `visit` структурно, сохранять их в metadata карточки и записи ленты.
- Для Basic ключ карточки — прогон, шаг, участник, визит. Имя модели — отображаемый провайдер, не ключ участника. Новая попытка исправления имеет новый attemptKey и относится к прежнему cardKey своего участника. Транспортные события сначала связываются с попыткой, затем с её карточкой.
- Все пути поиска карточки, дедупликации, post-terminal ревизий, частичного вывода и позднего финала используют тот же ключ. Нельзя исправить только финальный `sendWave`: живые транспортные обновления также должны получать идентичность из контекста своего запроса.
- Второй участник не попадает в `Δ` первого. Дополнительная техническая ревизия одного запроса остаётся в карточке этого же участника. Звёздочка/утверждение A не переносится B.
- Для других pipelines и исторической ленты без participantId сохранить существующий путь сопоставления. Не мигрировать старые карточки на основании подписи роли.

**Приёмка:** два участника Claude, разные и одинаковые тексты, обратный порядок ответов, исправление только A, позднее событие старого запроса A, восстановление ленты — всегда две самостоятельные карточки; текст, роль, requestId и копирование каждой относятся к одному участнику.

### D. C01+C02 — намерение и фактическая маршрутизация

**Файлы:** `results.js`, `disput/custom-run-record.js`, `shared/message-delivery.js`, `background/tab-manager.js`, `background/job-orchestrator.js`, `background/message-router.js`, `content-scripts/content-bootstrap.js`, `content-scripts/content-utils.js`, `content-utils/response-lifecycle-detector.js`. Сгенерированные bundles обновляются штатной сборкой после правок исходников, вручную не редактируются.

**Намерение страницы:** для каждой реально готовящейся к отправке попытки записать `chatIntent`:

| Поле | Значение |
|---|---|
| `newChat` | Фактически переданный странице/фону boolean, а не пересчитанный при экспорте |
| `reason` | `step_new`, `new_pages_first_request` или `continue`; первая причина соответствует приоритету условий текущего `isNewChat` |
| `bindingTabId` | Сохранённая вкладка продолжения либо null |
| `attachmentNames` | Имена файлов этой отправки, без base64; пустой список при отсутствии файлов |

`chatIntent` записывается до внешней отправки и связывается с ключом попытки; не хранится только на уровне прогона. Старые попытки без этих полей остаются читаемыми. Исходный контракт схемы не меняется.

Передать в `context.participants[modelName]` структурные `stepRef`, `participantId`, `visit`, `attempt`, `phase`, `attemptKey` вместе с существующим newChat/binding. `attemptKey` совпадает с ключом CustomRunRecord, runId передаётся отдельно. Фон переносит эти поля в событие выбора чата; не разбирает строку stageAttemptId для восстановления визита и номера попытки. Страница сохраняет chatIntent в запись до запуска внешней отправки; при необходимости использует тот же обязательный механизм checkpoint, с его существующей семантикой отказа.

**Фактический маршрут:** в момент выбора фоном записать событие `participant_chat_resolved` с ключом попытки, transportRequestId, tabId и `action = created | attached_unbound | continued | refused`, а также конкретной `reason`. При отказе tabId может быть null. Причина фиксируется в ветке принятия решения, не восстанавливается по URL. Если `newChat=false` привёл к созданию чата при первом запросе без привязки, сохранить именно `created`, не `continued`.

После получения такого события актуализировать известную попытку в записи через отдельный metadata-update, не обходя запрет переписывать завершённый ответ. Поздние сведения о маршруте могут дополнять пустые поля идентичности; не менять текст, приёмку и результат завершённой попытки.

Поле попытки для этого факта — `chatRoute = { action, reason, tabId, transportRequestId, eventId }`. Если фактических сведений нет, поле отсутствует/null; не заполнять его копией chatIntent. Два несовместимых route-факта не перезаписывают друг друга молча: исходные события сохраняются, а попытка получает явное указание конфликта.

**Идентичность событий:**

1. `navigation`, `completion_terminal`, `provider_stop` получают идентичность у производителя/фона. Сохранить исходную идентичность и ожидаемую отдельно, если они расходятся.
2. Использовать явный transportRequestId; учитывать его в top-level, `meta` и `metadata` по существующим конвертам. Если переданный ID неизвестен, не откатываться к последней записи модели.
3. При отсутствии ID допустима только подтверждённая привязка вкладки к конкретному запросу в момент события. Навигация старой вкладки не получает текущий запрос другой вкладки того же провайдера.
4. В нормализованной записи отдельно хранить `sourceTransportRequestId` (переданное значение), `requestId` (доказанно найденный запрос либо null), `attemptCorrelation = linked | unassigned | conflict` и причину. При неизвестном явном ID: sourceTransportRequestId сохраняется, requestId=null, причина `unknown_request_id`; подстановка последней модели запрещена. Исходный конверт не переписывать. Это корреляция **попытки**, не решение об отборе события прогона: собственный runId позволяет сохранить событие прогона даже при неизвестной попытке.
5. Сохранить ID запроса/участника при STOP_AND_CLEANUP и при подтверждении его результата. Отложенный `provider_stop` старой команды не относится к новой отправке.
6. В пределах этой же правки проверить другие ветки `observeRuntime`, которые участвуют в Basic (`focus`, `status`, `tab`): они также не должны назначать чужой запрос через безусловный fallback модели. Если соответствующая ветка не имеет доказательства запроса, оставить событие непривязанным, а не расширять архитектуру статусов.
7. В этом пакете производители runtime-событий создают sourceEventId до рассылки по правилам E. Пакет E затем использует уже доступный ID для хранения; ему не требуется повторно редактировать контентные исходники D. Пересборку производных content bundles выполняет интегратор I.

**Приёмка:** подготовить A и B одной модели; после B передать три типа событий с ID A — каждый остаётся на A. Повторить без ID, но с доказанной вкладкой A; с неизвестным ID; с чужим runId; с устаревшей командой остановки; с двумя возможными привязками. Неоднозначная попытка явно unassigned/conflict; исходный неизвестный ID не потерян. Собственный runId + неизвестный ID запроса остаётся событием выбранного прогона, но не назначается A или B. Новый чат, продолжение, свободная вкладка, отказ strict, флажок New pages и исправление в прежнем чате дают правильные intent/action.

### E. C04 — один журнал для двух страниц

**Файлы:** `shared/message-delivery.js`, новый `background/message-delivery-store.js`, `background/index.js`, `background/message-router.js`, `results.js`, `shared/message-delivery-view.js`. Изменения только хранения/чтения; не переносить всю диагностику или приёмку в фон.

- Единственный writer сохранённого журнала — фон расширения. Хранилище — `chrome.storage.session`, ключ `messageDelivery.journal.v2`; конверт `{version:2, events, collection}`. Цель — пережить перезагрузку/закрытие страницы, не перезапуск браузера или reload расширения.
- Страницы передают новые факты через `DELIVERY_JOURNAL_APPEND`; фон последовательно добавляет их и подтверждает запись. Экспорт читает `DELIVERY_JOURNAL_SNAPSHOT`, явная очистка использует `DELIVERY_JOURNAL_CLEAR`. Названия сообщений не использовать для неявного старта/очистки прогона.
- Загрузка любой страницы не удаляет журнал и не записывает поверх него свой локальный массив. Чтение Basic и старого Disput использует общий snapshot, независимо от наличия MessageDeliveryView в HTML.
- Для runtime-события `sourceEventId` создаётся ровно один раз у производителя до runtime fanout: SPA_NAVIGATION в content-bootstrap, PROVIDER_STOP_RESULT в content-utils, terminal в response-lifecycle-detector; у фонового события — в фоне перед рассылкой. Все потребители, повторные доставки и replay сохраняют ID. Если одно исходное событие создаёт несколько разных записей журнала, их eventId — sourceEventId + kind + стабильный порядковый номер внутри преобразования, одинаковый на обеих страницах. Для событий самой страницы producerId — новый уникальный ID экземпляра страницы при каждой загрузке; eventId = producerId + монотонный seq создаётся до append. ProducerId не переиспользуется после reload при сброшенном seq. Два разных наблюдения не схлопываются по равным времени/метке/модели.
- ACK append отправляется только после успешной записи storage.session. Если worker умер после записи, но до ACK, повтор с тем же eventId идемпотентен. Неподтверждённый хвост хранится в памяти отправителя до ACK и входит в доступный локальный export; если одновременно исчезли и отправитель, и неподтверждённая запись, гарантии восстановления нет. После suspension worker читает подтверждённый snapshot до обслуживания append/read; не обещать восстановление несохранённой RAM-очереди. При инициализации соблюдать действующий `__extensionLifecycleReady`, чтобы cleanup расширения не стёр подтверждённую новую запись.
- Экспорт объединяет подтверждённый snapshot с ещё доступными локальными записями по eventId. `collection` явно сообщает подтверждённый объём, локальные неподтверждённые события и ошибки записи. Недоступность фона не превращается в пустой «полный» отчёт и не блокирует исполнение Basic.
- Сохранить текущий предел 3000 записей; добавить общий предел 3 МиБ UTF-8 сериализованного конверта. Это предел всего журнала, а не каждого прогона. Вытеснять старые записи с точными счётчиками; не сохранять вторую полную копию prompt/answer в новых событиях.
- Очистка — только явная команда. Открытие нового прогона не стирает доступный предыдущий; выбранный Basic отбирается по ID при экспорте. При чтении старого ключа допускается однократный импорт существующих записей с отметкой legacy; отсутствие старого зеркала не восстанавливается догадкой.
- Запись из нескольких страниц проходит одну очередь фона. Восстановление после suspension service worker, дубли runtime-доставки и квота проверяются отдельно; локальный массив страницы не становится источником истины для чужого прогона.

**Приёмка:** R1 идёт на странице A; открыть B; выгрузить R1 из B; перезагрузить A; приостановить/восстановить service worker; снова выгрузить — подтверждённые записи сохранены, копий нет. Одно runtime-событие, полученное A и B и повторённое после рестарта worker, даёт одну запись; два реальных одинаковых по полям наблюдения дают две. Убить worker после write-before-ACK, повторить append — дубля нет. Затем R2 и экспорт R1: события не смешаны. Проверить явную очистку, вытеснение, ошибку записи, экспорт неподтверждённого локального хвоста. Перезагрузка расширения может очистить storage.session: это отражается как недоступный источник, не обещать долговечность на диске.

### F. C03 — непривязанные наблюдения и JSON

**Файлы:** `shared/basic-telemetry.js`, `results.js`. Версия нового экспорта — `basic-telemetry/2`; старые записи CustomRunRecord версии 2 читаются без миграции.

- Сохранить `customRun`, `executionActive`, `delivery.journal`, `telemetry.events`. Два последних содержат только доказанно относящиеся к выбранному прогону записи.
- Добавить `delivery.unassigned` и `telemetry.unassigned`: доступные в снимке соответствующего источника записи без достаточной привязки к прогону либо с конфликтом идентичности прогона. Каждая содержит исходное событие и `selectionReason`; это наблюдения источника, **не события выбранного прогона**. Не отбирать их «по похожей модели» и не объявлять принадлежность на основании времени.
- Разделить две оси: `runSelection = selected | unassigned | otherRun | invalid` и `attemptCorrelation = linked | unassigned | conflict`. Собственный runId с неизвестным ID запроса даёт selected + unassigned, а не потерю события и не назначение последнему участнику. Конфликт попытки при доказанном собственном прогоне остаётся selected + conflict. Конфликт идентичности самого прогона уходит в unassigned с исходными конфликтующими значениями. Доказанный другой runId — otherRun и не попадает в массивы выбранного прогона/unassigned.

- Сохранить границу exportedAt и явный источник каждого массива. Unassigned относится к доступному окну источника, которое может быть шире выбранного прогона. Старые часы производителей не считать синхронизированными с коллекторами.
- Экспорт по-прежнему применяет общую маскировку секретов; сырые события сохраняются, но бинарные файлы, ключи и новая копия полных текстов в unassigned не добавляются.

**Приёмка:** без requestId, но с собственным run/stage/batch событие остаётся selected; собственный run + неизвестный запрос — selected с attemptCorrelation=unassigned; полностью непривязанное — unassigned; известный другой run — otherRun; конфликт прогонов — unassigned; конфликт попытки при известном прогоне — selected с attemptCorrelation=conflict. Счётчики сходятся; фильтры UI ничего не отбрасывают; экспорт из другой страницы использует тот же сохранённый источник.

### G. C05+C06 — ожидания User и происхождение повторов

**Файлы:** `disput/custom-engine.js`, `disput/custom-run-record.js`, `results.js`.

**Ожидания:**

- Существующие вызовы ожидания объединить обёрткой регистрации, не меняющей решения и UI. Виды: `decision` (включая approve), `owner`, `asks`, `unknown`.
- Писать `custom_wait_start` и `custom_wait_end` с `waitId`, runId, stepRef, visit, kind, временем и исходом. Start — перед фактическим ожиданием после обязательного checkpoint; end — после ответа, отказа, Stop или ошибки.
- В CustomRunRecord хранить `waits` с теми же waitId и nullable endedAt; текущий checkpoint связывает `pendingOwner.waitId`. Начало/закрытие интервала записываются обязательным механизмом сохранения до следующего внешнего действия; checkpoint обновляет позицию, не заменяя историю ожиданий. Ошибка такого сохранения обрабатывается как существующий checkpoint_failed.
- При обычном Stop закрыть активное ожидание исходом `cancelled`/`stopped`. Если страница исчезла без факта окончания, endedAt остаётся null. При продолжении создать новый интервал со ссылкой `resumedFrom`, не придумывать время конца старого.
- Отдельный шаг owner и вопрос ASK регистрируются тем же способом. Ошибка checkpoint до открытия ожидания не создаёт фиктивный законченный интервал.

**Повторы:**

- Добавить в попытку `trigger = initial | automatic_retry | user_retry | user_resend | resume_unsent` и `triggerReason`. Инициатор задаётся в месте принятия решения; не вычисляется потом только по номеру attempt.
- `automatic_retry` различает пустой ответ и исправление непринятого; `user_retry` связан с событием решения User; `user_resend` — с выбором resend неизвестной отправки. Сохранить `retryOf` и ключ предыдущей попытки; номер попытки сам по себе не глобальный ID.
- «Проверить ответ» — чтение, не отправка: записать событие проверки и приёмку найденного текста на исходной неизвестной попытке, без `onRequest`, новой записи state=sent, нового chatIntent и новой транспортной отправки. Допустимо завершить исходную unknown-попытку найденным ответом с пометкой `recoveredBy=check`, сохранив её исходную идентичность и отдельное событие проверки. Непринятый найденный текст не запускает исправление сам по себе.
- У старых записей trigger неизвестен. Не дописывать automatic/user задним числом.

**Приёмка:** auto и manual политики, approve, owner, ASK, unknown/check/resend/skip, Stop и исчезновение страницы в каждом типе ожидания. Для автоматического исправления и ручного retry разные trigger, но одна и та же исходная попытка. Чтение чата не увеличивает число отправок.

### H. R01 — границы шага и сводка раундов

**Файлы:** `disput/custom-engine.js`, `results.js`, `shared/report-digest.js`, `shared/basic-telemetry.js`, `results/debate-telemetry-view.js` только если существующая сводка действительно использует её.

- Добавить `custom_step_start` в момент фактического входа в шаг, до его первого внешнего действия, включая owner. Продолжение сохраняет идентичность визита и пишет `custom_step_resumed`; не создаёт второй start или фиктивный второй законченный шаг.
- Единственный `custom_step_end` для визита фиксируется после решений и ASK, только с исходом `completed` или `skipped`. Stop/cancelled и пойманная ошибка до завершения пишутся отдельно как `custom_step_interrupted` с причиной и outcome=`stopped | cancelled | failed`, не как завершение визита. При последующем продолжении того же визита возможен один фактический end. Если процесс исчез без наблюдаемого события, время прерывания/конца неизвестно. `steps_done` не равен «каждая модель ответила и ни один шаг не пропущен».
- Событие interrupted при известной ошибке обеспечивает движок до возврата/выброса ошибки; страница дополняет его только для ошибки адаптера вне движка, если известен текущий шаг и ещё нет такого факта. Повторная обработка одной ошибки не создаёт второй факт. Это не обещание события при аварийном исчезновении страницы/процесса.
- Холст использует эти события: running до фактического конца шага; owner также получает running/done; неполный раунд или ожидание User не помечаются завершёнными только по наличию принятых ответов.
- Сводка в JSON Basic (`rounds`) содержит шаг/визит/вид, ожидаемых участников, известные результаты участников, количества попыток и подтверждённых отправок, start/end/outcome, список waitId и измеренное ожидание User. Не вводить отдельный экран сводки в этом пакете.
- Длительности считать только по сопоставимым часам. `modelDuration` брать из времён конкретного запроса; не использовать общий интервал волн как время модели. Незакрытый интервал и неизвестная граница дают null с причиной. Пересекающиеся интервалы ожидания не складывать дважды.
- Extract использует новые границы, для старого журнала сохраняет fallback с явным `basis=legacy_check`, а не выдаёт custom_step за доказанное завершение. Отсутствующие начала owner-шага в старом журнале остаются null.

**Приёмка:** round → owner → round, all accepted + ASK, частичный отказ + retry/skip/stop, отмена во время owner, продолжение после остановки. Отдельно Stop во время ASK: end ещё нет, есть interrupted; после продолжения и ответа User появляется один end того же визита. Пойманная ошибка даёт interrupted/failed; аварийное исчезновение не получает выдуманного времени конца. В сводке и холсте нет завершения до ASK; каждый факт имеет ссылку на исходную запись или попытку.

| S06 | Запоздалые три типа событий A после подготовки B | События остаются у A или явно непривязаны; последняя модель не используется для угадывания |
| S07 | Unknown → check found/rejected → resend/skip | Проверка не отправляет; повтор имеет правильного инициатора; принятый ответ не теряется |
| S08 | Round → ASK → owner → round; паузы и Stop | Полная история ожиданий; границы шагов и сводка совпадают с исполнением |
| S09 | R1 на странице A; экспорт из B и после reload A; затем R2 | Журнал R1 сохранён и отделён от R2; дубли устранены по eventId |
| S10 | Нет ID, чужой run, конфликт ID, вытеснение, ошибка хранения | Достоверные selected/unassigned/otherRun/invalid и collection; неполнота видна |
| S11 | Старые записи и старый журнал до новых полей | Читаются; новые поля неизвестны; fallback явно обозначен; исходные тексты и приёмка не переписаны |
| S12 | Другие pipelines и обычные ответы без participantId | Существующая лента/отправка/экспорт работают; изменение ключа Basic не затрагивает их |

Команды целевых проверок: `npx jest --config tests/jest.config.js tests/<имя>.test.js`. По завершении — `npm test`. Известное нестабильное падение `false-success-watcher-guard` отделять от новых дефектов по актуальной базовой линии; любое другое падение исследовать, не объявлять автоматически посторонним.

Chrome: [agent-live-chrome.md](../Agents/agent-live-chrome.md), отдельный профиль и CDP, расширение из основного чекаута. Минимум: обе страницы (`pipeline_panel.html`, `result_new.html`), реальное скачивание JSON, два участника одной модели в DOM, две страницы/перезагрузка и чтение сохранённого журнала. Провайдеры заменять детерминированным тестовым адаптером для воспроизведения Stop/волн. Такой прогон отмечать как стендовый, не как проверку реальных моделей. Для подтверждения внешней идентичности событий проверить конверты и background sender/tab binding, а не только вызвать observeRuntime вручную.

## 8. Готовность и доставка

Каждый пакет считается закрытым, когда исходный дефект воспроизведён, исправление доказано поведением, смежные проверки проходят, контракт и ограничения описаны. Итоговый отчёт содержит таблицу B01–R01: закрыто / не закрыто, тест/сценарий, ограничение. Зелёный общий набор без сценария дефекта не закрывает пункт.

Во время интеграции обновить [телеметрию](telemetry.md), [Basic: старт](../Pipeline%20scenarios/basic-start-here.md), при затрагивании поведения — соответствующие разделы Basic developer/windows и CHANGELOG. Исправить устаревшие формулировки о completed, границе ASK и полноте маршрутов. Данный план не заменяет описание фактически поставленного поведения.

При правках кода поднять версии во всех связанных файлах и изменяемых версионных константах; не менять версию схемы только из-за диагностических полей. Сборку content bundles выполнить штатными `build:content-bundle`/`build:bundles` в соответствии с фактически изменёнными исходниками. Проверить diff сгенерированных файлов, не принимать несвязанные пересборки.

Документирование этого плана само по себе версию расширения не повышает. При реализации после каждого принятого самостоятельного пакета — отдельный коммит; после закрытия всего этапа — тег. Перед доставкой проверить основной чекаут, чужие изменения и фактическую manifest-версию. В финале назвать доставленную версию, проверки и ограничения, напомнить `chrome://extensions → Reload` только если менялось расширение.
