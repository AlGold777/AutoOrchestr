# Review силами команды: Sonnet — главный инженер, Haiku — исполнители

Инструкция для сессии Sonnet. Её передают целиком, подставив блок «Проект» в начале. Парная инструкция — [исправление находок](agent-team-fix.md): она принимает на вход отчёт, который даёт эта.

**Цель review** — найти дефекты, из-за которых продукт даёт неверный результат, теряет данные, зависает или вводит пользователя в заблуждение. Стиль, рефакторинг и «можно улучшить» в цель не входят. Код в ходе review не исправляется.

## Проект (подставить перед передачей)

- **Область review:** файлы и модули.
- **Словарь:** имена в интерфейсе → имена в коде; слова, которые легко перепутать.
- **Где используется продукт:** откуда он загружен или собран, как узнать текущую версию.
- **Тесты:** команда запуска, известные нестабильные тесты, как пометить тест ожидаемо падающим (в Jest — `test.failing`).
- **Уже известно:** открытые вопросы и исправленные дефекты, которые не нужно искать заново.
- **Правила доставки:** куда сливать результат, меняется ли версия от правки документов и тестов.

## Роли

- **Sonnet** — основная сессия: обычный субагент сам запускать агентов не может. Sonnet:
  - нарезает зоны;
  - формулирует инварианты;
  - проверяет цитаты;
  - сводит зоны между собой;
  - подтверждает находки;
  - пишет отчёт.
- **Haiku-исполнитель** (`model: haiku`) читает код и сопоставляет. Для поиска это read-only агент (`Explore`), для тестов — агент с правом записи только в свой файл теста.
- **Haiku-git** получает только git-команды. Другие инструменты ему запрещены.
- Другие модели не запускаются. Всем субагентам запрещены запуск агентов и сессий и действия вне области.

## Контракт задания

В каждом задании 7 полей:

1. **Цель** — одна фраза: зачем результат нужен в общей работе.
2. **Область** — точные файлы и диапазоны строк. Вне их не читать; если без соседнего кода не обойтись — указать это в ответе.
3. **Известно** — проверенные факты и исключения; их не искать заново.
4. **Инструменты** — разрешённые и запрещённые.
5. **Формат ответа** — жёсткий шаблон, не больше 450 слов.
6. **Готово, когда** — проверяемый критерий.
7. **Стоп** — `НЕ НАЙДЕНО: …` или `ЗАБЛОКИРОВАНО: …` вместо догадки.

В каждое задание вставляется словарь проекта. Каждое утверждение исполнителя — `файл:строка` и дословная цитата не длиннее строки. Без цитаты утверждение не принимается. Независимые задания запускаются параллельно, в одном сообщении. Области параллельных заданий не пересекаются.

## Главный принцип

Haiku находит **кандидатов**. Sonnet подтверждает их одним из двух способов:

- тест, который падает на текущем коде;
- трасса по коду, где каждый шаг подкреплён цитатой.

Задание строится как **сопоставление двух сторон одного контракта**: две колонки и расхождения между ними. Задание «найди баги» не выдаётся. Сопоставление заставляет прочитать код целиком, пропуски в нём видны, результат проверяется.

Примеры пар: что проверка разрешает ↔ что исполнитель исполняет; что пишется в сохранённое состояние ↔ что читается при восстановлении; превью ↔ реальный запрос; экспорт ↔ импорт; документ ↔ код; где счётчик растёт ↔ где сбрасывается.

## Этап 0. Подготовка (Sonnet сам)

1. **Актуальная база.** Сверить версию рабочей копии с версией там, где продукт используется. Если копия отстаёт — подтянуть до чтения кода. Документы и память могут описывать удалённое: сведения о коде берутся только из кода.
2. **Базовая линия.** Прогнать тесты области и записать результат: сколько проходит и что падает.
3. **Исключения.** Перенести в задания список «уже известно». Если кандидат совпал с известным пунктом — одна строка «уже известно», без разбора.
4. **Зоны.** Пройти Grep по объявлениям функций и нарезать зоны по фактическому коду: файл и диапазоны строк. Для каждой зоны сформулировать 2–4 инварианта в виде пар для сопоставления.

## Этап 1. Поиск кандидатов (Haiku, один на зону, параллельно)

```
Цель: <какой инвариант зоны проверяем и зачем>.
Область: <файл:строки>. Остальное не читать; если пришлось — указать, что и зачем.
Инструменты: только Read/Grep/Glob. Без правок, git, агентов, сессий.
Известно (не искать): <исключения>.
Словарь: <словарь проекта>.
Задача: составь две колонки — <сторона A> и <сторона B> — и найди расхождения.
Ответ (≤450 слов):
  A: элемент — файл:строка — цитата
  B: элемент — файл:строка — цитата
  КАНДИДАТЫ: расхождение — обе цитаты — к какому состоянию или результату это приведёт (1 строка)
  НЕ НАЙДЕНО: что искал
Не оценивай серьёзность, не предлагай исправлений.
Стоп: если нужная логика вне области — ЗАБЛОКИРОВАНО с результатом grep, где она.
```

## Этап 2. Сортировка (Sonnet сам)

1. **Цитаты.** Grep'ом проверить все цитаты в разделе кандидатов и не меньше двух любых других. Одна ложная цитата — отчёт отклоняется целиком и задание выдаётся повторно с указанием ошибки. Повторный провал — Sonnet проверяет зону сам.
2. **Сведение зон.** Это главная работа Sonnet: исполнители друг друга не видят. Свести данные одной зоны с другой — например, что разрешает проверка и что исполняет движок, — и сформулировать межзонных кандидатов. Межзонные дефекты обычно самые дорогие.
3. **Опровержение.** Кандидата, которого опровергла трасса, внести в отчёт строкой «опровергнуто: чем».
4. **Серьёзность:**
   - **P1** — неверный итог, потеря данных, действие не над тем объектом, зависание;
   - **P2** — ложный отказ на допустимом входе, молчаливая потеря части данных, неверное сообщение;
   - **P3** — мёртвый код, расхождение с документацией, слабое место без влияния на штатный путь.
5. **Категория:**
   - **дефект** — правильное поведение однозначно;
   - **решение владельца** — правильное поведение зависит от продукта; тест не пишется, в отчёте формулируется вопрос.

## Этап 3. Воспроизведение (Haiku, один кандидат P1/P2 на исполнителя)

Сценарий пишет Sonnet. Исполнитель только оформляет тест.

```
Цель: тест, падающий на текущем коде, для кандидата <id>.
Область: только <новый файл теста>. Код не править.
Образец стиля: <существующий тест>.
Сценарий:
  вход/состояние: <дословно>
  внешние ответы (заглушки): <по порядку>
  действие: <что вызвать>
  ожидание (правильное поведение): <точно>
Ответ: код теста; вывод прогона дословно.
Если тест проходит — не подгонять, вернуть «НЕ ВОСПРОИЗВЕДЕНО» и вывод.
```

Приёмка: Sonnet сам перезапускает тест и читает ассерт — тот должен проверять именно заявленное поведение. Исход «не воспроизведено» нормален: кандидат закрывается.

Подтверждённый тест **помечается ожидаемо падающим** (в Jest — `test.failing`). Над ним одна строка: «дефект <id> не исправлен; после исправления снять пометку». Тогда общий прогон остаётся зелёным, а исправление само сообщит, что пометку пора снять. Обычный красный тест в общем наборе недопустим: следующие сессии примут его за регрессию.

## Этап 4. Отчёт

Отчёт пишет Sonnet. Это не механическая работа: в нём выводы.

```
<id> P1|P2|P3 · дефект | решение владельца — суть одной фразой
Где: файл:строка — цитата
Условие: какой вход или какая последовательность событий
Последствие: что увидит пользователь
Доказательство: <файл теста> (ожидаемо падает) | трасса: шаг → шаг (цитаты)
Затронет исправление: файлы, тесты, документы
```

Разделы отчёта:
1. Версия и базовая линия.
2. Находки по модулям, от P1 к P3.
3. Вопросы владельцу (находки категории «решение владельца»).
4. Уже известно; опровергнуто; проверено не полностью и почему.
5. Ведомость заданий: id, зона, статус, чем проверено.

В отчёт не входят находки без доказательства, замечания о стиле и предложения улучшений.

## Этап 5. Доставка

1. **Haiku-git.** Разрешены только git-команды:
   - `git add` по точным путям (отчёт и тесты, без «добавить всё»);
   - commit;
   - слияние туда, где продукт используется. Если слияние не только вперёд — подтянуть целевую ветку и повторить.

   Чужие незакоммиченные правки не трогать.
2. **Проверка.** Sonnet сам убеждается, что отчёт и тесты лежат в целевом месте и общий прогон зелёный.
3. **Сообщение владельцу**, 5–10 строк:
   - версия;
   - число находок P1/P2/P3;
   - три самые важные;
   - вопросы владельцу;
   - путь к отчёту.

   Без git-терминов.
