# Старт новой сессии: что нужно знать агенту

Документ для агента, который начинает работу в проекте с нуля, без памяти и без доступа к прежним разговорам. Правила процесса ниже записаны владельцем проекта в личных инструкциях и передаются здесь, чтобы не зависеть от аккаунта. Описание продукта — в [обзоре проекта](project-overview.md), навигация — в [карте документации](documentation-map.md).

## 1. Откуда загружено расширение и как доставлять правки

Расширение у владельца загружено из **основного чекаута** `/Users/restart/Documents/GitHub/AutoOrchestr`, а не из worktree. Коммит в ветке worktree до владельца не доходит.

- Ветку основного чекаута определяйте командой `git -C /Users/restart/Documents/GitHub/AutoOrchestr branch --show-current`. Это не обязательно `main`: на 22.10.2026 там `claude/gracious-mccarthy-fe9lrh`.
- **Перед первой строкой кода** определите версию, которая реально загружена: `grep '"version"' <основной чекаут>/manifest.json` (сверять с `extensionVersion` в последней телеметрии). Worktree может отставать от неё; правка на устаревшей базе потребует полного переноса.
- **Доставка.** Задача не завершена, пока правка не лежит в основном чекауте: после коммита `git -C <основной чекаут> merge --ff-only <ваша ветка>`. Если слияние не только вперёд — сначала подтянуть ветку основного чекаута в свою ветку (в worktree), разрешить конфликты, повторить.
- В основном чекауте могут лежать **чужие незакоммиченные правки**. Не затирать их: перед слиянием убедиться, что файлы, которые оно меняет, с ними не пересекаются (`git diff --name-only HEAD <ваша ветка>` против `git status --short`). При пересечении остановиться и сообщить владельцу.
- **Отчёт о доставке:** выполнить `grep '"version"' <основной чекаут>/manifest.json` и привести эту версию. Версия не совпала с заявленной — писать «НЕ доставлено», а не «Сделано». В конце одной строкой напомнить: chrome://extensions → Reload.
- Изменения только документации и стенда схем расширение не меняют: слияние их доставляет, перезагрузка расширения не нужна.

## 2. Версия, документация, git

- После **любых изменений кода** обновить версию в `manifest.json`, пакетном манифесте и версионных константах изменяемого файла (`ALGORITHM_VERSION`, `RULE_SET_VERSION` и т. п.). Изменение функционала — с правкой документации в том же коммите (документы Basic сверяются с кодом тестами `tests/basic-schema-guide.test.js` и `tests/basic-docs-refs.test.js`; запускаются Jest'ом, зависимости ставятся из `package.json`).
- Каждое законченное самостоятельное изменение — отдельный коммит; стадировать выборочно (`git add <путь>`), не `git add -A` по умолчанию. Перед разрушающими операциями (`checkout .`, `reset --hard`, `clean`, `stash`) — `git status --short`.
- **Коммит поручают субагенту Haiku** (`model: haiku`, это записано в корневом `AGENTS.md`). В задании ему перечислять только git-команды и запрещать другие инструменты: однажды такой субагент по ошибке запустил отдельную сессию (`hand_off_to_session`).
- Спрашивать владельца только о продукте и о действиях вовне (push в удалённый репозиторий, публикация). Ветками, слияниями и коммитами агент распоряжается сам; в отчётах — версия, что изменилось и где результат, без git-терминов.

## 3. Как работать с владельцем

- Отвечать коротко и по существу; отчёт «Поломано / Сделано» — версия и статус тестов одной строкой.
- Технические решения принимает агент: выбирает по назначению и данным, делает и сообщает выбранное. Не предлагать владельцу меню «А или Б» там, где есть очевидный вариант.
- Когда владелец обсуждает концепцию, отвечать в чате; документы и коммиты — после согласования.
- Если владелец указал пробел, прямо признать его до исправления; не выдавать его идею за уже имевшуюся.
- Слово владельца может означать элемент интерфейса, а не клавишу (например, «кнопка I» — кнопка «i» в шапке панели). Если смысл не очевиден, проверить на экране, а не угадывать.
- «Компонент» в разговорах о схемах — тип элемента схемы (как «сохранённый артефакт»), а не метафоры из кино и театра.
- Минимально достаточное решение: не добавлять функции, поля и пояснения без практической необходимости (корневой `AGENTS.md`).

## 4. Данные из браузера владельца

У владельца в браузере есть собственное GPT-расширение, открывающееся на любой странице (страницы моделей и нашего расширения). Через владельца ему можно поручать сбор данных, которые агент не получит сам: реальный DOM перед правкой селектора или детектора, состояние страницы при визуальном баге, сверка собранного ответа с видимым. Задание оформляется отдельным блоком (страница, момент, что собрать, формат вывода); просить **данные, а не выводы**: дословный текст, `outerHTML`, атрибуты, «не видно». Не просить того, что агент может получить сам (код, телеметрия в репозитории, встроенный браузер).

Описание — [стенд схем](Pipeline%20scenarios/canvas-prototype/README.md), [запрос для моделей](Pipeline%20scenarios/canvas-prototype/model-prompt.md), [план доработки Basic](Pipeline%20scenarios/basic_upgrade_oct11.md), [общая картина](Pipeline%20scenarios/basic-start-here.md).
