# Сценарий Research 2.0

**Версия:** 2.0 (2026-10-05). Заменяет `research.md` 1.0.
**Статус:** схема до пробного прогона; в код не подключена.
**Основа:** Research 1.0, ревью Astra, сверка с кодом основного каталога
(версия расширения 2.81.611).

Главное изменение против 1.0: сценарий опирается на **проверяемую цепочку**
«полученный источник → фрагмент → утверждение → фрагмент отчёта». В 1.0
вместо неё стояли отметки, которые ставила модель.

---

## 1. Результат

Исследовательский отчёт. Он выясняет, как обстоит дело, но не решает, что
делать.

| № | Часть | Требование |
|---|---|---|
| Р1 | Ответ коротко | 3–7 предложений; опирается только на Р2, Р3, Р5 |
| Р2 | Что установлено | Каждое утверждение ссылается на проверенные доказательства; указана степень уверенности |
| Р3 | Спорные места | Обе стороны с доказательствами и решение, либо «не решено» |
| Р4 | Не подтверждено и опровергнуто | Отдельно от установленного |
| Р5 | Что не выяснено | Каждая часть исходной спецификации, которая не закрыта, с причиной, включая сокращение объёма |
| Р6 | Ограничения | Ослабленная независимость, непрочитанные источники, отклонённые замечания критика, остаточный риск |
| Р7 | Источники | Каждый со статусом получения и проверки |

Отчёт целиком **не утверждает больше, чем доказано**.

## 2. Правила, на которых держится сценарий

1. **Согласие моделей не является подтверждением.** Подтверждает проверенное
   доказательство. Исключение — вопросы, где источник истины заранее объявлен
   как «согласие моделей» (этап 6); в отчёте они помечаются «согласовано».
2. **Утверждение и доказательство живут раздельно.** Битая ссылка
   опровергает доказательство, а не факт. Без доказательств утверждение
   становится «не подтверждено», а не «опровергнуто».
3. **Исходная спецификация неизменна.** Любое сужение объёма записывается в
   журнал изменений объёма и попадает в Р5. Приёмка сверяет отчёт с исходной
   спецификацией.
4. **Непроверенное не повышается.** Ни частичный итог, ни исчерпание бюджета,
   ни текст отчёта не делают непроверенное проверенным.
5. **Никто не проверяет своё.** Если исполнителей не хватает, независимость
   ослабляется по заранее заданным правилам (раздел 6), и это помечается.
6. **Доказательства не обрезаются.** Если материал не помещается, задание
   делится на части, а не урезается.

## 3. Цепочка данных

Идентификаторы присваивает **оркестратор** при разборе ответа. Предложенные
моделью идентификаторы не используются как ключи.

```
Вопрос Q ── Материал M ── Источник S ── Фрагмент F ── Доказательство E ── Утверждение C ── Фрагмент отчёта R
```

| Объект | Ключевые поля |
|---|---|
| Источник S | `id`, описание (название, автор, дата, URL), `origin`: найден моделью / документ пользователя / ответ владельца, `retrieval`: получен оркестратором / указан, не получен / недоступен, `snapshot_hash` |
| Фрагмент F | `id`, `source_id`, дословный текст, место (раздел, абзац, страница), окружение ±2 предложения |
| Утверждение C | `id`, `question_id`, текст (один факт), `kind`: прямое свидетельство / толкование, `found_by[]`, `merged_from[]` |
| Доказательство E | `id`, `claim_id`, `fragment_id`, `relation`: поддерживает / опровергает, `quote_check`, `meaning_check`, `checked_by`, `independence` |
| Фрагмент отчёта R | `id`, часть отчёта, текст, `claim_ids[]` |

Правила цепочки:
- при слиянии утверждений `merged_from` сохраняет все исходные утверждения и
  всех нашедших;
- утверждение без цепочки до фрагмента не может попасть в Р2;
- фрагмент отчёта без `claim_ids` недопустим, кроме Р1, который ссылается на
  фрагменты Р2, Р3, Р5.

## 4. Состояние утверждения

Хранятся **два независимых признака**:

| Признак | Значения |
|---|---|
| Достаточность | достаточно (выполнено требование этапа 6) / недостаточно / нет проверенных доказательств |
| Конфликт | нет / есть, решён / есть, не решён |

Плюс отдельный факт: есть ли проверенное **опровергающее** доказательство.

**Проверено** — доказательство, у которого:
- `quote_check = найдено`: оркестратор нашёл цитату в полученном тексте
  источника, без модели;
- `meaning_check` = поддерживает или опровергает: модель проверила, что
  фрагмент с окружением действительно говорит это, а не отрицание, чужое
  мнение, условие или устаревшую оценку.

Если источник не получен оркестратором, механической сверки нет. Тогда
доказательство считается **проверенным только моделью**.

**Степень уверенности для отчёта** выводится из признаков, первое подошедшее
правило побеждает:

| Степень | Условие |
|---|---|
| Опровергнуто | Есть проверенное опровергающее доказательство, конфликт не в пользу утверждения |
| Спорно | Конфликт не решён |
| Надёжно | Достаточно; все учтённые доказательства проверены полностью; не меньше K из независимых источников; независимость не ослаблена |
| Вероятно | Есть хотя бы одно проверенное поддерживающее доказательство, но не выполнены условия «Надёжно» (одно доказательство, проверено только моделью или ослабленная независимость) |
| Согласовано | Источник истины — согласие моделей; к тому же пришли исполнители не меньше чем из двух разных семейств моделей |
| Не подтверждено | Проверенных доказательств нет |

**Видов нехватки шесть, маршрутов два.** Вид нехватки записывается для
диагностики:
- нет факта;
- нет доверия;
- нет независимости;
- источник не получен;
- нет полномочий;
- нет воспроизводимости.

Маршрут при этом всего один из двух:
- **искать ещё** — первые четыре вида, пока не исчерпан лимит добора;
- **в остаточный риск** — «нет полномочий», «нет воспроизводимости», а также
  любой вид, когда лимит исчерпан.

## 5. Этапы

| № | Этап | Кто | Схема | Новая пустая беседа |
|---|---|---|---|---|
| 1 | Спецификация | Постановщик | Один | Да |
| 2 | Проверка спецификации | Критик | Автор и критик | Да |
| 3 | Опросник владельцу | 2–3 модели + Сводчик → человек | Параллельно, затем сведение | Да |
| 4 | Разбиения | 2–3 исследователя | Параллельно, разные ракурсы | Да, у каждого |
| 5 | Дерево вопросов | Сводчик | Один | Да |
| 6 | План доказательств | Проектировщик | Один | Да |
| 7 | Сбор материалов | Исследователи | Параллельно, ракурсы + опровержения | Да, у каждого |
| 8 | Получение источников | Оркестратор | Без модели | — |
| 9 | Извлечение и сведение | Сводчик | Один, частями по вопросам | Да |
| 10 | Проверка доказательств | Оркестратор + проверяющие | Механически, затем перекрёстно по смыслу | Да |
| 11 | Разбор противоречий | Судья | Один | Да |
| 12 | Отчёт | Составитель | Один | Да |
| 13 | Критика | Критик | Один | Да |
| 14 | Приёмка | Оркестратор + проверяющий | Механически, затем по смыслу | Да |

### 1. Спецификация

**Оркестратор → Постановщик:** запрос этапа + вопрос пользователя дословно.

**Ответ (контракт):**
- `question_verbatim`;
- `out_of_scope[]`;
- `input_conflicts[]`;
- `goal`, `audience`;
- `boundaries`: период, регион, область;
- `depth`;
- `readiness_criteria`: по частям Р1–Р7;
- `acceptable_uncertainty`;
- `source_quality`;
- `assumptions[]`;
- `owner_questions[]`: черновые вопросы для этапа 3.

Тему не исследовать.

### 2. Проверка спецификации

**Оркестратор → Критик:** спецификация без указания автора.

**Ответ:** `remarks[]` — у каждого замечания `field`, `severity`
(существенное / мелкое), `proposal`.

**Выходы:**
- существенных замечаний нет → этап 3;
- есть существенное замечание → назад к 1 с этим замечанием, не больше 2
  раз;
- лимит исчерпан, а неоднозначность меняет смысл вопроса → вопрос в
  опросник; в автоматическом режиме — остановка.

После этапа 3 спецификация замораживается как **исходная**.

### 3. Опросник владельцу

Вопросы составляют модели, человек только выбирает. Формат и порядок работы
описаны в разделе 9.

**Источники вопросов:** `owner_questions` спецификации, существенные замечания
этапа 2.

После ответов оркестратор применяет выбранные варианты к спецификации и
замораживает её.

### 4. Разбиения

**Оркестратор → 2–3 исследователя:** исходная спецификация, у каждого свой
ракурс.

**Ответ:** `questions[]`, у каждого вопроса:
- `text`;
- `answer_type`: факт / число / список / механизм / оценка;
- `depends_on[]`;
- `done_criterion`.

Нельзя ставить вопросы, на которые не ответить ни из источников, ни из
согласия моделей.

### 5. Дерево вопросов

**Оркестратор → Сводчик:** все разбиения с идентификаторами от оркестратора.

**Ответ:**
- `tree[]` — вопросы с зависимостями и важностью, не больше 8;
- `mapping[]` — какой вопрос из разбиений куда вошёл;
- `scope_reductions[]` — что не вошло, с причиной.

**Сводчик не меняет спецификацию.** Всё, что не вошло в дерево, попадает в
журнал изменений объёма и затем в Р5.

**Механическая проверка:**
- каждый вопрос разбиений присутствует в `mapping`;
- каждая часть исходной спецификации покрыта деревом или есть в
  `scope_reductions`.

### 6. План доказательств

**Ответ** — по каждому вопросу:
- `truth_source`: внешние источники / документы пользователя / владелец /
  согласие моделей;
- `sufficiency`: типы источников, приоритет первоисточников, свежесть, K;
- `perspectives[]`: обязательно включает «опровержения»;
- `queries[]`.

Вопросы с `truth_source = владелец` уходят во второй, короткий опросник.

**Механическая проверка:** у каждого вопроса заполнены все поля.

**Выходы:**
- поле пусто → назад к 6, не больше 2 раз;
- лимит исчерпан → остановка.

### 7. Сбор материалов

**Оркестратор → исследователи:** у каждого вопроса не меньше двух
исполнителей с разными ракурсами; вопросы идут в порядке зависимостей.

**Ответ:** `materials[]`, у каждого материала:
- `question_id`;
- `source`: название, автор, дата, тип, URL;
- `quote` — дословно;
- `locator`;
- `relation`: подтверждает / опровергает;
- `trust_limits`.

Брать только факты, даты, числа и цитаты. Если данных нет, писать «нет
данных», а не домысливать.

### 8. Получение источников (без модели)

Оркестратор открывает каждый URL и сохраняет текст страницы и
`snapshot_hash`. Для этого нужно право чтения страниц (раздел 10).

| Результат | `retrieval` |
|---|---|
| Текст получен | получен оркестратором |
| Платный доступ, PDF без текста, страница не отдала содержимое | недоступен |
| Права нет или URL отсутствует | указан, не получен |

Документы пользователя получаются сразу. Их происхождение известно, но
достоверность проверяется на общих основаниях.

### 9. Извлечение и сведение

**Оркестратор → Сводчик:** материалы частями по вопросам. Размер части
выбирается так, чтобы она помещалась целиком; обрезка запрещена.

**Ответ:**
- `claims[]` — по одному факту в каждом, с `kind` и `fragment_ref`;
- `merge[]` — какие утверждения слиты и из каких;
- `conflicts[]` — пары «утверждение A — утверждение B — в чём расхождение»;
- `processed_material_ids[]`.

**Механическая проверка:**
- `processed_material_ids` совпадает с отправленными; если нет —
  недостающее отправляется повторно;
- у каждого утверждения есть фрагмент.

Проверка полноты списка подтверждает учёт записей, но не сохранение смысла.
Смысл проверяется на этапе 10.

### 10. Проверка доказательств

1. **Механически, оркестратор:** ищет цитату каждого доказательства в
   полученном тексте источника после нормализации пробелов и регистра.
   Результат: найдено / не найдено / источник не получен.
2. **По смыслу, проверяющая модель:** получает утверждение и фрагмент с
   окружением. Отвечает: поддерживает / опровергает / не относится /
   это мнение, условие или устаревшая оценка.

Проверяющий — модель, которая не приводила это доказательство (раздел 6).
Каждое доказательство проверяется одним одинаковым запросом.

Затем оркестратор пересчитывает признаки утверждений (раздел 4).

> **Контрольная точка «материала достаточно»** считается механически по
> признакам и требованиям этапа 6:
> - все важные вопросы закрыты, либо их нехватка идёт в остаточный риск →
>   этап 11;
> - есть нехватка с маршрутом «искать ещё» → **точечный добор**: этапы 7–10
>   только по этим пунктам, не больше 2 кругов. Следующий круг назначается,
>   только если предыдущий добавил хотя бы одно проверенное доказательство;
> - лимит или резерв бюджета исчерпан → этап 11 с пометкой; незакрытое уходит
>   в Р5.

### 11. Разбор противоречий

**Оркестратор → Судья:** конфликты с доказательствами обеих сторон и
результатами проверки. Судья — модель, не участвовавшая в конфликте; если
такой нет — раздел 6.

**Ответ:** по каждому конфликту `decision` из вариантов:
- A;
- B;
- оба верны при условиях (каких);
- нужно больше данных → в добор, если лимит не исчерпан;
- не решено.

К каждому решению — `basis` со ссылками на доказательства.

Голосование и усреднение несовместимого запрещены.

### 12. Отчёт

**Оркестратор → Составитель** в чистом контексте: утверждения с признаками и
степенью, решения по конфликтам, журнал изменений объёма, остаточный риск.

**Ответ:** части Р1–Р7, разбитые на фрагменты; у каждого фрагмента
`claim_ids`.

Нельзя повышать степень уверенности и добавлять утверждения вне списка.

### 13. Критика

**Оркестратор → Критик:** отчёт и исходная спецификация, без указания автора.

**Ответ:** `remarks[]` — у каждого `report_fragment_id`, `type` (исправить
текст / не хватает доказательства) и `explanation`.

**Выходы:**
- «исправить текст» → назад к 12. Составитель исправляет или отклоняет с
  основанием; отклонённое уходит в Р6. Не больше 2 раз;
- «не хватает доказательства» → в добор, расходует общий лимит добора; если
  лимит исчерпан → в Р6.

### 14. Приёмка

**Механически, оркестратор:**
- каждый `claim_id` в отчёте существует и прослеживается до фрагмента;
- степень уверенности в отчёте совпадает с вычисленной;
- в Р2 нет «Опровергнуто», «Спорно», «Не подтверждено»;
- все конфликты есть в Р3;
- каждая часть исходной спецификации закрыта или есть в Р5;
- каждое замечание критика исправлено или отклонено с основанием.

**По смыслу, проверяющий:**
- фрагменты отчёта не искажают и не усиливают утверждения;
- отчёт закрывает критерии готовности исходной спецификации.

**Статус каждой части отчёта:** доказано / согласовано / ограничено.

**Выходы:**
- всё пройдено → готово;
- есть отказ → назад к самому раннему этапу, где возник дефект (7–12);
  возврат расходует лимит добора или правки;
- лимиты исчерпаны → выдача с пометкой «не прошёл приёмку полностью» и
  списком непройденных проверок.

## 6. Назначение ролей и ослабление независимости

Используется готовая функция `independence` из
`disput/debate-capability-registry.js`. Она даёт уровни: `self`,
`same_family`, `same_provider`, `synthesizer`, `independent_family`.

**Порядок выбора проверяющего и судьи:**
1. Модель другого семейства, не автор и не участник конфликта.
2. Модель того же семейства, но другая.
3. Та же модель в новой пустой беседе, без указания авторства.

Варианты 2 и 3 — **ослабленная независимость** (`degraded`). Она записывается в
доказательство и запрещает степень «Надёжно»: утверждение получает не выше
«Вероятно», и пометка попадает в Р6.

**При двух моделях:**
- проверка идёт перекрёстно;
- если автором слитого утверждения стали обе модели, проверка идёт по варианту
  3;
- судья выбирается по варианту 3, если спорят обе модели.

Сценарий выполним при двух моделях, но без «Надёжно» там, где обе были
авторами.

## 7. Объём

- `debate-context-budget.js` умеет обрезать контекст. Для этапов 9–14 обрезка
  доказательств запрещена: при превышении задание делится на части.
- Вложения разрешены. Полноту прочтения подтверждает возвращённый список
  обработанных идентификаторов, а не факт отправки файла.
- Предел части задаётся по провайдеру (раздел 10).

## 8. Бюджет и счётчики

Оркестратор ведёт счётчики, которые **останавливают** исполнение, а не только
описывают его:

| Счётчик | Начальный предел |
|---|---|
| Запросы к моделям, включая технические повторы (повторы учитываются отдельно) | 60 |
| Время прогона | 90 минут |
| Сообщения на одного провайдера | 15 |
| Возвраты: спецификация | 2 |
| Возвраты: план | 2 |
| Возвраты: добор (общий для этапа 10, критики и приёмки) | 2 |
| Возвраты: правка отчёта | 2 |
| Повтор отправки материала, не учтённого на этапе 9 | 1 на часть |

**Резерв на завершение.** С начала этапа 7 резервируется 30% от каждого
предела на этапы 10–14. Когда исполнение доходит до резерва, сбор
прекращается. Собранное проверяется на этапе 10, отчёт строится только из
проверенного, а непроверенное остаётся непроверенным в Р4 и Р5.

Числа начальные; уточняются пробным прогоном.

## 9. Опросник

**Вопрос:**

```json
{
  "id": "Q1",
  "text": "За какой период нужны данные?",
  "why": "Определяет границы поиска",
  "source": "spec | review | truth_owner | unverified_claim",
  "input": "single | multi",
  "options": [
    { "id": "Q1.a", "label": "2024–2026", "effect": { "target": "spec.boundaries.period", "value": "2024-2026" } },
    { "id": "Q1.b", "label": "Без ограничения", "effect": { "target": "spec.boundaries.period", "value": null } }
  ],
  "allow_comment": true,
  "required": true,
  "blocking": false,
  "default_option": "Q1.a",
  "when": null
}
```

**Ответ человека:**

```json
{ "question_id": "Q1", "selected": ["Q1.a"], "comment": "" }
```

**Порядок работы:**
1. **Оркестратор → 2–3 модели**, каждой в новой беседе: спецификация,
   замечания этапа 2 и запрос «предложи вопросы в этом формате».
2. **Оркестратор → Сводчик:** все списки. Сводчик сливает дубли, даёт от 2 до 6
   вариантов, у каждого варианта `effect`, оставляет не больше 12 вопросов.
3. **Оркестратор проверяет опросник сам:**
   - формат соответствует;
   - идентификаторы уникальны;
   - `effect.target` — существующее поле спецификации.
4. **Оркестратор → человек:** вопросы в панели расширения. Человек выбирает
   варианты и при желании пишет комментарий.
5. **Оркестратор применяет `effect` выбранных вариантов сам.**
6. **Комментарии → Постановщик.** Правка допускается только в полях,
   затронутых вопросами с комментарием; это проверяется сравнением версий.
7. **Если `when` открывает новые вопросы** — ещё один круг, не больше 2 кругов.

**Вариант по умолчанию:**
- для вопросов об уточнении задания допустим, в отчёте помечается;
- для вопросов о фактах, которые знает только владелец (`truth_owner`), и
  для подтверждения непроверенных утверждений (`unverified_claim`)
  `default_option = null`.

**Тот же механизм применяется ещё в двух местах:**
- после этапа 6 — вопросы с `truth_owner`; ответ становится источником с
  `origin = ответ владельца`;
- после этапа 10, только в режиме «с остановками» — важные утверждения,
  проверенные только моделью или не проверенные, с вариантами «подтверждаю /
  не подтверждаю / не знаю».

**Минимум для первого прогона:** вопросы по одному, одиночный выбор плюс
комментарий. В основу экрана можно взять `disput/debate-decision-request.js`
(2–5 вариантов, режимы auto / assisted / manual). Но его эффекты управляют
только ходом работы и не умеют менять поля спецификации. Множественного выбора
и комментария в нём нет. Это нужно добавить.

## 12. Что изменилось против 1.0

| Изменение | Причина |
|---|---|
| Цепочка источник → фрагмент → утверждение → отчёт с ключами от оркестратора | Без неё механические проверки 1.0 были невыполнимы |
| Утверждение и доказательство раздельно; битая ссылка не опровергает факт | Ревью Astra |
| Два признака (достаточность, конфликт) вместо четырёх взаимоисключающих отметок | Утверждение может иметь и подтверждения, и опровержения |
| Механическая сверка цитаты + смысловая проверка | Совпадение цитаты не доказывает утверждение |
| Этап 8 — получение источников оркестратором | Без него «цитата есть» подтверждала модель, которая могла её выдумать |
| Исходная спецификация неизменна, журнал изменений объёма | Сводчик мог урезать условия собственной приёмки |
| Опросник: вопросы строят модели, человек выбирает и комментирует | Требование пользователя; в 1.0 механизма не было |
| Правила ослабления независимости через `independence` | При двух моделях роли 1.0 были невыполнимы |
| Резерв бюджета; частичный итог не обходит проверку | В 1.0 частичный итог пропускал этап проверки |
| Документы пользователя проверяются на общих основаниях | Известное происхождение не означает достоверность |
| Счётчики вместо формулы худшего случая | Формула не была пределом и ничего не останавливала |
| Запрет обрезки доказательств, проверка полноты по идентификаторам | `debate-context-budget.js` обрезает контекст |
| Список того, что нужно готовить в коде до прогона | В 1.0 его не было |
| Убраны: таблица соответствия стеку, таблица «что откуда взято» | Не влияют на работу; история есть в 1.0 |
