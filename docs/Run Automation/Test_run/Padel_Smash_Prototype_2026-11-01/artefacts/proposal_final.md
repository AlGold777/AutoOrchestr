## Проект прототипа v2 — Padel Smash Coach

**Допущения (безопасные инженерные, где входные данные неполны):**

1. Оба аудита проверяют документ, а не работающий код. Все замечания разобраны по существу.

2. Смэш — базовый плоский (атакующий удар над головой), не подача. Виборa и бандеха не оцениваются.

3. Реальных видео и кадров нет — не нашёл. Подложки кадров на S05 — схематические SVG, а не фото. Реальные кадры появятся при замене имитации.

4. Ракурс сбоку, игрок — правша, два удара в подходе. Метки времени демонстрационные.

5. Каталог ошибок редакционный, тренер его не проверял, числовых порогов нет.

6. Android-устройства у меня нет, проверить я не мог. В приёмку заложена проверка на нём. Ссылки и аналоги из исходных материалов не проверены и не перенесены.

### 1. Задача

Кликабельный HTML-прототип: тренер записывает эталон смэша, спортсмен снимает подход и сохраняет видео, приложение показывает разбор. Анализ имитируется заготовками. Архитектура позволяет заменить имитацию настоящим анализом позы без правки экранов.

Принципы:

- запись, сохранение и анализ — три отдельных статуса со своей обработкой ошибок;

- имитация везде помечена «Демо»;

- при нехватке данных показывается явное сообщение, случайные ошибки не подставляются;

- каждая ошибка привязана к удару спортсмена, к удару эталона и к метке времени.

**Режимы запуска.** Основной режим — HTTPS или localhost: только он гарантирует камеру. Файл по `file://` годится для просмотра демо, запись там не гарантируется. После загрузки страницы сеть не нужна, внешних API нет.

### 2. Сквозной сценарий и экраны

**Тренер:** S01 (роль «Тренер») → «Записать эталон» → S02 → S03 «Сохранить эталон» → S01 («Эталон готов»).

**Спортсмен:** S01 → «Снять подход» → S02 → S03 «Сохранить и анализировать» → S04 → S05 → ошибка → «Повторить подход» → S02.

| ID | Экран | Переходы |
| --- | --- | --- |
| S01 | Упражнение «Смэш» | основная кнопка → S02; попытка из истории → S05; «Эталон» → плеер (окно) |
| S02 | Камера | «Остановить» → S03; «Отмена» → S01; ошибка камеры → «Выбрать файл» → S03 (отмена выбора возвращает в состояние ошибки S02) или «Демо-попытка 1/2» → S04 |
| S03 | Просмотр и сохранение | «Переснять» → S02; тренер: сохранить → S01; спортсмен: сохранить → S04; ошибка записи оставляет на S03 |
| S04 | Анализ | см. ниже |
| S05 | Результат | «Повторить подход» → S02; «Все попытки» → S01 |

**Три режима S04:**

- **Попытка с готовыми данными** (демо-попытки). Три шага по ~1 с, затем S05.

- **Новая запись или импорт.** Сначала выбор «Демо-сценарий 1 / 2» (по умолчанию 1). Выбор сохраняется как `mockScenarioId`, отдельно от `attemptId`. Затем шаги и S05 с плашкой «Ошибки не вычислены по вашей записи, показан демо-сценарий N».

- **Ошибка анализа.** Действия: «Повторить анализ» (S04), «Открыть демо-разбор» (выбор сценария), «К попыткам» (S01). Они доступны при любом числе повторов.

Модальные окна (экранами не считаются): плеер, замена эталона, увеличение кадра, выбор файла.

### 3. Содержимое экранов

**S01.** Шапка «PADEL COACH · Прототип», переключатель «Спортсмен / Тренер», карточка активного эталона, список «Мои попытки» с числом замечаний. В начале есть демо-эталон и две демо-попытки. Основная кнопка: тренеру «Записать эталон» или «Заменить эталон», спортсмену «Снять подход». Без эталона предлагается демо-эталон. Замена требует подтверждения и создаёт новую версию эталона, старые версии остаются, попытки хранят ссылку на свою.

**S02.** Живое изображение или демо-кадр, плашка роли («Эталон тренера» / «Подход спортсмена»), сетка, силуэтная зона, подсказка «Поместите в кадр всё тело, ракетку и зону удара», кнопки «Начать», «Остановить», «Отмена», таймер, REC. Состояния: подготовка, запись, остановлено, ошибка камеры. Экран идентичен для ролей, отличается только плашка.

**S03.** Плеер, длительность, метка «Эталон» или «Попытка N», «Переснять», «Сохранить…». Дальше можно идти только после подтверждённой записи видео и метаданных. Ошибка даёт «Повторить» и «Экспорт файла».

**S04.** Заголовок «Анализ смэша», бейдж «Демо», текст «Используются заранее подготовленные данные». Прогресс сценарный, не вычисленный. Без валидного эталона анализ не стартует.

**S05 — главный экран.**

- **Верх:** «Разбор смэша · Попытка N · Демо», «Найдено K замечаний». При K = 0: «В демо-данных замечаний нет» (вывода об идеальной технике нет).

- **Кадры:** два кадра рядом, слева спортсмен, справа тренер. Каждый кадр — схематическая подложка (`athleteFrameAsset`, `referenceFrameAsset`) с SVG-слоем скелета поверх. Проблемные суставы спортсмена выделены контрастным цветом, у тренера подсвечены те же суставы в правильном положении.

- **Под кадрами:** фаза, метки спортсмена и тренера (могут различаться, сопоставление по фазе), подпись «Схематические кадры и позы, не результат анализа реального видео».

- **Ограничение ракурса:** для SM02, SM05, SM06 добавляется пометка «Условная демонстрация: ракурс сбоку ограничивает оценку», подсветка суставов пунктиром.

- **Кадры:** тап открывает увеличение, режим «По одному» показывает кадры поочерёдно. Свободной перемотки нет, только переключение размеченных кадров. «Смотреть момент» открывает плеер на нужной метке (для заглушки — постер с таймкодом).

- **Список ошибок:** аккордеон, раскрыта одна выбранная (по умолчанию первая). Карточка: название, «Удар N · метка», признак, совет.

- **Выбор ошибки** — одна атомарная операция: меняются `selectedErrorId`, пара кадров, метки, подсветка, совет, блок кадров прокручивается в видимую область.

- **Низ:** «Повторить подход» (→ S02), «Все попытки» (→ S01).

**Правила.**

- Попытка 01 даёт три замечания, попытка 02 одно. Это показывает динамику без процента «улучшения».

- Результат анализа после показа сохраняется в `attempt.analysis`, при этом `mode` остаётся `mock`.

**Версии эталона.** Замена создаёт `ref-002` (version 2, `active`), прежний получает `archived`, `activeReferenceId` обновляется. Архивные эталоны в прототипе не удаляются.

При запуске записи в статусе `saving` без видео удаляются или предлагают повторить. В localStorage остаются только роль и последний экран. Если IndexedDB недоступна, сохранение считается неудачным, остаётся экспорт файла, анализ не стартует.

### 6. Замена имитации настоящим анализом

**Граница слоя.** Единственный вызов:

`AnalysisProvider.analyze({attemptId, referenceId, videoBlob, mockScenarioId?}, onProgress) → Promise<AnalysisResult>`

- `MockAnalysisProvider` возвращает `mockScenarios[mockScenarioId]`.

- `PoseAnalysisProvider` позже реализует тот же контракт. Выбор — одна строка конфигурации.

- Провайдер возвращает сам `AnalysisResult` без обёртки.

- Покадровый анализ выносится в Web Worker, прогресс идёт через `onProgress`. S04 и S05 читают только `AnalysisResult`.

**Схема `analysis-result.schema.json`** (создаётся при сборке):

- *Обязательные поля:* `schemaVersion`, `mode` (`mock` | `pose`), `status` (`ready` | `insufficient_data` | `error`), `coordinateSystem`, `frameSpec`, `errors[]`.

- *Опциональные:* `analysisVersion`, `modelVersion`, `qualityWarnings[]`, `unassessablePhases[]`, `confidence` (0..1, в каждой ошибке), `error {code, message, retryable}` при `status: error`.

- *Ошибки в `errors[]`:* поля как в разделе 5, `evidence.type` — `svg-preset` или `keypoints`. Для `keypoints` добавляются `athleteKeypoints[]` и `referenceKeypoints[]` вида `{name, x, y, v}`, а `*FrameAsset` указывают на извлечённые кадры.

**Координаты и масштаб.**

- Нормализованные 0..1, начало слева сверху, Y вниз, относительно кадра после применения `rotation`.

- `frameSpec` задаёт размер и поворот исходного кадра отдельно для спортсмена и эталона.

- SVG-слой берёт `viewBox = frameSpec` и тот же `preserveAspectRatio` (`meet`), что и подложка. Так разметка совпадает с кадром при любом размере экрана.

**Шаги настоящего провайдера:**

1. Проверить пригодность видео: полное тело, ракетка, свет, смаз.

2. Найти ключевые точки с достоверностью (например, MediaPipe Pose Landmarker — из материала 3, мной не проверено) и сгладить по времени.

3. Разбить подход на удары и фазы.

4. Выровнять фазы со эталоном (DTW или ключевые кадры).

5. Посчитать признаки, надёжные при ракурсе сбоку.

6. Применить правила и пороги, откалиброванные тренером по реальным записям. Сейчас порогов нет.

7. Вернуть результат в этом же формате.

Низкая достоверность даёт `insufficient_data` и «Недостаточно данных, переснимите». Момент контакта мяча и ракетки по одному скелету может быть неточным, могут понадобиться трекинг ракетки или ручная коррекция тренером.

### 7. План сборки HTML-прототипа

Файлы: `index.html`, `styles.css`, `app.js` (роутер, состояние), `data.js`, `poses.js`, `frames/*.svg`, `storage.js`, `provider-mock.js`, `analysis-result.schema.json`.

1. **Каркас.** Пять `<section>`, hash-навигация (`#s01`…`#s05`), mobile-first 390×844, без горизонтальной прокрутки.

2. **Данные.** `data.js` по разделу 5, 7 пар поз и подложек, валидация схемой и правилами при загрузке.

3. **S05 первым.** Подложки с SVG-слоем, аккордеон, метки, пометка ограничения ракурса, «По одному», увеличение.

4. **S04 и провайдер.** Три режима, выбор демо-сценария, обработка ошибки, мок в Web Worker-совместимой обёртке.

5. **S01 и хранилище.** Роли, версии эталона, транзакционное сохранение, восстановление после прерванной записи.

6. **S02 и S03.** `getUserMedia`, `MediaRecorder` с выбором MIME по поддержке браузера (MP4 не требуется), маршруты отказа камеры, импорт, экспорт.

7. **Склейка.** Оба сценария, повтор подхода без перезаписи истории.

8. **Проверка.** Матрица: Chrome desktop, Safari iOS, Android Chrome. Тесты отказов: отказ в доступе к камере, неподдерживаемый MIME, пустой результат MediaRecorder, переполнение или отключение IndexedDB, воспроизведение записанного видео. Каждый отказ должен приводить к определённому состоянию с выходом. Публикация: статический сайт по HTTPS.
