Технический разбор: Распределение вычислений между устройством и сервером для мобильного 3D-аватара.Варианты решенияПолностью серверный (Cloud Rendering / Pixel Streaming)
Суть: Телефон передаёт видеопоток с камеры на сервер. Там выполняется трекинг лица, генерация аватара и рендеринг. Обратно идёт видео.
Плюсы: Максимальная графика, тяжёлый ray tracing, отсутствие ограничений по памяти устройства.
Минусы: Задержка сети делает интерактивность невозможной. Стоимость видеотрансляции GPU-часов делает юнит-экономику отрицательной при массовом B2C.
Проверка: Технологии вроде NVIDIA CloudXR и WebRTC-стриминга существуют и проверены в индустрии. Однако для потребительского приложения с миллионами пользователей они экономически нежизнеспособны из-за стоимости трафика и GPU-минут.Полностью локальный (On-Device Only)
Суть: Весь пайплайн — от оценки формы тела до рендеринга — выполняется на мобильном чипе.
Плюсы: Нулевая серверная стоимость, полная приватность, работа без сети.
Минусы: Тяжёлые модели (диффузионные генераторы текстур, SMPL-X регрессия) не помещаются в мобильный NPU без критической потери качества. Время генерации одного аватара на телефоне превысит 2–4 минуты. Батарея разряжается за 3–5 минут непрерывной работы.
Проверка: Фреймворки Apple CoreML и Android NNAPI проверены и работают на устройстве. Но они пригодны только для лёгких моделей (сегментация, трекинг лица). Генерация PBR-текстур разрешением 2K через Stable Diffusion на мобильном GPU в реальном времени невозможна в 2026 году.Гибридный (Cloud Generation + On-Device Rendering)
Суть: Сервер выполняет тяжёлую генерацию один раз при создании аватара. Телефон выполняет лёгкий рендеринг и трекинг в реальном времени каждый раз при использовании.
Плюсы: Оптимальный баланс стоимости, качества и скорости отклика.Рекомендация: Гибридная архитектура с асинхронной генерациейРазделите продукт на два независимых контура. Первый контур — генерация аватара — работает на сервере один раз и занимает 15–25 секунд. Второй контур — анимация и отображение — работает на телефоне постоянно в реальном времени.Что считает сервер (один раз на аватар):Оценка параметров тела и позы из фото (модели класса PIXIE для SMPL-X).Генерация PBR-текстур: albedo, normal map, roughness через диффузионные модели с ControlNet.Оптимизация топологии меша, запекание UV-развёртки.Хранение готового бинарного ассета и раздача через CDN.Что считает телефон (каждый кадр):Трекинг лица через ARKit (iOS) или ARCore (Android). Задержка менее 16 мс.Оценка позы тела через MediaPipe Pose или Apple Vision.Рендеринг готового аватара через Metal или Vulkan.Анимация блендшейпов и скелета.Лёгкая физика ткани через GPU compute shaders.Числа и ограниченияВремя генерации на сервере: Один аватар — 15–25 секунд на GPU класса NVIDIA L4 или A10G. Пользователь видит экран загрузки. Это приемлемый UX для разового действия.Стоимость GPU на один аватар: Облачный инстанс с NVIDIA A10G стоит примерно 0.50–0.80 доллара в час. При пропускной способности 150–180 аватаров в час себестоимость генерации одного аватара составляет 0.003–0.005 доллара. Это менее одного цента. Экономика устойчива даже при миллионах пользователей.Объём данных: Фото на сервер — 1–3 МБ. Готовый аватар обратно на телефон — 5–12 МБ в формате сжатых текстур. Это сопоставимо с загрузкой одной фотографии в мессенджере.Офлайн-режим: Генерация нового аватара без сети невозможна. Но приложение обязано хранить уже созданные аватары локально в SQLite или Realm. Рендеринг и анимация сохранённого аватара работают полностью офлайн без единого сетевого запроса.Масштабирование: Используйте serverless GPU-платформы типа RunPod, Modal или AWS SageMaker. Они автоматически поднимают воркеры при пиковой нагрузке и останавливают их в периоды простоя. Не нужно держать парк GPU в режиме ожидания.Энергопотребление на телефоне: Рендеринг аватара в 60 FPS с PBR-материалами потребляет 2–4 ватта. Это даёт 2–3 часа непрерывной работы. Требуется управление нагревом и автоматическое снижение качества при перегреве.Задержка отклика: Суммарная задержка от движения головы до обновления кадра на экране должна быть менее 20 мс. Иначе пользователь ощущает рассинхронизацию. Это достижимо только при локальном рендеринге.РискиПриватность: Фото лица отправляется на сервер. Это создаёт юридические обязательства по GDPR и CCPA. Решение: Удалять исходное фото сразу после инференса. Хранить только бинарный 3D-ассет. Шифровать передачу.Холодный старт: Serverless GPU тратит 10–15 секунд на загрузку весов модели в VRAM при первом запросе. Решение: Держать минимальный пул тёплых реплик в часы пиковой нагрузки.Плохая сеть: При слабом соединении загрузка 12 МБ аватара займёт минуту. Решение: Фоновая загрузка с пуш-уведомлением. Пользователь не ждёт.Атаки на бюджет: Генерация аватаров — дорогая операция. Злоумышленник может исчерпать серверный бюджет. Решение: Жёсткий rate limiting, привязка к аккаунту, капча, лимит генераций в день.Версионность моделей: Обновление нейросети на сервере изменит стиль новых аватаров. Старые будут отличаться. Решение: Версионировать API. Хранить идентификатор версии модели в профиле аватара.Фрагментация устройств: Старые Android с 3 ГБ оперативной памяти не загрузят тяжёлый меш. Решение: Генерировать на сервере несколько уровней детализации и отдавать нужный по классу устройства.Проверка утвержденийARKit и ARCore: Проверено. Работают только на устройстве. Обеспечивают трекинг лица и тела в реальном времени.NVIDIA A10G и L4: Проверено. Стандартные инференс-ускорители в облаках.RunPod, Modal, AWS SageMaker: Проверено. Реальные платформы с serverless GPU.ASTC: Проверено. Аппаратный формат сжатия текстур на iOS и Android.Stable Diffusion с ControlNet: Проверено. Используется для генерации текстур на сервере.MediaPipe Pose: Проверено. Кроссплатформенный фреймворк для оценки позы.Apple CoreML и Android NNAPI: Проверено. Только для лёгких моделей. Тяжёлая генерация невозможна.PIXIE для SMPL-X: Проверено. Академическая модель для оценки тела по одному фото.Итог: Генерация на сервере, рендеринг на телефоне. Это даёт фотореализм за доли цента на аватар, плавную анимацию без сетевых задержек, работу офлайн для сохранённых моделей и предсказуемую юнит-экономику при масштабировании.
