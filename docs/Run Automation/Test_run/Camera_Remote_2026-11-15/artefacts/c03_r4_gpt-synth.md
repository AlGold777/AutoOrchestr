Итоговая концепция: удалённый спуск штатной Camera на iOS 261. Вывод и рекомендацияРекомендую BLE HID over GATT (HOGP) с управляющего Android-телефона как первый исследовательский вариант. Обычное Android-приложение выступает Bluetooth HID-периферией и отправляет Consumer Control / Volume Increment (0xE9). Целевой iPhone принимает системный ввод, а открытая штатная Camera потенциально интерпретирует его как нажатие затвора.Это не готовое решение, а проверяемая инженерная гипотеза с существенными аппаратными подтверждениями. Полная комбинация Android-приложение → iOS 26 → штатная Camera → исходный файл пока не продемонстрирована воспроизводимым испытанием.Архитектура сохраняет жёсткие ограничения: только два телефона, без root, jailbreak, дополнительного оборудования и собственной реализации камеры. Если спуск сработает, снимок создаёт именно Apple Camera, включая алгоритмы обработки, применимые в выбранном режиме. HDR и Deep Fusion не гарантируются для каждой экспозиции.Приоритеты: BLE HOGP — первый тест, классический Bluetooth HID — второй, управляющий iPhone — отдельная исследовательская ветка. Возврат оригинала проверяется после доказательства спуска.Главное техническое различие: iOS не предоставляет стороннему приложению публичный метод нажатия затвора Camera. HID использует другую границу системы — стандартный внешний ввод. Поэтому отсутствие Camera shutter API не означает запрет самой возможности удалённой съёмки.2. Ни один статус автоматически не означает остальные.

Архитектура BLE HID и требования протоколаУправляющий Android запускает BLE advertising и публикует HID Service. iPhone через системные настройки Bluetooth обнаруживает периферию, выполняет сопряжение и подписывается на Input Report. Android-приложение передаёт последовательность press/release. Никакое наше приложение не получает управление интерфейсом Camera.Публичный BluetoothGattServer.addService() существует начиная с Android API 18. Для Android 12+ применяются разрешения BLUETOOTH_CONNECT, а для advertising — BLUETOOTH_ADVERTISE. Универсального публично документированного запрета Android на службу 0x1812 нет. Реальная поддержка зависит от контроллера и прошивки. Спецификация Bluetooth SIG HOGP 1.2 от 21 апреля 2026 года предусматривает HID Service 0x1812, Battery Service, Device Information Service с PnP ID, HID Information, Report Map, Input Report и Report Reference 0x2908. HID Device должен поддерживать bonding; HID-характеристики требуют зашифрованного соединения. Для Report Host использование Protocol Mode необязательно, а для Boot Host действуют отдельные правила. Это требования Bluetooth SIG, не опубликованная матрица совместимости Apple Camera. Реализация должна контролировать четыре состояния: успешное соединение, завершение шифрованного сопряжения, подписку iPhone на Input Report и доставку корректной пары press/release. Состояние Connected само по себе недостаточно.В ClickNova найден конкретный однобитный дескриптор Consumer Control:Report Map, шестнадцатеричные байтыОбычный текст05 0C 09 01 A1 01 85 01

Report ID сопоставляется через 0x2908, поэтому байт E9 не нужно непосредственно передавать как состояние кнопки. Исходники: HidReportDefinition.h.Этот дескриптор имеет аппаратный прецедент на ESP32/iOS 26.5.2. Вторым кандидатом остаётся вариант с 16-битным Consumer Usage из обсуждения Nordic. Ни один из них не подтверждён на связке Android → iOS 26. Смешивать поля разных report map или делать вывод из одного отрицательного испытания недопустимо.4. Управляющий iPhone и минимальные ослабленияПроект Clak существует. Автор описывает iPhone → Mac как BLE HID-клавиатуру, в том числе uuidNotAllowed для краткого UUID 1812 и успешное использование 128-битного представления. Однако Apple Accessory Design Guidelines R18 (2022) прямо запрещают сторонним iOS-приложениям публиковать BLE HID Service. Поэтому Clak является техническим исследовательским прецедентом, а не документированным разрешением платформы; iPhone → iPhone Camera отдельно не подтверждён. Полностью исключать управляющий iPhone из исследования неправильно, но строить на нём поддерживаемую архитектуру без изменения позиции Apple также нельзя.Если HID не сработает, минимальные ослабления следующие: пользователь вручную открывает Camera; допускается дополнительный аппаратный BLE-пульт; либо снимается требование штатного приложения и используется AVFoundation/LockedCameraCapture. Последний вариант даёт законный собственный capture experience, но не выполняет исходную задачу. Sandbox, отсутствие публичного shutter API и правила App Review 2.5.1–2.5.2 препятствуют прямому управлению чужим Camera-процессом. 7.
