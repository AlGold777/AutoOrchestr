# Телеметрия Automation: бриф и заготовка

Назначение: помочь довести вкладку Automation (окно телеметрии) до состояния, в котором по
одному отчёту видно, что произошло с запросом к каждой модели. Это **гибрид**: здесь
описано, что нужно уметь показать и откуда брать данные; готовая часть — только сбор
наблюдений в [заготовке](automation-telemetry-starter.diff). Диагностику, пороги и вид
экрана выбирает исполнитель сам.

База: расширение 2.81.502. Заготовка применяется к ней как есть:

```bash
git apply --check docs/telemetry/automation-telemetry-starter.diff
git apply docs/telemetry/automation-telemetry-starter.diff
node node_modules/jest/bin/jest.js --config tests/jest.config.js tests/message-delivery.test.js tests/automation-journal-observations.test.js
```

После изменений кода — версия в `manifest.json`/`package.json` и запись в `docs/CHANGELOG.md`
(правило проекта).

## 1. Что уже есть в базе

Журнал доставки (`shared/message-delivery.js`, зеркало в `chrome.storage.session`) пишет:
отправку с меткой (`sent`), открытие вкладки (`tab`), смену статуса (`status`), первый текст
(`first_text`), итог (`verified`, `missing_token`, `empty_answer`), отброшенный устаревший
ответ (`stale_dropped`), отсутствие ответа в срок (`no_answer`). Разбор —
`shared/message-delivery-diagnosis.js`, экран — `shared/message-delivery-view.js`.

## 2. Что добавляет заготовка (только сбор наблюдений)

| Событие журнала | Что фиксирует | Откуда берётся |
| --- | --- | --- |
| `sent` + текст | текст промпта (до 2000 символов) | уже готовый промпт в `prepare` |
| итог + текст | текст ответа (до 1500 символов) | `receive` |
| `text_snapshot` | рост текста ответа, не чаще раза в 10 с | частичные ответы в `receive` |
| `page_navigation` | путь вкладки до и после смены адреса | сообщение `SPA_NAVIGATION` |
| `completion_decision` | решение логики завершения во вкладке и причина | сообщение `LLM_COMPLETION_TERMINAL` |
| `tab_focus` | каждое программное переключение на вкладку модели: вкладка, источник | `markProgrammaticTabFocus` в `human-presence.js` |

Старые события и их формат не меняются. Новые события видны в «Raw Delivery Events»; их
разбор и показ в остальных карточках — задача исполнителя.

Формат исходных сообщений (код базы):

- `SPA_NAVIGATION`: `{ llmName, oldUrl, newUrl, reason }` (`content-scripts/content-bootstrap.js`);
- `LLM_COMPLETION_TERMINAL`: `{ llmName, meta: { dispatchId, terminalResult: { status, reason } } }`
  (`content-utils/response-lifecycle-detector.js`);
- обе приходят из вкладок через `chrome.runtime.sendMessage`, их получает и страница
  результатов; страница **не отвечает** на них (отвечает фон), поэтому слушатель только
  записывает наблюдение и возвращает `false`.

## 3. На какие вопросы должен отвечать отчёт

Для каждой модели в запуске:

1. Что было отправлено и когда; дошла ли отправка до страницы модели.
2. Что происходило со вкладкой: открытие, смены адреса, кто и когда переключал на неё фокус.
3. Что решила логика завершения во вкладке и когда; пришёл ли после этого текст.
4. Как рос текст ответа и когда перестал расти.
5. Чем закончился запрос: полный ответ, неполный, ошибка, нет ответа, отменён; с текстом ответа.
6. Если запрос не удался или завис — по каким наблюдениям это видно и что делать пользователю.

## 4. Ситуации, которые отчёт должен различать

Формулировки — симптомы; как их определять и какие пороги брать, решает исполнитель.

- Запрос не ушёл: вкладка есть, отправки нет.
- Ответ пошёл, а завершения нет долго.
- Завершение объявлено раньше ответа (пустой итог, текст появляется позже).
- Ответ получен с ошибкой или оборван.
- Ответ без метки доставки; ответ с чужой меткой.
- Много программных переключений на вкладку, а результата нет.
- Отмена: остановилась ли генерация у провайдера.
- Панель и фон расширения работают на разных версиях (стоит подумать, как это будет видно в
  отчёте).

Каждая такая ситуация показывается с причиной и подсказкой «что проверить».

## 5. Рекомендации по реализации экрана и отчёта

- JSON-отчёт должен содержать версию расширения и весь журнал: из него ситуацию можно
  восстановить без перезапуска.
- Один отчёт — один запуск; различать запуски в одном журнале.
- Экран переиспользует существующие карточки вкладки (сводка, проблемы, путь сообщения,
  сырой журнал); оформление вкладки Automation уже подключено к стилям Disput.
- Тесты разбора строить на **реальных журналах**: образцы сохранять как фикстуры.
