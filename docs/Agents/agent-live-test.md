# Живое тестирование Basic: система работы ведущего

Для прогонов схем Basic на странице расширения в обычном Chrome (см. [agent-real-chrome-control.md](agent-real-chrome-control.md)) и для работы над результатом схемы (первый такой продукт — архитектура MVP «Remote Viewfinder»). Протокол заданий и ответов, роли исполнителя и проверяющего — [agent-team.md](agent-team.md); здесь только то, что добавляет живое тестирование. Модели агентов задаёт корневой `AGENTS.md` (Haiku 5.5).

Что добавлять в запрос на такое тестирование, причины остановок и первый отчёт по интерфейсу — [live-test-request-addendum.md](live-test-request-addendum.md).

## 1. Принцип

Ведущий (основная сессия) не выполняет рутину сам и не держит в голове список обещаний. Рутина — у агентов, память о процессе — у **журнала задач** и **офис-менеджера**. Новый агент создаётся, когда причина требует отдельной работы (раздел 4), и закрывается отчётом.

## 2. Постоянные роли

| Роль | Делает | Не делает |
|---|---|---|
| Ведущий | ставит задачи, решает, принимает, говорит с владельцем | не пишет код сам, если можно поручить; не задаёт технических вопросов владельцу |
| Оператор прогона | по схеме и версии: вставляет схему, запускает прогон кнопкой прогона (`#debate-run-toggle-btn`, не `#start-button`), заполняет окна User, снимает экспорт «Basic», чистит среду | не чинит код, не интерпретирует причины |
| Наблюдатель интерфейса | сверяет видимое с реальным: карточка и текст в чате модели, строки Basic и журнал, окна User, холст, блокировки; записывает «видимое — ожидаемое — доказательство» | не чинит, не объясняет причины; не видит исправлений ведущего |
| Аналитик провайдера | собирает живой DOM и поведение одного провайдера (через GPT-расширение владельца или скрипты), таблица «провайдер × проверка» | не меняет селекторы |
| Офис-менеджер | перед каждым этапом и перед отчётом сверяет журнал с правилами раздела 5 и возвращает короткий список напоминаний | не принимает решений и не меняет файлы кроме журнала |
| Исполнитель, проверяющий, расследователь | как в `agent-team.md` (2.2, раздел 4, раздел 5) | — |

## 3. Журнал задач

Два файла с разной ролью:

- **Журнал задач** — `.claude/plans/live-test-ledger.md` (ведёт ведущий, офис-менеджер читает): статус задач (id, агент, доказательство) и **обещания владельцу** (что просил, что сказано). Запись о задаче закрывается только с доказательством (версия, коммит, вывод команды, файл). Файл не входит в репозиторий: в основном чекауте он untracked, в worktree его может не быть.
- **Реестр проблем** — `docs/Agents/basic-issues-registry.md`, единственный список дефектов Basic. Каждая новая проблема (в том числе найденная в чужом прогоне) вносится в реестр в тот же ход, со ссылкой на экспорт. Журнал дефекты не дублирует.

Запись в журнале о задаче закрывается только с доказательством; дефект в реестре закрывается версией и тестом, «не проверено вживую» остаётся открытым хвостом.

## 4. Динамическое добавление агентов

Таблица — справочник причин: какой исполнитель нужен и что ему передать. Агент создаётся, когда причина требует отдельного исследования или большой работы. Мелкий шаг ведущий делает сам (AGENTS.md: минимально достаточное решение). Агент на каждую переменную не обязателен. Новый агент получает задание по шаблону `agent-team.md` одним сообщением; после отчёта он закрывается, запись остаётся в журнале.

| Причина | Кто занимается | Что передать |
|---|---|---|
| Сбой у конкретного провайдера | Аналитик провайдера X | страницу, момент, что собрать (DOM, строки журнала) |
| Причина сбоя неясна | Расследователь (agent-team, раздел 5) | симптом, версия, наблюдения |
| Причина доказана | Исполнитель + Проверяющий (agent-team, 2.2) | причина как требование, файлы |
| Расхождение интерфейса | Наблюдатель интерфейса | версия, схема, список проверок |
| Новая область знаний в продукте (WebRTC, разрешения iOS и т. п.) | Эксперт области | узкий вопрос; возвращает данные и источники, не вывод о продукте |
| Схему пишет модель | Оценщик схем | запрос, ответы моделей, число принятых «Вставить схему» |
| Новый класс отрицательного сценария | Оператор отрицательных сценариев | сценарий (стоп, перезагрузка, закрытая вкладка…) |
| Накопились обещания и риск забыть | Офис-менеджер (уже есть) | журнал |

**Пороги ожидания.** Молчание дольше 120 с — диагностика: статус, последний шаг, вывод журнала; ждать дальше вслепую нельзя. Предел ожидания ответа модели — 10 минут: после него участник пропускается, причина записывается в реестр. Ожидание User не ограничивается по времени, но окно показывает «Ожидает с HH:MM».

**Правило немедленной реакции.** Обнаружена проблема (сбой провайдера, расхождение интерфейса, молчание дольше 120 с, неверный результат) — ведущий в тот же ход записывает её в реестр и решает, кому она поручена (агент или сам): аналитик, расследователь, исполнитель. Откладывать до конца прогона нельзя.

**Правило коммитов и перезагрузки.** Коммит — сразу после каждого изменения (правило `CLAUDE.md`), а не после остановки прогона. Расширение во время прогона не перезагружается: перезагрузка стирает ответы текущего прогона. Перезагрузка — только при остановленном прогоне и после доставки. Пока прогон идёт, агенты готовят правки в своих worktree, ведущий собирает доказательства.

**Обновление вкладок моделей после перезагрузки (M-7).** Перезагрузка расширения оставляет открытые вкладки моделей со скриптами без связи с расширением (`Extension context invalidated`). Пока движок не восстанавливает такие вкладки сам (M-4 закрыт в коде, живьём не проверено), после перезагрузки каждую открытую вкладку модели обновить до начала прогона: F5 или закрыть и открыть заново в той же беседе. Только после этого расширение считается перезагруженным и сессии получают сообщение «перезагружено»; сообщать раньше нельзя (прогон на осиротевших вкладках дал `CONTEXT_LOST` и потерю попыток, `docs/Agents/basic-issues-registry.md`, M-4 и M-8).

**Один Chrome — один прогон.** Перед запуском проверяется кнопка `#debate-run-toggle-btn`: title «Остановить Basic» означает, что прогон уже идёт, новый не запускается. Вкладку телеметрии не оставлять открытой.

**Временное правило тестирования.** Если работа какой-то модели явно мешает процессу, ведущий исключает её из процесса (убирает участника из схемы или пропускает шаг), записывает причину в реестр и продолжает с оставшимися. При лимите использования модели (`usage_limit`) участник пропускается до сброса, время сброса записывается. Ведущий — главный архитектор, а не исполнитель текста задания: при расхождении плана и ситуации выбирает гибкое решение ради результата.

**Разрешение на серию прогонов.** Разрешение владельца на серию прогонов одной схемы Basic считается данным ответом в чате; ведущий фиксирует его в реестре или журнале (дата, схема, версия) и не спрашивает подтверждения на каждый прогон. Разрешение на отправку конкретного тестового prompt в модели (AGENTS.md) этим не заменяется: серийное разрешение покрывает только тестовые prompt'ы этой серии.

**Снимки прогона.** Кнопка «Basic» скачивает файл 4–5 МБ и открывает панель загрузок, поэтому снимков 2–3 за прогон, не чаще. Не каждый шаг: достаточно начала, середины и конца.

**Длинный запрос.** Claude не принимает вставку очень длинного запроса (кнопка отправки остаётся disabled, L-8). Оператор перед ожиданием проверяет кнопку отправки; если она disabled, это `send_not_taken`, а не ожидание ответа.

Ограничения: не больше трёх агентов одновременно; общая среда (один живой Chrome) — только последовательно; агент без нового знания дважды подряд — меняем подход, а не повторяем.

## 5. Напоминания офис-менеджера (контрольный список)

Он проверяет по журналу и по состоянию репозитория и возвращает только нарушенные пункты:

1. Каждое обещание владельцу имеет статус и доказательство.
2. Менялся код → версия поднята, документация и CHANGELOG обновлены, тесты прогнаны, коммит сделан агентом Haiku, правка лежит в основном чекауте, в отчёте версия из `grep '"version"' manifest.json`.
3. После доставки расширение перезагружено (разрешено владельцем); перезагрузка стирает ответы текущего прогона — отметить. После перезагрузки открытые вкладки моделей обновлены до прогона (раздел 4), и только затем сообщено «перезагружено».
4. Среда прогона чистая: тестовые вкладки закрыты, старый прогон остановлен, версия и схема записаны.
5. Запуск прогона только кнопкой прогона.
6. В разговоре нет слова «стенд»; отчёт короткий («Поломано / Сделано»); владельцу задаются только продуктовые вопросы, с вариантами.
7. Решения по концепции без согласования не оформляются документами.
8. Открытые находки без владельца.
9. Чужие неотслеживаемые файлы не тронуты.
10. Коммиты сделаны сразу после каждого изменения; во время прогона расширение не перезагружено.
11. Перед запуском кнопка `#debate-run-toggle-btn` не в состоянии «Остановить Basic» (иначе прогон уже занимает этот Chrome).
12. Снимков «Basic» за прогон не больше трёх; вкладка телеметрии не открыта.
13. Каждая новая проблема внесена в `docs/Agents/basic-issues-registry.md` в тот же ход.
