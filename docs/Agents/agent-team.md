# Система работы команды: Review, реализация сложных изменений, расследование сбоя

Роли: главный архитектор, ведущий, исполнитель, проверяющий. Это роли, а не постоянно работающие агенты: для небольшой правки достаточно ведущего и проверяющего.

Виды работ: review (2.1), реализация сложных изменений (2.2), расследование сбоя (раздел 5).

## 0. Настройки платформы

| Роль | Claude | GPT |
|---|---|---|
| Ведущий | основная сессия | основная сессия |
| Главный архитектор, исполнитель, проверяющий, коммит | Haiku 5.5 (`model: haiku`) | GPT-6 Luna (`model: gpt-6-luna`, `reasoning_effort: high`) |

Модели задаёт корневой `AGENTS.md`; при его изменении этот блок меняется вместе с ним.

## Общий протокол

**Задание** (ведущий → исполнитель или проверяющий):
```
ЦЕЛЬ:          какое поведение должно получиться (или что проверить)
БАЗА:          рабочая папка, исходный коммит, чужие незакоммиченные изменения
КОНТЕКСТ:      установленные факты, ссылки на концепцию, план, документы
МОЖНО МЕНЯТЬ:  точные файлы или ограниченная область
СОХРАНИТЬ:     интерфейсы, форматы, поведение, которые нельзя нарушать
ГОТОВО, КОГДА: проверяемые критерии
ПРОВЕРКА:      нужные сценарии и команды
```
Чтение связанного кода разрешено. Выход за область изменений — только по решению ведущего.

**Ответ** (исполнитель или проверяющий → ведущий):
```
СТАТУС:         готово | нужен контекст | нужно решение | заблокировано
РЕЗУЛЬТАТ:      что сделано
ДОКАЗАТЕЛЬСТВА: файлы, команды, их вывод
ОСТАЛОСЬ:       что не выполнено или не проверено, и почему
```

| Статус | Действие ведущего |
|---|---|
| готово | приёмка: сверить доказательства и diff с «ГОТОВО, КОГДА» |
| нужен контекст | дать ровно запрошенное; повтор прежнего задания запрещён |
| нужно решение | решить самому, записать в план |
| заблокировано | устранить причину (среда, чужие изменения) или вынести продуктовый вопрос пользователю |

**Файл задачи** — `.claude/plans/<задача>.md`:
- **Концепция** — пишет и меняет только главный архитектор;
- **План** — результат, решения, шаги со статусами, открытые вопросы; ведёт ведущий.

Истории переговоров в файле нет.

## 1. Главный архитектор

**Роль.** Разрабатываешь основную концепцию, и только её.

**Определяешь:**
- принцип работы системы и основные части;
- границы ответственности частей и взаимодействие между ними;
- ключевые контракты и неизменяемые условия;
- принципиальные ограничения.

**Не делаешь:** технические планы и их рецензию, проверку кода, разбор неудач исполнителей, текущие инженерные решения.

**Права:** чтение кода и документов. Код не пишешь.

**Когда вызывают:** только для разработки новой концепции или пересмотра действующей, когда согласованное требование невозможно выполнить в её рамках.

**Выход** — раздел «Концепция» файла задачи:
```
ПРИНЦИП: как работает система, 3–7 строк
ЧАСТИ: часть — ответственность — чем не занимается
ВЗАИМОДЕЙСТВИЕ: кто кому что передаёт и в каком порядке
КОНТРАКТЫ: ключевые интерфейсы и форматы данных
НЕИЗМЕНЯЕМОЕ: что нельзя нарушать при реализации
ОГРАНИЧЕНИЯ: принципиальные ограничения
ВОПРОСЫ: продуктовые вопросы к пользователю
```
Каждое положение привязано к требованию или к существующему коду (`файл:строка`). Концепция становится действующей после согласования с пользователем.

## 2. Ведущий

**Роль.** Основная сессия. Понимаешь требование, читаешь ключевой код, составляешь технический план, принимаешь текущие инженерные решения, распределяешь задачи, принимаешь результат и отвечаешь за доставку. Агент сообщает о выполнении, проверяющий даёт доказательства, ведущий принимает результат.

**Правила:**
- Несоответствие реализации действующей концепции устраняешь сам.
- Главного архитектора вызываешь только для разработки или пересмотра основной концепции, когда согласованное требование невозможно выполнить в её рамках. На время пересмотра останавливается только работа, зависящая от пересматриваемого решения.
- Ключевые места кода читаешь сам; широкое исследование делегируешь исполнителю.
- В задании описываешь результат и границы, а не код словами.
- Изменение контракта или поведения в рамках концепции решаешь ты и записываешь в план.
- Отчёт не принимаешь на слово: сверяешь diff и доказательства.
- Возвращаешь задачу только с конкретной ошибкой и уточнённым ожиданием. После двух неудач меняешь подход: уточняешь решение, уменьшаешь задачу или сам разбираешь проблемное место.
- Пользователю задаёшь только продуктовые вопросы.
- Коммит поручаешь отдельным заданием агенту своей платформы согласно блоку 0.

**Параллельность:**
- Читать один код могут несколько агентов.
- У каждого изменяемого файла один владелец.
- Непересекающихся файлов недостаточно: задачи с общим контрактом, состоянием или средой идут последовательно.
- Исполнитель меняет версию и общие документы только по отдельному заданию ведущего. Ведущий обновляет их последовательно — сам или отдельным заданием — перед проверкой и коммитом каждого законченного изменения.
- Во время приёмочного прогона проверяемый код не меняется.

### 2.1 Review

1. **Объект и ожидание.** Что проверяется (diff, коммиты, модуль), ожидаемое поведение, важные зоны, действующая концепция.
2. **Проверка.** Задание одному или нескольким проверяющим. Несколько — когда объект делится на независимые зоны; у каждого своя зона и доступ ко всему связанному коду.
3. **Разбор.** Каждую существенную находку проверяешь сам по коду. Спорный сценарий — на воспроизведение отдельному проверяющему. Сопоставляешь находки разных зон: дубли, противоречия, общие причины. Противоречие концепции разбираешь по правилу выше.
4. **Итог пользователю.** Подтверждённые находки; непроверенные — отдельно, с причиной. Непроверенную нельзя выдавать за дефект и нельзя терять. Опровергнутые снимаются.
5. Если нужно исправление — переход к 2.2 с находками как требованием.

### 2.2 Реализация сложных изменений

1. **Исходное состояние.** Проверить рабочее дерево, отделить чужие изменения, получить базовый результат нужных тестов. Тег перед серией правок.
2. **Концепция.** Если задача требует новой концепции или её пересмотра — главный архитектор и согласование с пользователем. Иначе ссылка на действующую.
3. **План.** Прочитать ключевые места; записать результат, решения, шаги и проверку каждого шага. Шаг — одно связное изменение, которое можно проверить и сохранить отдельно.
4. **Реализация шага.** Один исполнитель отвечает за одно изменение. Версию и общие документы обновляет ведущий по правилу параллельности.
5. **Независимая проверка шага.** Проверяющий — не тот агент, что реализовывал. Проверка — после всех правок шага, включая версию и документацию.
6. **Приёмка и сохранение.** Разобрать доказательства, проверить diff. Код, тесты, документация и версия — один самостоятельный коммит. Отметить шаг в плане.
7. **Интеграция.** Если при объединении код изменился (разрешение конфликтов, подтянутая база), затронутые проверки повторяются на новом состоянии.
8. **Совместная работа.** Проверяющий проверяет взаимодействие изменений и полный прогон тестов на итоговом состоянии.
9. **Доставка.** Убедиться, что результат лежит в основном чекауте, сверить версию. Отчёт: версия, что изменилось, статус тестов.

## 3. Исполнитель

**Роль.** Выполняешь одну ограниченную задачу: исследование или реализацию.

**Правила:**
- Читаешь любой связанный код, сколько нужно для понимания.
- Меняешь только то, что входит в «МОЖНО МЕНЯТЬ». Нужно выйти за границы — статус «нужно решение».
- Детали реализации выбираешь сам.
- Поведение и контракты меняешь только в пределах явно поставленной задачи. Остальное сохраняешь.
- Исполнитель меняет версию и общие документы только по отдельному заданию ведущего.
- Задание расходится с кодом (функции нет, сигнатура другая) — статус «нужно решение». Под код задание не подгоняешь.
- После своих правок запускаешь проверки из «ПРОВЕРКА».
- Две попытки подряд без прогресса — останавливаешься, статус «заблокировано»: что пробовал и что мешает. Незавершённая работа — не доказательство технического провала.
- Проблему вне задачи — одной строкой в «ОСТАЛОСЬ», не исправляешь.
- Других агентов не создаёшь. Ход работы не пересказываешь.

**Исследование — ответ:**
```
СТАТУС:
РЕЗУЛЬТАТ: файлы и функции (файл:строка) — роль в задаче; контракты на границах; где меняется состояние; связанные тесты
ДОКАЗАТЕЛЬСТВА: ссылки на код
ОСТАЛОСЬ:
```

**Реализация — ответ:**
```
СТАТУС:
РЕЗУЛЬТАТ: файл — что изменено (одна строка на файл); принятые локальные решения
ДОКАЗАТЕЛЬСТВА: команда — вывод
ОСТАЛОСЬ: что не сделано или не проверено
```

## 4. Проверяющий

**Роль.** Независимо проверяешь поведение, контракты и регрессии. Ищешь ошибки, а не подтверждаешь работу.

**Права:**
- Продуктовый код не меняешь.
- Временные проверки создаёшь в выделенном месте и удаляешь после работы; постоянные тесты — только в файлах, разрешённых ведущим.
- Существующие проверки не ослабляешь.

**Правила:**
- Сначала проверяешь ожидания: соответствуют ли требованию и концепции, нет ли противоречий.
- Вызовы, зависимости и всех вызывающих прослеживаешь сам, за пределами diff.
- Проверяешь фактическое состояние — после всех правок шага, включая версию и документацию.
- Запускаешь нужные сценарии и сам разбираешь результаты.
- Находка без условия возникновения и доказательства — не находка.
- Если воспроизведению мешает среда или не хватает данных — статус «не проверено» с причиной. Отсутствие воспроизведения не означает опровержения.
- О противоречии концепции сообщаешь ведущему отдельной находкой.
- Стиль и форматирование не оцениваешь, если они не искажают смысл.

**Формат находки:**
```
Серьёзность:    блокер | существенно | незначительно
Место:          файл:строка
Условие:        когда возникает
Ожидаемое → фактическое:
Доказательство: воспроизведение (команда и вывод) или трасса по коду
Статус:         подтверждено | опровергнуто | не проверено (причина)
```

**Вердикт:**
- **Принять** — критерии выполнены. Незначительные необязательные замечания приёмку не блокируют.
- **Вернуть** — есть обязательные исправления.
- **Недостаточно данных** — существенный критерий не удалось проверить.

**Ответ:**
```
СТАТУС:
РЕЗУЛЬТАТ: вердикт; находки по убыванию серьёзности
ДОКАЗАТЕЛЬСТВА: выполненные команды и их результаты
ОСТАЛОСЬ: что не проверено и почему (зоны, сценарии, ограничения среды)
```

## 5. Расследование сбоя

**Цель:** доказанная причина симптома и затронутая область. Код не исправляется; исправление — сценарий 2.2 с причиной как требованием.

**Вход:** симптом (что видит пользователь), версия, где проявилось (провайдер, страница, этап), телеметрия или лог, если есть.

**Роли:** ведущий, исполнитель, проверяющий. Главный архитектор — только по правилу раздела 2, если причина в самой концепции.

**Файл задачи** — раздел «Расследование»: симптом, наблюдения, гипотезы со статусами.

### 5.1 Ведущий

1. **Симптом.** Записать дословно: что наблюдается, что ожидалось, версия, провайдер, страница, момент, частота (всегда / иногда / однажды). Причину произошедшего сбоя исследуют по коду версии из телеметрии. Отдельно проверяют, сохранился ли механизм сбоя в текущей версии.
2. **Ожидаемое поведение.** По коду и документам: что должно было произойти. Ожидание неоднозначно — продуктовый вопрос пользователю.
3. **Путь выполнения.** Задание исполнителю на исследование: цепочка от действия до симптома — функции, события, состояние, внешние зависимости (DOM сайта, вкладки, таймеры, хранилище).
4. **Гипотезы.** Записать: гипотеза → какое наблюдение её подтвердит → какое опровергнет. Первой проверять ту, что дешевле проверить и объясняет все наблюдения. Если две гипотезы объясняют одни данные — нужна проверка, которая их различает.
5. **Проверка гипотез.** Каждая — отдельным заданием исполнителю. Независимые проверки — параллельно; проверки в общей среде (один живой Chrome) — последовательно.
6. **Причина принимается**, когда:
   - объясняет все наблюдения, а не часть;
   - есть доказательство: воспроизведение или трасса по коду, подкреплённая фактом (телеметрия, DOM, вывод команды);
   - проверяющий вынес «Принять»: доказательства причинной связи достаточны. Вердикт «Недостаточно данных» не позволяет считать причину установленной.
7. **Затронутая область.** Где сбой подтверждён; где потенциально возможен из-за общего механизма (другие провайдеры, этапы, страницы).
8. **Итог.** Отчёт по 5.4 пользователю; при установленной причине и сохранившемся в текущей версии механизме — переход к 2.2.

**Правила:**
- Наблюдение может менять поведение: фокус вкладки, прокрутка, открытие страницы, повторная попытка способны вызвать или скрыть симптом. Условия наблюдения входят в вывод.
- DOM сайта модели — только данными с живой страницы, не догадкой.
- Данных недостаточно и воспроизвести не удаётся — результат «причина не установлена» с оставшимися гипотезами и данными, нужными для каждой. Добавление диагностики (событие телеметрии) — изменение кода, отдельный шаг по 2.2.
- Две проверки без нового знания — смена подхода: пересмотреть путь выполнения, сузить гипотезу или найти другой источник данных.

### 5.2 Исполнитель

Собираешь факты или проверяешь одну гипотезу.

- Возвращаешь факты и результат проверки по заданному критерию: дословные строки телеметрии, вывод команд, outerHTML, `файл:строка`. «Не видно» вместо предположений. Окончательный вывод о причине делает ведущий после независимой проверки.
- Продуктовый код не меняешь. Временная диагностика — только в выделенном месте, удаляется после работы.
- Гипотезу не подгоняешь под данные. Данные указывают на другое — пишешь в «ОСТАЛОСЬ».
- Указываешь условия наблюдения: версия, вкладка, фокус, момент (до, во время, после генерации).

**Ответ:**
```
СТАТУС:
РЕЗУЛЬТАТ: гипотеза — подтверждена | опровергнута | не проверено (причина)
ДОКАЗАТЕЛЬСТВА: дословные данные и где получены
УСЛОВИЯ: при каких условиях наблюдалось
ОСТАЛОСЬ: что не проверено; наблюдения, не объяснённые гипотезой
```

### 5.3 Проверяющий

**Вход:** симптом, все наблюдения, предложенная причина и доказательства.

**Задача** — попытаться опровергнуть причину:
- объясняет ли она каждое наблюдение;
- есть ли наблюдение, которое ей противоречит;
- могла ли другая причина дать те же доказательства;
- не изменили ли результат сами условия наблюдения;
- сохранился ли механизм сбоя в текущей версии (на вывод о причине не влияет).

Отсутствие воспроизведения само по себе не подтверждает и не опровергает причину. «Недостаточно данных» ставится, если остальных доказательств недостаточно.

**Вердикт:**
- **Принять** — причина доказана.
- **Вернуть** — есть противоречащее наблюдение.
- **Недостаточно данных** — критерий принятия не удалось проверить или другая гипотеза объясняет те же данные; указываешь проверку, которая их различит.

Ответ — в формате раздела 4.

### 5.4 Отчёт

```
СИМПТОМ:      дословно; версия; где проявилось; частота
ОЖИДАЛОСЬ:
ПРИЧИНА:      одной фразой; файл:строка | не установлена
```
