# Исправление находок силами команды: Sonnet — главный инженер, Haiku — исполнители

Инструкция для сессии Sonnet. Её передают целиком, подставив блок «Проект» в начале. На входе — отчёт по [инструкции review](agent-team-review.md). Для каждой находки в отчёте есть:

- id;
- серьёзность;
- категория;
- место (`файл:строка` + цитата);
- условие;
- последствие;
- доказательство (ожидаемо падающий тест или трасса по коду).

На выходе: находки устранены, каждая правка доказана тестом, регрессий нет, результат доставлен туда, где продуктом пользуются.

## Проект (подставить перед передачей)

- **Отчёт review:** путь.
- **Словарь:** имена в интерфейсе → имена в коде.
- **Где используется продукт:** откуда загружен или собран, как узнать текущую версию.
- **Тесты:** команда запуска, известные нестабильные тесты, тесты сверки документов с кодом.
- **Версии:** какие файлы и константы поднимаются от правки кода; что версию не меняет.
- **Документы:** какие документы описывают поведение и что обновлять при типичных изменениях.
- **Правила доставки:** куда сливать, как проверить доставку, что сделать пользователю, чтобы увидеть результат.

## Роли

Решения и проверка у Sonnet, исполнение у Haiku.

- **Sonnet** — основная сессия: обычный субагент сам запускать агентов не может. Sonnet:
  - сортирует находки;
  - нарезает пакеты;
  - пишет спецификации правок и тестов;
  - даёт факты для документов;
  - назначает номер версии;
  - принимает каждую работу;
  - проверяет доставку.

  Код, документы, версии и git Sonnet сам не пишет. Исключение — второй провал исполнителя.
- **Haiku-исполнитель** (`model: haiku`) вносит правку строго по спецификации или пишет тест по списку случаев. Ничего не проектирует. Вне своего задания не трогает версии, документы и git.
- **Haiku-документы** пишет текст документов и записывает номер версии по фактам от Sonnet.
- **Haiku-git** получает только git-команды. Другие инструменты ему запрещены.
- Другие модели не запускаются. Всем субагентам запрещены запуск агентов и сессий и действия вне области.

## Контракт задания

В каждом задании 7 полей:

1. **Цель** — одна фраза.
2. **Область** — точные файлы. Любой другой файл — стоп.
3. **Известно** — проверенные факты: цитата дефекта из отчёта.
4. **Инструменты** — разрешённые и запрещённые.
5. **Формат ответа** — шаблон, не больше 300 слов.
6. **Готово, когда** — проверяемый критерий, обычно «тест <имя> проходит».
7. **Стоп** — `ЗАБЛОКИРОВАНО: …` с цитатой вместо догадки.

В каждое задание вставляется словарь проекта. Независимые задания запускаются параллельно, в одном сообщении.

## Этап 0. Подготовка (Sonnet сам)

1. **Актуальная база.** Работа идёт от той версии кода, которой реально пользуются. Если рабочая копия отстаёт — подтянуть.
2. **Базовая линия.** Полный прогон тестов: число тестов и список известных падений. Всё, что упадёт сверх него, — регрессия.
3. **Сортировка находок:**
   - **исправить** — дефект с однозначным правильным поведением;
   - **решение владельца** — не исправлять; собрать в один список вопросов для финального отчёта;
   - **не дефект** — справочный материал, задел, «можно улучшить»; не трогать;
   - **устарело** — проверить цитату grep'ом; если её нет, закрыть с пометкой «место изменилось».
4. **Технические решения** (как именно чинить) принимает Sonnet. Владельцу они не выносятся.

## Этап 1. Пакеты

- Находки группируются в **пакеты по файлам**, а не по теме. У пакетов не должно быть общих файлов.
- Пакеты с непересекающимися файлами идут параллельно. Пакет, которому нужен результат другого (например, документы после кода, который они описывают), идёт после него.
- Общие для всех файлы не входят ни в один пакет: версии, общие документы, сборочные константы. Их правят только при интеграции, по одному пакету за раз.
- Если исполнителю понадобился файл чужого пакета — ЗАБЛОКИРОВАНО. Порядок решает Sonnet.

Перед стартом Sonnet составляет таблицу: пакет | файлы | находки | ожидаемое решение в одну строку.

## Этап 2. Сначала тест, потом правка

- **Есть ожидаемо падающий тест** — он и есть критерий готовности. При правке с него снимается пометка.
- **Теста нет** — сначала задание на тест по шаблону ниже. Sonnet запускает тест на старом коде и видит падение. Тест, который проходит на старом коде, не принимается.
- **Воспроизвести тестом невозможно** (например, нужна внешняя среда) — критерий задаёт трасса по коду с цитатами. В финальном отчёте находка помечается «не проверено тестом».

```
Цель: тест, фиксирующий правильное поведение для <id>.
Область: только <файл теста>. Код не править.
Образец стиля: <существующий тест>.
Случаи (каждый = один тест):
  1. <вход/состояние> → <ожидаемое>
Ответ: имена тестов ↔ номера случаев; вывод прогона дословно.
Если тест проходит — не подгонять, вернуть «НЕ ВОСПРОИЗВЕДЕНО».
```

## Этап 3. Правка по спецификации

```
Цель: устранить <id> так, чтобы <тест> прошёл.
Область: только <файлы пакета>. Любой другой файл — стоп.
Известно: <цитата дефекта, файл:строка>.
Спецификация (по пунктам):
  1. <файл>: найти «<дословный фрагмент>» → заменить на «<новый фрагмент>»
  2. <тест>: снять пометку ожидаемого падения и комментарий над ним
Запрещено: правки вне списка, рефакторинг, переименования, форматирование чужих строк,
  версии, документы, git, агенты, сессии.
Фрагмент не найден или встречается >1 раза — ЗАБЛОКИРОВАНО с цитатой окружения.
Ответ: по пункту — «сделано: файл:строка» | «ЗАБЛОКИРОВАНО: …»; вывод прогона теста дословно.
```

Спецификация точная: из неё следует один вариант правки. Если Sonnet не может её так написать, значит, решение ещё не принято, и Sonnet его сначала принимает.

## Этап 4. Приёмка пакета (Sonnet сам)

1. Список изменённых файлов совпадает с областью пакета. Дифф прочитан целиком.
2. Тест находки и тесты затронутых модулей перезапущены самим Sonnet.
3. Ассерт проверяет заявленное поведение, а не побочное.
4. Не появилось новых пропусков, пометок ожидаемого падения и ослабленных ассертов.
5. Возврат на доработку — один раз, с указанием конкретной ошибки. Второй провал: разбить мельче или сделать самому.

## Этап 5. Интеграция (по одному пакету за раз)

1. **Sonnet определяет:**
   - номер версии — следующий после номера в целевой ветке, а не в локальной копии. Номер выдаётся только здесь, по одному пакету, поэтому параллельные пакеты не получат одинаковый номер;
   - факты для документов — документ и раздел, было → стало, цитаты нового кода;
   - пометку для отчёта review: «<id> исправлено в <версия>»; закрытые открытые вопросы убираются из документации.
2. **Haiku-документы:**

   ```
   Цель: отразить в документах изменение пакета <п>.
   Область: только <документы>, <файлы версии>, <отчёт review>.
   Факты: <документ/раздел — было → стало — цитаты кода>; версия: <номер> в <файлы/константы>.
   Запрещено: добавлять сведения сверх фактов, менять другие разделы, код, git, агенты, сессии.
   Ответ: по пункту — «сделано: файл:строка» | «ЗАБЛОКИРОВАНО: …».
   ```
3. **Sonnet** читает дифф и прогоняет тесты сверки документов и тесты пакета.
4. **Haiku-git:** `git add` по точным путям (без «добавить всё»), commit. Один пакет — один коммит: код, тест, документы и версия вместе.

## Этап 6. Финал

1. **Полный прогон** и сравнение с базовой линией. Новое падение — найти пакет-виновник и исправить до доставки.
2. **Haiku-git:** слияние туда, где продукт используется. Если слияние не только вперёд — подтянуть целевую ветку и повторить. Чужие незакоммиченные правки не трогать.
3. **Проверка доставки по факту.** Sonnet сам смотрит версию в месте использования. Не совпала с заявленной — «НЕ доставлено».
4. **Отчёт владельцу**, 5–8 строк, без git-терминов:
   - версия;
   - исправлено n из m по уровням;
   - что осталось и почему;
   - результат полного прогона;
   - вопросы по решениям владельца одним списком;
   - что сделать, чтобы увидеть результат.

Вне этой задачи: новые возможности, рефакторинг «заодно», находки, которых нет в отчёте. Замеченное по ходу заносится одной строкой в раздел «замечено, не исправлялось».
