OSI-стек оркестрации LLM

Нормативный документ. Задаёт слои оркестрации, их контракты, доказательства, отказы и сквозные протоколы. Все остальные спецификации (Completion V2, model-tabs, Disput pipeline) описывают реализацию отдельных слоёв и не должны ему противоречить. При конфликте сначала правится этот документ, затем код.

Версия стека: OSI-1.5 (2026-10-05). Состав и названия шести слоёв зафиксированы; изменения формулировок внутри слоя повышают минорную версию, изменение состава слоёв — мажорную.

1. Зачем стек

Оркестратор одновременно решает задачи разной природы: доставить текст во вкладку, дождаться конца генерации, проверить формат, зафиксировать состояние, провести дискуссию к решению. Без явных слоёв отказ одной природы маскируется под отказ другой: потерянный при извлечении маркер выглядит как «модель не поставила маркер», техническая пауза — как прогресс, исчерпание бюджета — как сходимость. Стек нужен, чтобы каждый отказ имел одного владельца, одно доказательство и одну реакцию.

Порядок чтения — снизу вверх. Если нижний слой не дал доказательства, проверка на верхнем слое не выполняется.

2. Правила стека

  1. Вверх передаётся свидетельство, а не статус. Верхний слой получает проверяемое свидетельство выполнения контракта нижнего слоя (Evidence, §4.3), а не ok. Без свидетельства результата нет.
  2. Отказ имеет два атрибута слоя: где обнаружен и где возник. detected_at_layer и origin_layer (§4.2) записываются раздельно. Например, отсутствие маркера обнаруживает L5, но если извлечение L1 не доказало полноту, origin_layer = L1. Атрибуция не меняется при движении вверх.
  3. Отказы L1–L3 никогда не попадают в статистику качества моделей. Технический отказ имеет blame ≠ model.
  4. Два типа критериев не смешиваются. Детерминированные проверки — L1–L5 и структурная валидация сценария на L6 (§5.L6, Scenario Definition): отказ и повтор или запрет запуска. Вероятностная оценка содержания ответов — только на L6: меняется вес, ответ не отбраковывается. В одном списке проверок не бывает критериев обоих типов.
  5. Прогресс — это подтверждённые результаты, а не активность. Признак живости модели берётся только из её вывода. Фокус, скролл, повторный опрос, recovery, перезагрузка вкладки и любые другие наши действия прогрессом не являются (эффект наблюдателя).
  6. Одна точка изменения логического состояния. Логическое состояние меняется только типизированным переходом LogicalCommit на L4. Каждый тип перехода требует своего свидетельства: принятый ответ — AcceptanceReceipt L5; отсутствие ответа — свидетельство исчерпания попыток или SKIP; решение сценария — решение L6 (§5.L4). Журналировать можно всё; двигать состояние может только коммит.
  7. Одна логическая работа — ровно один терминальный исход. Каждый logical_invocation_id завершается ровно одним коммитом: ResponseAccepted или ResponseAbsent. Принятие и коммит атомарны: AcceptedResponse без коммита не считается принятым; коммит ответа без AcceptanceReceipt невозможен.
  8. Три вида повтора не смешиваются (§4.7):
  9. capture retry — повторное чтение того же attempt; всегда первым;
  10. transport resend — повторная отправка того же пакета; только при доказанной недоставке (not_delivered). Отсутствие ACK, сохранённый черновик и отсутствие сообщения в ленте сами по себе не доказательство недоставки, а delivery_unknown. После выдачи submit-действия not_delivered требует гарантии финальности адаптера (§5.L3);
  11. rejection retry — новая попытка после отказа L5 при доказанной доставке; новый attempt_id, своя причина, свой бюджет и явный способ восстановления контекста.
  12. Рамка бедная. На L5 проверяется только то, что переживает L1-извлечение: никакой markdown, списков и визуальной разметки как критерия приёмки.
  13. Одна канонизация. Хэши на L1 и проверки на L5 считаются над одной канонической формой текста; канонизация версионируется вместе с рамкой (§4.4).
  14. Нет молчаливых пропусков. Каждый слой возвращает либо свидетельство, либо отказ с причиной. «Ответа нет» — тоже результат, он записывается с причиной так же, как принятый (Absence, §4.3).
  15. Технические повторы не расходуют бюджет сценария. Повторы L1–L5 не создают нового логического раунда и не продлевают сценарий; иначе отказоустойчивость транспорта имитирует сходимость дискуссии.
  16. Дедлайны вложены. Дедлайн верхнего слоя больше суммы дедлайнов нижних с запасом; иначе наверх приходит отказ, который некому обработать.
  17. Изменение версии рамки или сценария — новый run. Повтор с другой версией рамки, политики приёмки, канонизации или PipelineDefinition не является attempt прежнего run.
  18. Данные не издают протокол. Чужие ответы, цитаты и извлечённый текст не могут содержать действующие протокольные элементы (маркер, нонс, ограждение данных). Протокольная позиция валидна только в заданном месте.
  19. Логика сценария — до его формы. Этапы, роли, проверки и бюджет сценария выводятся из логики сценария (ScenarioLogic, §5.L6), а не придумываются. Этап, который не выводится ни из одного звена логики, лишний; часть результата, к которой не ведёт ни одна цепочка, не будет получена.

4.2. Паспорт ошибки

Каждый отказ записывается с полями:

Поле Значение
code Lx.REASON, например L3.CUTTED, L5.MARKER_MISSING
detected_at_layer Слой, где отказ обнаружен
origin_layer Слой, где отказ возник (по доказательствам)
blame model / channel / transport / route / frame / journal / scenario / user / provider
retryable yes / no
retry_scope capture / resend / rejection_retry / rebuild / fallback / none
proof_ref Ссылка на свидетельство (§4.3), на основании которого определены origin и blame
reason Человекочитаемое пояснение

Отказ без blame и без proof_ref не записывается как окончательный: он остаётся AMBIGUOUS и не попадает в статистику качества моделей. blame=model допустим только когда все нижние слои дали положительные свидетельства (например, L5.MARKER_MISSING при доказанно полном извлечении).

4.3. Происхождение свидетельств

Минимальный конверт любого свидетельства:

Evidence {
  evidence_id, type, producer_layer,
  run_id, round_id, logical_invocation_id, attempt_id, capture_id?,
  monotonic_ts, wall_ts, hash, version
}

Особые типы:

  • Absence{reason, exhaustion_proof} — доказанное отсутствие результата (исчерпание попыток, SKIP, карантин, неопределённая доставка). Записывается как результат, не как пустота, и служит свидетельством для терминального коммита ResponseAbsent на L4.
  • DeliveryOutcome{delivered | not_delivered | delivery_unknown, proof} — исход отправки (§5.L3). delivered и not_delivered требуют наблюдаемого свидетельства на странице; без него исход — delivery_unknown.
  • Quarantine{raw_hash, reason} — сырой текст, не прошедший приёмку после исчерпания повторов. Хранится для аудита; второго логического ответа не создаёт и отбраковкой на L6 не считается.

Существующая реализация: per-dispatch Evidence Ledger из completion-protocol-v2.md является частным случаем этого протокола для L3.

4.4. Канонизация и хэши

  • Каноническая форма текста: Unicode NFC, переводы строк \n, схлопнутые концевые пробелы строк, без семантической нормализации. Версия канонизации (canon_version) входит в версию рамки.
  • Хэшируются раздельно: frame_hash, body_hash, затем packet_hash = sha256(frame_hash ‖ body_hash ‖ round_nonce ‖ canonical(metadata)). packet_hash — идентификатор всего пакета (включая метаданные и вложения); с текстом на странице он не сравнивается.
  • rendered_prompt_hash = sha256(canonical(render(packet))) — хэш ровно того текста, который должен оказаться в поле ввода. Его вычисляет L5↓ при сборке, с ним сравнивает L1 при вставке.
  • Вложения проверяются отдельно: attachment_hashes[] из пакета против подтверждения загрузки каждого файла на странице (§5.L1).
  • frame_hash одинаков для всех участников раунда. body_hash может различаться по ролям.
  • Сырой ответ хэшируется до любой интерпретации (raw_hash), извлечённый текст — после канонизации (extracted_hash).
  • На L1 сравниваются канонический хэш фактического input.value (или содержимого composer) перед submit и rendered_prompt_hash. Несовпадение только из-за нормализации DOM — дефект канонизации, а не отказ L1.

4.5. Время

  • Монотонные часы — для таймаутов и свежести; wall-clock — только для записей журнала. Смешение источников порождает ложные old-answer и late-end.
  • Монотонное время сравнимо только внутри одного контекста исполнения (content script, background). Поэтому свежесть ответа доказывается в первую очередь структурно — узел ответа принадлежит ходу, начатому нашим подтверждённым сообщением, — и только затем временем внутри одного контекста.

4.7. Повторы и бюджеты

Значения по умолчанию; конфигурируемы, но всегда явны и записаны в версии политики.

Слой Что повторяется Бюджет После исчерпания
L1 Действие по тому же message_id 3 Отказ наверх → L2 решает о fallback
L2 Переход по fallback-цепочке длина объявленной цепочки, не больше 2 SKIP{reason} для адресата
L3 Capture retry 2 Определение DeliveryOutcome
L3 Transport resend (только not_delivered) 1 Absence{transport}

Различие повторов.

Вид Когда Что повторяется attempt_id Контекст переписки
Capture retry Ответ снят неполно, рано или не тот Только чтение тот же, новый capture_id не меняется
Transport resend Доказано not_delivered Отправка того же пакета новый, retry_kind=resend не меняется: предыдущей отправки не было
Rejection retry Доставка доказана, L5 отклонил ответ, отказ retryable Исполнение того же пакета новый, retry_kind=rejection, retry_reason=L5.<code> восстанавливается явно (ниже)

Восстановление контекста при rejection retry. Отклонённый ответ остаётся на странице, поэтому повторная отправка того же пакета в ту же переписку даёт модели другой контекст и запрещена. Допустимые способы, в порядке предпочтения; набор доступных способов берётся из CapabilitySnapshot адаптера (L2), выбранный способ записывается в attempt как context_restore:

  1. regenerate — штатная перегенерация того же хода, если интерфейс заменяет ею отклонённый ответ в текущей ветке;
  2. edit_resubmit — редактирование и повторная отправка нашего сообщения (новая ветка от того же места переписки);
  3. new_conversation — новая беседа; допустим только если пакет самодостаточен (self_contained=true, L5↓), то есть не опирается на историю переписки.

Корректирующее сообщение в ту же переписку («исправь формат») — это другой пакет с другим контекстом; в OSI-1.1 оно не используется как rejection retry. Если ни один способ недоступен, rejection retry не выполняется: Quarantine + Absence{rejected}.

4.8. Телеметрия

События: layer_enter, layer_exit, evidence, error, retry, fallback, commit, absence, quarantine. Метрики слоёв перечислены в §5. Телеметрия не является слоем и не может быть источником прогресса.

5. Спецификация слоёв

Для каждого слоя: назначение, подпротоколы, единица данных, контракт, предусловие, свидетельство вверх, критерий завершения, инварианты, границы, запреты, отказы, реакция, «не ошибка», признак прогресса, метрики, точечное усиление.

L6 — Сценарии

Назначение. Одна из важнейших функций L6 — формирование логики сценария: понять, из чего складывается нужный результат и какие шаги к нему неизбежно ведут от того, что есть на входе. Остальные функции слоя опираются на неё: оформление логики в pipeline (этапы, роли, проверки, бюджет), выбор протокола (debate, расширение, критика, арбитраж), план раундов, назначение ролей, критерий остановки, решение о том, что сжимать в контексте, и исполнение сценария.

Ошибку логики нельзя исправить на нижних слоях: L1–L5 надёжно доставят, проверят и зафиксируют ответы на этапы, которые не ведут к результату. Поэтому логика формируется и проверяется до того, как появляется первый этап.

Подпротоколы. Scenario Logic · Scenario Definition · Scenario Planning · Protocol Transition · Reconciliation (claims, расхождения, disposition) · Semantic Assessment · Stop Decision.

Единица данных. ResultSpec, InputGap, ScenarioLogic, FailureModeMap, PipelineDefinition, ScenarioPlan, Claim, DisputeGraph, Disposition (accepted / rejected / open / deferred), ConvergenceDelta, SemanticAssessment, RoundDecision, StopDecision, RunVerdict.

Scenario Logic. Формирование логики идёт от результата назад, а не от начала вперёд. Методика с примерами — how-to-design-a-scenario.md, часть 1; пример применения — research.md.

  1. ResultSpec — описание результата. Что это за вещь; из каких частей она состоит (parts[], каждая часть получает идентификатор); какими проверяемыми свойствами обладает каждая часть; что человек сделает с результатом; чего в результате быть не должно (граница сценария).
  2. InputGap — разбор входа. Что приходит на вход (вопрос пользователя, документы, знания и умения моделей), насколько этому можно доверять, чего не хватает до результата по каждой части и какого рода эта нехватка (фактов, ясности цели, способа сделать, знания о слабых местах, выбора между вариантами). Род нехватки определяет набор ходов сценария.
  3. Обратный ход. Для каждой части результата отдельно задаётся вопрос «что должно существовать непосредственно перед этим?», пока цепочка не упрётся во вход. Одинаковые звенья разных цепочек сливаются в одно. Каждое звено размечается:
Разметка звена Вопрос Куда переходит
error_cost Испортит ли результат ошибка в этой вещи? Если да — отдельная проверка (контрольная точка) перед следующим звеном
multi_model_value Что дают несколько моделей: diversity (ракурсы и охват), independence (подтверждение, не подсказанное другим), collision (спор проявляет слабое) или none Число участников роли (L2); independence — участники не видят чужих ответов (L5↓); collision — протокол debate или критики; none — одна модель
progress_definition Для звена, которое может повторяться: что считается шагом вперёд? Условие дополнительного круга и детектор эха (L6.ECHO); без шага вперёд повтор не назначается (правило 5)
  1. FailureModeMap — карта поломок. Как сценарий может сломаться (выдумка, согласие двух неправых моделей, слишком широкая задача, потерянная часть задачи, находка пропала при сведении, спор замазан, итог утверждает больше найденного, процесс не кончается) и на каком звене или проверке каждая поломка ловится.

ScenarioLogic{logic_id, result_spec, input_gap, chains[], links[], failure_modes[], logic_hash} — итог формирования логики: слитая схема звеньев, каждое с разметкой. Пересказ схемы словами («сначала…, потом…, если…, то…») должен помещаться на страницу; схема мысленно прогоняется на трёх задачах — простой, слишком широкой и с противоречащими источниками. Эти две проверки выполняет человек или отдельный прогон моделей: они оценивают смысл логики и поэтому детерминированными не являются.

Прослеживаемость логики в определение. PipelineDefinition выводится из ScenarioLogic и ссылается на неё (logic_ref = logic_id + logic_hash). Каждый этап и каждая контрольная точка несут derived_from — ссылку на звено логики, из которого выведены. Следствия разметки звена обязательны: error_cost = high → контрольная точка с условием-предикатом; multi_model_value → число участников и режим видимости чужих ответов; progress_definition → условие повтора этапа.

Scenario Definition. PipelineDefinition{pipeline_id, pipeline_version, definition_hash, logic_ref, stages[], edges[], gates[], human_gates[], stop_rules, failure_policy, result_criteria, versions} описывает:

  • Этапы и раунды. Этап содержит один или несколько раундов; число раундов фиксированное либо ограничено условием выхода с жёстким максимумом. У каждого этапа указан протокол (debate, критика, расширение, арбитраж).
  • Задания ролям. Что роль должна выяснить, предложить или проверить на этапе. Это смысловое задание (body); в промпт его превращает L5↓. Определение описывает роли, а не модели: связывание роли с моделью — L2 при запуске.
  • Входы и выходы. Какие результаты и артефакты предыдущих этапов используются, какие артефакты этап обязан произвести, что передаётся дальше и что можно сжимать.
  • Управление исполнением. Последовательность, параллельные ветки, условия их объединения и перехода между этапами.
  • Поведение при отказах. Можно ли продолжать без участника или артефакта, минимальный кворум принятых ответов, когда выдаётся частичный итог, когда прогон останавливается.
  • Критерии результата. Что означает успешное завершение каждого этапа и всего pipeline. Критерии pipeline совпадают со свойствами частей ResultSpec.
  • Контрольные точки (gates[]). Место, где нельзя идти дальше, пока не выполнены условия. Условие — предикат над полями артефактов («поле заполнено», «у каждого пункта есть источник», «число не больше»), а не оценка («качественно»). У каждой точки — куда возвращаться и сколько раз.
  • Участие человека (human_gates[]). Только там, где модель не вправе решать за человека: цель, границы, спорные ценности. Указывается, можно ли пройти сценарий без остановок.

Структурная валидация (детерминированная; выполняется при фиксации версии PipelineDefinition и повторно при создании ScenarioPlan с конкретными входами):

  • каждая ссылка между этапами указывает на существующий этап и существующий выход;
  • каждый обязательный вход этапа производится одним из предшествующих этапов или передан во входных данных запуска;
  • у каждого цикла есть условие выхода и жёсткий максимум итераций;
  • у каждого этапа есть хотя бы одна роль, протокол и критерий перехода;
  • параллельные ветки имеют определённое условие объединения;
  • из начального этапа достижим хотя бы один конечный, недостижимых этапов нет;
  • бюджеты этапов в сумме не превышают бюджет pipeline;
  • версии рамки, политики приёмки и протоколов, на которые ссылается определение, существуют и совместимы;
  • определение ссылается на существующую ScenarioLogic с совпадающим logic_hash;
  • каждый этап и каждая контрольная точка имеют derived_from на звено логики, и каждое звено превращено в этап или проверку;
  • к каждой части ResultSpec ведёт путь этапов;
  • у каждого звена с error_cost = high есть контрольная точка перед следующим звеном;
  • у каждого повторяемого этапа есть progress_definition;
  • у каждой поломки из FailureModeMap есть этап или проверка, где она ловится;
  • условие каждой контрольной точки записано как предикат над полями артефактов;
  • у каждого возврата есть предел.

Валидация проверяет полноту и прослеживаемость логики, но не её смысл: что выбраны правильные части результата и правильные звенья, проверить детерминированно нельзя (см. выше).

Определение, не прошедшее валидацию, не получает версию и не может быть запущено. Эти проверки не оценивают качество сценария — только его исполнимость.

Pipeline, спроектированный моделями. Прогон, задача которого — спроектировать сценарий, проходит все шесть слоёв как обычный прогон. Его итог — кандидат ScenarioLogic и выведенный из неё кандидат PipelineDefinition. Логика проектируется раньше определения и рассматривается отдельно. Перед использованием кандидат проходит структурную валидацию и получает зафиксированную версию; до этого он не может быть исполнен. Отдельного слоя для этого нет.

Semantic Assessment. Вероятностные оценки, которые нельзя сделать детерминированно на L5: SemanticAssessment{kind, subject_ref, confidence, method, evaluator, evaluator_version}, где kind — compression_fidelity (сохранён ли смысл сжатого фрагмента) или injection_suspect (похоже ли, что ответ выполняет инструкции из чужих данных). Оценка никогда не отклоняет ответ: она меняет вес, помечает ответ и может повлиять на решение следующего раунда (например, подать фрагмент без сжатия). Метод и уверенность записываются всегда.

Контракт. - Validate(PipelineDefinition) → pipeline_version | DefinitionRejection (детерминированно). - Plan(pipeline_version, inputs, params, budgets) → ScenarioPlan (детерминированно; фиксируется коммитом RunStarted). - ScenarioPlan + закоммиченные на L4 исходы + Disposition + бюджет → RoundDecision{continue | next_stage | change_protocol | stop, reason}; в конце — RunVerdict{achieved | not_achieved | aborted, stop_reason}. Решение о переходе использует только условия, объявленные в PipelineDefinition. Каждое решение становится состоянием только через коммит L4 (RoundOpened, ProtocolChanged, RunStopped).

Предусловие входа. До раунда 1 коммитом RunStarted зафиксирован ScenarioPlan: версия pipeline, прошедшая валидацию, цель, роли, этапы, лимиты раундов, бюджет токенов/времени, критерий существенности расхождения, критерий остановки как измеримый предикат по DisputeGraph, правила смены протокола, правила взвешивания, политика отказов.

Свидетельство вверх. StopDecision с stop_reason: converged / max_rounds / budget_exhausted / blocked / echo / aborted. Перечень открытых существенных расхождений. Частичный итог — замороженный DisputeGraph, а не пустота.

Критерий завершения. Все существенные расхождения имеют disposition, либо явно зафиксирован not_achieved с перечнем открытых.

Инварианты. - Ни один существенный claim не исчезает без disposition. - Решение stop/continue воспроизводимо из ScenarioPlan + Disposition + budget. - L6 видит только ответы, закоммиченные на L4; сырой ответ L6 не виден. - Итог собирается только из принятых ответов. - Отбраковки нет: все принятые на L5 ответы участвуют с весом.

Не входит в слой. Проверка формата и рамки (L5), доставка и повторы (L1–L3), запись журнала (L4), выбор адаптера (L2).

Запрещено. Прямая запись в журнал в обход L4. Проверка формата ответа. Повтор раунда «на всякий случай». Вердикт «кончились раунды» без явного not_achieved. Смена протокола внутри раунда. Запуск невалидированного или неверсионированного PipelineDefinition. Этапы, придуманные до описания результата и не выведенные из логики. Изменение ScenarioPlan после RunStarted: переход, не объявленный в определении, — новый run.

L5 — Контекст

Назначение. Контекст и артефакты: какие данные получает исполнитель и в каком виде возвращает результат.

Подпротоколы. Две независимые функции одного слоя, которые не смешиваются ни в коде, ни в журнале, ни в таксономии ошибок:

  • L5↓ Context Build — сборка пакета: неизменяемая рамка + сменное тело + чужие ответы как данные + сжатие контекста по решению L6.
  • L5↑ Acceptance Gate — детерминированная приёмка сырого ответа.

Единица данных. PromptPacket{frame, body, artifacts[], round_nonce, frame_hash, body_hash, packet_hash, rendered_prompt_hash, attachment_hashes[], self_contained, versions}, CompressionManifest, AcceptancePolicy, AcceptanceReceipt, AcceptedResponse, Rejection{code, origin_layer, retryable}.

Контракт. - Build(frame, body, artifacts, compression_decision) → PromptPacket - Validate(extracted_text, policy, round_nonce) → AcceptedResponse | Rejection

Предусловие входа. Рамка собрана и её хэш стабилен; нонс раунда присутствует; внешние фрагменты помечены как данные и экранированы; допуск лимита и N повторов заданы в AcceptancePolicy.

Свидетельство вверх. - ↓ packet_hash (идентификатор пакета), rendered_prompt_hash (эталон для проверки вставки на L1), attachment_hashes[]; у каждого вложения указаны источник, версия и пометка «данные». - ↑ AcceptanceReceipt{acceptance_policy_version, canon_version, checks[{name, result}], round_nonce, extracted_hash} либо причина отказа.

Проверки приёмки (только детерминированные, без LLM-суждений): зоны ответа; язык; лимит длины с явным допуском (по прогону ebe8b806 — около +30%); маркер последней строкой; нонс совпадает с раундом; маркер и нонс валидны только в своей позиции.

Критерий завершения. Либо AcceptedResponse, либо Rejection с причиной. Сырой ответ результатом не считается.

Инварианты. - frame_hash одинаков у всех участников раунда; нонс общий на раунд. Персональная идентичность живёт в конверте L4, в промпт не попадает. - Сжатие не затрагивает неизменяемую рамку. - Все валидаторы чистые, детерминированные и версионированные. - Рамка при повторе не меняется. - На L5 нет семантических проверок. Сохранность смысла при сжатии и подозрение на инъекцию — вероятностные оценки L6 (SemanticAssessment).

Не входит в слой. Выбор адресата (L2), выбор протокола и решение о том, что сжимать (L6), отправка (L3), запись состояния (L4), оценка смысла (L6).

Запрещено. Markdown, списки и разметка как критерий приёмки. Сжатие «на глаз» без CompressionManifest. Персональный нонс в промпте. Действующий маркер или нонс внутри данных.

Повторяемый отказ при доказанной доставке — rejection retry (§4.7): тот же logical_invocation_id и тот же PromptPacket, новый attempt_id с retry_kind=rejection и retry_reason=L5.<code>, явный context_restore, не больше N раз. Признак прогресса. Принятые ответы.

Метрики. first_try_acceptance_rate, rejection_by_reason, rejection_blame_split (модель против канала), retry_per_response, compression_ratio, protocol_token_escapes, prompt_hash_mismatch, context_restore_by_method.

L4 — Сеансовый

Назначение. Связывает session, round, role и model; ведёт append-only журнал; обеспечивает идемпотентность и восстановление.

Подпротоколы. Event Recording (наблюдение) · Logical Commit (изменение состояния) · Replay / Recovery · Reconciliation с фактическим состоянием страницы.

Единица данных. - ObservedAttempt — любая попытка, включая технические и отклонённые. Журналируется, состояние не двигает. - LogicalCommit{kind, subject_id, proof_ref, attempt_id?, prev_hash, entry_hash, schema_version} — типизированный переход; единственное, что двигает состояние. - Event{event_id, trace_id, run_id, session_id, round_id, role, model, attempt_id, causation_id, monotonic_ts, wall_ts, source}. - StateSnapshot / Checkpoint на границах раундов.

Типы переходов. Коммит без свидетельства своего типа невозможен.

kind Субъект Обязательное свидетельство Терминальный для логической работы
RunStarted run_id Зафиксированный ScenarioPlan со ссылкой на версию PipelineDefinition, прошедшую структурную валидацию —
RoundOpened round_id RoundDecision{continue} L6 со ссылкой на scenario_plan_id + зафиксированный RoutePlan L2 —
ResponseAccepted logical_invocation_id AcceptanceReceipt L5 + хэш AcceptedResponse да
ResponseAbsent logical_invocation_id Absence{reason, exhaustion_proof}: исчерпание бюджета повторов, SKIP L2, delivery_unknown после дедлайна или карантин после rejection retry да
ProtocolChanged run_id RoundDecision{change_protocol, reason} L6 на границе раунда —
RoundClosed round_id Все логические работы раунда имеют терминальный исход —
RunStopped run_id StopDecision + RunVerdict L6 —

Контракт. ObservedAttempt → append. Свидетельство нужного типа + ключ идемпотентности → ровно один LogicalCommit → новое состояние. Логическая работа завершается ровно одним терминальным коммитом: ResponseAccepted или ResponseAbsent; второй терминальный коммит — L4.DOUBLE_COMMIT.

Предусловие входа. Журнал доступен; предыдущее состояние восстановлено или явно открыт новый раунд; ключ идемпотентности вычислим.

Свидетельство вверх. Replay журнала даёт то же логическое состояние; каждый коммит содержит proof_ref на свидетельство своего типа и, для ответов, ссылку на породивший attempt; хэш-цепочка цела.

Критерий завершения. Ровно один терминальный коммит на логическую работу; раунд закрывается RoundClosed, прогон — RunStopped.

Инварианты. - At-least-once наблюдение, exactly-once логический коммит. - Нет вечно ожидающих слотов: каждая логическая работа к дедлайну раунда получает терминальный исход. - Один round + role — максимум один логический ответ. - Состояние — свёртка журнала; вне журнала состояния нет. - Журнал append-only; откат — компенсирующее событие, удаление запрещено. - Порядок строго «коммит → возврат наверх».

Не входит в слой. Форматирование промпта, маршрутизация, проверка формата, работа с DOM, оценка содержания.

Запрещено. Тихая перезапись. Новое логическое событие при повторе. Хранение сырых стримов в журнале состояния (они — свидетельства L3).

L3 — Транспортный

Назначение. Доставка запросов и съём ответов: таймауты, съём стрима, определение завершения, проверка свежести.

Подпротоколы. Dispatch · Capture · Completion · Freshness. Completion — отдельный версионированный предикат, а не таймаут. Реализация предиката — Completion Protocol V2.

Единица данных. RequestEnvelope{request_id, attempt_id, packet_hash, target, sent_at}, ResponseEnvelope{attempt_id, capture_id, sent_at, first_output_at, last_output_at, capture_at, raw_hash, length, completion_status, via_fallback}, CompletionReport, DeliveryOutcome{delivered | not_delivered | delivery_unknown, proof}.

completion_status: complete / cut / timeout / empty / stale / continue_required / ambiguous.

Контракт. PromptPacket + адресат + дедлайны → ResponseEnvelope (полный, свежий ответ с метками времени) либо доказанный отказ доставки или завершения. Неполный ответ не выдаётся как завершённый.

Предусловие входа. Маршрут выбран, адресат доступен, дедлайны заданы, нонс вложен в пакет.

Свидетельство вверх. DeliveryOutcome + capture_complete + freshness_evidence + raw_hash + length.

Исход доставки. Определяется по наблюдаемому состоянию страницы (L1), а не по ACK. ACK подтверждает, что команда дошла до исполнителя; его отсутствие не говорит ничего о том, произошла ли отправка.

Исход Свидетельство
delivered Наше сообщение появилось в ленте, или началась генерация хода, начатого нашим сообщением
not_delivered (до submit) Submit-действие (клик Send, Enter) не выдавалось: composer transaction не дошла до SUBMITTING, либо явная ошибка до side-effect (команда отклонена, вкладка недоступна до вставки). Свидетельство — журнал composer transaction
not_delivered (после submit) Только при submit_finality = explicit и полученном сигнале (ниже): провайдер подтвердил, что именно эта отправка завершена без принятия; при этом нашего сообщения в ленте нет, черновик с rendered_prompt_hash на месте, генерация не началась
delivery_unknown Всё остальное: потерян ACK, навигация или выгрузка вкладки во время submit, лента не читается, а также «сообщения нет, черновик на месте» после submit без гарантии финальности

Гарантия финальности отправки. Отсутствие наблюдаемого подтверждения не доказывает недоставку: первый submit может ещё обрабатываться, пока интерфейс показывает черновик, и завершиться после окна стабилизации. Поэтому после выдачи submit-действия адаптер вправе заявить not_delivered только если в CapabilitySnapshot объявлено submit_finality = explicit и получен соответствующий сигнал:

submit_finality Что гарантирует адаптер Когда допустим not_delivered после submit
none Ничего Никогда; исход delivery_unknown
explicit Провайдер выдаёт терминальный сигнал, относящийся к этой конкретной отправке и означающий, что она завершена без принятия: например, ответ сервера с отказом в приёме именно этого сообщения или пометка «не отправлено» у нашего сообщения в ленте Только после такого сигнала

Что не является сигналом explicit: обрыв соединения, таймаут, отклонённый клиентский promise, ошибка нашего скрипта, исчезновение индикатора отправки, любая ошибка без привязки к конкретной отправке. Эти события не говорят, принял ли провайдер сообщение; исход остаётся delivery_unknown.

Статистика не даёт гарантии. Измеренная на прогонах задержка (T_final, максимум или перцентиль) не доказывает, что следующая отправка не будет принята позже. Поэтому T_final разрешено использовать только как предел ожидания перед выводом delivery_unknown, но никогда как основание для not_delivered и resend.

По умолчанию у каждого адаптера submit_finality = none. Перевод в explicit — изменение версии адаптера с описанием сигнала и свидетельством того, что он относится к конкретной отправке.

При delivery_unknown сначала выполняется сверка (повторное чтение ленты и composer). Если исход остаётся неизвестным, повторная отправка запрещена: capture продолжается до общего дедлайна; появившийся ответ на наш ход переводит исход в delivered; иначе — Absence{delivery_unknown}.

Критерий завершения. Ответ полон и свеж, либо доказан отказ.

Инварианты. - Ответ не может быть старше запроса. - Повторное чтение ответа ≠ повторная отправка запроса. - Transport resend возможен только при not_delivered; при delivery_unknown — никогда. - Транспорт нейтрален к смыслу. - Ответ без меток времени наверх не поднимается.

Три таймера с разными кодами: до первого вывода (stuck), между фрагментами (stall), общий (hard). Тишина без признака конца — подозрение на обрыв, а не завершение.

Завершение требует нескольких независимых признаков (UI вернулся в idle, и поток замолчал на окно подтверждения, и содержимое стабильно). Один признак — только кандидат.

Не входит в слой. Выбор модели и пресета, приёмка по формату, запись состояния, интерпретация смысла.

Запрещено. Смешивать cut и false-success в одну ошибку. Считать recovery, фокус, скролл прогрессом. Повторять send по таймауту ожидания ответа или по отсутствию ACK. Выдавать rejection retry за transport resend.

L2 — Маршрутизация

Назначение. Выбор пресета и модели; адресация и маршрутизация: какому исполнителю и какой операции принадлежит сообщение.

Подпротоколы. Capability Check · Route Planning · Fallback · Circuit Breaker.

Единица данных. RoutePlan{route_plan_id, entries[], policy_version, capability_version}, RouteEntry{role, target, preset, adapter, operation, fallback[], route_decision_id}, CapabilitySnapshot{stream, limits, context_window, frame_version, context_restore[]: regenerate | edit_resubmit | new_conversation, submit_finality: none | explicit, T_final?} (T_final — только предел ожидания), RouteDiff, SKIP{reason}.

SKIP{reason} — свидетельство для Absence и терминального коммита ResponseAbsent на L4.

Идентичность исполнителя = имя + провайдер + наблюдаемая версия модели, если интерфейс её показывает; иначе исполнитель помечается version_unpinned.

Контракт. Сценарий (роли от L6) + CapabilitySnapshot → RoutePlan; маршрут логируется до отправки.

Предусловие входа. Есть хотя бы один исполнитель с нужными возможностями; fallback-цепочка объявлена; пакет помещается в контекстное окно адресата; квота доступна.

Свидетельство вверх. План покрывает всех адресатов раунда; по каждому — доставка или SKIP{reason}; версии политики и снапшота возможностей записаны; выбранная fallback-цепочка записана.

Критерий завершения. Маршрут зафиксирован, адресаты покрыты, доставка каждого залогирована.

Инварианты. - Состав ролей раунда фиксируется в RoutePlan до рассылки и не меняется. - Каждый адресат получает ровно одну логическую операцию. - Маршрут строится относительно снапшота возможностей, а не текущего изменяемого состояния. - Роль назначает L6; адаптер роль не выбирает. - Target и preset не меняются после dispatch без нового RouteDecision.

Замена исполнителя внутри раунда. Роль (слот) неизменна. Исполнитель заменяется только по заранее объявленной fallback-цепочке; каждая замена — новый route_decision_id и новый attempt_id при том же logical_invocation_id. Ответ помечается via_fallback и приписывается фактическому исполнителю, а не исходному. Цепочка ограничена, циклы запрещены.

Не входит в слой. Вкладки и DOM (L1), формат ответа (L5), журнал (L4), сценарий (L6).

Запрещено. Тихая подмена модели или пресета. «Умная» маршрутизация без лога. Выдача ответа fallback-модели за ответ исходной.

Типовые отказы.

Код Описание blame
L2.WRONG_RECIPIENT Сообщение ушло не тому исполнителю route
L2.RECIPIENT_SKIPPED Адресат раунда пропущен без SKIP route

L2.CAPABILITY_MISMATCH Пресет обещает то, чего не умеет адаптер route

Реакция. Отказ с причиной, переход по объявленному fallback; изменение доступности — новая версия плана, а не правка старой.

Не считается ошибкой модели. Недоступность модели или адаптера — отказ маршрутизации.

Признак прогресса. Нет.

Метрики. route_coverage, fallback_rate (по причинам), skip_rate, route_replan_count, quota_denied_count, распределение раундов по исполнителям.

Точечное усиление. Явный fallback-протокол; отказ, а не «тихое протекание». Circuit breaker: подряд идущие отказы L1 временно выводят адаптер из ротации. L1 публикует состояние канала (готов / занят / сломан) — это вход для L2.

L1 — Канальный

Назначение. Обмен сообщениями расширения и доступ к интерфейсу модели: как передать команду или событие между панелью, фоном и вкладкой; можно ли сейчас взаимодействовать со страницей и наблюдать её состояние.

Подпротоколы. IPC (panel ↔ background ↔ tab) · Page Health · Composer Transaction · Extraction.

Единица данных. ChannelMessage{message_id, parent_id, seq, tab_id, action, payload_hash}, Invocation, InvocationReceipt{tab_ok, auth_ok, page_state, selector_found, inserted_hash, attachments_confirmed[], submitted_observed, draft_still_present, extracted_hash, extraction_complete, selector_map_version}, PageHealth, ExtractionManifest.

Состояния страницы: visible, authorized, input_ready, streaming, idle, blocked (капча, баннер, модальное окно), busy (вкладка занята автоматом).

Контракт. Команда с адресом вкладки → подтверждённое действие в DOM + сырой текст страницы.

Предусловие входа. Вкладка найдена; авторизация валидна; страница input_ready; селекторы существуют; канал сообщений жив.

Свидетельство вверх. - Вставка: канонический хэш фактического содержимого composer перед submit равен rendered_prompt_hash L5 (не packet_hash: тот идентифицирует весь пакет с метаданными). - Вложения: каждый файл из attachment_hashes[] подтверждён страницей (имя, размер, состояние загрузки); проверка отдельная от текста. - Отправка: наше сообщение появилось в ленте переписки (наблюдаемый эффект), а не «кнопка не вернула ошибку». - Извлечение: сырой текст + extraction_complete + extracted_hash. - ACK содержит message_id и observed_effect, а не просто ok.

Последовательность composer transaction уже реализована: COMMAND_ACCEPTED → ATTEMPT_PREPARED → BASELINE_ACKED → ATTACHMENT_SETTLED → PROMPT_COMMITTED → SUBMITTING → SUBMITTED (см. completion-protocol-v2.md).

Критерий завершения. Действие подтверждено наблюдаемым эффектом; извлечён сырой текст.

Инварианты. - Один Invocation не может вызвать два submit-side-effect. - Слой не интерпретирует содержимое: сырой текст вверх без правок. - Сбой интерфейса не является ошибкой модели. - Перед повторным submit сначала доказать, что предыдущий не произошёл (not_delivered, §5.L3). - Повторное IPC-сообщение с тем же message_id не повторяет side-effect: получатель дедуплицирует по message_id и возвращает сохранённый observed_effect.

Не входит в слой. Решение accepted/rejected, изменение промпта, выбор модели.

Запрещено. Записывать DOM-ошибку как «модель не поставила маркер». Слать сообщения без ACK. Подбирать нормализацию извлечения на живом прогоне.

9. Требует проверки

  • Порог сходства для детектора эха и критерий существенности расхождения — калибруются на прогонах, пока задаются в ScenarioPlan вручную.
  • Допуск лимита +30% основан на одном прогоне (ebe8b806).
  • Хэш фактического содержимого composer доступен не во всех провайдерах (contenteditable с нестандартной моделью ввода) — проверить по адаптерам; там же проверить, совпадает ли render(packet) с тем, что адаптер реально вставляет (переносы строк, вложения как текст).
  • Уровень submit_finality и способы context_restore (regenerate, edit_resubmit) — определить для каждого из девяти интерфейсов и занести в CapabilitySnapshot. До этого все адаптеры работают с submit_finality = none.
  • Реализационный долг: существующий bounded send-only retry после неподтверждённого Send (completion-protocol-v2.md) противоречит OSI-1.3, если он срабатывает по таймауту или окну ожидания. Он допустим только для адаптеров с submit_finality = explicit после сигнала об отказе в приёме конкретной отправки.
  • Прослеживаемость derived_from и проверки L6.LOGIC_* в коде не реализованы; существующие сценарии (Architecture) логику в формате ScenarioLogic пока не имеют. Research — первый сценарий, написанный от логики.
  • Методы SemanticAssessment (оценщик, калибровка уверенности) не выбраны.
  • Структурное доказательство свежести (принадлежность узла ответа ходу) — проверить на каждом из девяти интерфейсов.
